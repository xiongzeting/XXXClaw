# ContextWeave：MiniClaw 四层记忆检索 vs 全量拼接

> **结果状态（2026-09-04 更新）**：下面的 6 题数字来自旧版 ContextWeave 适配器。旧适配器会用 Benchmark 专用规则从历史文本生成 Semantic 和 Procedural，因此这些数字只能作为历史实验记录，暂时不能继续作为“真实生产写入链路”的最终简历数据。现已删除这些专用规则，改为每个真实 Session 独立归档、生产版 Episode 整理、显式稳定事实写入，以及统一 `MemoryManager.prompt_context()` 召回。新版已完成 1 题容器烟雾验证，但必须重新跑成对样本并重新评分后，才能替换本页旧指标。

## 一、最重要的结果

本轮使用 2026 年发布、面向 Coding Agent 个人长期工作记录的 ContextWeave，运行 6 个真实编码任务，每题分别跑两组，共 12 条 Agent 轨迹。

| 指标 | MiniClaw 检索组 | 全量拼接组 |
|---|---:|---:|
| 官方 Docker 工作区平均分 | **74.33** | 71.50 |
| 达到最低任务要求（>=60） | **6/6，100%** | **6/6，100%** |
| 达到官方参考水平（>=80） | **2/6，33.3%** | 0/6，0% |
| 平均注入记忆 Token | **14,184** | 120,581 |
| 累计模型输入 Token | **1,310,037** | 6,519,595 |
| 未命中缓存的输入 Token | **221,013** | 516,395 |
| 输出 Token | 28,522 | 29,354 |
| 估算模型成本 | **$0.04198** | $0.09732 |
| Agent 执行时间合计 | **950.71 秒** | 1,070.53 秒 |
| 模型请求数 | 71 | 74 |
| Tool Call 数 | 125 | 103 |

与全量拼接相比，MiniClaw 检索组：

- 记忆注入量减少 **88.24%**。
- 累计输入 Token 减少 **79.91%**。
- 未缓存输入 Token 减少 **57.20%**。
- 估算成本减少 **56.87%**。
- Agent 执行时间减少 **11.19%**。
- 官方工作区平均分提高 **2.83 分**，没有出现以明显质量下降换 Token 的情况。

6 个成对任务中，检索组相对全量拼接为：**3 胜、3 平、0 负**。

## 二、测试的到底是什么

两组使用完全相同的：

- 历史会话和历史事实。
- 当前编码任务。
- Docker 起始工作区。
- `gpt-5.6-luna` 模型。
- MiniClaw AgentLoop、Goal、工具和安全配置。

唯一主要变量是历史记忆如何交给模型。

### MiniClaw 检索组

历史材料先映射到：

- Working Context：当前任务、当前工作区、当前 Agent 轨迹。
- Episodic：过去每次任务的目标和结果。
- Semantic：从历史中保守提取的稳定事实、偏好和约束。
- Procedural：可复用的操作流程。
- Archive：完整历史原文，用于证据恢复。

查询时由 BM25 和本地 Bi-Encoder 双路召回，经 RRF 融合、Cross-Encoder 重排和跨来源去重，最终在约 15k Token 预算内注入相关原文。6 题一共注入：

- Episodic：57 条。
- Archive：29 条。
- Semantic：20 条。
- Procedural：18 条。

Working Context 不属于“从历史库召回的条目”，它在 Agent 运行期间始终直接保留。

### 全量拼接组

使用同一份四层记忆生成材料，但不做查询筛选，直接将全部历史内容拼接到任务开头。

因此它不是能力更弱的空白基线，而是一个很强但昂贵的对照组：模型理论上能看到全部历史，代价是每次后续 Tool Call 都携带很长的上下文。

## 四、正确率如何判定

不能把下面这些当作“任务答对”：

- Agent 进程退出码为 0。
- Goal 状态变成 success。
- 模型最终回复声称“已经完成”。
- 测试命令只在模型文本中出现。

本轮使用 ContextWeave 官方 Workspace Metric：独立 Judge 实际打开候选结果镜像和官方参考镜像，检查工作区文件、脚本、数据产物与可运行证据，再给出 0～100 分。

- 60 分：满足任务的最低要求。
- 80 分：达到官方参考工作区的完成水平。
- 80 分以上：部分实现超过参考基线。

因此本轮可以合理报告“6/6 达到最低任务要求”，但不能写成“6/6 完美完成”。

## 五、召回指标应该怎样理解

依据 ContextWeave 发布的 relevant previous subtasks，检索组在 6 题中都召回了所有必须关联的历史会话，严格会话来源 Recall 为 **100%**；宏平均 Precision 约为 **61.2%**。

这个指标只认能够追溯到具体历史 subtask 的条目：

- Archive 的 `source_path` 可以追溯。
- Episodic 的 `session_id` 可以追溯。
- Procedural 的来源任务可以追溯。
- Semantic 中即使保存了正确事实，但没有原始 session ID，也不会被这个指标计为命中。

所以它证明的是“官方标记的相关历史任务有没有被召回”，不能等同于通用的 `Recall@5`，也不能证明每个关键证据句都完整出现。

## 六、这轮暴露的问题

### 1. 软压缩重复尝试

全量拼接组因为上下文长期超过 80k，共触发 46 次软压缩检查，但 46 次都因为确定性压缩无法达到目标而中止；之后每一轮又重新尝试。

这没有直接造成任务失败，但产生了无效检查和 Trace 噪声。更合理的整体修复是加入冷却或迟滞：上下文结构没有实质变化时，不重复执行相同的软压缩尝试；跨过新的 Token 档位或出现可归档回合后再重试。

### 2. 检索节省了大量 Token，但 Tool Call 更多

检索组共 125 次 Tool Call，全量拼接组为 103 次。较短上下文让模型更愿意实际读取、修改和验证工作区，但也说明检索结果并没有替代 Agent 主动探索。

这不是单纯坏事：官方分数没有下降，执行时间反而减少 11.19%。后续可以继续观察是否存在重复 Read/Grep，而不是为了降低 Tool Call 数强行少搜索。

### 3. 全量拼接在本批压力题中尚未直接崩溃

虽然记忆材料估算达到 147k～154k Token，但供应商实际计费 Token 峰值约为 102k～107k，仍处于 128k 模型窗口内，因此不能声称“全量拼接超过窗口后失败”。

可以声称的是：在接近窗口上限时，检索组将累计输入 Token 降低约 80%，同时保持或略微提高工作区质量。

### 4. Benchmark 运行器的 Windows 兼容问题

运行中修复了三类评测基础设施问题：

- 忽略 macOS `._*` AppleDouble 二进制旁路文件，避免被误当成 JSON。
- 正确转义写入 Codex `config.toml` 的 Windows 路径。
- Codex CLI 未把最终 JSON 打印到标准输出时，验证并读取 Judge 已写入的 `result.json` 和 `criteria.json`。

这些只修复评测器可运行性，没有修改题目、Agent Prompt、检索规则或单个 Case 的答案。

## 七、简历上可以怎么写

建议使用保守版本：

> 在 ContextWeave 6 个真实 Coding Agent 长程任务（12 条对照轨迹）上，相比全量历史拼接，将平均记忆注入量降低 88%、累计输入 Token 降低 80%、估算成本降低 57%，官方 Docker 工作区平均分由 71.5 提升至 74.3，最低要求完成率保持 100%。

必须同时准备好说明：

- 样本只有 6 题，不代表全量榜单结果。
- “100%”是达到 60 分最低要求，不是满分率。
- 成本来自当前 `.env` 中配置的模型单价。
- 质量由官方工作区 Judge 评分，而不是 MiniClaw 自评。
