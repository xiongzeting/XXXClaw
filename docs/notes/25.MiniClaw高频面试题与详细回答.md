# MiniClaw 高频面试题与详细回答

> 使用方式：先熟练掌握 P0 问题，再准备 P1 实现追问，最后用 P2 展示工程判断力。回答时不要一次性把所有细节全部说完，建议先给结论，再讲设计、关键机制、取舍和结果，给面试官留下继续追问的空间。

## 一、项目开场介绍

### 1. 请你用 30 秒介绍一下 MiniClaw

**参考回答：**

MiniClaw 是我参考 pi-mono 的分层思想和工具协议，用 Python 独立实现的 Coding Agent。它主要解决四类问题：第一，普通 Agent 在长任务中容易把“模型不再调用工具”误认为“任务已经完成”，所以我在 Agent Loop 外实现了持久化 Goal 状态机和外层监督器；第二，针对上下文不断膨胀和压缩后遗忘，我实现了软硬阈值分级压缩、完整历史归档以及分层长期记忆；第三，针对模型执行文件和 Shell 操作的风险，我实现了参数校验、allow/ask/deny 风险策略、人工审批、WorkspaceGuard 和受限 Docker Runtime；第四，我统一记录模型、工具、Goal 和压缩事件，把线上失败轨迹转换成 Eval Case，形成 Trace 到 Eval 的回归闭环。

项目的重点不是“接了一个大模型 API”，而是把 Agent 做成一个可持续运行、可恢复、可约束、可验收和可评测的工程系统。

### 2. 请你用 2 分钟完整介绍这个项目

**参考回答：**

MiniClaw 的核心架构分为 `llm`、`agent` 和 `coding_agent` 三层。`llm` 层负责屏蔽不同模型服务的消息、流式事件、Tool Call 和 Usage 差异；`agent` 层只实现通用 Agent Loop，也就是“请求模型—执行工具—把结果交回模型—继续推理”；`coding_agent` 层负责组装编码场景需要的工具、Goal、Memory、Runtime、审批、项目指令和 Trace。这样产品策略不会反向污染通用循环。

在任务完成性上，我把模型的一次自然停止定义为一次 attempt，而不是整个任务结束。外层 `GoalSupervisor` 会读取持久化 Goal 状态，只要仍处于 `active` 或 `verifying`，就自动构造继续提示并启动下一次 attempt。最终完成必须经过真实验证：验证命令退出码为 0、验证发生在最后一次代码修改之后、每条验收条件都有精确证据，必要时还会经过独立 Judge。

在上下文管理上，我使用 soft/hard 两级阈值。软阈值优先进行确定性、低成本压缩，例如把大型工具输出落盘、归档旧回合，只在 Prompt 中保留引用、任务 Checkpoint 和近期原文；硬阈值下如果确定性压缩仍不够，再调用模型生成摘要。完整旧消息不会被摘要替代后丢弃，而是以 JSONL 和 Artifact 形式保存并建立索引。

记忆按生命周期拆为 Working Context、Archive、Semantic、Episodic 和 Procedural。召回时使用 BM25 与本地 SentenceTransformer Bi-Encoder 双路召回，通过加权 RRF 融合，再让 Cross-Encoder 对有限候选精排。这样既保留文件名、错误码等精确匹配能力，也补充语义召回能力，同时把昂贵的 Cross-Encoder 控制在小候选集内。

在安全方面，所有工具调用统一经过 ToolExecutor，先做递归 Schema 校验，再做路径和风险检查。风险策略分为 allow、ask、deny；ask 会进入 Human-in-the-loop 审批。文件工具由 WorkspaceGuard 约束在有效工作区内，Bash 默认进入无网络、只读根文件系统、限制 CPU、内存、进程数和权限的临时 Docker 容器。

最后，系统把模型请求、工具调用、审批、Goal 状态、压缩和运行结果统一写入 Trace。生产失败可以转成 Eval Case，在不重新执行危险工具的前提下重放模型边界，对比模型、Prompt 和工具定义，并通过 Dashboard 观察成功率、延迟、Token、成本和失败聚类，形成工程闭环。

# P0：最高优先级问题

## 3. 这个项目最核心的问题是什么？你为什么要做它？

**参考回答：**

我认为 Coding Agent 真正难的不是“模型会不会写代码”，而是如何让一个概率模型可靠地完成长链路工程任务。普通 Demo 通常有四个明显缺口：

1. 模型停止不等于任务完成。它可能改完代码但没测试，也可能只完成一半就输出总结。
2. 上下文不能无限增长。日志、源码和多轮 Tool Result 会反复进入模型输入，成本和延迟不断增加。
3. 模型拥有工具后会产生真实副作用。路径逃逸、危险 Shell、凭据泄漏和资源耗尽都必须由系统控制，不能只靠 Prompt 约束。
4. 结果难以客观验收。只看最终自然语言回答，无法判断代码、测试和验收条件是否真正满足，也无法把线上失败稳定转成回归样例。

所以 MiniClaw 的主线不是增加更多工具，而是围绕“持续执行、上下文治理、安全边界、可验证完成、数据闭环”补齐 Agent 工程层。

**面试时必须强调：**

- 大模型负责提出动作和使用工具，系统负责控制生命周期、权限和验收。
- 不能把可靠性完全建立在“再写一段更强的 Prompt”上。
- Goal、Memory、Runtime、Trace 都放在 Agent Loop 外围，各自解决不同的系统问题。

## 4. MiniClaw 的整体架构是怎样的？为什么这样分层？

**参考回答：**

整体依赖方向可以概括为：

```text
CLI / 飞书 / Benchmark
          ↓
coding_agent：产品装配层
  ├─ Goal / Memory / Tools
  ├─ Approval / Runtime / Instructions
  ├─ Trace
  ├────────────→ agent：通用循环
  └────────────→ llm：模型协议层
                         ↑
agent ──────────────────┘
```

`llm` 层只处理 Provider-neutral 的消息、模型事件、流式输出、Tool Call、Usage、超时、重试和模型降级。它不知道 Coding Agent、工作区和 Goal。

`agent` 层只负责一次通用运行：追加用户消息，请求模型，执行模型要求的工具，把 Tool Result 按原顺序放回上下文，再次请求模型，直到模型不再调用工具或达到轮次上限。它只依赖抽象的工具执行协议，不依赖具体的文件工具、Memory 或 Docker。

`coding_agent` 层是产品层，负责把编码工具、GoalSupervisor、MemoryManager、ApprovalGate、Runtime、项目指令和 Trace 组装起来。

这样设计主要有三个原因：

1. **职责稳定。** 模型协议变化不会迫使 Goal 状态机变化，Docker 安全策略也不会进入 Agent Loop。
2. **可复用。** 同一个 Agent Loop 可以用于普通聊天、Coding Agent 或 Benchmark，不是所有 Agent 都被迫拥有 Goal 和文件系统。
3. **可测试。** 每层都有明确输入输出，可以用假模型、假工具和临时工作区独立测试，不必每个测试都请求真实模型。

如果把所有逻辑塞进一个大循环，短期代码看起来更少，但后续会出现策略耦合：工具决定任务是否完成、Trace 写入影响主流程、Runtime 知道模型状态，最终难以替换和验证。

## 5. 为什么要在 Agent Loop 外再做 GoalSupervisor？

**参考回答：**

因为 Agent Loop 的停止语义和用户任务的完成语义并不相同。

Agent Loop 能观察到的只是：“这一轮模型没有继续请求工具。”这可能表示任务完成，也可能表示模型过早停止、只做了阶段总结、忘了验证，甚至因为上下文复杂而放弃继续执行。

我的处理方式是：

```text
一次 AgentLoop.run 自然停止
          ↓
只算一次 Goal attempt 结束
          ↓
读取持久化 Goal 状态
          ↓
active / verifying → 自动续跑
其他终态          → 整个任务结束
```

GoalSupervisor 不干预 Agent Loop 内每一个推理回合，只监督完整 run。这样既保留通用 Agent Loop 的简单性，又能在编码产品层实现长任务策略。

续跑时不是简单重复原问题。系统会根据 Goal 状态生成不同提示：如果还没有新鲜验证，就继续工作和验证；如果验证已经成功但没有申请完成，就进入 completion review，要求模型检查证据或调用 `goal_complete`，避免无意义地继续改代码。

这里最关键的设计思想是：**把模型自然停止看成一个可恢复事件，而不是系统的最终真相。**

## 6. 你说是六状态 Goal 状态机，六个状态分别是什么？如何流转？

**参考回答：**

六个状态是：

- `active`：目标仍在执行，需要继续工作。
- `verifying`：模型已经进入最终验证阶段，但尚未通过完成门禁。
- `complete`：所有验收条件和验证门禁通过，任务完成。
- `waiting_for_user`：缺少必须由用户决定的信息，暂时不能继续。
- `failed`：出现不可恢复错误，或超过 attempt、时间等限制。
- `cancelled`：用户主动取消或系统收到取消信号。

主要流转为：

```text
active → verifying → complete
  │          │
  │          └─ 验证失败或证据不足 → active / verifying
  ├─ 缺少用户决定 → waiting_for_user → active
  ├─ 不可恢复错误或超限 → failed
  └─ 用户取消 → cancelled
```

GoalState 会持久化 Goal 原文、逐条验收条件、状态、attempt 数、时间和费用预算、检查点、最近验证、验证历史、Judge 拒绝原因、验收证据和最终结果。

持久化的价值有两个：第一，进程重启后可以恢复，而不是让模型重新猜当前进度；第二，CLI、飞书等入口可以共享同一套任务语义，同时不同会话又使用独立的状态文件。

## 7. 系统如何判断任务真的完成，而不是模型自己说“完成了”？

**参考回答：**

完成不是靠自然语言判断，而是通过 `goal_complete` 门禁。至少要满足以下条件：

1. Goal 当前处于 `verifying`。
2. 存在最后一次文件修改之后产生的、新鲜验证结果。
3. 验证必须来自真实 Bash 执行，且真实退出码为 0。
4. 当前没有仍在运行的验证任务。
5. 每条验收条件都恰好提供一条证据。
6. 证据中的 criterion 必须和原验收条件逐字一致，不能改写、合并或漏项。
7. 如果验收条件要求覆盖率，验证输出中必须能提取并满足覆盖率要求。
8. 如果启用了独立 Judge，Judge 也必须批准；解析失败、超时或字段不一致时 fail closed。

例如模型先运行测试并通过，随后又修改了代码，那么成功的 `edit` 或 `write` 会清除旧验证，把状态重新置为 `active`。因为旧测试只能证明旧代码，不能证明修改后的代码。

这个“验证新鲜度”是完成门禁中最重要的点之一。很多 Agent 会出现“测试通过—继续改代码—直接宣布完成”的错误，如果不记录修改与验证之间的先后关系，就无法发现。

## 8. 为什么 Goal 不直接放进 Agent Loop？

**参考回答：**

Goal 是 Coding Agent 的产品策略，而不是 Agent 的通用定义。

如果把 Goal 放进 Agent Loop，会产生几个问题：

- 普通对话或其他类型 Agent 也被迫承担编码任务状态。
- Agent Loop 会依赖持久化目录、验收条件和产品提示词，难以复用。
- 工具回合和 Goal attempt 两个粒度容易混在一起。
- 后续接入不同平台时，通用循环需要感知 CLI、飞书会话和任务目录。

因此我保持 Agent Loop 只处理单次运行，把 GoalSupervisor 放在外层。Agent Loop 的输出是一次 attempt 的结果，GoalSupervisor 决定是否需要下一次 attempt。

这是典型的机制与策略分离：Loop 提供执行机制，Goal 提供长任务监督策略。

## 9. 你的上下文压缩具体是怎么做的？

**参考回答：**

压缩不是直接把全部历史交给模型总结，而是一个从低成本、确定性处理到模型摘要的渐进流程：

```text
大型 Tool Result 实时落盘
        ↓
超过 Soft Trigger
        ↓
选择完整回合切点
        ↓
旧消息和工具原文写入 JSONL / Artifact
        ↓
生成确定性任务 Checkpoint
        ↓
保留近期原始消息
        ↓
若超过 Hard Trigger 且仍过大，再调用模型摘要
```

首先，大型工具结果在刚产生时就会制品化。全文写入工作区内部的 Artifact，Prompt 中只保留工具名、文件路径、大小、哈希和头尾预览，避免后续每轮重复发送几十 KB 的日志。

达到软阈值后，系统从最近消息向前计算保留预算，并尽量在完整 User Turn 边界切分，避免把 Assistant Tool Call 和对应 Tool Result 拆开。被移出的消息会完整写入 JSONL Archive，并加入检索索引。

然后程序生成确定性 Checkpoint，记录当前请求、之前进度、归档路径与哈希、最近语义台账、重要文件状态和可恢复工具结果。Checkpoint 的职责是保证任务能继续，不是代替所有历史事实。

软阈值阶段优先只使用这种确定性压缩。如果确定性 Checkpoint 仍不够小，软阶段可以暂缓切换；达到硬阈值后必须回收空间，此时才调用模型生成摘要。即使模型摘要失败，也会退回确定性方案，不让主任务因为压缩失败而完全中断。

最后 Prompt 由“Checkpoint + 检索到的相关历史 + 近期原文”组成，而完整原文继续保存在 Archive 中。

## 10. 为什么要设置软阈值和硬阈值？一个阈值不够吗？

**参考回答：**

两个阈值是在成本、信息损失和系统安全之间做分级处理。

软阈值表示上下文开始变得昂贵，但还没有迫近模型极限。此时系统优先做可重复、低成本、信息损失可控的操作，例如大输出落盘、旧 Tool Result 引用化、完整历史归档和确定性 Checkpoint，不急着调用模型摘要。

硬阈值表示如果继续增长，下一轮可能没有足够空间留给系统提示、工具定义和模型输出。因此硬阈值下必须压缩，必要时允许模型生成更短摘要，并在失败时使用确定性 fallback。

这样设计比单阈值更稳：

- 如果阈值太低且每次都调用模型摘要，会增加延迟、费用和摘要漂移。
- 如果阈值太高才第一次处理，大型上下文可能已经来不及安全回收。
- 分级策略允许系统先做低风险治理，再在真正必要时使用有损但压缩率更高的模型摘要。

还需要保留 Reserve，给模型最大输出、下一轮工具调用和协议字段预留空间，不能把上下文窗口全部用满。

## 11. 既然已经有摘要，为什么还需要 Archive 检索？

**参考回答：**

因为摘要只能维护任务连续性，不能保证保留未来所有可能被问到的细节。

摘要模型在压缩发生时并不知道用户未来会问什么。比如一段很长的调试历史中，摘要可能保留“最终修复了缓存问题”，但丢掉某个错误码、用户原话、具体文件名或一次失败尝试。之后如果问题恰好需要这些细节，仅靠摘要无法恢复。

所以我把“继续做当前任务”和“恢复完整事实”拆开：

- Checkpoint/摘要负责当前任务状态、已完成工作、下一步和关键路径。
- Archive 保存被移出 Prompt 的完整原始消息和工具输出。
- 新问题到达后，系统根据当前请求检索 Archive，把相关原始证据重新注入上下文。

这也是为什么 BM25、向量、RRF 仍然属于上下文压缩体系的一部分：它们不是参与压缩，而是从压缩后移出的历史中恢复相关证据。

一句话概括：**摘要用于 continuity，归档检索用于 fidelity。**

## 12. 你的记忆为什么要分层？每一层分别保存什么？

**参考回答：**

因为不同信息的生命周期、可信度、写入条件和读取方式不同，放在一个 Memory 文件里会相互污染。

我把记忆拆为：

| 层 | 保存内容 | 生命周期 |
| --- | --- | --- |
| Working Context | 当前实际发给模型的消息 | 当前会话、持续压缩 |
| Archive Memory | 被压缩移出的完整消息、工具原文和 Artifact | 当前会话可恢复历史 |
| Semantic Memory | 用户偏好、项目约束、环境信息、稳定事实 | 跨会话长期存在 |
| Episodic Memory | 一次历史任务的 Goal、结果、错误与经验 | 跨会话任务经历 |
| Procedural Memory | Skill 目录、操作指南和参考资料 | 随项目维护、按需加载 |

例如“用户长期偏好 Python”适合 Semantic；“本次测试在第 46 行失败”属于 Working Context 或 Episode；完整测试日志属于 Archive；“如何发布 Python 包”属于 Procedural Skill。

分层以后可以分别设置写入策略：Semantic 写入非常保守，不能把模型猜测和临时日志自动变成长期事实；Archive 则以完整保存为主，即使内容不够稳定也可以保存，因为它代表历史证据，而不是系统认定的真理。

## 13. 长期记忆的检索链路是怎样的？

**参考回答：**

检索采用两阶段结构：第一阶段追求高召回，第二阶段追求高精度。

```text
Query
  ├─ BM25 Top-N
  └─ 本地 Bi-Encoder Top-N
             ↓
       Weighted RRF
             ↓
   小候选集确定性打分
             ↓
      Cross-Encoder
             ↓
           Top-K
```

BM25 负责精确词面匹配，特别适合代码场景中的文件名、函数名、错误码、版本号和专有名词。本地 Bi-Encoder 把 Query 和文档分别编码，补充同义表达和语义相似召回。两路分数尺度不同，所以不直接加原始分数，而是根据各自排名使用加权 Reciprocal Rank Fusion。

RRF 后只保留有限候选，再让 Cross-Encoder 同时阅读 Query 和 Candidate，进行更精细的相关性判断。最终分数不是 100% 依赖 Cross-Encoder，还会保留一部分确定性分数，避免通用模型对中文、代码符号和精确实体误排。

Semantic、Archive 和 Episodic 可以先在各自来源内召回，再做跨来源融合，最后只运行一次 Cross-Encoder，让不同来源在同一尺度上竞争，避免重复推理。

## 14. 为什么同时使用 BM25 和 Bi-Encoder？只用向量数据库不行吗？

**参考回答：**

只用向量检索在自然语言语义相似上有优势，但 Coding Agent 的证据中有大量不适合模糊语义匹配的字符串，例如：

- `WorkspaceGuard.resolve()` 这样的函数名；
- `NON_ZERO_EXIT` 这样的错误码；
- `src/MiniClaw/...` 文件路径；
- 版本号、Commit ID、配置键；
- 用户原话中的少见实体。

这些内容通常是 BM25 更稳定。Bi-Encoder 的价值是补充词面不同但含义相近的表达，例如用户问“如何限制命令资源”，历史文档写的是“CPU、memory、PID quota”。

因此我把 BM25 作为精确召回主通道，把 Bi-Encoder 作为语义补充，再通过 RRF 融合。这样不会要求两个通道的原始分数具有相同尺度，也不会因为向量模型降级就让整个记忆不可用。

真正的工程目标不是选一个“最先进”的检索器，而是针对代码数据同时覆盖精确实体和语义表达，并设计可降级链路。

## 15. RRF 是什么？为什么不直接把 BM25 分数和余弦相似度相加？

**参考回答：**

BM25 分数和向量余弦相似度来自不同分布，数值尺度没有可比性。直接使用 `0.5 × BM25 + 0.5 × cosine`，会受到语料规模、Query 长度和模型输出范围影响，权重难以稳定迁移。

RRF 不关心原始分数，只使用每条召回结果在不同通道中的排名：

```text
score(d) = w_bm25 / (k + rank_bm25(d))
         + w_vector / (k + rank_vector(d))
```

一个候选如果在 BM25 和 Vector 中都靠前，会得到更高分；只被一条通道召回，也仍然有机会进入候选池。

MiniClaw 使用加权 RRF，是因为代码记忆中精确词面通常比纯语义更可靠，所以 BM25 权重更高，Vector 作为补充。RRF 的主要优点是简单、稳定、可解释，对两路原始分数的尺度变化不敏感。

## 16. Bi-Encoder 和 Cross-Encoder 有什么区别？为什么两个都要？

**参考回答：**

Bi-Encoder 分别编码 Query 和 Document：

```text
Query → 向量 q
Document → 向量 d
cos(q, d) → 相似度
```

文档向量可以提前计算和缓存，所以适合对大量文档快速召回。但因为 Query 和 Document 在编码阶段没有逐词交互，精排能力有限。

Cross-Encoder 把 Query 和 Document 作为一对共同输入 Transformer：

```text
[Query, Document] → Transformer → relevance score
```

它能理解更细的否定、条件、动作结果和实体关系，但每个 Query-Document 对都要单独推理，不能低成本扫描整个库。

因此 MiniClaw 让 Bi-Encoder 负责 Recall，让 Cross-Encoder 负责对 RRF 后的小候选集做 Precision。Cross-Encoder 缺失或加载失败时，系统会退回 BM25、向量、RRF 和确定性重排，并在 Trace 中记录实际后端和降级原因。

## 17. 如何避免长期记忆被错误信息污染？

**参考回答：**

核心原则是：Archive 可以完整，Semantic 必须保守。

Archive 代表“历史上确实出现过这些内容”，不等于系统认定内容永远正确，所以可以保存完整对话和工具证据。

Semantic Memory 只接收有限类别的稳定事实，例如 preference、project、environment 和 fact。自动提取只扫描用户消息，并要求明确的“记住”“长期记忆”等指令，不会把模型推测、临时日志或一次失败自动提升为长期事实。

写入前还会做：

- Secret 和凭据拒绝；
- 临时措辞识别；
- 单条和总文件大小限制；
- 大小写不敏感去重；
- 同 subject 不同 value 的冲突检测；
- 冲突必须显式选择保留旧值、替换或并存；
- 文件锁和原子替换，避免并发丢更新。

在读取侧，召回结果会明确标注它来自记忆，当前用户请求和系统规则优先，不能让旧记忆覆盖当前指令。

## 18. Tool Runtime 的完整执行链路是什么？

**参考回答：**

一次 Tool Call 不会直接调用系统 API，而是统一经过执行边界：

```text
模型生成 Tool Call
      ↓
工具查找与参数预处理
      ↓
递归 JSON Schema 校验
      ↓
项目指令刷新检查
      ↓
风险分类与 ApprovalGate
      ↓
WorkspaceGuard / Runtime
      ↓
具体工具执行
      ↓
超时、取消、异常归一化
      ↓
按工具语义截断输出
      ↓
Tool Result + Trace
```

参数校验解决结构错误，例如缺少必填字段、类型错误、未知枚举和嵌套对象不合法。审批解决“参数合法但行为危险”的问题。WorkspaceGuard 解决文件路径是否处于允许工作区的问题。Docker Runtime 解决 Bash 进程的系统权限和资源边界问题。输出策略解决一次工具结果挤爆模型上下文的问题。

这几个层次不能互相替代。例如 Schema 正确的 `rm -rf` 仍然危险；路径在工作区内的无限循环仍然会耗尽资源；Docker 中运行也不代表删除工作区文件是安全的。

## 19. allow / ask / deny 是怎样工作的？为什么需要人工审批？

**参考回答：**

系统先对已经通过 Schema 校验的 ToolInvocation 做风险分类，识别破坏性文件操作、Git 操作、数据库写入、网络和外部写入、系统变更、敏感文件以及整文件覆盖等能力。

然后结合项目 allowlist 和全局策略决定：

- `allow`：符合策略或白名单，直接执行。
- `ask`：暂停在工具边界，由 CLI、飞书或未来 UI 请求用户确认；超时或拒绝都不执行。
- `deny`：无论模型如何请求都拒绝执行。

为什么不能只靠 Prompt 让模型“不要做危险操作”？因为 Prompt 是概率约束，模型可能误判，也可能被仓库内容或外部数据中的提示注入影响。审批必须位于模型输出之后、真实副作用之前，由确定性代码执行。

审批记录进入 Trace 时会脱敏，后续 `tool.call` 事件再记录真实执行状态，因此可以区分“模型提出了危险操作”“用户是否批准”和“操作是否成功”。

## 20. WorkspaceGuard 如何防止文件越界？

**参考回答：**

WorkspaceGuard 不是简单检查字符串里有没有 `..`，而是把用户路径解析为规范化宿主路径，并基于真实父目录进行校验。

主要保护包括：

1. 拒绝 `..` 或绝对路径逃出工作区。
2. 对已经存在的路径组件做真实路径解析，防止通过工作区内符号链接跳到外部目录。
3. 新建文件时检查最近存在的父目录，避免在不存在的尾部路径中绕过边界。
4. 按 `read/write/search/execute` 动态检查路径策略，而不是只在启动时扫描一次。
5. 对 `.env`、密钥、凭据、内部 `.aster` 状态等敏感路径设置不同权限。
6. `.git` 可读取部分非敏感元数据，但 Write/Edit 和全文搜索受到限制。
7. Docker 模式下维护宿主路径和 `/workspace` 路径的稳定映射。

需要准确说明边界：WorkspaceGuard 保护的是框架文件工具。它不能限制一个在宿主机执行的任意 Shell 命令，所以不可信任务的 Bash 必须进入 Docker 或更强的系统沙箱。

## 21. Docker Runtime 做了哪些隔离？为什么说它仍然不是绝对安全？

**参考回答：**

每次 Bash 调用都会启动一个临时容器，挂载有效工作区到 `/workspace`，命令结束、超时或取消后清理容器。主要限制包括：

- 默认 `network none`；
- 根文件系统只读；
- 删除全部 Linux capabilities；
- `no-new-privileges`；
- 限制 CPU、内存、PID 和文件描述符；
- `/tmp` 使用有大小限制的 tmpfs；
- 只注入固定、非敏感环境变量；
- API Key、飞书 Secret 和宿主其他环境变量不进入容器；
- 对 Direct 模式下的敏感工作区路径做动态遮蔽挂载；
- 命令超时或取消时强制移除容器，并终止本地 Docker CLI 进程树。

但 Docker 不是“绝对安全”的理由也必须说清楚：

- 挂载到容器的工作区文件仍然可能被删除或破坏。
- Direct 模式的修改会真实落到源项目。
- 容器隔离不能代替 Git、备份和审批。
- Docker 本身和宿主内核仍属于信任边界。
- 开启网络后会引入新的数据外传和供应链风险。
- Linux 容器不能证明代码在 Windows 或 macOS 原生环境也正确。

所以我的设计是纵深防御：Schema、风险策略、人工审批、WorkspaceGuard、Docker、资源限制、Trace 各自控制不同风险。

## 22. Direct 和 Snapshot 工作区模式有什么区别？

**参考回答：**

Direct 模式把源工作区直接作为有效工作区，文件工具和 Docker 挂载都操作真实项目。优点是修改立即可见，不需要同步；风险是误操作也会直接影响源目录。

Snapshot 模式在 Session 沙箱目录中创建一次安全副本，后续文件工具和 Bash 都只操作副本。复制时排除凭据、私钥、`.aster` 内部状态、依赖目录、缓存、构建产物、符号链接和超限文件。Manifest 记录源目录、任务 ID、复制数量、字节数和排除项。

Snapshot 适合多会话、Eval、失败复现和不希望直接修改真实项目的场景。它的代价是需要额外磁盘和复制时间，而且当前不会自动把结果合并回源项目。

选择原则是：本地可信开发任务可以使用 Direct；不可信输入、Benchmark 或需要强隔离的会话优先 Snapshot。

## 23. Trace 到 Eval 的闭环具体是什么？

**参考回答：**

完整闭环是：

```text
真实 CLI / 飞书运行
        ↓
统一 trace.jsonl
        ↓
失败 Run 转为 Eval Case
        ↓
替换模型 / Prompt / Tool 配置做安全重放
        ↓
eval-results.jsonl
        ↓
失败聚类、Dashboard、基线对比和回归告警
        ↓
候选方案进入隔离工作区集成验证
```

Trace 不只记录最终文本，还记录：

- `run.started/completed`；
- 普通 Agent、Goal Judge 和 Compaction 的模型请求；
- Tool Call 参数、结果、耗时和错误；
- 审批请求和决定；
- Goal 前后状态；
- Compaction 触发、策略和压缩前后 Token；
- Runtime 配置、Token、成本和延迟。

失败轨迹可以生成可移植 Eval Case，保存当时的脱敏模型上下文、模型输出、Prompt Hash、Tool Hash 和失败签名。重放时默认只重放模型决策边界，不重新执行真实工具，避免再次产生写文件、删除或网络副作用。

这个重放只能证明“模型在相同边界下是否做出更好的决策”，不能单独证明代码已经修好，所以结果会标记为 model-boundary-only。最终仍要在 Snapshot 或 Fixture 中运行真实验证。这个置信边界必须明确，不能把离线模型重放宣传成端到端任务通过。

## 24. 为什么 Trace 放在 ModelClient 外层，而不是只写在 Agent Loop 里？

**参考回答：**

因为并不是所有模型请求都来自普通 Agent Loop。

MiniClaw 还有两类重要模型调用：Goal 的独立 Judge，以及硬压缩时的模型摘要。如果只在 Agent Loop 里记录，就会漏掉这些成本、错误和延迟。

所以我用 `TracingModelClient` 包装 Provider-neutral ModelClient，所有通过模型层发出的请求都统一进入 Trace，再用 metadata 标记 purpose，例如 `agent`、`goal_judge`、`compaction` 和 `trace_replay`。

工具、Goal 和压缩事件则由 CodingAssistant 关联到当前 run。这样 Agent Loop 不需要知道 Trace 文件和 Dashboard，同时 Trace 又能覆盖所有模型边界。

另一个原则是 Trace 只能观察，不能改变执行决策；Trace 写入失败不能让用户任务失败，否则可观测性系统反而成为主流程单点故障。

# P1：实现细节与深挖问题

## 25. 通用 Agent Loop 是怎样工作的？

**参考回答：**

一次 run 的基本过程是：

```text
追加 User Message
      ↓
根据当前状态生成动态 System Prompt
      ↓
调用 ModelClient，流式接收文本和 Tool Call
      ↓
追加 Assistant Message
      ↓
按来源顺序执行所有 Tool Call
      ↓
把 Tool Result 追加回消息历史
      ↓
再次请求模型
      ↓
无 Tool Call / 达到限制 / 错误 / 取消时结束
```

Loop 自身提供最大轮次、上下文转换 hook、动态系统提示和取消传播，但不内置 Memory、Goal、项目指令或具体工具。这样上下文压缩可以通过 transform hook 接入，项目指令可以通过动态 Prompt Provider 接入，而不需要改循环的核心状态机。

Tool Result 必须按 Tool Call 原始顺序放回消息历史，即使底层未来并行执行，也要保持协议顺序稳定，否则模型侧的 `tool_call_id` 对应关系可能被破坏。

## 26. ToolExecutor 为什么要统一做递归 Schema 校验？

**参考回答：**

模型生成的 Tool Call 本质上是不可信结构化输入。常见问题不只是顶层字段缺失，还包括嵌套数组中元素类型错误、枚举非法、对象出现未知字段、数字范围不合法等。

如果每个工具各写一套校验，会产生行为不一致和重复代码，也容易在新工具中遗漏。因此 ToolExecutor 在进入具体工具前统一递归校验 Schema，并把错误归一化为结构化 ToolResult，让模型有机会修正参数，而不是直接抛异常破坏整次 run。

校验之后仍需要具体工具的语义校验。例如 Schema 只能保证 `oldText` 是字符串，不能保证它在文件中唯一；只能保证 path 是字符串，不能保证路径没有逃出工作区。

## 27. read、bash、grep 为什么采用不同的输出截断策略？

**参考回答：**

因为不同工具的高价值信息分布不同。

- `read` 通常先需要文件头部的 import、类型定义和模块结构，所以保留头部，并提供 offset 继续读取。
- `bash` 的测试总结、异常堆栈和退出原因通常在末尾，所以保留尾部；完整超大输出另外落盘。
- `grep` 需要同时控制匹配数量、总字节数和单行长度，防止一个 minified 文件或大量命中挤爆上下文。

如果所有工具统一保留前 50KB，Bash 最关键的失败摘要可能被截掉；如果统一保留尾部，读取源码又会丢失文件定义。工具输出治理必须理解工具语义，而不是只有一个通用字符串截断函数。

## 28. edit 工具为什么不直接使用字符串 replace？

**参考回答：**

编码修改需要明确、可审计和可恢复的语义。直接 `str.replace` 有几个风险：目标可能出现多次、多个 replacement 可能重叠、前一个修改可能改变后一个匹配位置，还可能意外改变换行风格和 BOM。

MiniClaw 的 edit 会：

1. 让所有 `oldText` 都相对于同一份原始文件定位。
2. 要求每个 `oldText` 唯一，出现多次就拒绝猜测。
3. 检测多个编辑区间是否重叠或嵌套。
4. 按位置从后向前应用，避免前面文本长度变化影响后面下标。
5. 精确匹配失败时只进行有限的 Unicode、智能引号、横线和行尾空白规范化。
6. 保留原文件的 CRLF/LF 和 UTF-8 BOM。
7. 返回 diff 和 firstChangedLine，便于审计和 UI 展示。
8. 使用按文件路径划分的修改队列，避免两个并发 edit 基于同一旧版本互相覆盖。

这个工具的价值不是“能改文件”，而是把模型模糊的文本修改意图转换为确定性、失败可解释的文件变更。

## 29. 如何处理超大 Tool Result，为什么不直接丢弃？

**参考回答：**

直接丢弃会导致模型失去诊断证据，而完整放进上下文会导致后续每轮重复付费。

MiniClaw 会把超阈值结果完整写入 `.aster/context-artifacts` 或 `.aster/tool-output`，计算大小和 SHA-256，在 Tool Result 中只保留路径和头尾预览。模型需要更早内容时，可以使用 read 分段恢复。

压缩旧消息时，还会把未制品化的旧 Tool Result 写入 Artifact，并把归档副本替换为轻量引用。原始 Session Transcript 仍然保持 append-only，不会原地改写。

这相当于把 Tool Result 从“每轮重复发送的 Prompt 内容”转换为“可按需读取的外部状态”，同时保留可审计性。

## 30. 压缩时如何避免把 Tool Call 和 Tool Result 切开？

**参考回答：**

系统先从最新消息向前累计需要保留的 Token，得到一个近似切点，然后继续寻找完整 User Turn 边界，优先在下一轮用户消息之前切分。

这样可以让一个回合中的 User 请求、Assistant Tool Call、Tool Result 和 Assistant 结论尽量处于同一侧。只有单个回合本身就非常大、无法找到合适边界时，才使用更细的安全切点。

这个不变量很重要，因为 Tool Result 脱离对应的 Assistant Tool Call 后，模型消息协议可能不合法，也会让摘要和恢复难以理解执行因果。

## 31. 模型摘要失败怎么办？压缩会不会让任务中断？

**参考回答：**

硬压缩不能把模型摘要当成唯一成功路径。

系统先生成确定性 Checkpoint，并完整写入 Archive。需要模型摘要时，以无工具请求调用当前 ModelClient，并在 Trace 中标记为 compaction。如果返回空内容、超时、异常或格式不可用，就退回确定性 fallback。

因此即使摘要模型失败，完整历史已经归档，当前请求和最近原文仍保留，系统可以继续运行。压缩失败也会记录 Trace，但不会轻易破坏主任务。

设计上先保存可恢复原文，再执行有损摘要，避免“摘要失败等于历史丢失”。

## 32. 多次压缩后如何避免摘要越来越失真？

**参考回答：**

如果只做“摘要的摘要”，误差会逐轮累积。因此 MiniClaw 不把完整事实建立在摘要链上。

每次压缩都会：

- 保存新移出的完整原始消息；
- 把原始分块加入 Archive Index；
- 在新 Checkpoint 中合并之前的任务状态；
- 保留最近原始消息；
- 根据新请求重新检索历史原始证据。

摘要链只负责维持当前任务连续性。需要精确事实时，系统从多个 Archive 中检索原文，而不是相信多轮摘要中可能已经变形的一句话。

## 33. Archive 的父子分块为什么这样设计？

**参考回答：**

用于召回的块需要短，否则一个长消息会稀释关键词和向量语义；用于回答的证据又需要连续上下文，否则只看到一小段可能缺少前因后果。

所以 Archive 使用父子召回：

- 子块大约按固定字符数切分，用于 BM25、Bi-Encoder 和 Cross-Encoder 排序。
- 命中后，把锚点子块的前后相邻块展开成父节点，作为最终证据注入模型。

Cross-Encoder 只重排锚点子块，而不是整个展开父节点，因为它通常有最大输入长度。如果前置内容先占满窗口，真正命中的信息反而会被截掉。

这实现了“短块负责找得准，父节点负责看得全”。

## 34. 本地 Bi-Encoder 的冷启动和性能问题怎么处理？

**参考回答：**

本地 SentenceTransformer 第一次需要加载模型并编码尚未缓存的文档，冷启动明显；之后同一文档可以复用向量，只编码新 Query，延迟会大幅下降。

当前做法包括：

- 只从本地 Hugging Face 缓存加载，不在在线任务中隐式下载。
- 进程级模型缓存和锁，避免多个会话重复加载。
- 批量编码 Query 和未缓存文档。
- 文本向量内存缓存。
- device 为 auto 时优先 CUDA，不可用时回退 CPU。
- 模型或依赖失败时退回 LocalHashVectorEncoder，并在 Trace 中标记 fallback。

后续最有价值的优化是文档向量持久化和增量索引，而不是每次降低候选质量。否则进程重启后仍要重新编码大语料。

## 35. Cross-Encoder 为什么不是 100% 决定最终排名？

**参考回答：**

Cross-Encoder 更擅长自然语言相关性，但当前通用模型可能偏英文搜索数据，对中文、代码符号、路径、版本号和错误码不一定稳定。

因此最终得分由 Cross-Encoder 分数和归一化确定性分数融合。确定性部分包含 RRF、Query 覆盖率、Subject 覆盖率、完整短语和来源特征。

这样既使用 Cross-Encoder 的语义交互能力，又保留 BM25 和精确字符串信号。更重要的是，Cross-Encoder 不可用时可以自然降级，不会让检索链断掉。

## 36. Goal 状态文件如何保证可靠性？

**参考回答：**

Goal Store 会限制文件类型和大小，拒绝读取符号链接，使用进程间锁避免并发写丢失，写入时先写临时文件再原子 replace。验证输出只保留有界尾部，验证历史也限制数量，避免状态文件无限增长。

持久化状态还会检查合法状态迁移和数据结构。不能让模型通过普通文本直接修改 Goal 文件，只能通过受控的 Goal 工具和 Store API 改变状态。

如果发生进程重启，新的 Supervisor 会从状态文件恢复 attempt、checkpoint、最后验证和剩余预算，而不是仅从聊天文本推断。

## 37. 系统如何处理中断和取消？

**参考回答：**

一次 attempt 使用共享 CancellationToken，向下传播到 Agent Loop、模型流、工具执行、审批等待、Goal Judge、Compaction 以及 Host/Docker 命令。

Host 命令取消时终止进程树；Docker 命令取消时先删除具名容器，再回收本地 Docker CLI。Agent Loop 会为当前和剩余未执行的 Tool Call 合成 cancelled Tool Result，保证持久化消息协议仍然完整，不会留下 Assistant 发出了多个 Tool Call、却只有部分 Tool Result 的非法历史。

Write/Edit 使用暂存和原子替换，避免用户取消后后台写入又迟到提交。

Trace 会记录 `run.cancelled`、取消的模型请求、取消的工具调用、Goal 的 `cancelled` 终态和最终 run 状态。Dashboard 的错误率会排除用户主动取消，避免把正常取消误算为系统故障。

## 38. 如何处理项目里的 AGENTS.md 或动态指令？

**参考回答：**

项目指令按作用域分层加载：用户全局指令、工作区根目录、已激活的祖先目录、目标文件最近目录，最后才是当前用户请求。

每个目录只选择一个最高优先级的指令文件，记录来源路径、Scope、深度、内容哈希和文件签名。预算从更局部的来源向外分配，但渲染时保持从低优先级到高优先级的顺序，让最近目录规则最后生效。

read 和 grep 会激活目标目录作用域。write 和 edit 在真正修改前执行 fail-before-mutation 检查：如果相关 AGENTS.md 在当前 System Prompt 生成后新建或改变，工具先返回 `instructions_refresh_required`，下一轮刷新 Prompt 后模型才能重试，避免在旧规则下先改文件、之后才发现新约束。

## 39. 如果多个会话同时写 Memory 或同一个文件，如何避免竞争？

**参考回答：**

需要区分两类并发：

第一类是同一个代码文件的 Write/Edit。系统按规范化绝对路径建立修改队列，把“读取旧版本—计算新内容—原子写入”放在同一个临界区。同一文件串行，不同文件仍可并行。

第二类是跨会话共享的 Semantic Memory 和 Goal 状态。它们使用进程间文件锁和临时文件原子替换，避免两个进程基于同一旧文件同时写回造成丢更新。冲突解决还会在提交前重新检查原值，避免使用过期状态覆盖其他会话的新修改。

只锁最后的 write 系统调用是不够的，因为两个任务可能已经读到相同旧内容并各自计算结果，最后一个写入会覆盖前一个。

## 40. 安全系统如何应对 Prompt Injection？

**参考回答：**

MiniClaw 的思路不是声称可以仅靠模型识别所有 Prompt Injection，而是让不可信文本无法直接跨越确定性执行边界。

仓库文件、网页内容和工具输出即使诱导模型执行危险命令，最终 Tool Call 仍要经过：

- Schema 校验；
- 风险分类；
- allow/ask/deny 策略；
- 用户审批；
- WorkspaceGuard；
- Docker 权限和网络限制；
- 敏感路径与环境变量隔离。

记忆召回内容也会标注为历史证据，不能覆盖当前用户请求和系统规则。Trace 写入前会对凭据类字段和常见 Token 形式脱敏。

需要诚实说明：这些措施降低了 Injection 造成真实副作用和数据泄漏的概率，但不能证明模型永远不会被诱导。安全性应通过类似 AgentDojo 的攻击任务持续评测，而不是一次设计完成后就认为问题永久解决。

## 41. 你参考了 pi-mono，哪些是参考，哪些是你自己的工程实现？

**参考回答：**

我参考的是 pi-mono 的分层方向、Provider-neutral 模型协议、Agent Loop 与产品解耦、五类 Coding Tool 契约，以及外层任务监督等思想。

但 MiniClaw 不是对 TypeScript 代码逐行翻译，而是基于 Python 的模块、异步模型和本地运行环境重新实现，并围绕自己的问题做了扩展，例如：

- Python 原生的 llm/agent/coding_agent 依赖边界；
- 持久化六状态 Goal、验证新鲜度和逐条验收证据；
- soft/hard 分级压缩、Archive Index 和可恢复 Artifact；
- Semantic/Archive/Episodic/Procedural 分层记忆；
- BM25、本地 Bi-Encoder、RRF 和 Cross-Encoder 检索链；
- WorkspaceGuard、ApprovalGate、Direct/Snapshot 和 Docker Runtime；
- 覆盖 Agent、Judge、Compaction 的统一 Trace；
- 从真实失败生成 Eval Case、模型边界重放、失败聚类和 Dashboard。

面试时我会明确说明参考来源，同时重点讲自己解决的具体问题、代码边界、异常路径、测试和取舍，而不是把开源项目的设计全部说成原创。

## 42. 这个项目中最难的部分是什么？

**参考回答：**

最难的不是某一个算法，而是维护跨模块不变量。

例如“任务完成”同时涉及 Goal 状态、Bash 真实退出码、最后一次文件修改时间、逐条验收证据、可选 Judge 和进程恢复。如果只在 Prompt 中要求“修改后再测试”，模型仍然可能遗漏；如果把逻辑散落在 Bash、Edit 和 Assistant 中，又很难证明没有旁路。因此我把执行结果 hook 放在统一 ToolExecutor 边界：成功修改会使旧验证失效，成功的最终验证生成结构化证据，`goal_complete` 只从 GoalStore 读取可信状态。

压缩也类似。它既要降低 Token，又要保证 Tool Call/Result 协议完整、当前请求不丢、旧原文可恢复、失败时可降级，并且不能让摘要模型成为单点故障。这要求在切点、Archive、Artifact、Checkpoint、检索和 Trace 之间维护一致性。

所以我认为最难的是把模型的不确定行为包在确定性的状态机、文件格式和执行门禁里，并保证重启、取消和异常时这些不变量仍成立。

## 43. 这个项目最有价值的技术亮点是什么？

**参考回答：**

我会按以下顺序回答：

1. **Goal 外层监督和验证门禁。** 它把“模型停答”与“任务完成”分离，并通过真实验证和证据使任务可验收。
2. **可恢复的上下文治理。** 不是单纯摘要，而是 Artifact、完整 Archive、Checkpoint、近期原文和检索恢复的组合。
3. **分层记忆和混合检索。** 根据生命周期拆分存储，并通过 BM25、Bi-Encoder、RRF 和 Cross-Encoder兼顾精确召回与语义精排。
4. **纵深安全执行边界。** Schema、风险策略、HITL、WorkspaceGuard 和 Docker 分别控制不同风险。
5. **Trace 到 Eval。** 让真实失败成为可重放、可聚类和可回归的数据资产，而不是一次性聊天记录。

这些亮点彼此是连起来的：Goal 让完成可定义，Trace 让过程可观察，Eval 让改动可比较，Runtime 让试错有边界，Memory 让长任务可以持续。

## 44. 你做过哪些验证？如何证明这些设计有效？

**参考回答：**

我把验证分为三层：

**第一层，确定性单元测试。** 覆盖状态迁移、验证失效、Schema 校验、路径逃逸、符号链接、敏感路径、edit 唯一匹配和重叠、BOM/换行保留、输出截断、Memory 冲突和检索降级等。

**第二层，Runtime 和集成烟雾测试。** 验证 Docker 能读取挂载工作区、Snapshot 写入不会影响源目录、凭据不会进入 Snapshot、Direct 模式敏感路径会被遮蔽、超时命令会终止且容器被清理、网络保持关闭。

**第三层，Benchmark 和 Trace 分析。** 使用长记忆任务评估证据召回和最终回答，记录 Bi-Encoder 后端、Cross-Encoder 是否应用、候选数、耗时和正确证据是否进入 Top-K；使用 Coding/Efficiency 任务观察压缩前后 Token、成功率和工具错误；使用安全 Benchmark 评估 Prompt Injection 下的任务效用和攻击成功情况。

我会避免只报一个端到端正确率，因为失败可能发生在召回、重排、上下文组织、回答模型或工具执行。Trace 需要把这些阶段拆开，分别判断“没召回”“排错了”“证据有了但模型没用对”还是“Runtime 执行失败”。

## 45. Cross-Encoder 的效果如果提升不大，为什么还保留？

**参考回答：**

首先不能因为理论上更强就宣称一定显著提升。当前小样本测试中，Cross-Encoder 对候选 Top-1/Top-5 和最终正确率只有小幅净提升，同时增加了 CPU 延迟，而且存在个别回归。

我保留它的原因是：

- 它已经接入真实检索链，并且能够改善部分词面相似但关系不同的候选排序。
- 它是可配置、可观测、可降级的增强层，不是硬依赖。
- Trace 能识别它是否真正应用、耗时多少、是否导致误排。
- 后续可以用更大的固定样本评估 MRR、NDCG、Recall@K 和最终答案正确率，再决定默认权重和模型。

工程上正确的态度是把它作为待持续验证的精排能力，而不是为了简历亮点夸大结果。

## 46. 为什么不用数据库，而使用 Markdown 和 JSONL？

**参考回答：**

项目早期优先选择 Markdown 和 append-only JSONL，原因是部署简单、透明、容易人工检查、方便 Git 忽略和迁移，也适合单机 Coding Agent 的会话规模。

- Goal 使用小型 JSON，便于原子替换和恢复。
- Trace、Archive Index 和冲突事件使用 JSONL，适合追加写入和流式分析。
- Semantic/Episodic 使用 Markdown，便于用户直接审阅和修改。

但这不是说文件存储适合无限扩展。随着多用户、高并发和百万级记录增长，需要把索引和元数据迁移到 SQLite/PostgreSQL 或专用检索服务，并增加事务、压缩、生命周期管理和权限隔离。

选择文件存储是当前规模下的工程取舍，不是对数据库的否定。

## 47. 如果上下文窗口越来越大，压缩系统还有必要吗？

**参考回答：**

仍然有必要。更大的上下文窗口只是提高上限，不会消除以下问题：

- 每轮重复输入大量旧日志会增加成本和首 Token 延迟。
- 超长上下文中模型对中间信息的利用并不稳定。
- 旧工具输出里有大量已经无关的噪声。
- 会话可以持续跨越多个模型窗口甚至跨进程重启。
- 敏感或大体积结果不应该永久进入每轮 Prompt。

上下文治理的目标不只是“防止报超限错误”，还包括控制成本、提高信噪比、保留可恢复证据和支持跨会话状态。因此即使模型窗口变成几百万 Token，Artifact、Archive、Checkpoint 和按需检索仍然有工程价值，只是阈值和策略会变化。

## 48. 为什么不让模型自己反思几轮，代替 Goal 状态机？

**参考回答：**

自我反思仍然是模型输出，无法提供确定性保证。模型可能连续几轮都重复同一个错误，也可能在没有测试的情况下自信地认为完成。

Goal 状态机解决的是系统层问题：状态持久化、attempt/time/cost 限制、验证新鲜度、逐条验收证据、取消、等待用户和进程恢复。这些信息需要由代码和真实工具结果维护，不能只存在于模型自然语言里。

模型反思可以作为某个 attempt 内的推理策略或独立 Judge，但不应该替代外层监督和完成门禁。

## 49. 目前项目还有哪些不足？

**参考回答：**

我会主动说明以下限制：

1. Cross-Encoder 和 Bi-Encoder 的效果验证样本仍有限，需要更大规模固定集和统计置信度。
2. 文档向量主要做进程内缓存，进程重启后的持久化增量索引仍可优化。
3. Snapshot 当前不会自动合并回源项目，需要设计可审阅的 Patch/Apply 流程。
4. Docker 每次 Bash 创建临时容器，安全边界清晰，但有启动开销，复杂项目还需要定制镜像。
5. Docker bind mount 中的工作区仍可被破坏，必须结合版本控制、备份和审批。
6. 文件式存储适合单机规模，多用户高并发下需要数据库和租户隔离。
7. Model-boundary Replay 不执行真实工具，不能代替完整工作区集成测试。
8. 风险分类基于规则，面对复杂 Shell 拼接、编码绕过和新型攻击仍要持续扩展测试。
9. 模型价格未配置时成本字段只能保持 0，不能凭空估算真实费用。

主动讲清限制不会削弱项目，反而能说明我理解能力边界，没有把“可运行”夸大成“生产绝对安全”。

## 50. 如果让你继续做，你下一步会优化什么？

**参考回答：**

我会按优先级做四件事：

1. **完善端到端 Eval Harness。** 在隔离 Snapshot 中准备 Fixture、执行真实工具、运行验收命令，并把模型边界指标和最终代码正确性统一起来。
2. **持久化向量索引。** 根据文档哈希增量编码，避免进程重启后对大型 Archive 全量计算。
3. **Snapshot 结果交付。** 生成可审阅 Patch、风险摘要和一键 Apply，而不是直接自动覆盖源项目。
4. **强化安全策略。** 对 Shell 做更细的能力解析，扩展 AgentDojo 类攻击评测，增加网络代理、域名白名单和外部写入审计。

如果面向多用户部署，还会补充数据库、租户隔离、任务队列、制品生命周期、密钥管理和容器池化。

# 压力追问：面试官可能挑战你的点

## 51. 面试官：你这个 GoalSupervisor 不就是“模型停了再问一句继续吗”？

**参考回答：**

如果只是无条件发送“请继续”，确实价值有限，而且可能进入死循环。MiniClaw 的区别是外层 Supervisor 基于持久化状态和结构化证据决策：

- 每次自然停止只增加一次 attempt；
- 只在 `active/verifying` 时继续；
- attempt、时间和费用有上限；
- work 和 completion review 使用不同继续提示；
- 文件修改会使旧验证失效；
- 完成必须满足真实退出码、验证新鲜度和逐条验收证据；
- 缺少用户选择时进入 `waiting_for_user`，不可恢复时进入 `failed`；
- 用户取消后进入 `cancelled`，不会继续自动运行。

因此它不是重试 Prompt，而是一个对任务生命周期有明确状态、预算和完成门禁的监督系统。

## 52. 面试官：你的安全分类还是规则匹配，很容易被绕过吧？

**参考回答：**

是的，单独的命令规则不能证明安全，所以我没有把它当成唯一边界。

规则分类的作用是识别常见高风险能力并触发审批；WorkspaceGuard 控制文件工具路径；Docker 控制 Bash 权限、网络和资源；敏感环境不注入容器；Trace 用于事后审计和扩展攻击样本。不同层共同降低绕过后的影响。

后续可以把 Shell 从纯文本规则升级为 AST/语法树分析，对管道、重定向、命令替换和编码内容做规范化，再结合 egress proxy、只读挂载、一次性凭据和更强内核沙箱。但即使这样也不应该宣称绝对安全，而应该通过持续红队 Benchmark 验证。

## 53. 面试官：本地模型加载失败，检索质量会不会突然下降？

**参考回答：**

会有质量差异，所以系统必须做到“可降级且可观测”，不能静默假装仍在使用神经模型。

Bi-Encoder 不可用时退回本地 Hash Vector，再与 BM25 和 RRF 继续工作；Cross-Encoder 不可用时保留确定性重排顺序。每次检索记录 backend、model、device、load_error、fallback、候选数和耗时。

这样线上质量变化可以从 Trace 中定位到模型未加载，而不是错误归因于用户问题或回答模型。对于严格生产环境，还可以把模型可用性作为启动健康检查，不允许降级实例接收需要高质量检索的流量。

## 54. 面试官：为什么不直接让 LLM Judge 看最终答案并决定完成？

**参考回答：**

Judge 也是概率模型，不能替代真实测试和确定性门禁。

MiniClaw 的顺序是先检查真实验证退出码、验证是否发生在最后修改之后、每条验收条件是否有精确证据，再把这些不可信证据交给 Judge 做补充审查。Judge 只能收紧，不能绕过基础门禁；它返回非法 JSON、超时或字段不一致时 fail closed。

也就是说，测试负责验证可执行事实，GoalStore 负责维护时序和证据完整性，Judge 只负责检查更难形式化的语义完成度。

## 55. 面试官：Trace 保存完整上下文，会不会泄露隐私？

**参考回答：**

这是一个真实风险。为了支持重放，Trace 比普通指标日志更敏感，所以系统在写入前会按字段名和常见 Token 模式脱敏，限制单个字符串大小，避免保存超长二进制数据，并把 `.aster` 默认排除在版本控制之外。

但普通源码、用户 Prompt 和命令输出仍可能包含业务信息，不能因为做了正则脱敏就认为可以公开分享。生产环境还需要目录权限、静态加密、保留期限、用户删除、访问审计和按租户隔离。高敏场景可以只保存 Hash、结构化指标或经过授权的采样 Trace，在可重放性与隐私之间做配置化取舍。

## 56. 请讲一个你在项目中发现并修复的典型问题

**参考回答：**

我遇到过一个典型问题：模型先运行测试成功，之后为了优化实现又修改了文件，最后直接调用完成工具。如果系统只保存“历史上有一次测试成功”，就会错误地把任务标记为完成。

我先把问题抽象成验证证据的时序一致性：完成证据必须晚于最后一次影响结果的修改。然后没有把逻辑分别写进 edit 和 write，而是在统一 ToolExecutor 的成功结果 hook 中处理。任何成功的代码修改都会清除旧验证、重置验证历史并把 Goal 状态返回 active；只有之后新的 `goal_verification=true` Bash 成功，才能重新进入 verifying 和完成门禁。

我为“测试成功—修改—完成失败”“修改—重新测试—完成成功”“失败的修改不清除验证”等路径补了测试。最终这个修复不仅解决一个 Case，还形成了统一的不变量，后续新增修改类工具也可以接入同一执行边界。

# 最后背诵：高质量回答结构

遇到任何项目追问，可以按下面五步组织：

1. **先说问题。** 原方案在什么场景会失败。
2. **再说结论。** 你的核心设计是什么。
3. **讲关键链路。** 数据或状态如何流转。
4. **讲不变量与异常。** 如何处理重启、失败、取消、降级和并发。
5. **讲取舍和证据。** 为什么不用更简单的方案，测试或 Trace 如何证明。

示例句式：

> 普通 Agent Loop 只能判断模型是否自然停止，不能证明用户目标完成。因此我在 Loop 外增加持久化 GoalSupervisor，把一次自然停止定义为一次 attempt，并要求真实验证、验证新鲜度和逐条验收证据都通过后才能进入 complete。这样通用 Loop 保持简单，编码产品又获得了长任务续跑和可验收能力。代价是状态管理更复杂，所以我用原子持久化、合法迁移、attempt/time 限制和 Trace 来控制异常路径。
