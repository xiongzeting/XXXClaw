# Eval3 结果失败归因：模型表现与 Agent 改进

复核日期：2026-09-07。仅讨论结果维度失败的 10 题，不把安全、效率失败混入。依据是冻结的实际模型请求、工具调用、逐阶段回答与候选交付；没有重新调用模型，未改评分或 Agent 实现。

## 1. 先回答核心问题

**本轮大部分结果错误，不能归因于 Agent 把题面压缩丢失。模型在持有要求时仍出现了实现或推导错误。最有直接证据的 Agent 设计问题，是错误推导进入事实记忆；其次是通用验证流程没能发现公开契约遗漏。**

逐题检查发现：除刻意使用隔离会话的 memory 题外，其他 9 题最后一次 Agent 模型请求中，所有阶段的用户题面均以完整字符串存在。没有发现压缩/归档事件，也没有额外压缩模型请求。因此，题名含 compression 不等于这次实际发生了压缩，更不能据此认定是压缩模块损坏了答案。

这是对本次行为的归因，不代表 Luna 永远做不出这些题。没有做同一断点、同样上下文、固定预算下的重复采样或换模型对照，不能给出“模型占 70%、Agent 占 30%”的因果比例。

## 3. 四题更偏契约落实遗漏，Agent 更容易做防护

| 案例 | 已观察错误 | 本轮归因 | 最小防护 |
|---|---|---|---|

| diagnose_and_patch_release_r3 | 源目录缺失返回 2，要求运行错误 1；参数错误才是 2 | 模型错误处理分支分类不准确，验证缺少退出码边界 | 将成功/参数错误/业务或运行错误列成小表，实际检查 stdout、stderr、退出码 |
| recovery_schema_upgrade_rollback | 要求 `after_version`，实现匹配 `after_version.json` | 精确故障标识被改写；自己的测试跟着错误标识走，没有触发要求中的中断 | 从原始题面保留字面量故障名，验证要求的故障确实到达指定提交点 |

这四题仍是模型生成的错误，**不是已经证明有四个 Agent 代码 bug**。它们更适合由 Agent 的交付检查补上：规则明确、检查便宜、无需替模型解决整个业务算法。

例如迁移题第三轮回答明确声称“保持旧 transform 接口”，但后续实际验证主要调用新入口与 CLI，未覆盖该函数。增加泛泛的“请认真检查”价值有限；在改动前保留旧入口，并在改动后真的调用一次，才有可验证的收益。

## 4. memory 题：已经能定位到的双重问题

原始规则是 `signed-audit > lab-log > verbal`，a/prod/db 的 lab-log 5432 在整个 9 月有效。新增 signed-audit 的 null 仅在 `[9/10,9/20)` 生效；verbal 的 7777 不能在 9/20 超过仍有效的 lab-log。

错误链路如下：

1. 第三轮生成错误记忆时，请求上下文里同时存在 5432 和正确来源优先级。
2. 模型仍提出保存“verbal 7777 按来源优先级覆盖 signed-audit null”的错误结论；这一步首先是模型推导错误。
3. 模型调用 `memory(action='remember', category='fact', conflictPolicy='replace', ...)`，将推导结论当事实写入。
4. 实际工具结果分别为 `Remembered [fact]`、`Replaced conflicting [fact] memory`、再次 `Remembered [fact]`。不是所有旧事实都被删除：改了标题的段落被追加，相同标题的来源规则条目被替换。正确原文与错误摘要随后共存。
5. 模型之后修正了 null 的窗口，却仍保存窗口外为 7777 的错误摘要。最终隔离查询继续输出 7777。

因此不能简单诊断为“BM25/BGE 没召回 5432”。最终请求中仍能找到原始 5432。真正需要解决的是：**把模型推导与用户原始事实分开，避免错误结论因写入 memory 而取得事实地位。**

相关代码已与本轮冻结源码比对，内容一致：

- [memory/tools.py:103](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/tools.py:103>) 对 preference 写入要求可核验的用户原话；fact 写入没有同等的原话校验流程。
- [memory/tools.py:158](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/tools.py:158>) 将模型选择的 `conflictPolicy` 传入存储层；`remember` 不使用调用中填写的 `oldContent`。
- [memory/semantic.py:93](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/semantic.py:93>) 用文本标题等启发式提取 subject；同一配置换个标题就可能成为另一个条目。
- [memory/semantic.py:204](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/semantic.py:204>) 同 subject 且 replace 时直接替换，没有核验新增证据是否真的使旧业务记录失效。
- [memory/tools.py:312](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/tools.py:312>) 记录证据时写入 `confidence=1.0`；这是固定元数据，不是经过语义核验的真实性证明。

第一版不必建设知识图谱或让存储层理解所有业务。保留可追加的原始证据，给模型推导单独的类型与来源，就能先减少错误长期化。

## 5. 先改哪些 Agent 机制

### P0：事实记忆与推导摘要分离，约 2–3 天

保留现有 memory 工具，对内部记录增加宿主持有的来源元数据：原始用户消息/文件位置、记录类型、版本和被替代关系。元数据由宿主根据真实来源生成，不把模型自己填写的一段 evidence 当作已证实事实。

- 原始事实优先保存可定位的原话或观察证据；模型自行合并出的“最终配置”进入推导摘要，引用输入记录，不能覆盖原始证据。
- 新增 a3、a4 是增加来源记录，不是删除 a1。只有明确指向原记录的更正、撤回或版本更新才能改变该记录的有效状态。
- 推导摘要依赖的事实或规则变更后，将摘要标为过期；再次回答要核对来源。存在冲突时可以回读，不能因为摘要写得更晚就优先采用。
- 第一版可以用追加日志和类型标签实现。原记录保持可恢复；遇到复杂语义先保留双方，不必每次向用户询问。
- 精确语义无法仅靠字符串包含检查保证。程序能检查来源存在、引用有效、替代关系合法，业务推导仍要验证。

验收不只重跑最终问答：在第三轮故意让模型提出错误派生值，检查它无法覆盖原始 5432，并确认新会话仍能拿到来源规则与原记录。使用新端口、新日期和新租户变体，避免硬编码这一题。

### P1：交付前的契约检查，约 1–2 天

先做成本低的通用检查：公开函数/CLI 兼容、明确退出码、用户指定故障名。改动前从已有代码和用户原始要求保存入口信息；改动后基于真实调用结果与当前文件哈希收集证据。

内部只维护简短的有效要求与来源，不向模型暴露 checkpoint、verification_rebind 或验收字段登记工具。最终回答仍自动保存，运行检查不等于最终 judge 通过。

检查能够发现“没有验证旧接口”，不应声称机器已经理解任意自然语言要求。项目没有可靠兼容检查时，可要求模型沿原调用方式执行一次最小样例；核对具体命令，而不是它的“兼容已验证”自述。

### P1：反例验证和实现采用不同出发点，约 1–2 天

对排序/去重/覆盖/撤回任务，先从原始要求找一个最危险的规则组合，再验证候选实现。这里的独立性来自**预期结果依据原始要求**，不是把候选代码的逻辑重写一遍。

推荐的轻量流程：需求明确后记录 2–4 个待验证性质；改动完成后用现有 bash 执行。相同模型也可以做，但仍存在关联错误，不把它当绝对独立 judge。先不用额外 Agent，保持原有步数和 token 上限。

对 transaction，检查 `30+8+10=48`；对 shipping，检查同组更正调换顺序结果不变；对 protocol，检查合法单项覆盖非法全局；对测试题，检查明确要求的重复输入会触发业务断言。

### P2：做小规模断点对照，再决定是否换模型

在已失败案例的错误发生前冻结上下文，做以下对照：同一 Luna 重复原请求；同一 Luna 加来源分离/契约检查；更强模型使用原上下文。预算、输入与工作区状态保持一致，副作用在独立副本中执行。

如果 Luna 在完整清晰上下文下反复犯相同逻辑错误，而更强模型稳定成功，才更有依据认定能力瓶颈；如果同一 Luna 经小幅流程修复即稳定通过，则优先保留 Agent 改动。以上是建议实验，本次未执行、没有产生额外 API 费用。

## 6. 不建议先做的改动

- 不优先升级 BGE-M3、RRF 或 Cross-Encoder：现有证据不是关键原始值完全召回失败。
- 不优先重写压缩：9 题原始题面完整、没有压缩事件；这次成绩不能作为压缩效果或缺陷的实证。
- 不直接添加多 Agent 互审：会增加成本，也可能共享相同错误假设。
- 不仅靠加一句“严格遵守全部要求”：模型多次能正确复述要求，却没有落实到代码和验证。
- 不把 10 个题名写进运行时分支：修的是可泛化的记忆来源和验证机制，曝光题只是回归。

## 7. 与模型/Agent 归因分开的评测问题

shipping 漏发基础费率，release 原故障注入未命中实际 API，cross-file 参考解也有低修订冲突盲点，transaction 数量/单价分解不明确，extract 通用模板含 before 与 batch 内容。这些分别影响题面或观测质量，不应伪装成模型或 Agent 的能力缺陷。

本轮最终判断已避开前三类无效指控，使用明确公开规则下的独立反例。extract 的最终 ID 契约仍有明确反例，但通用模板可能诱导模型添加 before 别名，因此该题的“模型主责”置信度应低于纯净题面。下一 revision 应修题，原分与本次分析不追溯改写。
