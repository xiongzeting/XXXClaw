# 6. Goal 与外层监督

## 1. 为什么需要 Goal

普通 AgentLoop 的停止条件很简单：模型这一轮没有再请求工具，就返回最终文本。这只能说明“模型自然停下来了”，不能证明任务真的完成。

例如，模型可能：

- 修改了代码但忘记运行测试；
- 只运行了一个 happy path 测试；
- 输出“已经完成”，实际验收条件还有遗漏；
- 在长任务中只报告了阶段进度；
- 进程重启后丢失任务当前状态。

Goal 把“模型停答”和“任务完成”拆成两个概念：

```text
一次 AgentLoop.run 自然停止
        ↓
只表示一次 attempt 结束
        ↓
读取持久化 GoalState
        ↓
active / verifying ? 继续下一次 attempt : 真正结束
```

这个设计参考 `pi-mono/packages/mom`。MiniClaw 保持相同的核心状态、验证门禁和外层循环，但使用 Python 模块实现，并接入现有的 Memory、工具执行器和飞书会话目录。

## 2. 放在哪一层

Goal 不放进通用 `AgentLoop`。

```text
Feishu / CLI
     ↓
CodingAssistant（产品装配层）
     ↓
GoalSupervisor（外层循环）
     ↓
AgentLoop（一次模型/工具运行）
     ↓
ToolExecutor
```

这样做的原因是：

- `AgentLoop` 只负责模型消息、工具调用和单次运行，不知道“编码任务是否完成”；
- Goal 是编码助手的产品策略，不是所有 Agent 都需要；
- 普通聊天仍然可以只运行一次；
- 飞书每个 conversation 可以拥有独立 Goal；
- 以后 Docker runtime、审批或其他平台可以复用同一个 AgentLoop。

主要模块如下：

```text
src/MiniClaw/coding_agent/goal/
├─ config.py       Goal 和 Judge 环境变量
├─ state.py        GoalState 数据结构
├─ store.py        goal.json 持久化和状态迁移
├─ prompts.py      命令解析、状态文本、继续提示词
├─ tools.py        goal / goal_complete
├─ judge.py        可选独立完成审查
└─ supervisor.py   AgentLoop 外层监督循环
```

## 3. 持久化状态机

状态与 pi Mom 一致：

```text
active
  │
  ├─运行验证────────→ verifying ──完成门禁通过──→ complete
  │                       │
  │                       └─验证或 Judge 不通过──→ active/verifying
  │
  ├─必须由用户决定──→ waiting_for_user ──resume──→ active
  │
  └─不可恢复错误/超限──────────────────────────→ failed
```

`GoalState` 保存：

- Goal 原文和逐条验收条件；
- 当前状态；
- attempt 数量；
- 创建、更新时间；
- 最近检查点；
- attempt、时间、费用上限；
- 最近验证和最多 4 条验证历史；
- Judge 最近一次拒绝原因；
- 每条验收条件的最终证据；
- 最终结果。

文件位置：

```text
普通 CLI：.aster/goal.json
飞书：.aster/feishu/sessions/<session-key>/goal.json
Judge 审计：同目录 goal-judge.jsonl
```

`GoalStore` 对文件做了以下保护：

- 只接受普通文件，不读取符号链接；
- 最大 128KB，避免异常状态无限膨胀；
- 进程间锁，避免同时写入丢失更新；
- 先写临时文件，再使用原子 replace；
- 验证输出只保留尾部 16k 字符；
- 验证历史最多保留最近 4 条。

## 4. 外层监督循环

核心逻辑在 `GoalSupervisor`：

```python
while goal.status in {"active", "verifying"}:
    attempt = store.begin_attempt()
    if not attempt.allowed:
        break

    result = run_one_agent_loop(prompt)
    state = store.finish_attempt(cost_usd, result.final_text)

    if result.stop_reason in {"error", "aborted"}:
        break
    if state.status not in {"active", "verifying"}:
        break

    prompt = build_goal_continuation_prompt(state)
```

因此模型第一次说“完成了”但没有通过完成门禁时，Supervisor 会再发起一次 attempt。继续提示有两种模式：

### work

出现以下情况时继续实质工作：

- 没有新鲜的成功验证；
- 验证失败；
- Goal 仍为 active；
- 文件修改使旧验证失效。

### completion_review

验证已经成功，但模型没有调用或没有通过 `goal_complete` 时，不鼓励无意义地继续改代码，而是要求审查证据、补充缺失验证，或立即申请完成。

默认限制与 pi 一致：

```text
最多 attempt：20
最长时间：4 小时
最大费用字段：10 美元
```

MiniClaw 当前没有模型价格表，所以 `spent_cost_usd` 接口和持久化字段已保留，默认运行成本暂记为 0；attempt 与时间限制已经真实生效。

## 5. 两个 Goal 工具

### `goal`

支持：

```text
status
checkpoint
waiting_for_user
failed
```

- `status`：读取持久化状态；
- `checkpoint`：记录真正有意义的阶段进度；
- `waiting_for_user`：只有确实缺少用户决定时使用；
- `failed`：不可恢复的终止失败。

### `goal_complete`

参数：

```json
{
  "final_result": "具体完成结果",
  "criteria_evidence": [
    {
      "criterion": "必须与原验收条件逐字一致",
      "evidence": "来自文件或验证输出的具体证据"
    }
  ]
}
```

它不是普通的“标记完成”按钮，而是完成门禁入口。

## 6. 验证门禁

完成 Goal 必须同时满足：

1. 当前状态为 `verifying`；
2. 至少有一条新鲜验证成功；
3. 验证命令真实退出码为 0；
4. 没有仍在运行的验证；
5. 每条验收条件恰好有一条证据；
6. `criterion` 必须与原验收条件逐字一致，不能翻译、拆分、合并或改写；
7. 如果 Goal 要求覆盖率，验证输出必须能读到覆盖率且达到目标；
8. 开启 Judge 时，独立审查也必须通过。

模型通过 Bash 工具声明最终验证：

```json
{
  "command": "python -m unittest discover -s tests -v",
  "goal_verification": true
}
```

`goal_verification=true` 不能用于伪造结果。Goal 层读取的仍然是 Bash 工具真实的 `exit_code` 和真实输出。

## 7. 为什么修改文件会让验证失效

假设流程是：

```text
测试通过 → 又修改 app.py → 直接 goal_complete
```

旧测试不能证明新代码仍然正确。因此 `ToolExecutor` 的 Goal 结果钩子会在成功的 `edit` 或 `write` 后执行：

```text
status = active
last_verification = null
verification_history = []
checkpoint = Verification invalidated: ...
```

模型必须在最后一次文件修改之后重新运行验证。这个钩子放在统一执行边界，而不是分别把 GoalStore 注入 `edit.py` 和 `write.py`，因此五个通用编码工具仍然不依赖 Goal 产品逻辑。

## 8. 独立 Judge

Judge 默认关闭，可通过环境变量开启。它使用当前 MiniClaw LLM 层发送一个无工具请求，而不是绕过本项目直接调用其他实现。

Judge 输入包括：

- Goal；
- 原始验收条件；
- Agent 声称的最终结果；
- Agent 提供的逐条证据；
- 已记录的真实验证命令、退出码和输出。

这些内容全部被提示词声明为“不可信证据”。Judge 必须返回严格 JSON，并满足：

- 每个 criterion 精确出现一次；
- 每项都有 passed；
- `approved` 必须等于所有 passed 的逻辑与；
- JSON 错误、超时、字段不一致时 fail closed；
- 拒绝后 Goal 保持 verifying，允许下一次 attempt 补证据。

## 9. CLI 与飞书命令

创建：

```text
/goal 修复登录流程
验收条件：
- 正常登录成功
- 错误密码被拒绝
- 完整测试通过
```

也支持 `goal` 和中文 `目标` 前缀。

管理命令：

```text
/goal status
/goal resume
/goal cancel
/goal cancel 取消原因
```

飞书仍按 conversation session 隔离，因此群聊线程 A 的 Goal 不会影响线程 B。

## 10. Goal 与 Memory/压缩的关系

两者是相邻但独立的服务：

```text
GoalStore：保存任务是否完成、验证证据、attempt 状态
MemoryManager：保存对话、长期事实、阶段摘要并自动压缩模型上下文
```

每个 Goal attempt 内部仍然通过 `CodingAssistant._run_once` 执行，所以原有 Memory 流程保持生效：

```text
每轮 turn_finished
  → MemoryManager.maybe_compact
  → 80k 软触发 / 100k 硬触发
  → 保留近期约 20k
  → 压缩后目标约 30k
```

压缩不是模型调用的工具。它是产品层自动上下文变换。原始 JSONL transcript 继续追加，压缩只改变下一次模型请求看到的上下文视图。

长期稳定事实则由 `memory` 工具显式管理；程序性指南由 `skill` 工具按需读取。Goal 不替代 Memory，Memory 也不负责判断 Goal 是否完成。

## 11. 可配置环境变量

MiniClaw 原生变量：

```text
MINICLAW_GOAL_MAX_ATTEMPTS
MINICLAW_GOAL_MAX_DURATION_SECONDS
MINICLAW_GOAL_MAX_COST_USD
MINICLAW_GOAL_JUDGE_ENABLED
MINICLAW_GOAL_JUDGE_MODEL
MINICLAW_GOAL_JUDGE_TIMEOUT
```

旧的 pi-mono `CLAW_*` 名称不再作为运行时别名。CLI 和飞书统一读取 MiniClaw `.env`，再把配置传给自己的 Goal 和 LLM 层；API Key 不写入代码、文档或测试。
