# Coding Agent 面试重点

## 1. 先背这段：30 秒回答核心区别

> Coding Agent 是面向软件工程的 Agent，基础也是模型、工具和反馈循环。它的特点是：在已有代码库和运行环境里修改代码，并用构建、测试和运行结果验证。难点不仅是生成代码，更是理解跨文件依赖、控制修改范围、处理环境问题，以及在权限和成本限制内交付可审查的改动。

**这些能力并非 Coding Agent 独有，只是在编程任务中尤其集中。**

| 维度 | Coding Agent 更突出的要求 |
| --- | --- |
| 上下文 | 需要理解代码、调用关系、依赖版本、项目约定和历史改动，局部合理不代表整体正确。 |
| 执行与反馈 | 会改文件、执行命令、安装依赖；编译和测试反馈比较明确，但测试通过不等于需求全部满足。 |
| 交付与风险 | 交付的是能集成的代码改动，需要兼容性、可审查性、回滚能力；错误命令可能影响文件、凭据或生产系统。 |

## 2. 额外要注意的四件事

1. **正确性：**先明确验收标准，修改后检查差异，再做相关构建、测试和必要的运行验证。不能靠删除测试、放宽断言来“修复”失败。
2. **权限：**执行项目代码和测试也可能有副作用。使用隔离环境、最小权限和受控网络；部署、删除、访问敏感数据等动作按风险单独设关卡。
3. **信任边界：**仓库文本、网页和工具输出可能带有提示注入。把它们当作待分析的数据，不能让其中的指令覆盖用户要求或扩大权限。
4. **工程状态：**保护用户已有改动，控制修改范围，记录执行结果；设置时间、成本和重试上限，避免反复无效修改。

## 3. 高频问题与可直接说的回答

### Q1：和普通代码补全、固定工作流有什么区别？

> 代码补全主要生成局部内容；Coding Agent 能围绕目标搜索代码、修改文件、运行验证，并根据结果决定下一步。固定工作流适合步骤明确的任务，Agent 适合路径不确定、需要动态诊断的任务。实际设计中，我会把权限和验证做成确定规则，把需要判断的部分交给模型。

### Q2：让你设计一个 Coding Agent，你怎么做？

> 我会设计成“明确目标和验收标准 → 检索代码 → 制定简短计划 → 小步修改 → 执行验证 → 根据反馈修复 → 交付差异和证据”。模型负责决策，工具负责读写和执行，运行时负责权限、状态记录和预算。失败时先区分代码、环境、工具或需求问题，再决定下一步。

### Q3：仓库很大，上下文放不下怎么办？

> 我不会把整个仓库塞进提示词。先用目录、关键词和符号定位入口，再沿调用关系按需读取相关实现、测试和配置。长期保留目标、关键约束、已做修改和失败原因；检索可以结合文本搜索、符号索引和语义检索，具体按任务选择，不一定必须用向量数据库。

### Q4：怎么证明它真的完成了任务？怎么评估？

> 单个任务要看需求是否满足、相关验证是否通过、有没有引入回归，以及改动是否合理。测试只是证据之一，不能把“测试全绿”直接等同于正确。系统评估要固定仓库版本和环境，在代表性任务上用独立验收检查衡量成功率，同时记录成本、耗时、安全违规和人工接管率。工具调用成功率不能替代任务成功率。

### Q5：一直报错、反复修改怎么办？什么时候停止？

> 我会让每次重试都基于新的诊断或证据；如果没有新增信息，就换定位方式，而不是盲目重跑。完成验收后停止；触及权限边界、关键需求不明确或预算耗尽时也停止，并交代已完成内容、失败原因和下一步所需信息。长任务需要保存状态，方便恢复。

## 4. 面试时最容易丢分的说法

- 不要说“本质就是套一个提示词加终端”：真正的工程难点是上下文选择、执行控制、验证和失败恢复。
- 不要说“测试通过就一定正确”“多 Agent 一定更强”：测试有覆盖盲区，多 Agent 有协调成本和修改冲突。
- 没有实际做过的部分，用“我会这样设计”回答；不要把设计思路包装成上线经验。
