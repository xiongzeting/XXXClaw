# Goal 监督与验收：AgentLoop 外的六状态持久化状态机

> 核心思想：**模型的一次自然停止只代表一次 Attempt 结束，不代表 Goal 完成。**  
> AgentLoop 只负责一次模型—工具循环；GoalSupervisor 位于 AgentLoop 外部，读取持久化状态、执行预算检查、判断是否达到验收门槛，并在未完成时自动发起下一次 Attempt。

## 1. 为什么要把 Goal 监督放在 AgentLoop 外

普通 AgentLoop 的退出条件通常是：模型不再返回 Tool Call，而是返回一段自然语言。这个条件只能说明“模型本轮不准备继续调用工具”，不能证明用户目标已经完成。

模型可能因为以下原因过早停止：

- 做完一半后先汇报进度；
- 忘记执行测试；
- 测试通过了，但没有覆盖全部验收条件；
- 把“代码看起来正确”误判成“目标已经完成”；
- 上下文压缩后遗漏剩余任务；
- Judge 驳回完成申请后没有继续修复；
- 一次模型调用达到自身停止条件，但整个长任务仍未结束。

因此系统需要区分三种概念：

| 概念 | 含义 | 结束依据 |
|---|---|---|
| Turn | 一次模型回复，以及这次回复触发的工具调用 | 当前回复处理完毕 |
| Attempt | 一次完整 AgentLoop 运行 | 模型自然停止、报错或取消 |
| Goal | 用户要求完成的持久化长任务 | 状态机进入终态，成功必须通过验收门 |

如果把 Goal 监督直接塞进 AgentLoop，会让底层循环同时承担模型协议、工具执行、重试策略、业务完成判断和持久化恢复，职责混乱且难以测试。当前设计让 AgentLoop 保持通用：它仍然可以服务普通对话；只有存在 `active` 或 `verifying` Goal 时，CodingAssistant 才把执行交给外层 GoalSupervisor。

## 2. 总体架构

```text
CLI / 飞书 / CodingAssistant
          │
          │ 创建或恢复 Goal
          ▼
┌───────────────────────────────┐
│ GoalSupervisor：外层监督循环  │
│ - 读取持久化 Goal             │
│ - 检查次数/时间/成本预算       │
│ - begin_attempt               │
│ - 生成首次或续跑 Prompt        │
│ - 判断是否继续                │
└──────────────┬────────────────┘
               │ 每次只运行一个 Attempt
               ▼
┌───────────────────────────────┐
│ AgentLoop                     │
│ 模型 → Tool Call → 工具结果   │
│ 无 Tool Call → 自然停止       │
└──────────────┬────────────────┘
               │
               ├─ edit/write 成功 → 旧验证失效
               ├─ bash(goal_verification=true) → 登记真实验证
               ├─ goal(...) → checkpoint/wait/failed
               └─ goal_complete(...) → 完成验收/Judge
                              │
                              ▼
                    .aster/goal.json
                    Trace goal.snapshot
```

主要实现位置：

- `src/MiniClaw/agent/loop.py`：一次 AgentLoop；无 Tool Call 时自然返回。
- `src/MiniClaw/coding_agent/goal/state.py`：六状态数据模型。
- `src/MiniClaw/coding_agent/goal/store.py`：状态转换、验证、预算和原子持久化。
- `src/MiniClaw/coding_agent/goal/supervisor.py`：AgentLoop 外层自动续跑。
- `src/MiniClaw/coding_agent/goal/tools.py`：模型可用的 `goal`、`goal_complete` 工具。
- `src/MiniClaw/coding_agent/goal/judge.py`：可选独立完成 Judge。
- `src/MiniClaw/coding_agent/assistant/coding.py`：组件装配、结果转换和 Trace。
- `tests/test_goal.py`：状态机、验收和自然停止续跑测试。

## 3. 六状态模型

```text
                         验证通过
       创建/恢复       ┌──────────► verifying ───────► complete
          │            │                │                 成功终态
          ▼            │                │ 验证失败/修改文件
        active ─────────┘                └──────────► active
          │  │
          │  ├─ 必须等用户选择 ─────────► waiting_for_user
          │  │                                  │ resume
          │  └──────────────────────────────────┘
          │
          ├─ 明确不可恢复或预算耗尽 ─────► failed
          │
          └─ 用户取消/取消链路 ──────────► cancelled
```

### 3.1 `active`

Goal 正在执行，仍需要修改、调查或补充验证。

典型进入方式：

- 创建 Goal；
- 用户从 `waiting_for_user` 恢复；
- 验证命令失败；
- 验证后又成功执行了 `edit` 或 `write`，导致旧证据失效；
- 模型写入 checkpoint。

### 3.2 `verifying`

Goal 已经开始最终验证，或者验证已经通过、正在等待完成验收。

进入方式：执行 `bash(..., goal_verification=true)` 时先登记 verification 并进入该状态。命令成功后保持 `verifying`；命令失败则回到 `active`。

`verifying` 不等于完成。它表示“现在存在候选验证证据”，还必须调用 `goal_complete`，逐项提交验收证据，并通过本地规则和可选 Judge。

### 3.3 `complete`

成功终态。只有 `goal_complete` 验收成功才能进入，模型自己说“完成了”不能直接写入该状态。

完成时保存：

- `final_result`；
- 每一条验收条件对应的 `criteria_evidence`；
- 已持久化的真实验证记录；
- Attempt、成本和时间等运行数据。

### 3.4 `waiting_for_user`

非终态，但暂停自动续跑。仅用于确实需要用户决定的情况，例如需求歧义、不可替用户选择的产品策略或缺少授权。

模型通过 `goal(action="waiting_for_user", summary="...")` 进入；用户执行 resume 后回到 `active`。这样不会把“等待输入”误记成失败，也不会让监督器在无法决策时空转。

### 3.5 `failed`

失败终态。来源包括：

- Attempt 次数达到上限；
- 总持续时间达到上限；
- 累计成本达到上限；
- 模型明确报告不可恢复的终止失败。

失败原因写入 `final_result`，便于恢复现场、展示状态和 Trace 分析。

### 3.6 `cancelled`

取消终态。用户取消时同时中断当前 AgentLoop，并将仍在运行或等待用户的 Goal 持久化为 `cancelled`。它与 `failed` 分开，因为取消是外部控制决策，不应污染任务失败率。

## 4. 合法转换与责任归属

| 起始状态 | 事件 | 目标状态 | 谁负责 |
|---|---|---|---|
| 无状态 | create | `active` | 外部入口/CodingAssistant |
| `active` | 开始最终验证 | `verifying` | Bash 结果转换器 + GoalStore |
| `verifying` | 验证失败 | `active` | GoalStore |
| `verifying` | 后续 edit/write | `active` | 工具结果转换器 |
| `active/verifying` | checkpoint | `active` | `goal` 工具 |
| `active/verifying` | 必须等用户 | `waiting_for_user` | `goal` 工具 |
| `waiting_for_user` | resume | `active` | 外部入口 |
| `active/verifying` | 验收通过 | `complete` | `goal_complete` + GoalStore/Judge |
| `active/verifying` | 预算耗尽 | `failed` | GoalSupervisor/GoalStore |
| 可运行状态 | 明确终止失败 | `failed` | `goal` 工具 |
| `active/verifying/waiting_for_user` | cancel | `cancelled` | 用户取消链路 |

`complete`、`failed`、`cancelled` 是终态，不允许被普通自动续跑重新打开。当前实现只允许 `waiting_for_user → active` 的显式恢复。

## 5. 持久化数据结构

Goal 保存在会话目录的 `goal.json` 中，实际部署通常表现为 `.aster/goal.json`。关键字段如下：

```json
{
  "version": 1,
  "goal": "修复登录并通过测试",
  "status": "active",
  "acceptance_criteria": [
    "正确密码可以登录",
    "错误密码被拒绝"
  ],
  "attempt_count": 2,
  "created_at": "2026-09-03T08:00:00Z",
  "updated_at": "2026-09-03T08:10:00Z",
  "last_checkpoint": {
    "at": "2026-09-03T08:09:00Z",
    "summary": "已修复密码比较，下一步补失败路径测试",
    "source": "agent"
  },
  "limits": {
    "maxAttempts": 20,
    "maxDurationMs": 14400000,
    "maxCostUsd": 10.0
  },
  "spent_cost_usd": 0.13,
  "current_attempt_started_at": null,
  "last_verification": null,
  "verification_history": [],
  "last_judge_rejection": null,
  "criteria_evidence": [],
  "final_result": null,
  "requested_by": "user"
}
```

### 为什么 Goal 状态不能只放在对话上下文

- 上下文会压缩、截断或重建；
- 进程重启后内存状态会丢失；
- 模型输出属于不可信声明，不是权威状态；
- 多个组件需要在不请求模型的情况下读取 Goal；
- Trace、CLI、飞书状态查询和恢复逻辑都需要稳定数据源。

GoalStore 才是事实来源，Prompt 中的 Goal JSON只是它的一份投影。

## 6. 持久化一致性与安全

### 6.1 加锁的读—改—写

所有状态修改都在文件锁内完成：

```text
获取锁 → 重新读取最新状态 → 校验转换 → 修改副本 → 原子落盘 → 释放锁
```

不能先在锁外读取，再直接覆盖，否则并发的取消、Judge 或工具结果可能互相丢失更新。

### 6.2 原子替换

写入过程不是直接覆盖 `goal.json`，而是：

1. 在同目录创建唯一临时文件；
2. 写入完整 JSON；
3. flush 并 `fsync`；
4. 用原子 replace 替换正式文件；
5. 清理残留临时文件。

这可以避免进程崩溃或机器断电时留下半截 JSON。

### 6.3 输入与文件约束

- 拒绝符号链接或非普通 Goal 文件；
- Goal 文件最大 128 KiB；
- Goal、checkpoint、验证输出都有长度限制；
- 验证历史只保留最近 4 条；
- 反序列化时校验版本、状态、字段类型和 Attempt 非负性；
- 文本先做空白归一化，拒绝空字段；
- 验收条件去重且最多 20 条。

这些限制同时防止状态无限膨胀、异常文件注入和长期运行后的上下文污染。

## 7. 一次完整监督时序

### 7.1 首次 Attempt

```text
用户创建 Goal
  → GoalStore.create(status=active, attempt_count=0)
  → GoalSupervisor 读取状态
  → begin_attempt：预算检查、attempt_count += 1
  → 生成首次 Prompt，注入目标、精确验收条件和完成协议
  → 调用 AgentLoop.run(prompt)
```

首次 Prompt 明确告诉模型：

- 自然停止只结束一次 Attempt；
- 必须把每个验收条件转成可执行检查；
- 最后一次文件修改之后才运行最终验证；
- 验证必须使用 `goal_verification=true`；
- 必须查看真实输出并调用 `goal_complete`；
- 不可避免的用户决策应进入 `waiting_for_user`。

### 7.2 模型自然停止

AgentLoop 发现模型没有 Tool Call，就发出 `run_finished` 并返回。GoalSupervisor 不把它解释为成功，而是：

1. 收集本 Attempt 的最终文本、停止原因、成本和 Trace run id；
2. `finish_attempt` 累加成本、写自动 checkpoint、清空当前 Attempt 起始时间；
3. 再次读取和评估 Goal 状态；
4. 若仍为 `active/verifying`，生成 continuation Prompt 并自动运行下一次 Attempt。

因此模型说“目前已完成主要修改，稍后可测试”只会成为一次 checkpoint，不会让 Goal 结束。

### 7.3 续跑 Prompt 的两种模式

`assess_goal_continuation` 会把续跑分成两类：

**继续工作模式**：Goal 仍为 `active`、没有新鲜成功验证，或验证仍在运行。Prompt 要求继续工作，不要只报告进度。

**完成审查模式**：Goal 为 `verifying` 且已经存在新鲜成功验证，但还没有完成。Prompt 要求优先审查并调用 `goal_complete`，避免为了“显得还在工作”而无意义地改动已经正确的代码。

### 7.4 何时停止自动续跑

监督器在以下情况返回：

- `complete`；
- `waiting_for_user`；
- `failed`；
- `cancelled`；
- 当前 Attempt 报错；
- 当前 Attempt 被取消；
- 预算检查拒绝启动下一次 Attempt；
- continuation assessment 判定不应继续。

当前实现对普通自然停止自动续跑，但对 `error` 和 `aborted` 不做无限自动重试，避免把基础设施故障或用户取消变成失控循环。模型传输层自身的瞬时重试属于另一层机制。

## 8. Attempt 预算与熔断

默认限制：

- 最多 20 次 Attempt；
- 最长 4 小时；
- 最多 10 美元累计成本。

每次 `begin_attempt` 前和 `finish_attempt` 后都检查限制。两侧都检查的原因是：

- 开始前阻止已超预算任务再发模型请求；
- 结束后及时计入本次新产生的成本和 Attempt 数；
- 即使最后一次 Attempt 自然停止，达到边界时也立即持久化为 `failed`。

这里有一个容易忽略的边界：`attempt_count` 在 begin 时增加，而限制条件使用 `>=`。因此上限为 1 时，第一轮可以启动，但第一轮结束后会进入 `failed`，不会再启动第二轮。

预算的目标不是判断业务成功，而是保证自主运行有界。业务正确性由验收门判断，资源安全由预算门判断。

## 9. 验证证据如何进入 Goal

### 9.1 为什么不能相信模型声称“测试通过”

自然语言可能是猜测、旧输出、截断内容或幻觉。系统只认可实际工具执行产生的记录。

模型调用：

```text
bash(command="pytest -q", goal_verification=true)
```

工具结果转换器会：

1. 用 Tool Call id 创建 verification id；
2. 在执行结果返回时登记命令；
3. 保存开始/完成时间、退出码、截断后的真实输出或错误；
4. 只有工具成功且退出码为 0，才记为 passed；
5. 成功后保持 `verifying`，失败后回到 `active`。

`goal_verification=true` 不是让 Bash 本身更严格，而是告诉 GoalStore：这次真实命令是最终验收证据。

### 9.2 新鲜验证

旧测试通过不代表新代码通过。当前实现通过两种方式保证新鲜度：

- 成功 `edit/write` 后清空验证历史并回到 `active`；
- verification bundle 只选择 checkpoint 之后、最近一次失败之后的成功记录。

因此下面的流程不能完成：

```text
pytest 通过 → 又修改 app.py → 直接 goal_complete
```

修改会使旧验证失效，必须重新运行最终检查。

### 9.3 多条验证记录

可以用多条聚焦命令共同证明目标，例如单元测试、类型检查和构建。完成验收会组合所有新鲜、完成、passed 且退出码为 0 的记录。

任意验证仍在运行时拒绝完成；最近一次失败之后的更早成功也不再作为新鲜证据。

## 10. `goal_complete` 完成门

模型调用 `goal_complete` 时必须提交：

- `final_result`：完成结果摘要；
- `criteria_evidence`：每条精确验收条件对应的具体证据。

本地验收依次检查：

1. Goal 必须处于 `verifying`；
2. 不能存在仍在运行的验证；
3. 至少有一条新鲜验证成功且退出码为 0；
4. `criteria_evidence` 必须包含每条验收条件恰好一次；
5. 条件文本必须精确一致，不能翻译、拆分、合并或改写；
6. 对可机器识别的硬指标进行额外校验，例如覆盖率目标必须在真实输出中出现且达标；
7. 可选独立 Judge 必须批准；
8. 真正提交完成前再次检查状态版本，防止审查期间 Goal 已发生变化。

只有全部通过才写入 `complete`。

### 为什么要求“精确条件文本”

如果允许模型自由改写，它可能把“错误密码必须被拒绝”改成“登录功能正常”，从而悄悄降低验收标准。精确匹配保证完成申请针对的是用户原始合同。

### 为什么 evidence 不能只有一个总摘要

总摘要很容易掩盖遗漏。逐项 evidence 强迫系统建立：

```text
验收条件 A → 哪条测试/哪段输出证明 A
验收条件 B → 哪条测试/哪段输出证明 B
```

它既方便 Judge，也方便用户和 Trace 事后审计。

## 11. 独立 Goal Judge

Judge 默认可关闭，开启后使用独立模型、温度 0、无工具调用，对完成候选进行二次审核。

Judge 输入包括：

- Goal；
- 精确验收条件；
- 标记为不可信的模型最终声明；
- 标记为不可信的逐项 evidence；
- GoalStore 记录的真实验证命令、退出码和输出。

Judge 必须返回严格 JSON，并为每条验收条件恰好给出一次 passed/reason。解析器还会验证：

- schema 正确；
- 条件集合与原条件完全一致；
- `approved` 必须严格等于所有 criterion 都 passed；
- 空响应、超时、畸形 JSON、模型错误全部 fail closed。

Judge 驳回或自身失败时，Goal 保持 `verifying`，记录 `last_judge_rejection`，监督器下一轮进入完成审查模式，要求补证据或修复具体缺口。

Judge 不是绝对真理，它的价值是把“执行者自评”变成“执行者提交证据，独立角色审核”。确定性规则仍应优先由代码实现，Judge 主要处理难以完全形式化的语义覆盖。

## 12. 并发与竞态处理

最关键的竞态是：Judge 审查期间，另一个操作改变了 Goal，例如用户取消、文件又被修改、验证被替换。

`validate_completion` 先生成候选并记住当时的 `updated_at`；Judge 返回后，`complete` 在锁内重新读取状态。如果时间戳不一致，则抛出 `GOAL_CHANGED`，拒绝使用旧候选完成新状态。

这个机制相当于轻量乐观并发控制：

```text
读取版本 → 锁外做耗时 Judge → 加锁重读 → 版本一致才提交
```

不能在整个 Judge 网络调用期间持有文件锁，否则取消、状态查询和工具结果都会被长时间阻塞。

## 13. Checkpoint 的作用

Checkpoint 是持久化的监督进度，不等于对话上下文压缩摘要。

- Agent checkpoint：模型通过 `goal(action="checkpoint")` 主动写入实质进展。
- Automatic checkpoint：Attempt 自然停止后，如果本轮没有更新 checkpoint，监督器把最终文本截断后保存。

自动 checkpoint 只在 Goal 仍为 `active` 时写入，避免覆盖验证状态或终态结果。续跑 Prompt、状态展示和进程恢复可以据此知道“做到了哪里、下一步是什么”。

## 14. 与 Trace、Memory、取消链路的关系

### Trace

Goal 状态变化会形成 `goal.snapshot`，典型阶段包括：

- `run_started`；
- 工具调用导致 Goal 改变后的 `after_tool`；
- 单次 AgentLoop 完成后的 `run_completed`；
- 外层 `finish_attempt` 和预算判定完成后的 `attempt_finished`。

最后一个阶段尤其重要，因为 Attempt 上限可能是在 AgentLoop 已结束后才把 Goal 改为 `failed`。只记录内层 run_completed 会漏掉真正终态。

### Memory

Memory 可以帮助模型恢复语义上下文，但不负责恢复 Goal 状态。GoalStore 是权威数据源；即使 Memory 检索没有命中，监督器仍能从 `goal.json` 恢复状态和预算。

### Cancellation

取消同时作用于两层：

- CancellationToken 中断模型、工具、Docker、Compaction 或 Judge；
- GoalStore 把可运行/等待状态写为 `cancelled`。

这样“进程停了”和“持久化状态停了”保持一致，重启后不会把已取消任务自动续跑。

## 15. 崩溃恢复语义

持久化使进程重启后可以继续，但需要明确 at-least-once 语义：

- `attempt_count` 在模型调用前持久化增加，因此启动后立即崩溃也会消耗一次 Attempt；
- 这是保守选择，可防止反复在同一点崩溃却永远不触发上限；
- 工具副作用本身不一定可回滚，恢复后模型必须先检查工作区真实状态；
- `current_attempt_started_at` 可用于识别上次未正常收尾的 Attempt；
- 原子写保证恢复时看到旧完整状态或新完整状态，不会看到半写 JSON。

如果未来需要跨机器高可用，可以把文件存储替换为带版本号的数据库记录，但 GoalStore 接口和外层监督模型不需要改变。

## 16. 测试与验收方案

至少应覆盖以下测试矩阵：

### 状态机

- 创建后为 `active`、Attempt 为 0；
- `waiting_for_user → resume → active`；
- 非等待状态不能 resume；
- 终态不能再次开始 Attempt；
- 只有允许状态可以 cancel；
- 达到次数、时间、成本上限后进入 `failed`。

### 自动续跑

- 第一次自然停止但未完成时自动启动第二次 Attempt；
- `attempt_count` 与实际外层运行次数一致；
- 首次 Prompt 和续跑 Prompt 内容不同；
- `complete/waiting/failed/cancelled` 后不续跑；
- error/aborted 不会无限重试。

### 验证与完成

- 未验证时拒绝 `goal_complete`；
- 验证退出码非 0 时回到 `active`；
- 验证成功后进入 `verifying`；
- edit/write 后旧验证失效；
- 缺少任一验收条件 evidence 时拒绝；
- 条件被改写、重复或多出时拒绝；
- 所有条件和新鲜验证满足时进入 `complete`；
- 覆盖率等客观指标未出现在输出或未达标时拒绝。

### Judge

- 全部条件通过才 approved；
- approved 与逐项结果不一致时 fail closed；
- 漏条件、重复条件、错误 schema、畸形 JSON、空响应和超时都拒绝完成；
- 审查期间状态变化触发 `GOAL_CHANGED`。

### 持久化与可观测性

- 新 GoalStore 实例能读取原 Goal；
- 并发修改不会产生损坏 JSON；
- 超大文件、符号链接和非法状态被拒绝；
- `attempt_finished` Trace 记录预算判断后的最终状态；
- 取消后持久化状态和 Trace 一致。

## 17. 设计取舍与可改进点

### 17.1 为什么错误后不由 GoalSupervisor 无限重试

自然停止通常是模型行为，可以通过续跑 Prompt 修正；`error` 可能是鉴权、网络、程序缺陷或基础设施故障。无差别重试既浪费预算，也可能形成高频故障循环。传输瞬时错误应由模型客户端的有界重试负责，GoalSupervisor 只处理业务层续跑。

可改进为：按错误类别设置退避、最大连续错误数和可恢复错误白名单。

### 17.2 为什么用文件而不是数据库

单会话、单机编码 Agent 中，文件方案透明、便于调试、可随会话目录迁移，也无需额外服务。文件锁和原子替换足以满足当前并发模型。

当出现多进程跨机器调度、复杂查询或大量 Goal 时，应迁移到数据库，并使用 revision/CAS 保持同样的乐观并发语义。

### 17.3 当前验证失效只挂在 edit/write

Bash 也可能修改工作区。当前明确的 edit/write 成功会使验证失效，但任意 Bash 的副作用不容易静态判断。更强方案是：

- 最终验证前后计算工作区 snapshot/hash；
- 每个修改型工具统一发出 workspace mutation event；
- Goal verification 绑定 Git tree 或文件快照 id；
- 完成时确认当前快照与验证快照一致。

这比依赖工具名称更完整。

### 17.4 时间戳作为版本号

当前用 `updated_at` 检测 Judge 竞态，简单有效，但严格系统更适合显式单调 `revision`。这样不依赖时钟精度，也更方便数据库 CAS 更新。

### 17.5 验证命令本身是否可信

退出码 0 只能证明命令成功，不能证明命令足够强。例如 `echo ok` 也会成功。当前通过 Prompt、逐项 evidence、客观规则和可选 Judge 缓解。更强方案是根据验收条件生成受控测试计划，或限制可接受验证类型。

## 18. 面试常问问题与参考回答

### 1. 这个 Goal 系统解决的核心问题是什么？

解决长任务中“模型自然停止被错误当成任务完成”的问题。系统把自然停止降级为一次 Attempt 结束，由 AgentLoop 外的 GoalSupervisor 根据持久化状态、真实验证和逐项验收证据决定继续、等待、失败还是完成。

### 2. 为什么一定要放在 AgentLoop 外？

AgentLoop 的职责是处理一次模型—工具交互协议，它不知道具体业务何时完成。外层监督器可以复用同一个 AgentLoop，多次运行 Attempt，并独立处理预算、恢复、验收与终态。分层后普通对话不受 Goal 逻辑污染，单元测试也更清晰。

### 3. Turn、Attempt、Goal 有什么区别？

Turn 是一次模型回复；Attempt 是一次完整 AgentLoop，从输入运行到自然停止、错误或取消；Goal 跨多个 Attempt 持久存在，只有状态机进入终态才结束。

### 4. 六个状态为什么这样划分？

`active` 和 `verifying` 分离执行与验收；`waiting_for_user` 表示可恢复暂停；`complete`、`failed`、`cancelled` 分别表达成功、系统/任务失败和用户控制终止。这样自动调度、产品展示和指标统计都不会混淆。

### 5. 模型说“完成”为什么不能直接 complete？

模型输出是不可信声明，可能遗漏条件或引用旧测试。完成必须基于实际工具记录的新鲜成功验证、逐项 evidence 和可选独立 Judge，由 GoalStore 执行确定性状态转换。

### 6. 如何防止测试通过后又改代码，却仍拿旧测试完成？

成功 edit/write 会调用 `invalidate_verification`，清空验证历史并把状态改回 `active`。完成门只接受 checkpoint 和最近失败之后的新鲜成功验证。更完整的演进方向是把验证绑定工作区 snapshot。

### 7. 为什么既需要 verification，又需要 criteria evidence？

Verification 证明某个真实命令成功；criteria evidence 证明用户的每一条验收条件由什么结果覆盖。前者防止纯口头声明，后者防止一条泛化测试掩盖条件遗漏。

### 8. Judge 和普通模型有什么区别？

普通模型是执行者，会产生代码和完成声明；Judge 是独立审查者，无工具、温度 0，只根据不可信声明和已记录证据逐项验收。Judge 失败时 fail closed，不能把解析失败当通过。

### 9. 如果 Judge 审查时用户取消了怎么办？

取消 Token 会中断 Judge；即使 Judge 已返回，完成提交还会比较候选读取时与当前 `updated_at`。状态发生变化就触发 `GOAL_CHANGED`，旧候选不能覆盖取消或新修改。

### 10. 为什么持久化要临时文件加原子替换？

直接覆盖可能在崩溃时留下半截 JSON。临时文件完整写入并 fsync 后再原子替换，可以保证读取者看到旧版本或新版本，不看到中间态。文件锁负责并发修改串行化。

### 11. 进程在 begin_attempt 后崩溃，Attempt 怎么算？

算一次。Attempt 数在模型调用前持久化增加，采用保守的 at-least-once 记账，避免任务反复崩溃却永远不达到熔断上限。恢复时再检查真实工作区和 checkpoint。

### 12. 为什么要限制次数、时间和成本三种预算？

三者覆盖不同风险：次数限制无效循环，时间限制卡死或低频长循环，成本限制昂贵模型调用。只设其中一种都可能留下漏洞。

### 13. waiting_for_user 为什么不是 failed？

等待用户代表任务仍可能成功，只是自主执行缺少必要决策。把它记为 failed 会污染失败指标，也不利于用户回答后原地恢复。

### 14. cancelled 为什么和 failed 分开？

cancelled 是用户或上层主动终止，不代表实现能力失败。分开后产品语义、SLA、成功率和故障分析更准确。

### 15. 如何避免 Supervisor 变成死循环？

每次续跑前检查状态，次数、时间和成本均有硬上限；error/aborted 不无限重试；waiting 和三种终态立即停止；每轮 Attempt 都持久化计数并留下 Trace。

### 16. 为什么完成前要精确匹配验收条件文本？

防止执行模型通过改写、合并或弱化条件来降低标准。用户定义的验收条件相当于不可被执行者偷偷修改的合同。

### 17. Goal 状态和 Memory 有什么区别？

Goal 是调度和验收的权威状态，必须确定、结构化、可原子更新；Memory 是帮助模型回忆的语义资料，可能被检索、压缩或遗漏。不能用 Memory 代替状态机。

### 18. 如何做可观测性？

记录 run、model request、tool call、verification、Judge、取消和 `goal.snapshot`，并关联 run id。特别要在外层 finish_attempt 后再记录一次快照，否则会遗漏预算耗尽产生的最终失败状态。

### 19. 如果让你继续演进，你优先改什么？

第一优先是让 verification 绑定工作区 snapshot，而不是只靠 edit/write 失效；第二是增加显式 revision/CAS；第三是可恢复错误的分类退避；第四是把验收条件编译成结构化测试计划，提高验证命令质量。

### 20. 用一句话概括这个设计。

**我把 LLM 的自然停止从“任务完成信号”降级成“单次尝试结束信号”，再用 AgentLoop 外的持久化六状态监督器，以预算、新鲜真实验证、逐项证据和可选独立 Judge 决定 Goal 是否真正完成。**

## 19. 面试时可直接讲的两分钟版本

MiniClaw 的底层 AgentLoop 只负责一次模型和工具循环。传统实现看到模型没有 Tool Call 就结束，但这只能证明模型本轮停止，不能证明用户目标完成。所以我在 AgentLoop 外实现了 GoalSupervisor，把每次自然停止定义为一次 Attempt。

Goal 独立持久化为六个状态：active、verifying、waiting_for_user，以及 complete、failed、cancelled 三个终态。Supervisor 每轮开始前原子增加 Attempt 并检查次数、时间、成本预算，然后运行一次 AgentLoop。自然停止后会保存成本和 checkpoint；如果 Goal 仍可运行，就根据当前状态生成续跑 Prompt 自动开始下一轮。

成功不是模型自己声明的。模型必须在最后修改之后执行标记为 Goal verification 的真实 Bash 命令，系统记录命令、退出码和输出；任何后续 edit/write 都会让旧证据失效。之后模型调用 goal_complete，为每条原始验收条件提交精确对应的 evidence。本地规则先检查新鲜验证、条件完整性和覆盖率等硬指标，再由可选独立 Judge 逐项审核。全部通过后 GoalStore 才原子写入 complete。

持久化采用文件锁、临时文件、fsync 和原子替换；Judge 期间不长期持锁，而是在提交时用 updated_at 做乐观并发检查，避免旧审核覆盖取消或新修改。所有状态变化进入 Trace。因此即使模型过早停止、上下文被压缩或进程重启，外层监督器仍能恢复并继续，直到真正验收通过或进入明确终态。

## 20. 最值得强调的设计亮点

1. **停止与完成解耦**：自然停止只是 Attempt 结束。
2. **监督器在 AgentLoop 外**：底层循环保持通用，长任务策略可独立演进。
3. **六状态持久化**：运行、验证、等待、成功、失败、取消语义清楚。
4. **证据驱动完成**：真实命令、新鲜验证、逐项条件和独立 Judge 四层验收。
5. **验证会失效**：验证后修改代码必须重新验证。
6. **自主运行有界**：次数、时间和成本三重预算。
7. **并发安全**：文件锁、原子替换和乐观版本检查。
8. **可恢复、可审计**：GoalStore 是事实来源，Trace 记录完整状态轨迹。
