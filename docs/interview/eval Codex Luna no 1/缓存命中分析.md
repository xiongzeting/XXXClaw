# MiniClaw 缓存命中低：原因与改法

分析日期：2026-09-06。数据来自 efficiency-revision-v2 的三题冻结轨迹，共 88 次成功主模型请求；对照当前代码。这里只做分析，没有修改 MiniClaw 实现或原评测分数。

## 主要结论

最直接的问题是：**动态检查点和召回记忆放在历史对话前面，更新很小一段内容，也会破坏后面很长的相同前缀。** 三题的 system 消息和工具定义在题内均未变化，不应把这次问题优先归因于它们。

前缀缓存可以理解为“从开头连续复用”：前面保持一致，后面追加内容，比较容易命中；前面中途改字，后面的相同历史不能仅凭内容相同就全部复用。具体缓存分块、路由与保留策略由服务决定，客户端相同前缀不保证服务端一定命中。

## 请求证据

以下按相邻成功主模型请求的 messages 完整对象比较。每题首个请求不参加相邻分类；比例是组内 cached input / input，不是逐请求百分比的简单平均。

| 题目 | 全部主/辅助输入命中率 | 只在原 messages 后追加的请求 | 追加组命中率 | 已有 messages 被改写的请求 | 改写组命中率 |
|---|---:|---:|---:|---:|---:|
| 配置迁移 | 48.9% | 19 | 83.6% | 9 | 1.3% |
| 阶梯发票 | 22.3% | 5 | 87.2% | 21 | 9.1% |
| 脱敏 | 17.2% | 5 | 45.3% | 26 | 13.9% |

配置迁移 9 次改写全部最早发生于 messages[1]，即 system 后的第一条消息；发票有 18 次，脱敏有 21 次发生在同一位置。这是实际请求差异，不是仅根据代码推测。分组存在请求长度、阶段、路由等混杂因素，并非 A/B 实验，不能直接承诺改完就达到 84% 或 90%。

典型现象：

- 配置迁移第 2 次请求：检查点从空 criteria 变为有验收项，缓存为 0。第 17 次请求：前置检查点增加 verification_error，输入 9,193 tokens，缓存仍为 0。
- 发票、脱敏跨轮时：前置内容从检查点变为召回记忆，或在召回列表前部切换 episode/archive 记录。archive ID、顺序和摘要片段变化，稳定历史位于这些变化之后。
- 脱敏最后一个请求，召回块达 30,419 字符，包含本任务之前轮次的会话记录。不能把这些内容全部判为无用，但说明“当前上下文已经知道的内容”与“长期召回”存在需要继续处理的重叠。

## 代码怎么造成的

`agent/loop.py::_request_messages()` 的消息顺序是：

```text
system
→ 当前任务检查点
→ 当前召回记忆
→ 经过投影/压缩的历史消息
```

tools 是模型请求的独立字段，并不是这里的一条消息。服务最终如何把 tools 与消息序列编码，不能从客户端列表直接断言。

`coding_agent/assistant/coding.py::_provide_memory_messages()` 每次读取当前检查点，并把 `_instruction_memory_context` 放在历史前面。

`memory/manager.py` 在每轮开始召回，也会根据新工具证据动态刷新；新内容合并后按检索得分重新排序，渲染包含记录标识及来源元数据。相关性排序本身有用，但不断重写已经发送过的前部证据，会降低前缀稳定性。

`memory/working.py` 在压缩时以摘要替代历史前缀。这是有意用一次缓存失效换取后续输入减少，不能一概当成错误。需要计算压缩成本、丢失的缓存收益和未来节省，避免短间隔反复改写。

## 当前版本已经做了什么

当前工作区不是这轮评测的冻结版本：

- `assistant/progress.py::context()` 已缩短检查点，不再完整重复旧说明和文件哈希。
- `memory/manager.py` 已在自动召回阶段过滤当前 active messages 覆盖的部分原文。
- 动态召回也已有内容指纹判断，没有新内容时保留旧块。

这些已有改动应保留，不要重复开发。但动态块仍在历史前面；变化的摘要、近似重复内容和重新排序并不一定被原文匹配过滤，所以还没有解决主要结构问题。旧轨迹的数值不能直接当成当前版本的新成绩。

## 压缩调用不是全部原因

发票有 5 次独立摘要请求，输入 15,773、缓存 0；脱敏 7 次，输入 17,117、缓存 0。去掉这些辅助请求，主模型输入命中率分别只有 23.5% 和 18.1%，相对整体只提高约 1.2 和 0.9 个百分点。

因此，不能只取消摘要模型来解决缓存；更要检查摘要、检查点、召回变化怎样影响后面的主模型请求。也不能为了命中率不再压缩，导致总输入无限增长。

## 建议按这个顺序改

| 优先级 | 从什么改成什么 | 为什么 | 必须保住什么 |
|---|---|---|---|
| P0 | 每次在历史前替换完整检查点，改成在完整对话/工具结果组之后追加有版本的新状态 | 已发送历史保持稳定，小状态变化不再打断长历史 | 新状态明确替代旧状态；撤回要求、文件版本失效和完成拦截继续有效 |
| P0 | 每次在前面重排整块记忆，改成已发送证据固定，只追加新增/更新/撤回证据 | 避免检索分数轻微波动导致整段历史失去稳定前缀 | 记忆仍是不可信证据，不提升为用户指令；需要新证据时仍能召回 |
| P1 | 只按原文覆盖去重，扩展为 task_scope + record_id + content_version 的来源去重 | 同一逻辑任务的 turn1/turn2 不应被当成独立外部知识反复注入 | 被压缩且确实需要的旧证据仍可恢复；失效内容不能继续当作有效依据 |
| P1 | 只按长度触发压缩，增加最小压缩间隔、预期净节省与状态变化判断 | 避免刚建立稳定前缀又频繁重写 | 达到上下文安全边界仍必须压缩；不能靠留下废话刷命中率 |
| P2 | 核实服务的缓存路由能力，再支持稳定的会话缓存键 | 相同前缀也可能被分配到不同缓存节点 | 按租户/工作区/模型/逻辑会话隔离；不能每个请求随机换 key；不假定兼容服务支持该字段 |

推荐结构：

```text
固定 system / 固定工具定义
→ 稳定历史（已有用户要求、模型回复、完整工具调用与返回）
→ 本次必要的状态/证据增量
```

变化的检查点不能被错误持久化成更高优先级指令，也不能插入未完成的 assistant-tool 配对之间。旧状态积累到必要程度，在明确压缩边界合并为新基线；不能无限追加所有快照。

## 为什么还不能只怪 MiniClaw

Codex 的三题缓存约 87%～91%，但总 tokens 是 MiniClaw 的 2.34 倍。重复发送大量相同历史也能提高命中率，因此高命中率不自动等于高效率。

两边服务基础地址相同，但 MiniClaw 用 `/chat/completions`，Codex 配置为 Responses；请求格式、路由元数据、原生系统前缀和缓存保留方式可能不同。MiniClaw 当前请求构造没有显式 `prompt_cache_key`，但无法确认这就是低命中的原因，或该兼容服务是否支持它。不能断言“换 API”或“加 key”就能修好。

## 怎么验证改进有效

先补与题目无关的请求构造回归：状态更新不得改写稳定历史；记忆顺序变化不重排已发送块；新增/撤回证据及时生效；完整工具调用与返回不被拆开；压缩后旧状态不能覆盖最新用户要求。

再固定模型、推理参数、API 路由、工具环境和题目，分别测“仅改变动态内容位置”“再加记忆来源去重”“再改压缩策略”，避免一次修改多个机制而无法归因。网络中断保留现场、有限恢复，重试等待和已报告成本单列。

核心指标：独立功能通过率、每题未缓存输入、总输入/输出、缓存输入、模型请求数、压缩成本、TTFT 和总耗时。新增 `stable_prefix`、`first_changed_component` 和组件版本指标，但离线字符/字节前缀估计不得冒充服务端 token 缓存量。

只有正确性不下降、未缓存成本或有效耗时下降，才能称优化成功；“命中率变高”单独不够。
