# MiniClaw 九个工具：使用方法、执行结果与面试题

> 本文只描述当前项目已经实现的行为。目标不是背代码，而是能回答三个问题：模型怎么调用工具、一次调用经过哪些安全边界、调用完成后系统状态发生了什么变化。

## 一、先记住这一张图

```text
模型生成 Tool Call
        ↓
ToolExecutor 查找工具、整理参数、递归校验 JSON Schema
        ↓
检查任务是否已经取消
        ↓
Project Instruction Preflight
发现目标目录有尚未注入的新 AGENTS.md 时，首次 Write/Edit 暂停并要求重试
        ↓
ApprovalGate 风险分类
无风险直接通过；有风险按 allow / ask / deny 和白名单处理
        ↓
┌──────────────────────────────┬─────────────────────────────┐
│ read / write / edit / grep   │ bash                        │
│ WorkspaceGuard              │ ToolRuntime → Docker        │
│ 宿主 Python 文件操作         │ 默认在 /workspace 执行       │
├──────────────────────────────┼─────────────────────────────┤
│ memory                      │ skill                       │
│ Memory Store API            │ Procedural Store 路径边界    │
├──────────────────────────────┼─────────────────────────────┤
│ goal                        │ goal_complete               │
│ GoalStore 状态机             │ 验证证据 + 可选 Judge         │
└──────────────────────────────┴─────────────────────────────┘
        ↓
统一得到 ToolResult：content、is_error、details
        ↓
Goal / 项目指令 / Artifact 后处理
        ↓
结果写入当前消息、Session 和统一 Trace
```

一句话口诀：

```text
先验参，再看项目规则，再判风险，最后由各工具自己的边界执行；
执行后统一进消息、Artifact、Goal 和 Trace。
```

需要特别纠正一个容易说错的点：**不是只有五个基础工具才经过 Runtime，也不是九个工具都进入 Docker。**九个工具都经过统一 `ToolExecutor`，但只有 `bash` 使用命令 Runtime 并默认进入 Docker；其余工具在宿主 Python 进程中执行，并由 WorkspaceGuard、Memory Store、Skill Store 或 GoalStore 限制能力。

## 二、九个工具总览

| 工具 | 用途 | 默认需要审批 | 实际执行边界 | 主要副作用 |
|---|---|---:|---|---|
| `read` | 读取一个文件 | 否 | WorkspaceGuard，宿主 Python | 无文件副作用；可能激活局部项目指令 |
| `grep` | 搜索工作区文本 | 否 | WorkspaceGuard + ripgrep，宿主进程 | 无文件副作用；命中文件会激活局部项目指令 |
| `write` | 新建或完整覆盖文件 | 新建通常否；覆盖已有文件要审批 | WorkspaceGuard，宿主 Python | 原子创建或替换文件；使旧 Goal 验证失效 |
| `edit` | 精确替换一个或多个文本块 | 普通源码修改通常否 | WorkspaceGuard，宿主 Python | 原子修改文件；使旧 Goal 验证失效 |
| `bash` | 运行命令、测试、构建 | 只对命中的风险能力审批 | ApprovalGate + Docker Runtime | 可以修改工作区、启动进程；验证命令可更新 Goal |
| `memory` | 搜索或修改长期记忆、归档、Episode | 否 | Memory Store API | 可能修改跨会话 Semantic Memory 或冲突记录 |
| `skill` | 列出或读取流程型技能 | 否 | ProceduralMemoryStore | 无写入；把操作指南返回给模型 |
| `goal` | 查看或更新长任务状态 | 否 | GoalStore 状态机 | 写 Checkpoint，进入等待或失败状态 |
| `goal_complete` | 请求完成 Goal | 否 | GoalStore 验收 + 可选独立 Judge | 验收通过后将 Goal 置为 `complete` |

### 哪些调用会直接通过、需要审批或直接拒绝

```text
直接通过
  read、grep、skill、goal、goal_complete
  memory 的 read/search/conflict_list/archive_search/episode_*
  普通 edit、新建普通文件的 write
  未命中风险规则的 bash

需要审批
  write 覆盖已有文件
  write/edit 修改审批配置或敏感路径
  bash 命中网络、删除、Git 改写、系统修改、覆盖等风险能力

直接拒绝
  Schema 不合法、未知工具、路径逃逸、受保护路径访问
  审批策略为 deny、用户拒绝、审批超时、无审批入口
  Docker 超时或取消、命令非零退出
  Goal 状态转换不合法、完成证据不足
```

“直接通过”只代表不需要 Human-in-the-loop，并不代表跳过边界。例如 `read` 不审批，但仍会被 WorkspaceGuard 拒绝读取 `.env`。

## 三、每次 Tool Call 的完整生命周期

### 3.1 ToolExecutor：统一入口

模型返回的不是 Python 调用，而是结构化 Tool Call：

```json
{
  "call_id": "call_001",
  "name": "read",
  "arguments": {
    "path": "src/app.py",
    "offset": 1,
    "limit": 200
  }
}
```

Executor 首先按名称查找工具。名称不存在时，不执行任何操作，直接返回：

```text
unknown tool: 工具名
```

随后依次进行：

1. 深拷贝参数，避免工具准备参数时修改原始 Tool Call。
2. 调用工具可选的 `prepare_arguments`。当前主要用于 `edit` 的兼容格式转换。
3. 递归执行 JSON Schema 校验。
4. 检查 Cancellation Token。
5. 执行项目指令 Preflight。
6. 执行 ApprovalGate。
7. 调用工具本体。
8. 将异常归一化为 `ToolResult(is_error=True)`。
9. 依次执行 Goal、Instruction、Artifact 三类结果转换。
10. 最后应用 Executor 的 100,000 字符兜底上限。

Schema 校验不只检查顶层字段，还会检查：

- 字符串、整数、数字、布尔、对象和数组类型。
- 必填字段。
- 枚举值。
- 数值最小值。
- 数组最少元素数和每个元素的结构。
- `additionalProperties: false` 时拒绝未知字段。

例如下面调用不会进入审批或文件系统：

```json
{
  "name": "read",
  "arguments": {
    "path": "README.md",
    "offset": 0
  }
}
```

因为 `offset` 最小值是 1，Executor 会提前返回参数错误。

### 3.2 Project Instruction Preflight：不是审批，而是防止没读规则就修改

项目指令支持全局规则、工作区根规则和目标目录附近的局部规则，默认总预算为 12,000 Token。

Preflight 只对 `read/write/edit/grep` 解析目标路径：

- `read` 会激活目标文件附近的项目规则，供下一轮模型请求注入。
- `grep` 会激活搜索位置；搜索成功后还会激活实际命中的文件。
- `write/edit` 如果首次触及一个含有新局部规则的目录，本次修改不会执行，而是返回 `PROJECT_INSTRUCTIONS_REFRESH_REQUIRED`。
- 下一模型轮拿到刷新后的项目指令，再重试原修改。

它不“执行 AGENTS.md”，也不决定操作危险程度。它只保证模型修改目标文件前看过适用于该目录的规则。

### 3.3 ApprovalGate：只拦风险，不是所有写操作都询问

ApprovalGate 对规范化后的调用进行风险分类。配置支持：

- `allow`：命中风险也自动允许，但仍记录审批决策。
- `ask`：默认策略，等待 CLI 或飞书用户批准。
- `deny`：命中风险直接拒绝。
- 项目白名单：只有每个命中的风险能力都匹配允许规则，才可免询问。
- 默认等待 300 秒，超时自动拒绝。

审批绑定规范化 Tool Call Hash。审批后调用内容发生变化，就会返回 `APPROVAL_CALL_CHANGED`，避免“批准 A、执行 B”。路径白名单先规范化为工作区相对路径，并拒绝包含 `..` 的歧义路径；命令白名单还要求 Shell 连接符结构相同，避免宽泛 `*` 顺带放行额外命令。

### 3.4 ToolResult：所有工具统一返回什么

```python
ToolResult(
    content="给模型看的结果",
    is_error=False,
    details={"结构化元数据": "..."},
)
```

- `content` 会作为 `role=tool` 消息加入当前对话。
- `is_error` 告诉 AgentLoop 该调用是否失败。
- `details` 保存退出码、Diff、路径、审批信息、截断信息等结构化数据。
- 工具失败不会伪装成模型异常，模型可以看到错误并修正下一步。

### 3.5 执行后为什么可能只看到 Artifact 引用

任意工具返回内容达到默认 16 KiB 后，Working Context 会把完整结果写入：

```text
.aster/context-artifacts/<session-id>/...
```

当前 Tool Message 不再保存整块大文本，而只保留：

- Artifact 路径。
- 内容 Hash。
- 长度等元数据。
- 一小段预览。

这是 L1“大工具输出制品化”，目的是避免一次大输出迅速挤满上下文。Artifact 仍可通过 `read` 只读访问。

`bash` 还有一层专用处理：原始输出超过展示上限时，完整输出先写入 `.aster/tool-output/bash-*.log`，返回末尾 2,000 行或 50 KiB；如果这段返回结果仍超过 16 KiB，又可能被 Working Context 进一步制品化。因此一次超大 Bash 输出最多可能产生“完整日志 Artifact + 当前上下文 Artifact”两份不同用途的文件。

### 3.6 Trace 审计到底记录什么

每个完成、失败、阻塞或取消的 Tool Call 都会形成 `tool.call` Trace，包含：

- Tool Call ID 和工具名。
- 参数。
- 开始与结束时间、耗时。
- `success/error/blocked/cancelled` 状态。
- 成功结果或错误文本。
- ToolResult details。
- 取消原因。

审批请求和审批决定另记为 `approval.requested`、`approval.decision`；Goal 状态变化记为 `goal.snapshot`；大结果和压缩会留下 Artifact、Compaction 事件。Trace 的用途是事后回答“模型为什么做、系统是否批准、工具实际做成没有、花了多久”，并可从失败轨迹生成 Eval Case。

## 四、`read`：读取文件

### 4.1 参数

```json
{
  "path": "src/MiniClaw/agent/loop.py",
  "offset": 1,
  "limit": 200
}
```

| 参数 | 必填 | 含义 |
|---|---:|---|
| `path` | 是 | 工作区相对路径，或工作区内部绝对路径 |
| `offset` | 否 | 从第几行开始，1-based，默认第 1 行 |
| `limit` | 否 | 最多读取多少行 |

### 4.2 内部发生什么

```text
Schema 校验
→ 激活目标附近项目指令
→ 无需审批
→ WorkspaceGuard.resolve(access="read", must_exist=True)
→ 后台线程读取字节
→ UTF-8 解码，非法字符替换
→ 截断与分页提示
→ Tool Message / Artifact / Trace
```

WorkspaceGuard 会：

- 把 Docker 可见的 `/workspace/...` 或相对路径映射为真实宿主路径。
- 解析 `..` 和符号链接后的真实路径。
- 确认目标仍位于工作区。
- 动态判断目标是否受保护，而不是只依赖启动时扫描。

### 4.3 返回规则

- 普通文本最多展示前 2,000 行或 50 KiB。
- 可用 `offset` 和 `limit` 继续分页。
- 如果首行本身超过 50 KiB，不返回半行，提示改用 Bash 读取有限字节。
- PNG、JPEG、GIF、WebP 当前只返回 MIME 元数据；Python `ToolResult` 尚不能直接附图。
- 读取目录会失败。
- `offset` 超过文件结尾会失败。
- 无法按 UTF-8 正确解码的字节会使用替换字符，不会让整个调用崩溃。

### 4.4 能读什么，不能读什么

允许示例：

```text
README.md
src/MiniClaw/agent/loop.py
.git/HEAD
.aster/tool-output/bash-xxx.log
.aster/context-artifacts/<session>/xxx.txt
```

拒绝示例：

```text
../outside.txt
C:\Users\...\workspace之外的文件
.env
.env.local
.git/config
.git/credentials
.ssh/**、.aws/**、.kube/**
.aster/goal.json
.aster/trace.jsonl
.aster/memory/MEMORY.md
```

`.aster` 默认是 Runtime 内部目录，只有工具输出和上下文 Artifact 两个目录对 `read` 开放。

### 4.5 使用后状态变化

- 不修改目标文件。
- 目标路径附近的 AGENTS.md 等规则会被激活，下一轮注入。
- 大于 16 KiB 的结果会制品化。
- 调用和结果进入 Session 与 Trace。
- 不直接修改 Goal；但模型可用读取结果作为后续验收证据的一部分。

### 4.6 常见错误

- 用 `read` 一次读取整个巨型文件：应使用 offset/limit 分页，或先 grep。
- 试图读 `.env`：审批通过也没用，WorkspaceGuard 会拒绝。
- 把 `offset` 当作 0-based：本工具从 1 开始。

## 五、`grep`：搜索内容

### 5.1 参数

```json
{
  "pattern": "class ToolExecutor",
  "path": "src",
  "glob": "*.py",
  "ignoreCase": false,
  "literal": true,
  "context": 2,
  "limit": 100
}
```

| 参数 | 必填 | 含义 |
|---|---:|---|
| `pattern` | 是 | 正则表达式；`literal=true` 时按普通文本 |
| `path` | 否 | 搜索文件或目录，默认 `.` |
| `glob` | 否 | 文件过滤，如 `*.py`、`src/**` |
| `ignoreCase` | 否 | 忽略大小写 |
| `literal` | 否 | 关闭正则语义，固定字符串搜索 |
| `context` | 否 | 返回命中行前后多少行 |
| `limit` | 否 | 最大命中数，默认 100 |

### 5.2 内部发生什么

```text
Schema 校验
→ 激活搜索位置附近的项目指令
→ 无需审批
→ WorkspaceGuard.resolve(access="search")
→ 调用 rg --json --line-number --hidden
→ 排除所有受保护路径
→ 再次逐条校验返回路径
→ 激活实际命中文件附近的局部规则
→ Tool Message / Artifact / Trace
```

这里采用“双保险”：启动 `rg` 前生成受保护路径排除 Glob；收到每条匹配后又用 WorkspaceGuard 检查一次。

### 5.3 返回规则

- 遵守 `.gitignore`，同时允许搜索普通隐藏文件。
- 默认最多 100 个匹配。
- 达到上限会主动终止 `rg`，提示增大 limit 或缩小查询。
- 单行过长会截断，整体结果最多 50 KiB。
- `context > 0` 时会读取命中文件并渲染上下文。
- 没有命中返回 `No matches found`，这是正常结果，不是工具错误。
- `rg` 未安装、搜索路径非法或进程异常退出才算失败。

### 5.4 使用后状态变化

- 不修改文件。
- 命中文件会成为已激活指令目标，局部 AGENTS.md 可在下一轮注入。
- 大结果可能进入 Context Artifact。
- 查询、命中结果和耗时进入 Trace。

### 5.5 常见错误

- 本来想搜普通字符串，却忘记 `literal=true`，导致 `.`、`[]` 被当作正则。
- 对根目录使用极宽泛模式，返回大量无关结果。
- 把“无匹配”当系统错误；它只表示当前范围没找到。
- 试图搜索 `.git/**`、`.aster/**` 或密钥目录；搜索访问会被过滤或拒绝。

## 六、`write`：创建或完整替换文件

### 6.1 参数

```json
{
  "path": "docs/design.md",
  "content": "# Design\n\n内容...\n"
}
```

| 参数 | 必填 | 含义 |
|---|---:|---|
| `path` | 是 | 目标文件路径 |
| `content` | 是 | 要写入的完整 UTF-8 内容，不是增量片段 |

### 6.2 内部发生什么

```text
Schema 校验
→ 检查目标附近项目指令
→ 必要时先阻塞一次，刷新 AGENTS.md 后重试
→ ApprovalGate 判断新建/覆盖/敏感文件
→ WorkspaceGuard.resolve(access="write")
→ 按真实目标路径进入文件修改队列
→ 创建父目录
→ 写临时文件
→ 原子替换正式文件
→ 成功后使旧 Goal 验证失效
→ Tool Message / Trace
```

### 6.3 审批规则

- 新建普通文件：通常不审批。
- 完整覆盖已有文件：`file-overwrite`，中风险，需要按策略处理。
- 修改 `.miniclaw/approval.json`：`approval-policy-change`，Critical。
- 修改凭据或密钥类路径：`sensitive-file`，高风险；随后 WorkspaceGuard 通常仍会拒绝。

审批不是最终权限。即使用户批准写 `.env`，WorkspaceGuard 仍会阻止模型工具访问它。

### 6.4 为什么不会留下半个文件

`write` 不直接一边写一边覆盖正式文件，而是：

```text
生成同目录临时文件
→ 写入完整内容并刷新
→ 再原子替换目标
```

同一真实路径还有异步修改队列，两个并发写请求会串行执行。取消发生在正式替换前时，不会把半写文件当成最终结果。

### 6.5 使用后状态变化

- 文件被创建，或原内容被完整替换。
- 若有活跃 Goal，之前的成功验证会因文件再次变化而失效，必须重新运行验证。
- 返回写入的 UTF-8 字节数。
- Tool Call、审批和执行结果进入 Trace。

### 6.6 常见错误

- 想改几行却用 write 重写整个文件：更容易丢失并发修改，应优先 `edit`。
- 误以为 write 是追加：它是完整替换。
- 第一次碰到局部 AGENTS.md 时看到错误就不断改参数：正确做法是让下一轮读取新规则后原样重试。
- 以为“已审批”等于“一定能写”：路径边界仍有最终否决权。

## 七、`edit`：精确替换文本

### 7.1 参数

```json
{
  "path": "src/app.py",
  "edits": [
    {
      "oldText": "timeout = 30\n",
      "newText": "timeout = 60\n"
    },
    {
      "oldText": "retry = 1\n",
      "newText": "retry = 3\n"
    }
  ]
}
```

### 7.2 核心语义

- 目标文件必须已经存在。
- 每个 `oldText` 必须在原文件中恰好匹配一次。
- 多个编辑块不能重叠。
- 所有编辑都基于同一份原始文件定位，不是“前一个编辑完成后再匹配下一个”。
- 保留 UTF-8 BOM。
- 保留原文件 CRLF 或 LF 换行风格。
- 使用与 write 相同的同路径队列和原子写。

### 7.3 内部发生什么

```text
prepare_arguments 兼容旧格式或字符串化 edits
→ 递归 Schema 校验
→ 项目指令 Preflight
→ ApprovalGate 检查敏感路径/审批配置
→ WorkspaceGuard.resolve(access="write", must_exist=True)
→ 唯一匹配和非重叠校验
→ 原子写入
→ 生成 Diff 和首个变更行
→ 使旧 Goal 验证失效
→ Tool Message / Trace
```

### 7.4 返回内容

给模型的 `content` 是简短成功摘要；`details` 里包含：

- 规范化后的真实路径。
- Diff 字符串。
- 第一个发生变化的行号。

### 7.5 审批与拒绝

- 普通源码 edit 默认不审批。
- 敏感文件或审批配置会进入审批分类。
- 工作区外、符号链接逃逸、`.aster/**`、`.git/**`、`.env` 等最终由 WorkspaceGuard 拒绝。

### 7.6 常见错误

- `oldText` 太短，在文件中出现多次：工具会拒绝，应该加入足够上下文使其唯一。
- 多个 edits 的范围重叠：应合并成一个替换块。
- 第二个 oldText 按第一个修改后的文本编写：所有块都必须匹配原文件。
- 文件不存在时使用 edit：应使用 write 新建。

## 八、`bash`：在 Docker 中运行命令

### 8.1 参数

```json
{
  "command": "python -m pytest tests/test_runtime.py -q",
  "timeout": 180,
  "goal_verification": true
}
```

| 参数 | 必填 | 含义 |
|---|---:|---|
| `command` | 是 | 交给容器内 `sh -c` 的命令 |
| `timeout` | 否 | 秒数，必须大于 0；默认 120 秒，最大 900 秒 |
| `goal_verification` | 否 | 是否把本命令登记为最终 Goal 验证 |

`goal_verification=true` 不是“让命令更严格”，而是告诉 GoalStore：这条命令的退出码和输出要作为完成验收证据。

### 8.2 审批如何判断 Bash

安全命令通常直接通过：

```text
python -m pytest -q
python -m compileall src
git status
git diff
rg "ToolExecutor" src
```

风险规则按能力集合返回，不只保留一个“最高风险”：

| 风险能力 | 级别 | 典型命令 |
|---|---|---|
| `external-write` | Critical | 上传数据、`git push`、带数据的 POST/PUT/PATCH/DELETE |
| `destructive-filesystem` | Critical | `rm`、`Remove-Item`、格式化、不可逆删除 |
| `destructive-git` | Critical | `reset --hard`、`clean -f`、强推、删分支、rebase |
| `database-destruction` | Critical | DROP、TRUNCATE、DELETE FROM |
| `sensitive-file` | High | Shell 重定向修改 `.env`、凭据或私钥 |
| `system-change` | High | 安装系统软件、改权限、杀进程、改服务 |
| `network-access` | High | curl/wget/ssh、git pull/clone、包安装、HTTP URL |
| `filesystem-overwrite` | Medium | `>`、Set-Content、Copy-Item、Move-Item 等直接覆盖 |

例如：

```text
curl -d @data.json https://example.com && rm -rf build
```

会同时产生 `external-write`、`network-access` 和 `destructive-filesystem`。只有三个能力全部被策略或白名单允许，命令才执行。

风险分类是防误操作层，不是 Shell 语义证明器。真正的隔离还依赖 Docker、网络关闭、受保护路径遮蔽和资源限制。

### 8.3 Docker 实际怎么运行

当前默认配置是 `docker + direct`：

```text
宿主工作区 D:\MIniClaw
       ⇅ 可写 bind mount
容器 /workspace
```

每次 Bash 调用创建一个临时容器，命令结束、超时或取消后删除。默认约束包括：

- 镜像：`miniclaw-runtime:py311`。
- 工作目录：`/workspace`。
- 网络：`none`。
- CPU：1 核。
- 内存：1,024 MiB，swap 不额外增加。
- PID：最多 256。
- 根文件系统只读。
- 丢弃全部 Linux capabilities。
- `no-new-privileges`。
- `/tmp` 是 128 MiB tmpfs，并带 `nosuid,nodev,noexec`。
- 打开文件数 1,024。
- 不保留 Docker 日志驱动输出。
- `HOME=/tmp`、`TMPDIR=/tmp`、`CI=1`。

`direct` 的含义是：工作区本身以可写方式挂进容器，所以正常构建、测试和代码生成能直接反映到宿主项目。Docker 限制系统、进程、网络和凭据暴露，但**不保证工作区文件只读**；危险删除仍必须由 ApprovalGate 拦截。

### 8.4 敏感文件如何对 Bash 隐藏

每次启动容器前，Runtime 动态扫描当前存在的受保护路径，并在容器目标位置挂载空文件或空目录进行遮蔽。因此运行期间后来创建的 `.env`、`.aster` 状态或凭据目录，也会在下一次 Bash 调用时重新判断。

这和 read/write 的策略不同：Bash 不逐个解析命令中出现的所有路径，而是通过风险分类 + Docker 遮蔽保护敏感位置。

### 8.5 超时、取消和输出

- 未指定 timeout：120 秒。
- 用户指定值超过 900 秒：调用被拒绝。
- 超时：强制删除容器并终止 Docker 进程树。
- 用户取消：Cancellation Token 从 CLI/飞书贯穿 AgentLoop、ToolExecutor 到 Docker；当前容器被删除，剩余 Tool Call 不再启动。
- stdout 和 stderr 合并。
- 内部最多保留最后 10 MiB；超过时前部被丢弃并标记 `capture_truncated`。
- 给模型最多展示末尾 2,000 行或 50 KiB。
- 展示被截断时，完整已捕获输出保存到 `.aster/tool-output/bash-*.log`。
- 非零退出码返回 `is_error=true`，并在 details 中保留 `exit_code`。

### 8.6 Goal 验证如何联动

带 `goal_verification=true` 的命令返回后，会由 Goal 结果转换器把这次真实执行登记为验证记录：

```text
Bash 已经实际执行并返回 ToolResult
→ 以 Tool Call ID 登记 verification ID 和命令
→ exit_code == 0 且 ToolResult 非错误：passed=true
→ 否则 passed=false
→ 输出或错误写入 Goal verification history
→ 成功时 Goal 进入 verifying，失败时回到 active 继续修复
```

如果验证成功后又执行 `write/edit`，该验证会失效，防止用修改前的测试结果证明修改后的代码。

### 8.7 常见错误

- 把普通探索命令标成 `goal_verification=true`：最终验收会被无关命令污染。
- 以为 Docker 让工作区不可修改：direct 模式就是为了允许修改工作区。
- 以为网络命令审批通过后一定成功：默认容器网络仍为 none。
- 命令产生海量日志却只看末尾：应读取返回的 fullOutputPath。
- 非零退出后仍声称测试通过：系统明确将其标成工具错误。

## 九、`memory`：长期事实、会话归档和 Episode

### 9.1 它不是一个动作，而是 11 个动作

| action | 必要参数 | 是否写入 | 是否审批 | 用途 |
|---|---|---:|---:|---|
| `read` | 无 | 否 | 否 | 读取完整 Semantic `MEMORY.md` |
| `search` | `query` | 否 | 否 | 搜索稳定事实 |
| `remember` | `category`, `content` | 是 | 否 | 新增稳定事实 |
| `replace` | `category`, `oldContent`, `content` | 是 | 否 | 替换已有事实 |
| `forget` | `category`, `content` | 是 | 否 | 删除指定事实 |
| `conflict_list` | 可选 `status` | 否 | 否 | 查看待处理或已处理冲突 |
| `conflict_resolve` | `conflictId`, `resolution` | 是 | 否 | 明确解决记忆冲突 |
| `archive_search` | `query` | 否 | 否 | 搜当前或指定 Session 的完整压缩归档 |
| `episode_list` | 可选 `limit` | 否 | 否 | 列出历史 Session 摘要 |
| `episode_search` | `query` | 否 | 否 | 搜索历史任务摘要 |
| `episode_read` | `sessionId` | 否 | 否 | 精确读取一个完整 Episode |

可选通用参数：`limit`；`archive_search` 可传 `sessionId`；`remember` 可传 `conflictPolicy`；`conflict_list` 可传 `pending/resolved/all`。

### 9.2 Semantic：稳定事实

搜索示例：

```json
{
  "action": "search",
  "query": "这个项目使用什么测试框架？",
  "limit": 5
}
```

写入示例：

```json
{
  "action": "remember",
  "category": "project",
  "content": "项目统一使用 pytest 运行测试。",
  "conflictPolicy": "reject"
}
```

Semantic 类别只有四种：

- `preference`：用户稳定偏好。
- `project`：跨会话有效的项目事实和约定。
- `environment`：稳定环境信息。
- `fact`：其他长期事实。

`search` 使用 BM25 主检索 + 向量辅助 + 第一级 RRF + 单库 rerank。返回记录 ID、分类、内容、各路分数和被新记录替代的旧 ID。

写入前会处理 Secret、重复和冲突。默认冲突策略是 `reject`：发现旧事实与新事实可能冲突时，不猜哪条正确，而是创建冲突记录并返回错误。只有用户明确选择后，才调用：

```json
{
  "action": "conflict_resolve",
  "conflictId": "conflict-id",
  "resolution": "replace"
}
```

可选 resolution 为 `keep_existing`、`replace`、`keep_both`。

### 9.3 Archive：压缩前的完整原始证据

```json
{
  "action": "archive_search",
  "query": "库存扣减前后状态和执行步骤",
  "sessionId": "session",
  "limit": 5
}
```

不传 `sessionId` 时只搜当前 Session。Archive 保存的是压缩时落盘的原始消息和旧工具结果，不依赖摘要保留所有细节。

召回方式是：

```text
子块 BM25 + 向量
→ 第一级 RRF + 单库 rerank
→ 最多 Top-5 父节点
→ 带上命中块前后各 1 个相邻块
→ 按原始顺序返回证据
```

这就是“父子召回”：小块适合精确匹配，父节点和邻居负责恢复动作前状态、动作、动作后状态的连续语境。

### 9.4 Episodic：历史任务摘要

```json
{
  "action": "episode_search",
  "query": "以前修过的订单并发问题",
  "limit": 5
}
```

Episode 的一个检索单元就是一次完整 Session 摘要，所以使用 BM25 + 向量 + RRF + rerank，但不额外做父子扩展。找到相关 Session 后，如果需要完整摘要，再调用：

```json
{
  "action": "episode_read",
  "sessionId": "2026-09-order-fix"
}
```

### 9.5 重复 Query 去重

Semantic Search 和 Archive Search 带 QueryTracker：完全重复或近似重复的查询可复用缓存，并返回查询是否产生新结果的元数据。它的目的是阻止 Agent 反复换几个近义词却拿回相同证据、浪费 Token 和循环次数。

### 9.6 Memory 为什么不走 WorkspaceGuard

模型不能给 `memory` 任意文件路径。它只能选择预定义 action，由 MemoryManager 把请求路由到固定的 Semantic、Archive 和 Episodic 存储。因此它的安全边界是受限 API，而不是通用文件路径解析。

Memory 的查询和写入都不经过人工审批，避免 Goal 在内部记忆维护时反复暂停。写入安全由 Semantic Store 自身负责：拒绝 Secret 和临时结果、去重、检测冲突，并要求冲突通过明确 resolution 解决。

### 9.7 使用后状态变化

- 查询动作：只把检索结果加入当前 Tool Message 和 Trace，不改长期数据。
- `remember/replace/forget`：修改 `.aster/memory` 下的内部数据。
- 冲突写入：可能新增冲突记录，但不会未经选择覆盖旧事实。
- 大检索结果：仍会经过 16 KiB Artifact 化。
- Memory 文件本身受 WorkspaceGuard 保护，模型不能绕过 Memory API 直接 edit。

### 9.8 常见错误

- 把一次测试输出、临时路径或 Secret 写进 Semantic Memory。
- `search` 没找到就直接回答 Unknown，没有继续 `archive_search` 深挖原始证据。
- 遇到冲突时模型自行决定 replace；正确做法是向用户展示冲突并等待选择。
- 用 archive_search 搜所有历史 Session，却没有传正确 sessionId。
- 把 Episode 当完整原始轨迹；它是任务摘要，细节证据仍在 Archive。

## 十、`skill`：按名称读取流程指南

### 10.1 参数

列出技能：

```json
{
  "action": "list"
}
```

读取技能主文件：

```json
{
  "action": "read",
  "name": "pdf"
}
```

读取技能目录内的其他资源：

```json
{
  "action": "read",
  "name": "pdf",
  "resource": "references/layout.md"
}
```

### 10.2 内部发生什么

- Skill Store 启动时发现 `.aster/skills/*/SKILL.md`。
- 从 Frontmatter 提取准确名称和描述。
- `list` 返回目录，不做搜索。
- `read` 必须使用准确 Skill 名称。
- `resource` 默认为 `SKILL.md`。
- 资源真实路径必须仍在该 Skill 目录内，`../` 逃逸会失败。
- 单个资源最大 64 KiB。
- 读取 `SKILL.md` 时移除 Frontmatter，再返回名称和正文。

### 10.3 为什么不用 BM25 + 向量

Skill 是少量、强结构化、按名称选择的操作规程。系统提示只放名称和描述，模型判断相关后精确读取；这比把所有 Skill 内容做模糊召回更可控，也能确保必须完整阅读的流程不会只召回一个碎片。

### 10.4 使用后状态变化

- 不修改 Skill。
- 指南正文成为 Tool Message，影响模型后续操作选择。
- 大于 16 KiB 时可能进入 Context Artifact。
- 调用进入 Trace。

### 10.5 常见错误

- 猜一个不存在的 Skill 名称。
- 使用模糊名称，实际上要求精确匹配。
- 用 resource 访问技能目录外文件。
- 只看目录描述就执行复杂流程，没有先 read 完整 SKILL.md。

## 十一、`goal`：查看和更新长任务状态

### 11.1 参数和动作

查看状态：

```json
{
  "action": "status"
}
```

记录实质进展：

```json
{
  "action": "checkpoint",
  "summary": "已完成 Runtime 修改并通过单元测试，下一步补充集成测试。"
}
```

等待用户决策：

```json
{
  "action": "waiting_for_user",
  "summary": "需要用户选择是否允许破坏性数据库迁移。"
}
```

终态失败：

```json
{
  "action": "failed",
  "summary": "依赖的外部服务已永久下线，当前验收标准无法实现。"
}
```

除 `status` 外都必须提供非空 `summary`。

### 11.2 六状态是什么

当前真实状态名是：

```text
active
verifying
complete
waiting_for_user
failed
cancelled
```

- `active`：仍在工作。
- `verifying`：已经有最终验证流程，等待完成验收。
- `complete`：验收通过的成功终态。
- `waiting_for_user`：确实缺少用户决策，暂停自动续跑。
- `failed`：真正无法继续的失败终态。
- `cancelled`：用户取消。

### 11.3 `goal` 工具不能创建 Goal

Goal 由外部入口创建，例如 CLI/飞书调用 CodingAssistant 的 Goal 创建能力。模型侧 `goal` 工具只能查看或更新已经存在的 Goal。没有 Goal 时：

- `status` 返回 `none`。
- 其他 action 返回“没有活跃 Goal”，不会偷偷创建状态文件。

### 11.4 为什么 checkpoint 不等于压缩摘要

Goal Checkpoint 是一句“任务监督状态”，例如已完成什么、下一步是什么；上下文压缩 Checkpoint 是为了缩短 Working Context 的任务摘要。两者目的不同，只是名字相似。

### 11.5 使用后状态变化

- `status` 只读。
- `checkpoint` 写入实质进度，但 Goal 通常仍为 active。
- `waiting_for_user` 停止外层自动续跑，等待用户恢复。
- `failed` 将 Goal 置为终态失败。
- 每次 Goal 文件变化都会形成新的 `goal.snapshot` Trace。
- 不经过 Human-in-the-loop，因为这些 action 不直接产生外部系统副作用；它们受 Goal 状态机合法转换约束。

### 11.6 常见错误

- 每做一个微小步骤就 checkpoint，制造大量状态噪音。
- 遇到一次工具失败就调用 failed；普通错误应修复并继续。
- 为避免继续工作而滥用 waiting_for_user；只有缺失用户决策才应暂停。
- 以为模型自然停止等于 Goal 完成；Supervisor 会把自然停止当作一次尝试，Goal 未完成就继续。

## 十二、`goal_complete`：有证据地完成 Goal

### 12.1 参数

```json
{
  "final_result": "已修复超时处理并补充回归测试。",
  "criteria_evidence": [
    {
      "criterion": "所有 Runtime 单元测试通过",
      "evidence": "python -m pytest tests/test_runtime.py -q 返回 18 passed，退出码 0。"
    },
    {
      "criterion": "取消后容器被清理",
      "evidence": "取消集成测试通过，并检查到 container_removed=true。"
    }
  ]
}
```

### 12.2 完成前的硬条件

1. 必须已经存在可运行 Goal。
2. Goal 必须处于 `verifying`。
3. 必须至少有一条新的 `bash(goal_verification=true)` 成功完成。
4. 验证退出码必须是 0。
5. 最近失败验证之后必须重新出现成功验证。
6. 最后一次文件修改之后必须重新验证。
7. `criteria_evidence` 必须覆盖每一条验收标准，criterion 要与原标准一致。
8. 验证输出必须能为目标和验收标准提供客观证据。
9. 开启独立 Judge 时，还必须通过 Judge。

### 12.3 Judge 失败时为什么 Fail Closed

- Judge 认为证据不足：Goal 保持 `verifying`，模型继续补工作或证据。
- Judge 自身报错：不会误标完成，同样返回错误并保持可继续状态。
- Goal 在 Judge 审核期间被其他操作改变：用更新时间检查拒绝旧候选，防止竞态完成。

### 12.4 使用后状态变化

- 验收通过：Goal 进入 `complete`，保存 final_result 和逐项证据，Supervisor 停止续跑。
- 验收失败：返回具体缺口，Goal 不会进入成功终态。
- Goal 快照、Tool Call 和可选 Judge 结果写入 Trace。
- 不需要人工审批，因为它不执行文件、网络或系统操作；真正副作用已经在前面的工具阶段受控。

### 12.5 常见错误

- 没运行验证就调用 goal_complete。
- 普通 Bash 没带 `goal_verification=true`。
- 用“代码看起来没问题”作为验收证据。
- 修改文件后仍复用旧测试结果。
- 漏掉某一条验收标准，或擅自改写 criterion。

## 十三、一条完整工具轨迹

假设 Goal 是“修复读取配置时的崩溃，并通过测试”。

### 第 1 步：模型搜索代码

```json
{"name":"grep","arguments":{"pattern":"load_config","path":"src","glob":"*.py"}}
```

发生：

```text
Executor 验参
→ Preflight 激活 src 和命中文件的 AGENTS.md
→ 无审批
→ WorkspaceGuard 排除受保护目录
→ rg 返回 4 个匹配
→ Tool Message 和 tool.call Trace
```

### 第 2 步：读取目标文件

```json
{"name":"read","arguments":{"path":"src/config.py","offset":1,"limit":240}}
```

如果 `src/AGENTS.md` 是刚发现的局部规则，下一模型轮会把它注入系统提示。

### 第 3 步：精确修改

```json
{
  "name":"edit",
  "arguments":{
    "path":"src/config.py",
    "edits":[{"oldText":"return data['timeout']","newText":"return data.get('timeout', 30)"}]
  }
}
```

第一次调用可能被 Instruction Preflight 阻塞，明确告诉模型先刷新规则。本次没有改文件，也不会进入审批。下一轮重试后：普通源码 edit 无审批，WorkspaceGuard 校验路径，原子替换成功，旧 Goal 验证被作废，Diff 进入 details。

### 第 4 步：运行小范围测试

```json
{"name":"bash","arguments":{"command":"python -m pytest tests/test_config.py -q","timeout":120}}
```

该命令不命中危险规则，无需审批；进入无网络、受限资源的临时 Docker。若返回非零退出码，工具标记失败，模型继续修复。

### 第 5 步：记录进展

```json
{
  "name":"goal",
  "arguments":{
    "action":"checkpoint",
    "summary":"配置默认值修复完成，小范围测试通过，准备运行完整验收。"
  }
}
```

GoalStore 更新 checkpoint，Trace 新增 Goal Snapshot，但不会因此完成任务。

### 第 6 步：运行最终验证

```json
{
  "name":"bash",
  "arguments":{
    "command":"python -m pytest -q",
    "timeout":600,
    "goal_verification":true
  }
}
```

若输出很大：Bash 先把完整输出存到 `.aster/tool-output`，只返回尾部；返回内容仍超过 16 KiB 时再变成 `.aster/context-artifacts` 引用。GoalStore 保存验证命令、退出码和证据。

### 第 7 步：完成验收

```json
{
  "name":"goal_complete",
  "arguments":{
    "final_result":"配置缺失 timeout 时不再崩溃，完整测试通过。",
    "criteria_evidence":[
      {
        "criterion":"配置缺失时使用默认超时",
        "evidence":"新增默认值逻辑；完整测试包含缺失 timeout 场景并通过。"
      },
      {
        "criterion":"项目测试全部通过",
        "evidence":"python -m pytest -q 退出码 0。"
      }
    ]
  }
}
```

GoalStore 校验证据和新鲜验证；可选 Judge 通过后状态变为 `complete`。外层 Supervisor 此时才停止自动续跑。

## 十四、三个不要混淆的“上限”

| 上限 | 默认值 | 负责什么 |
|---|---:|---|
| 项目指令预算 | 12,000 Token | 限制 AGENTS.md 等规则注入量 |
| 单个大结果 Artifact 阈值 | 16 KiB | 工具结果过大时落盘，只给模型引用和预览 |
| Executor 最终结果上限 | 100,000 字符 | 防止任何 ToolResult 无限制返回 |
| Read/Grep/Bash 展示上限 | 2,000 行或 50 KiB | 每个基础工具自己的展示策略 |
| Bash 捕获上限 | 10 MiB | Docker 进程输出的内部尾部捕获 |
| Bash 时间上限 | 默认 120 秒，最大 900 秒 | 防止命令长期占用资源 |
| Working Context 软/硬阈值 | 80k / 100k Token | 决定归档和是否执行硬压缩 |

它们处于不同层：项目指令预算管规则，工具输出上限管单次结果，Context 阈值管整段对话，命令超时管进程生命周期。

## 十五、面试最容易问的问题与参考回答

### 1. MiniClaw 为什么要有统一 ToolExecutor？

因为工具本体只应该关心业务动作。参数校验、取消、Preflight、审批、异常归一化、结果后处理和总输出上限属于横切能力，放在 Executor 可以保证所有工具行为一致，也避免每个工具重复实现后产生安全缺口。

### 2. 九个工具是否都进入 Docker？

不是。只有 Bash 需要执行任意命令，因此进入 Docker Runtime。read/write/edit/grep 是受控文件 API，在宿主 Python 中执行并由 WorkspaceGuard 限制；memory、skill、goal 工具没有任意路径或任意命令能力，由各自 Store API 和状态机约束。

### 3. 为什么 read 和 grep 不审批？

审批主要处理真实副作用和敏感能力。普通只读操作没有副作用，频繁询问会让 Agent 无法自主工作。机密性风险由 WorkspaceGuard 动态禁止 `.env`、凭据、内部状态等路径，而不是让用户每次点击确认。

### 4. 为什么普通 edit 不审批，write 覆盖却审批？

Edit 要求旧文本唯一匹配、变更范围明确，并返回 Diff；Write 会完整替换已有文件，误操作破坏面更大，因此覆盖已有文件被归类为中风险。两者修改敏感路径时都会进入更高风险分类，而且仍受 WorkspaceGuard 最终约束。

### 5. 审批是不是安全边界的最后一层？

不是。审批解决“用户是否授权该风险”，WorkspaceGuard 和 Docker 解决“即使授权或分类遗漏，执行能力仍受哪些技术边界限制”。例如用户批准写 `.env`，WorkspaceGuard 依然可以拒绝。

### 6. 一条 Bash 命令同时包含多种风险怎么办？

分类器返回 capability 集合，例如网络上传、文件删除和 Git 改写。白名单或策略必须覆盖每个能力，不能只按最高风险标签放行整条命令。Trace 也会记录完整 capabilities。

### 7. 白名单如何避免 `docs/../src/app.py` 绕过？

先拒绝含父目录引用的白名单路径，再通过 WorkspaceGuard 解析真实路径并转成规范化工作区相对路径，最后匹配 Glob。审批还绑定规范化 Tool Call Hash，批准后参数变化会拒绝执行。

### 8. Docker 已经隔离了，为什么还要审批？

因为 direct 模式把真实工作区可写挂载到 `/workspace`。Docker 能限制宿主系统权限、网络、资源和敏感路径暴露，但容器内合法进程仍能修改或删除工作区文件。审批负责危险意图，Docker 负责执行环境，两者解决不同问题。

### 9. Docker 的 root filesystem 只读，为什么代码还能修改？

只读的是容器镜像根文件系统；`/workspace` 是单独的可写 bind mount。这样依赖环境和系统目录不可篡改，但 Agent 仍能完成编码任务。

### 10. Bash 超时和用户取消有什么区别？

超时由 Runtime 的命令时间预算触发；取消由用户信号从入口贯穿 AgentLoop、LLM、Executor 和容器。两者都会终止进程、强制删除容器并回收资源，但 Trace 中超时是错误，用户取消标记为 `cancelled`，不会当普通失败统计。

### 11. ToolExecutor 有统一超时吗？

Executor 本身支持统一 timeout 字段，但当前 CodingAssistant 创建时没有设置全局工具超时。实际已启用的明确超时主要是 Bash Runtime 的默认 120 秒/最大 900 秒，以及审批默认 300 秒。这个回答要区分“框架能力”和“当前配置”。

### 12. 为什么输出既截断又 Artifact 化，不重复吗？

不重复。工具级截断决定当前最有用的展示窗口，例如 Bash 保留尾部错误；Artifact 化负责把较大 Tool Message 从活跃上下文移走，同时留下可追溯的完整内容。一个优化可读性，一个控制 Context Token。

### 13. 为什么 Bash 保留输出末尾，Read 保留开头？

命令的错误摘要、测试失败和退出信息通常在末尾；源码和文档的声明、导入和结构通常从开头更有用。工具按内容分布选择不同截断策略。

### 14. Edit 为什么要求唯一匹配？

如果 oldText 出现多次，工具无法确定模型意图，自动选一个位置可能静默改错代码。唯一匹配把歧义变成显式错误，要求模型先读取更多上下文再提交精确修改。

### 15. Write/Edit 如何处理并发和崩溃？

同一规范化路径进入异步修改队列，防止同时覆盖；写入先落临时文件，再原子替换正式目标。取消发生在提交前不会留下半文件。它提供的是单进程内的文件级串行和原子提交，不等于数据库事务。

### 16. Project Instruction Preflight 为什么在审批前？

先确认模型已看到目标目录规则，再判断这次真实调用是否需要授权。若规则尚未刷新，本次修改根本不会执行，也没必要让用户审批一个随后会被项目规则阶段阻塞的操作。

### 17. 为什么 Read 也会影响系统状态？

它不改文件，但会激活目标附近的局部项目指令，使下一轮系统提示发生变化；此外结果会进入 Session、可能生成 Artifact，并写 Trace。所以“无文件副作用”不等于“系统完全无状态变化”。

### 18. Memory 为什么修改不再审批？

Memory 属于 Agent 内部知识状态，如果 remember、replace、forget 都等待人工批准，长任务和自动续跑会频繁停顿。当前设计让所有 Memory action 直接进入受限 Store API；Secret 和临时结果会被拒绝，重复内容会去重，冲突默认不覆盖而是生成冲突记录。它用结构化约束控制风险，而不是 Human-in-the-loop。

### 19. Semantic、Archive、Episodic 分别解决什么？

Semantic 保存可独立复用的稳定事实；Archive 保存压缩前完整原始消息和工具证据；Episodic 保存一次历史任务的整体摘要。前者回答“长期事实是什么”，中者回答“当时原文到底说了什么”，后者回答“以前做过什么任务、结果如何”。

### 20. 为什么 Archive 有父子召回，Semantic 和 Episode 没有？

Archive 原文长，必须切成小块才能精确搜索，但回答通常需要命中块前后的连续语境，所以再扩展父节点和邻居。Semantic 单条事实已经是完整最小单元；Episode 单条记录就是完整 Session 摘要，再扩父节点收益不大。

### 21. Skill 为什么不走向量搜索？

Skill 数量较少且有名称、描述和完整规程。系统提示展示目录，模型选中后精确读完整资源，可以避免模糊召回只拿到半段强约束流程。Skill 自己限制资源必须留在 Skill 目录内。

### 22. Goal 工具为什么不需要审批？

Goal 工具修改的是 Agent 自己的监督状态，不直接删除文件、联网或修改外部系统。其安全性来自合法状态转换、摘要要求、验收证据和外层 Supervisor。若 Goal 中需要真正高风险副作用，执行该副作用的 Bash 或 Write 调用仍会单独审批；Memory 则由受限 Store API 控制，不需要整个 Goal 每一步都让用户蹲守。

### 23. 模型说“完成了”为什么不算完成？

模型自然停止只算一次尝试。Goal 必须有修改后的新鲜真实验证、退出码 0、逐项验收证据，并通过可选独立 Judge；最后只有 `goal_complete` 将状态写成 `complete`，Supervisor 才停止续跑。

### 24. 为什么修改文件后旧验证会失效？

否则 Agent 可以先跑一次成功测试，再修改代码，最后拿修改前的结果证明修改后正确。Result Transform 在每次成功 write/edit 后使旧验证失效，强制重新验证当前文件状态。

### 25. Trace 审计和普通日志有什么区别？

普通日志主要面向排错文本；Trace 以统一事件结构关联模型请求、Token、成本、延迟、Tool Call、审批、Goal、Compaction 和取消状态。它不仅能查故障，还能生成 Eval Case、离线重放和计算质量/成本指标。

### 26. 当前 Tool Runtime 还有哪些现实边界？

风险分类基于规则，不可能理解全部 Shell 语义；Docker direct 模式仍允许修改真实工作区；当前图片 read 只返回元数据；Trace 会记录丰富的工具参数和结果，因此必须把 `.aster` 当受保护内部数据，并继续完善敏感字段脱敏和保留策略。回答限制比声称“完全安全”更可信。

## 十六、最后的面试版总结

可以用下面这段话概括工具系统：

> MiniClaw 向模型提供 read、grep、write、edit、bash、memory、skill、goal 和 goal_complete 九个工具。所有 Tool Call 先由统一 Executor 完成参数准备、递归 Schema 校验、取消检查和错误归一化，再依次经过项目指令 Preflight 与基于多风险能力的 Human-in-the-loop Approval。文件工具由动态、操作感知的 WorkspaceGuard 阻止工作区和符号链接逃逸；Bash 默认运行在无网络、受限 CPU/内存/PID、只读根文件系统的临时 Docker 中，同时把真实工作区以 direct 模式挂载以完成编码。Memory、Skill 和 Goal 不开放任意路径，而由受限 Store API、冲突处理和六状态 Goal 状态机控制。执行后的结果统一进入消息、Artifact、Goal 状态和 Trace，最终完成还必须通过修改后的新鲜 Bash 验证和逐项验收证据。

最短口诀：

```text
九个工具，一个入口；
文件看 Guard，命令进 Docker；
风险才审批，内部状态走 Store；
大结果落 Artifact，所有过程进 Trace；
模型说完不算完，Goal 验证通过才 complete。
```
