# MiniClaw Eval 数据划分与持续闭环

## 1. 最终采用的结构

没有只采用“回归集＋增强集”两份数据，而是按照常见 Agent 产品和模型评测流程拆成四条 Track：

```text
                     ┌─ 1. Regression Gate
代码或配置变化 ──────┤     已知能力，必须不退化
                     │
                     ├─ 2. Development / Challenge
                     │     可查看错误，用于分布级改进
                     │
准备发布 ────────────┼─ 3. Frozen Held-out
                     │     未曝光，不允许按单题调参
                     │
真实使用 ────────────└─ 4. Production Trace / Canary
                           监控漂移，失败聚类后回流
```

原因是只有两份数据会出现一个根本问题：增强集一旦被反复查看和修改，就已经成为开发集，不再能客观证明模型性能提升。必须额外保留一份冻结数据。

当前版本清单：

```text
evals/splits/v1/
├─ manifest.json
├─ exposure-longmemeval-v2.json
├─ development-longmemeval-v2.ids
├─ development-repoguard.ids
├─ development-ai-efficiency.ids
└─ heldout-longmemeval-v2.ids
```

`exposure-longmemeval-v2.json` 单独登记哪些题已经看过、哪些题曾经失败、哪些题归入 Development，以及哪些题被冻结为 Held-out。这样重新生成划分时不会因为忘记历史运行记录而把已见题误放进保留集。

## 3. Regression Gate：稳定回归门禁

### 内容

继续使用：

```text
evals/full.json
├─ smoke.json       4
├─ regression.json 10
└─ resilience.json  8
```

### 为什么保留这 22 题

它们已经覆盖：

- 正常 Coding、Goal 和真实验证。
- 项目指令。
- 跨 Session Memory。
- 历史 Benchmark 失败。
- Approval、WorkspaceGuard 和 Docker。
- L1/L2/Archive/L3 压缩。
- 429、断网和 Fallback。
- 审批通过与超时。
- 运行中取消。
- Assistant 重建后的 Goal 恢复。

回归集的要求不是“越来越难”，而是：

```text
以前已经会的能力，以后绝不能悄悄坏掉。
```

因此它是 Blocking Gate。任何 Required Check 失败都应阻止发布或合并。

### 新冻结基线

已新增：

```text
evals/baselines/gpt-5.6-luna-full-v1.json
```

对应真实运行：

| 指标 | 结果 |
|---|---:|
| Case | 22 / 22 |
| Attempt | 23 / 23 |
| Token | 128,315 |
| 成本 | $0.017668 |
| 四路并行墙钟时间 | 201.95 秒 |

后续运行会比较正确率、五维得分、Token、成本、p95 延迟、错误率、Case 和 Capability 是否退化。

## 4. Development / Challenge：允许分析的增强开发集

Development 不是发布门禁。它用于发现当前系统还不会什么，并衡量一次通用改进是否对整个分布有效。

### 4.1 LongMemEval-V2：60 题

选择结果：

- 40 个此前已经运行过的题。
- 其中 37 个是历史失败，优先进入开发集。
- 再补 20 个此前未曝光题，使类型分布保持均衡。

覆盖 12 个 Stratum：

```text
Domain
├─ web
└─ enterprise

Question Type
├─ dynamic-environment
├─ dynamic-environment-abs
├─ procedure
├─ procedure-abs
├─ static-environment
└─ static-environment-abs
```

每个组合约 4～6 题。它不是只挑某一种失败，而是同时覆盖动态状态、静态证据、流程知识和不存在信息时拒答。

为什么把历史失败放 Development：

- 可以查看具体错误。
- 可以做检索、上下文组织和 Judge 分析。
- 可以验证 Cross-Encoder、父子召回、查询改写等改动是否整体提升。
- 不应根据单题答案添加 Prompt 特例。

### 4.2 RepoGuardBench：72 次执行

选择 12 个完整 Coding Task，每个 Task 作为一个不可拆分单元运行：

```text
1 个 Clean Run
+ 5 个攻击载体
  ├─ README
  ├─ Issue
  ├─ Code Comment
  ├─ Test Log
  └─ Rule File
= 6 次执行
```

总计：

```text
12 × 6 = 72
```

同一个 Coding Task 的 Clean 和五类攻击必须留在同一 Track，不能把 Clean 放开发集、攻击版放保留集，否则会形成任务泄漏。

该组用于同时观察：

- Clean Utility。
- Attack Attempt Rate。
- Attack Completion Rate。
- Safe Completion Rate。
- Approval 阻止次数。
- WorkspaceGuard 阻止次数。
- Docker Bash 是否执行。

### 4.3 AI Efficiency：40 次执行

固定 20 个上游工具压缩任务，每个任务运行两个 Arm：

```text
Full
  启用当前大工具结果 Artifact

Artifact-off
  关闭大结果 Artifact，其他安全限制不变
```

总计：

```text
20 × 2 = 40
```

采用成对任务，而不是让两种配置随机跑不同题。这样才能把正确率、Token 和压缩差异归因于 Artifact 机制，而不是题目难度。

### Development 的使用规则

- 可以查看题目、答案、Trace 和检索结果。
- 可以根据失败簇修改通用机制。
- 不能在产品 Prompt 中加入某个 Case 的答案或专用规则。
- 单题改善不算版本提升，必须看按 Domain/Question Type/Carrier/Family 的整体分布。
- Development 下降不会立即阻止提交，但应生成报告和趋势告警。

## 5. Frozen Held-out：80 个未曝光题

Held-out 当前选择 LongMemEval-V2 的 80 个文本题。

生成时扫描了本地历史结果：

```text
LongMemEval-V2 可用文本题：422
此前曝光：40
此前失败：37
Held-out 候选：362
最终冻结：80
```

约束检查：

| 检查 | 结果 |
|---|---:|
| Development/Held-out Question ID 重叠 | 0 |
| Development/Held-out Query Family 重叠 | 0 |
| Held-out 中此前已曝光 Question | 0 |

Held-out 也按 12 个 Domain/Question Type Stratum 近似均衡，每层约 6～7 题。

### 为什么不把 RepoGuard 和 AI Efficiency 放入当前 Held-out

这两个数据集已经在历史运行中大范围或全量曝光：

- RepoGuardBench 已经运行过完整 94 Task × Carrier 分布。
- AI Efficiency 固定 20 题也已经运行过。

再从里面随机切一部分叫 Held-out 只是形式上好看，实际上开发者已经看过分布和结果。因此当前只把真正未曝光的 LongMemEval-V2 题放入冻结集。

这也意味着当前 Held-out 的限制是：它主要证明记忆、检索与状态理解的泛化，尚不能独立证明安全和 Coding 的未见数据泛化。未来需要新版本 RepoGuard、未运行的 Coding Benchmark 或新增真实生产任务来补齐。

### Held-out 使用纪律

- 不在日常开发中反复运行。
- 只在版本发布、简历最终数据冻结或重大架构变化后运行。
- 首先只看聚合指标和分层指标。
- 不根据单个 Held-out 题直接修改 Prompt。
- 一旦详细分析某题，该题就进入 Exposed Registry，下一版本不能继续作为 Held-out。
- 被分析的代表失败可以进入 Regression，但必须从剩余未曝光池补充新的 Held-out。

因此本次没有立即运行这 80 题。现在运行并逐题分析，等于刚建好保留集就把它污染掉。

## 6. Production Trace / Canary

第四条 Track 不来自固定公开题库，而来自真实使用：

```text
真实会话
  ↓
统一 Trace
  ↓
结果/工具/Goal/安全异常
  ↓
失败签名与聚类
  ↓
高频或高风险失败
  ↓
最小化 Fixture
  ↓
加入 Regression
```

生产失败不能全部直接加入回归集，否则会无限膨胀。建议满足至少一条才提升：

- 同一失败签名重复出现。
- 属于高风险安全或数据损坏问题。
- 代表一种明确的新分布。
- 曾经修好但再次出现。
- 能构造成稳定确定性 Oracle。

偶发网络抖动、第三方服务临时不可用和不可复现失败应进入 Reliability/Quarantine，而不是污染能力回归集。

## 7. 数据泄漏控制

### 7.1 显式 ID，而不是每次随机抽样

所有选择写入 `.ids` 文件，执行顺序固定。Benchmark 适配器新增：

- LongMemEval-V2：`--question-id-file`。
- RepoGuardBench：`--task-id-file`。
- AI Efficiency：`--task-id-file`。

这避免同一命令每次抽到不同题，导致无法比较版本。

### 7.2 Source Version Lock

`manifest.json` 保存：

- 上游仓库 URL。
- Git Commit。
- LongMemEval-V2 Questions SHA-256。
- Haystack SHA-256。
- 选择 Seed。
- 每个 Track 的 ID 文件。

上游数据变化后必须生成 `v2`，不能悄悄覆盖 `v1`。

### 7.3 Query Family 去重

LongMemEval-V2 Small 会让不同问题共享公共检索语料，因此不能按“任意共享轨迹”分组，否则整个数据集会连成一组。

这里采用：

```text
规范化 Question
  → Query Family 指纹
  → 同一问题或精确近似实例不得跨集合
```

共享的公共干扰语料属于测试时输入，不视为监督答案泄漏。

后续还可以加入 Embedding 近似去重，把语义高度相似的 Query 绑定到同一 Family。

### 7.4 Task-level Grouping

RepoGuard 的 Clean 和所有攻击载体按 Task ID 成组，AI Efficiency 的 Full 与 Artifact-off 按 Task ID 成组，不允许拆到不同集合。

## 9. 失败如何回流

### 判定器错误

例：模型用 `grep` 有效读取证据，但 Eval 强制要求 `read`。

处理：修通用判定器，支持等价证据方式；不修改产品 Prompt。

### 分布级能力错误

例：动态状态题普遍只召回孤立片段，缺少动作前后状态。

处理：修改父子召回、时间窗口或字段级检索，然后看整个动态状态 Stratum 是否提升。

### 单 Case 偶然错误

例：某个答案措辞不同但没有形成稳定错误簇。

处理：记录，不立即修改产品；通过重复运行判断是否是随机波动。

### 基础设施错误

例：Docker daemon 不可用、模型服务短时断开。

处理：进入 Reliability 或 Quarantine 指标，不直接算模型能力下降。

## 10. 判断一次优化是否有效

不能只看总正确率，至少比较：

### 结果

- Overall Accuracy。
- 各 Domain/Question Type/Carrier/Family 准确率。
- Clean Utility 与 Safe Completion。
- 旧回归 Case 是否全部保持通过。

### 过程

- Evidence Recall。
- Tool Call 和重复 Tool Call。
- Memory 注入。
- Approval/WorkspaceGuard/Docker 事件。
- Compaction Layer 是否真实触发。

### 效率

- Input/Output Token。
- Agent 与辅助 Token。
- 成本。
- TTFT 和 p95 延迟。
- Retrieval 时间。
- 墙钟时间。

### 稳定性

- 重复运行 Pass Rate。
- `pass_all`。
- 429、断网和 Fallback。
- 取消后副作用。
- Goal 重启恢复。

一项修改只有在 Regression 不退化，并且 Development 的一个或多个完整分布提升，同时成本没有不可接受增长时，才算有效增强。

## 11. 如何运行

### 验证冻结清单

```powershell
python -m MiniClaw.evaluation.splits validate evals\splits\v1\manifest.json --project-root .
```

### 查看某条 Track 的命令

```powershell
python -m MiniClaw.evaluation.splits commands evals\splits\v1\manifest.json --track regression
python -m MiniClaw.evaluation.splits commands evals\splits\v1\manifest.json --track development
python -m MiniClaw.evaluation.splits commands evals\splits\v1\manifest.json --track heldout
```

### 重新生成同版本清单

```powershell
python -m MiniClaw.evaluation.splits build --project-root . --output evals\splits\v1
```

同一数据版本与 Seed 会得到相同的选择顺序。若上游数据、暴露记录或策略发生实质变化，应生成 `v2`，而不是覆盖已经用于报告的 `v1`。

## 13. 面试时怎么讲

> 我没有只分训练题和测试题，而是按 Agent 产品常见流程拆成四条评测 Track：22 个稳定端到端 Case 作为 Blocking Regression Gate；172 次外部 Benchmark 执行作为可查看错误的 Development Challenge；80 个从未运行过的 LongMemEval-V2 题作为冻结 Held-out，只在发布时运行；真实会话则通过 Trace 聚类回流。所有题目使用固定 ID，按 Domain、Question Type 和 Task Group 分层，Clean/Attack、Full/Ablation 不跨集合，并锁定上游 Commit 和数据 SHA。历史失败只有在判定器确认正确、能够稳定复现且代表一个分布时才进入回归集，避免为单个 Case 修改 Prompt。
