# 实测暴露的 Agent 工程问题

> **简历主导的面试总手册（含购物 GRPO、MiniClaw、星级问题与当前版本边界）**：见 [面试官视角_简历主导双项目超级详细面试手册.md](面试官视角_简历主导双项目超级详细面试手册.md)。本文件继续保留为 MiniClaw 工程问题与迭代证据记录。

以下记录来自 MiniClaw 的实际故障、代码修改和已完成的验证。未复测的修改单独标注，不能当作已验证的面试成绩。

**最新有效性复盘见末尾第 15 节。**v1～v9 真正值得保留的是已读文件复用、召回去重、累计历史预算与稳定请求前缀；本次大幅降低成本还包含 **v10 撤除复杂验收接口**，不能全记成 v9 的能力提升。下面的早期迭代保留历史经过，不代表旧验收协议现在仍在使用。

## 项目大改动：面试重点看这九项

这里的升级主要是让模型**少读重复内容、少做无用操作、做完有证据、中断能接着做**。不是重新训练模型，而是改进模型周围的检索、执行和验收程序。

| 重点 | 原来有什么问题 | 改成了什么 | 优化了什么 |
|---|---|---|---|
| **1. 把失败变成可复现的评测** | 看最终回答、翻零散日志，难判断到底哪里错了 | 用同一条 Trace 串起模型请求、工具结果、审批、压缩和成本；在独立工作区跑真实任务，再分别检查结果、过程、效率、安全和运行状态 | 能定位“答错、乱改、太贵还是断网”；先修评分程序，再修共性问题。已用于修复的题只算回归，不再冒充新题成绩 |
| **2. 记忆检索不用每次从头算** | 每次搜索重新处理文档、计算相似度；只靠词语或语义相近也容易漏掉代码路径和错误码 | 把词语索引和向量保存到磁盘；索引完整且有效时，新问题复用已有索引。路径精确匹配、关键词、语义三路一起找，再合并排序 | 减少重复计算，同时照顾“意思相近”和“名字必须准确”两种需求；本地模型或索引不可用时记录降级，继续使用可用检索方式 |
| **3. 召回从“找到摘要”变成“找到依据”** | 只在开头查一次；找到上次任务摘要，也未必知道当时具体做了什么 | 工具带来新线索后有限补查；命中历史会话后继续查对应原文。返回调用、结果及附近结论，并限制注入条数和总篇幅 | 模型能获得新线索对应的历史证据，又不必把整份历史全部读一遍；记忆作为历史资料注入，不能覆盖系统规则 |
| **4. 上下文从“越积越多”变成“按需回读”** | 大工具输出反复发送；旧历史压成摘要后，又被自动召回塞回来 | 大结果保存为文件，先给简短预览和位置；旧历史保留摘要与原文入口。同会话历史不重复自动注入，摘要去重，真正变短才采用压缩 | 减少每次请求重复读的内容。两道真实题观察到 token 下降约 **65% / 54%**；不是严格单因素对照，其中一道仍超成本预算，详见第 4 节 |
| **5. 文件搜索按已知范围找** | 知道文件位置也可能扫描整个项目；无关文件也做昂贵检查 | 完整路径直接查，已知目录只查该目录；全局搜索先看文件名，再对匹配结果做完整安全检查 | 少翻目录、少做无用检查。实测完整路径 **13 ms**、指定目录 **16 ms**；全局无结果仍需遍历，详见第 5 节 |
| **6. 工具执行有统一边界，取消能传到底** | 工具各自处理执行环境；停掉模型回复后，命令或后续写入还可能继续 | 统一参数检查、审批和工作区边界；命令可选 Host/Docker 后端。共享取消信号传到模型请求、审批和命令执行，并阻止后续工具启动 | 执行路径更一致，中断后减少继续产生副作用的风险。文件工具仍在宿主运行；Docker 约束命令后端，不能说所有操作都进了容器 |
| **7. 中断从“整题重来”变成“保留进度继续”** | 步数耗尽直接报错；断网后重跑容易重复已完成操作 | 触顶保存上下文、剩余工作和下一步，标记暂停；断网只有限重试中断的模型请求，保留已有工具结果和剩余预算 | 减少重复工作，区分任务未完、网络故障与能力失败。当前新增恢复机制仅有离线回归证据，尚不能声称真实难题因此通过 |
| **8. 完成后独立复核，保留证据** | 总额正确可能掩盖明细遗漏；内部验收合同又使模型反复登记字段、返工 | 当前自动保存答案、实际文件、Trace 与用量；结果由后置 LLM 复核，其余四维由程序评分。旧模型侧验收协议已在 v10 撤除 | 做题与独立评分分开，不再把模型自写验证当成正确性保证；为什么撤掉旧方案及实际收益见第 15 节 |
| **9. 会话和记忆不再各管各的** | 页面切了会话，服务端上下文没切；某个记忆写入入口绕过检查，造成重复或临时偏好入库 | 页面、请求和 Agent 绑定同一会话 ID；手动写入、自动提炼、压缩归档共用来源与分类校验 | 减少串话和错误记忆干扰，避免模型沿着错误上下文继续做。已有真实前端切换、刷新、跨会话偏好及临时偏好复测，详见第 2、3 节 |

**优先讲哪几项？**讲效率，先看第 **15** 节的证据筛选，再参考早期的 **2、4、5**；讲可靠执行，选 **6、7**；讲交付质量，选 **1、8**。不要把旧验收合同讲成当前已验证成功的架构；恢复测试、阅卷纠错和真实能力成绩分别说明。

早期升级依据：[Trace 与评测闭环](../notes/7.Trace与Eval数据闭环.md)、[端到端 Eval](../notes/29.端到端Eval.md)、[记忆系统重构](../notes/27.记忆系统重构重点.md)、[持久化检索](../notes/28.BGE持久化检索升级.md)、[工具运行体系](工具统一Runtime模块详细讲解.md)、[端到端取消](../notes/11.端到端取消与中断.md)。各文档记录的是不同阶段，测试数不累加，也不据此推算通用成功率。

## 1. Eval 驱动的修改迭代记录

后续由 Eval 暴露的问题和对应修改统一追加在这里，按“原来的问题 → 修改 → 验证状态”记录。保留原始失败与原始评分，未复测不写“已解决”或提升比例。

### ① 阅卷程序判错：先把评分修准（此前已验证）

**原来：**文件不存在，也可能被当作“空内容”判通过；字符串 `"false"` 可能被当成真。Docker 路径与 Windows 路径没对应好，又把正确写入误判为越界。

**修改：**先确认文件和阶段记录存在，再检查内容；严格检查裁判返回的数据类型。路径统一映射到工作区后再判断是否允许写入。

**效果：**此前真实 Windows + Docker 检查中，合法路径通过，额外写入及写后删除被识别。原始 **7/30** 保留，纠正评分另存 **11/30**，隔离 4 条纯误报；这是阅卷纠错，不是模型能力提升。

### ② 做到一半撞上步数上限：留下能接着做的进度（2026-09-06，简单离线回归通过）

**原来：**`redaction_priority`、`shipping_caps`、`version_resolution` 在第 7 轮做到 32 步后直接报错，用户再说一句“继续”才完成。系统没有把“预算用完”和“任务失败”清楚分开。

**修改：**仍保留 32 步上限，最后 3 步提醒收尾或保存进度。增加持久化检查点，记录剩余工作、待验收项、已有验证证据和下一步；触顶后保存当前上下文，明确报告“暂停、尚未确认完成”。提供恢复入口，恢复时带上检查点并要求复用已完成结果。Trace 和 Eval 单独记录暂停，不计为成功，也不混作模型报错。

**为什么：**预算用完应该像“存档暂停”，不能直接崩掉，也不能假装做完。保存下一步，比单纯把上限调大更容易控制成本和排查问题。

**当前效果：**离线检查确认触顶后保存暂停状态，重建 Assistant 后能继续，示例中的已成功写入不重复执行。尚未复测三道旧题，不能声称它们已通过或耗时下降。

### ③ 总额对了，但漏了异常订单：每项结果都要核对（2026-09-06，简单离线回归通过）

**原来：**`cash_refund_reconciliation` 的净额 **2300** 正确，但漏报 **O-5**。P5、P6 是两笔不同交易，各 300；重复的 P5 只去掉一条后，支付仍为 600，超过订单上限 300，应该报异常。

**修改：**数据任务要求从正式输入运行可重放的程序，按交易 ID 去重，输出分组金额、选中 ID 和规则检查。增加交付验收清单，要求逐项覆盖所有字段；验证命令必须返回每项是否通过及比较证据。缺项、失败或只有“JSON 合法”不能满足整份清单；后续写文件或执行命令会清除旧验证，防止改完继续使用旧成绩。原始输入、失败记录和完整预期异常列表保留。

**为什么：**总额正确不代表明细正确。不能让“大数对了”掩盖“漏了一笔”，也不能只凭模型口头说核验过就结束。

**当前效果：**离线检查确认只验证总额、漏验异常列表不能完成；假布尔值、重复检查项、失败命令不能充当有效证明，后续修改会使旧证明失效。未跑真实对账题，不能声称已消除漏算；清单与验证程序仍由模型编写，最终仍需独立 Eval 核对。

### ④ VPN 切换造成断网：只重试断点，不把网络波动当能力差（2026-09-06，简单离线回归通过）

**原来：**部分题因 ConnectError、ReadError 未交付；也有题最终正确，但历史 `model_errors=1` 使严格健康检查不通过。这两种情况不能混为“Agent 不会做题”。

**修改：**沿用受限退避，Agent 的当前响应先缓冲，流中断时丢弃未交付片段、仅重发当前请求。请求内重试耗尽后，新版 Eval 最多再恢复一次该请求，保留先前工具结果和剩余步数，不重跑整题或全量题集。记录供应商请求 ID（服务端有返回时）、重试、是否已输出和恢复关系；只有明确关联且成功的恢复才解除旧运行的“仍未交付”状态。

**评测口径：**用户切换 VPN 的短暂断网属于环境因素。恢复后看实际交付和恢复状态；原始错误、重试记录与累计开销照常保留。网络错误与非网络错误分开，不能因为历史网络错误非零就否定正确交付；仍未交付或结果、过程、安全验收不通过，仍要如实报告。v5 使用这一口径，v4 和原始成绩不覆盖。

**当前效果：**离线注入连接失败、流中断和成功写入后的断网，确认只重发中断请求、无示例中的重复写入；持续断网会在有限次数后停止，未关联的后续成功不会抹掉旧失败。没有跑真实题目，未新增模型成绩。这条协作偏好也已写入项目根目录 `AGENTS.md`。

**本次三项合并验证：**`tests.test_task_recovery`、`tests.test_agent_loop`、`tests.test_llm_streaming`、`tests.test_evaluation`、`tests.test_goal` 共 **49 项通过，约 3 秒**。使用本地临时文件、脚本化模型回复和模拟网络故障，不调用真实模型，不运行 Eval 题集。

代码入口：`src/MiniClaw/agent/loop.py`、`src/MiniClaw/coding_agent/assistant/progress.py`、`src/MiniClaw/coding_agent/assistant/coding.py`、`src/MiniClaw/evaluation/runner.py`。

### ⑤ 评测结果做成可追溯页面，补上下一轮门槛（2026-09-06）

**展示：**第一轮 30 题按开发、保留、测试与五种能力展示，可筛选案例、展开对话和判分依据。先纠正路径误报，再按用户约定把 6 道网络波动的可用性按通过计：综合 **15/30**、可用性 **27/30**。原始记录保留，这是评分口径调整，不是模型能力提升。

**新增观察：**工具失败次数、单题耗时进入案例表和详情，本轮不新增判错。下一次启动的套件初始门槛为：过程 `tool_errors ≤ 5`；效率普通题 **600 秒**、压缩题 **900 秒**。阈值可调，尚未通过新批次验证；正在执行的冻结批次继续用原规则。

### ⑦ 第二轮继续补验收与失败恢复（2026-09-06）

**原来：**总额、主版本正确可能掩盖字段算错或 ID 漏报；验证程序写一句 `passed=true` 不等于真的比较过。复核格式出错又可能清掉其他有效证明；两个文件分别替换，仍可能留下半次提交，重试再扣一次。

**修改：**新增按字段比较实际值与预期值的验收协议，核对类型、成员、顺序和重复数量；可直接读取输出 JSON 并绑定文件版本。最终 JSON 的绑定字段必须与已验证内容一致。错误复核只作废对应证明，验收没过就保存暂停，不能当完成。新增通用故障探针，在提交前后注入异常，再以同一请求重试，检查是否半次提交或重复执行。

**效果与限制：**132 项离线检查通过、1 项跳过；实际命令链路确认漏字段的回复被拦截，修正后正常完成且不重放工具。字段与恢复合同需显式登记，预期值和场景声明仍可能写错，不能替代独立 Eval；探针不会自动修好业务事务。尚未复跑真实难题，安全 P2 的瞬时写入、撤权、链接竞争覆盖也未补齐。**本次改动不在此前已启动的 6 题冻结版中。**详见 [非效率问题修复](eval%20no%202/非效率问题修复.md)。

### ⑧ 验收越改越复杂，反而反复返工（2026-09-06，v5 机制修复）

**原来：**新验收器要求嵌套比较数据，提示却仍教旧格式；一项错误还可能让同批合法结果丢失。v4 六题验收报错 103 次，五题各耗尽两次步数。

**修改：**增加由运行时绑定编号和版本的观测结果接口，兼容唯一可识别的旧数据布局；逐项保存证据，返回具体失败点，需求修订须关联更新的用户消息。无进展的同一协议错误连续三次就明确暂停，保留业务严格检查和原预算。

**当前效果：**最终快速检查 266 项，265 通过、1 跳过；Windows + Docker 六项短检查通过，未跑模型题。具体修改及历史前缀处理见文末第 9 节，不能据此声称真实题成本已经下降。

### ⑨ 验收外层与字段位置混淆，交替报错绕过暂停（2026-09-06，v6）

**原来：**v5 三题出现 20 次 `/observations/...` 路径混淆；纠正读取位置也得重跑命令，两种错误交替出现、改动验证脚本又会重置无进展计数。

**修改：**判定器兼容唯一可识别的外层布局，字段名等于检查编号时不用填路径；保存原始命令证据，新增只纠正字段绑定的重解析接口。无进展按新增有效验收项计数，不再按报错文字或文件变动清零。具体见文末第 10 节。

**验证：**282 项本地检查中 **281 通过、1 跳过**，Windows + Docker **8 项通过**。仅重读旧 Trace 的 65 次结构化验收输出，34 次旧报错现在能解析；其中上述 20 次路径混淆，18 次能识别且比较值符合预期，另 2 次命令未成功，仍拒绝。**这是解析器复核，不是新版模型成绩；原分数未改，尚未重跑 Luna。**

### ⑩ 撤掉中途报错三次就暂停（2026-09-06，v7）

**原来：**把“尚未新增有效验收项”当成“没有进展”，可能在模型正常修格式、修代码时提前打断。

**修改：**移除验收错误触发的提前暂停；中间工具或验收失败继续把具体错误交给模型修复。保留严格最终验收、32 步硬上限和原题预算，错误次数只作诊断。字段重解析及原始证据复用继续保留。

**验证与重跑：**45 项本地检查全部通过，确认连续五次报错、格式与数值错误交替出现后仍可修复完成。按用户要求停止 v6 六路批次，标为“用户中断、被新版本替代”，保留原始记录；v7 已使用独立冻结代码和工作区，六题六路 Luna 重新启动，尚无完整成绩。第 10 节的三次暂停规则仅是历史设计，现已撤除。

### ⑪ 验收分类附加了不相关要求，旧错误又反复回传（2026-09-06，v8）

## 4. 长任务太费 token：从“压完又塞回去”改成“少重复、压了真能省”

**出了什么问题？**对话变长后，系统会把旧内容整理成摘要，让模型少读一些。但原来的自动记忆搜索又可能把本次对话已经压缩的历史找回来，重新放进模型要读的内容里；摘要还可能再抄一遍已经保留的用户要求。模型每次继续工作都要读这些重复内容，累计消耗就很高。这里的 token 可以粗略理解为模型读写文字的计量单位。

**具体改了什么？**主要是下面四处：

| 遇到的情况 | 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|---|
| 搜索记忆时，又找到本次对话的旧记录 | 已经用摘要表示的历史，仍可能被自动放回上下文 | 当前对话仍在使用时，自动搜索不再注入同一会话的历史归档；其他会话的记忆照常查 | 避免刚缩短的内容又被展开 |
| 用户要求已经完整保留 | 摘要里可能再复制一份 | 摘要注明要求见保留的原文，把篇幅留给新增进展、约束和结论，并合并重复信息 | 同一要求不用让模型反复读两份 |
| 生成摘要后没省下多少内容，或者暂时不适合压缩 | 暂缓压缩也可能产生归档文件；缺少统一的节省门槛 | 先估算压缩前后大小，达到最低节省要求才采用摘要、保存归档；同一段内容没有收益就不反复总结 | 总结本身也花钱，不能为了压缩而压缩 |
| 发现总消耗很高，却不清楚花在哪 | 缺少足够细的来源记录 | 分别估算对话、记忆、摘要、工具结果等占用，并单独记录模型服务返回的实际用量 | 找出反复发送的大头，判断下一步该优化哪里 |

可以理解为整理资料：**把厚资料做成一页笔记后，就不要每次开会又把整叠资料发一遍；笔记也不用再抄一份手头已有的要求。如果整理完没变短，就不要反复整理同一叠。**

**会不会为了省钱把记忆删掉？**原始对话记录和已归档内容仍保留，需要细节时可以主动查阅；其他会话的记忆仍能召回。完整保留在上下文中的用户要求不会被摘要替代。省下来的主要是自动重复塞入的内容，摘要里仍要保留关键约束和进展。

**怎么确认改对了？**相关代码测试 **138 项通过**。另用固定输入、固定摘要单独检查机制：压缩后上下文从 **3,264 → 1,714 个估算 tokens**，用户要求从 **2 份 → 1 份**，并确认原文、归档和重新加载正常；连续三次暂缓压缩产生的多余归档从 **3 个 → 0 个**。这些是固定条件下的机制验证，不代表所有真实任务都能省同样比例。

**实际效果：**使用同一个模型、相同题目和原有预算，完成复测后观察到：

| 真实任务 | 修改前总 tokens | 修改后总 tokens | 其他变化 | 修改后是否完成 |
|---|---:|---:|---|---|
| 记忆召回题 `multi_hop_assets` | 272,432 | 94,457，减少约 **65%** | 工具调用 **35 → 10 次** | **8/8 轮成功**，各项验收通过 |
| 压缩题 `version_resolution` | 553,471 | 255,445，减少约 **54%** | 工具调用 **82 → 34 次**，压缩 **39 → 12 次** | **8/8 轮成功**，结果通过，成本仍超预算 |

**还有什么限制？**压缩题仍比 **240,000 tokens** 的原预算高约 **6.4%**，没有靠调高预算让它通过。旧版压缩题只有 **7/8 轮成功**，新版完整完成，因此不是两次同样顺利执行的严格对照；两版还包含其他代码差异，各题也只完成一次有效复测，不能把全部下降都归功于这一项优化。连接失败的首轮记录另行保留，没有拿那次较低的消耗当优化成绩。各来源的 token 数是估算，实际总用量以模型服务记录为准。

**面试可以这样说：**“我发现长任务贵的一部分原因是重复读：历史刚压成摘要，又被记忆搜索塞回来，摘要还会重复用户要求。我让自动搜索跳过本次会话的历史归档，摘要只补充必要信息，并且只有真正缩短内容才采用压缩。原始记录仍可查。两道真实题复测的 token 分别下降约 65% 和 54%，结果都完成了，但压缩题仍超成本预算，这个结果还需要更多对照验证。”

详情：[压缩与召回成本修复](../压缩与召回成本修复.md)。

## 5. 搜索太慢：从“到处找、每个都细查”改成“按范围找、匹配后细查”

**出了什么问题？**用户明明给了文件位置，搜索工具还是可能把工作区里的文件夹一层层翻过去。工作区包含大量依赖、外部项目时，要检查的文件就很多，所以页面一直显示“搜索中”。这部分慢发生在搜索工具内部。

**具体改了什么？**主要是下面三处：

| 用户要找什么 | 原来的做法 | 修改后的做法 | 为什么更快 |
|---|---|---|---|
| `tower-defense/index.html`，已经知道完整位置 | 仍可能递归搜索整个工作区 | 沿着这个路径检查文件，存在就返回，不存在就结束 | 不再翻其他文件夹 |
| `tower-defense/*.html`，只知道目录和文件类型 | 没有充分利用已知目录，搜索范围过大 | 只进入 `tower-defense` 查找 | 少查无关目录和文件 |
| `**/*shoot*`，不知道在哪个目录 | 遍历时，对大量无关路径也反复做完整路径解析和安全检查 | 用 `os.scandir` 获取目录项，先看名称是否匹配，再对匹配结果做完整安全检查 | 仍然要遍历，但每个无关文件少做了昂贵操作 |

可以理解为找书：**知道书架和书名就直接去取；只知道书架就只找这一架；只知道名字里有某个词才逐架找，但先看书名，符合条件才详细检查。**

**安全检查有没有被删掉？**没有。进入目录前仍排除受保护目录和链接；准备返回的文件仍经过 WorkspaceGuard 检查。优化的是无关文件的重复开销，不是让受保护文件也能被搜出来。

**怎么确认改对了？**测试不仅看“搜没搜到”，还检查搜索过程：完整路径不能启动递归；指定目录不能跑去扫描其他目录；没匹配的文件不做完整路径检查。另外检查受保护文件不会返回、新建文件能立即找到。

**实际效果：**已有前端实测中，完整路径搜索用了 **13 毫秒**，指定目录搜索用了 **16 毫秒**，全工作区查找一个不存在的名称用了 **3.122 秒**。这些是工具本身的耗时；对应整轮回复约 25～30 秒，还包含模型处理等等待，不能混在一起计算加速比。这是一次实测，不保证每次都一样快。

**还有什么限制？**不知道目录、又找不到结果时，仍然需要把可搜索范围翻完。“最多返回 10 条”只是限制结果数量，不代表最多检查 10 个文件。因此，全局无结果搜索仍比直接查路径慢。

**面试可以这样说：**“我发现搜索工具没有利用用户已经提供的路径，找一个已知文件也可能扫描整个项目。我把它改成完整路径直接查、已知目录只查该目录；必须全局查时，先匹配名称，再对结果做完整安全检查。核心是少查无关文件、减少每个文件的处理成本，同时用测试确认没有漏掉安全检查。”

代码：`src/MiniClaw/coding_agent/tools/search.py`；回归：`tests/test_search_paths.py`；实测：[前端验收记录](../../.aster/frontend-table-review/REPORT.md)。

## 6. 功能做对却反复收尾、页面误报完成：修协议并减少重复上下文（2026-09-06）

**补充：按需开放 `goal_complete`。**原来普通任务也带着 Goal 完成工具，增加工具说明 token，还可能无效调用、反复收尾。现在仅在 Goal 为 `active` / `verifying` 时开放；其余状态从模型工具定义和系统提示工具列表中移除，并禁止执行，普通任务验收后直接回复。已验证工具随 Goal 状态开放；看板第一阶段原题复测中，`goal_complete` 调用从 **5 次 → 0 次**，从触顶暂停变为正常收尾，独立功能检查 **8/8 通过**。这里统计的是该完成工具的调用次数，不是全部工具调用；具体节省多少 token 尚未单独测量。

**验证状态：**96 项针对性离线回归通过；无头 Edge 的四种结束态与暂停恢复按钮检查通过。原题复测目前完成 7/9 次请求：合并、路径完整通过 382/382 项独立功能检查，但 token 分别为 595,710（+21.87%）和 426,157（-18.42%），均超预算，尚不能说成本整体优化成功。看板第一阶段 8/8 通过且正常收尾，但 4 次命令超时使本阶段耗时 876.707 秒；后两阶段仍待完成。下一步重点是定位验证脚本卡住、继续减少重复历史输入；已恢复网络重试不扣可用性分。保持原来的 32 步和每题 180,000 tokens / 45 次工具 / 900 秒预算。文件快照不代表完整捕获任意 Host shell 的瞬时副作用；自写验收仍需独立 Eval 核对。详见 [前端难题修复与复测](eval%20前端%20no%201/前端难题修复与复测.md)。

## 7. 第二轮效率优化：减少重复读取与历史重发（2026-09-06）

**出了什么问题？**文件刚读完就被换成简短引用，模型拿不到需要的内容，又读一遍；旧工具记录和工具说明还会反复发送，任务越长，累计消耗越高。

**具体改了什么？**

| 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|
| 新读到的内容也可能立即缩成引用，压缩后又从头读 | 新片段先完整使用一次；保留少量已读片段，复用前检查文件内容版本 | 少做重复读取，文件改过就重新读 |
| 相同读取结果、正常代码中的 error 字样都可能造成大段历史保留 | 旧的同参数同内容读取去重，按工具真实失败状态保留错误 | 缩短重复历史，同时保留有效报错 |
| 工具说明发两遍，固定开销还可能触发反复摘要 | 完整说明只在工具定义中发送；按实际历史大小判断是否值得压缩 | 少发重复说明，避免没有收益的总结 |

**怎么确认改对了？**186 项离线检查通过，6 类新版判定器用合法与错误实现校准；另将原 20 题中的 6 题冻结后，两路 Luna 各跑一次，保持原题与预算。

**实际效果：**6 题总 tokens 从 **3,529,367 → 1,730,372，减少 51.0%**。发票、脱敏、运费的 read 次数分别从 **58→5、43→7、31→5**；没有步数暂停。

**还有什么限制？**该轮仍有 **5/6 超 token 预算**，配置迁移反增 **28.2%**；结果全过 **2/6**，五维全过 **0/6**。当时只定位了会话身份、旧摘要、验收格式和小工具历史累计四处问题。单次复测且包含其他改动，不能把全部降幅归因于这一项。详见 [效率复测与超预算根因](eval%20no%202/Luna效率复测结果与超预算根因.md)。

**随后补修：**共享对话使用固定会话 ID，并去掉当前历史已覆盖的召回原文；旧摘要降为历史参考，普通任务验收通过后进入交付，新需求或文件变动重新开放工具；验收读取兼容 stdout/stderr 与独立日志行，仍严格检查业务字段、版本和退出码；旧成功工具记录增加累计预算，以可回读引用代替反复重发。203 项离线检查中 202 通过、1 跳过；六题两路 Luna 已另冻结为 v3 复测，原题和预算不变，不覆盖上一轮成绩。

## 8. 动态状态放在历史前面：改成尾部追加，减少缓存前缀被打断（2026-09-06）

**出了什么问题？**每次都把“最新检查点、最新召回记忆”放在历史前面。一句验收报错或记忆排序变化，就可能让后面没变的长历史无法复用缓存。

| 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|
| 在历史前替换整块检查点 | 完整工具返回之后，追加带版本的状态变化；撤回明确记录 | 小变化不打断前面的历史，旧状态不能覆盖当前验收 |
| 召回重排就可能重发整块 | 按作用域、来源编号和内容版本识别，只追加新增、更新或移出的引用 | 排名轻微变化不重发，真正变化仍及时生效 |
| 状态无限积累或摘要频繁重建 | 增量达到条数/大小边界才合并；摘要增加最小间隔，安全边界仍强制处理 | 不为缓存保留无限废话，也少做低收益重写 |

**怎么确认改对了？**213 项离线检查中 212 通过、1 因环境条件跳过。直接检查“状态改变后上一请求前缀不变”，并覆盖撤回、文件版本失效、重启、压缩恢复及工具配对。内部状态保留在审计里，不显示为聊天回复。

**实际效果与限制：**请求组装已改好，并记录首次变化位置与稳定前缀字节数；**尚无这版的模型 A/B 收益**。正在跑的 v3 六题冻结于本次修复之前，不能用其成绩归因于本改动。后续以正确性不下降、未缓存输入或有效耗时下降为准，不拿命中率单独当成功。详见 [请求前缀缓存修复](eval%20Codex%20Luna%20no%201/请求前缀缓存修复.md)。

**后续复测：**v4 六题已结束。缓存占比提高，但总 tokens 从 173 万增至 351 万；进一步定位到验收循环和历史投影仍在重写旧消息。因此不能把本节机制测试当作整体优化成功。随后修复如下。

## 9. 验收反复返工、旧历史反复改写：让接口和状态真正配套（2026-09-06）

**出了什么问题？**程序升级了验收格式，却仍教模型用旧格式；模型不断改脚本、换编号，已经做对的任务也难收尾。另一方面，检查点移到历史尾部后，历史裁剪仍每次改动旧工具记录，继续打断缓存前缀。

| 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|
| 模型反复手写验收 JSON、版本和检查编号 | 程序提交实际观测，运行时绑定编号、版本与文件；唯一可识别的旧布局自动规范化并审计 | 少花时间猜格式，错误实际值仍不通过 |
| 一项格式错误连带丢掉同批合法结果 | 每项独立保存；未执行的命令不清空旧证明；具体失败值进入反馈 | 只修受影响的项，不整批重做 |
| 修格式也不断新建要求、升级版本 | 固定需求，更新须关联新的用户消息；同一无进展错误重复三次就保存进度并暂停 | 防止验收清单越修越长，避免空转到步数上限 |
| 每个请求重新裁剪一小段旧历史 | 保存已发送视图，同阶段尽量稳定；到边界批量归档，重启也可复用 | 将少发历史与缓存复用放在一起考虑 |

**怎么确认改对了？**快速检查 **266 项：265 通过、1 因环境条件跳过**，约 22 秒；实际 Windows + Docker **6 项短检查通过**。确认错误比较仍拒绝、合法同批结果保留、回复修正不重复执行测试、越界绑定在执行前拒绝，以及历史视图的稳定与重启恢复。

**实际效果与限制：**这些机制已验证，**尚未跑新版 Luna 题目，不能填写 token 节省比例**。预期值仍可能被模型推导错，库存事务和发票算法仍需独立 Eval 验证；没有靠改单题答案或调高预算过关。详情：[v5 验收与历史前缀修复](eval%20no%202/v5验收与历史前缀修复.md)。

**后续 v5 六题结果：**相对 v2，结果全过 **2/6 → 4/6**，未缓存输入下降约 **22.2%**，但总 tokens 增加约 **27.3%**，效率仍只有 **1/6** 通过。验收错误反馈为 52 次，说明接口与无进展保护仍有缺口，不能把前面的离线通过等同于整体效率优化成功。随后补修如下。

## 10. 验收格式反复猜、两种错误来回换：少填格式，复用证据，及时暂停（2026-09-06）

> 历史 v6 记录：本节“三次无进展就暂停”已在 v7 撤除；格式识别与证据复用曾保留至 v9，模型侧验收与重绑定接口又在 v10 整体撤除。此处仅记录实验过程，最终保留项见第 15 节。

**出了什么问题？**验证程序已经输出实际结果，模型却把“外层包装”和“字段位置”混在一起。修读取位置也要再执行测试；报错换一种说法、改一下脚本，又被当成有进展，继续耗费请求。

| 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|
| 必须套 `observations`，还要手填内部字段路径 | 接受裸对象或带包装对象；字段名等于检查编号时直接读取，多写一层路径仅在含义唯一时纠正 | 把可识别的格式差异交给程序处理，减少模型猜格式 |
| 字段位置填错后，重新执行整条验证命令 | 保存原始输出和执行记录；用 `verification_rebind` 只修字段位置，再解析已有结果 | 格式修正不应重复跑测试或重放副作用 |
| 同一报错连续三次才停；换报错或改文件就重新计数 | 没有新增有效验收项时，交替协议错误也累计；三次后保存进度并暂停 | 改了脚本不代表验收有进展，及时停止空转 |

**哪些仍不能通过？**多个 JSON 结果有歧义、输出截断、命令非零退出、缺失实际值、实际值不符合预期，仍严格拒绝。重解析不能修改预期值、需求版本或被测文件清单；声明的文件变化、用户新指令、需求撤回或证据被改后，旧证据不能复用。错误反馈提供可见字段、证据编号和修正方式。复用检查只覆盖声明的文件，模型自写测试仍须独立 Eval 核对。

**怎么确认改对了？**282 项本地检查中 **281 通过、1 跳过**，约 33 秒；实际 Windows + Docker **8 项短检查通过**。真实命令增加一次计数后，纠正字段绑定不再增加计数；交替报错、修改验证脚本、重复验收已通过的同批项目，都不能绕过无进展暂停。仍保留 32 步上限与原有预算。

**实际效果与限制：**旧 Trace 的 **65 次**结构化验收输出仅交给新解析器重读，其中 **34 次**旧报错现在能够解析；原先 **20 次**外层路径混淆中，**18 次**能识别且比较值符合预期，另 **2 次**命令未成功，仍拒绝。此复核没有执行原命令，也没有复核当时的文件版本或重新评定整题成绩。**尚未跑新版 Luna，不能据此承诺 token 或耗时下降。**原始输出、原分数和 v2～v5 冻结版本保留。

验证记录：[本地回归](../../.aster/evals/efficiency-revision-v6-validation.json)、[Windows + Docker](../../.aster/evals/efficiency-revision-v6-smoke.json)、[旧输出解析复核](../../.aster/evals/efficiency-revision-v6-parser-replay.json)。

## 12. 普通验收被要求做四种故障测试：按实际要求验，分清本次错误与旧问题（2026-09-06，v8）

**原来：**只要模型把检查归为 recovery，系统就附加提交前、提交中、响应丢失和重试四种测试。简单的文件修改范围检查也被套进来。新接口拒绝这种分类，旧接口又可能因 recovery/scenarios 字段差异反复报错；参数尚未通过校验，也被概括为“命令执行失败”。

| 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|
| 分类决定四项固定故障测试 | 新合同明确登记所需场景；分类本身不增加要求 | 检查实际任务，避免无关的额外验收 |
| 故障验收必须切到旧接口，字段稍错就返工 | 两种接口均可提交场景；唯一的 recovery 别名规范化为 scenarios，双字段歧义仍拒绝 | 减少换接口和猜字段，明确指出缺少哪个场景 |
| 冗余 check_ids 直接拒绝，错误被包装成命令失败 | 仅在与 comparisons 中编号完全一致时接受冗余字段；其他参数错误原样指出，说明命令尚未执行 | 修可识别的格式差异，不悄悄删验收项 |
| 验证其他项目时，旧错误也让本次显示失败 | 本次协议错误、实际比较失败、历史未解决项分别返回 | 模型知道这次做对什么、还有什么没解决 |

**严格检查保留：**明确登记的故障场景仍必须提交对应观测，不能靠修格式删场景；实际值错误、缺比较项、场景标记不合法仍拒绝。旧会话保留原有场景合同，新批次从新会话执行。历史未解决项仍阻止宣布全部完成。模型自写测试及场景声明不等于独立故障验证，最终仍由冻结 Eval 核对。

**当前效果：**293 项本地检查中 **292 通过、1 跳过**，约 33 秒；Windows + Docker **8 项通过**。v7 已停止，原记录保留；v8 六题六路 Luna 已重跑，题目、外部判定器、32 步上限和原预算不变，报错仍继续交给模型修复。

**统计口径：**本次协议错误记录在 task_verification.error，历史未解决项另存 pending_errors；unresolved_error 保留与旧版“任一待解决错误都反馈”的可比口径。后续报告需同时核对，不能把重新分类带来的计数下降说成 token 优化。

记录：[本地回归](../../.aster/evals/efficiency-revision-v8-validation.json)、[Docker 检查](../../.aster/evals/efficiency-revision-v8-smoke.json)、[v8 启动](../../.aster/evals/efficiency-revision-v8/execution.json)。

## 13. 验收少填重复格式，分清哪里出错：只修通用问题（2026-09-06，v9）

**原来：**每次验证都要重填比较项和文件，漏 artifacts、写错 JSON 位置就返工；测试后顺手执行失败的 Git 命令，也让整条验收命令失败。旧错误与新错误混看，容易把接口问题说成模型算错。历史虽然被裁剪，读文件快照又补回来，只看裁剪量看不出净成本。

| 原来的做法 | 修改后的做法 | 为什么这么改 |
|---|---|---|
| 每条命令重复填写检查合同 | task_checkpoint 可一次登记 comparisons/artifacts；后续 verification 只填 criterion_id；未登记不能省略 | 少重复参数；期望值和文件范围保持固定，新旧接口均不能借修格式偷改期望 |
| 模型反复手写验收 JSON | Python 提供 emit，把实际计算值序列化成统一 observations；Host 可导入、Docker 只读挂载 | 减少引号和外层格式错误；函数不生成正确答案，错误实际值仍失败 |
| 环境诊断与验收混在一条命令 | 增加 diagnostic 用途，禁止同时标记验收；说明工作区是否有根目录 .git | 辅助命令失败单独反馈；不忽略非零退出，不拆 shell 字符串猜哪段成功，文件变更仍使旧证据失效 |
| 所有验收失败都叫协议错误 | 分别记录 plan_error、execution_error、protocol_error、comparison_failed；历史 pending 单列，旧记录缺依据时保留未分类 | 区分参数、命令、格式与实际比较错误；分类不等于判定责任，模型写错期望也可能导致比较失败 |
| 只看历史裁剪，忽略回放加回内容 | 记录裁剪前、回放前、最终历史 tokens，以及回放增加量和净变化 | 先确认额外成本在哪；目前不删除有效读快照，不把估算净增加直接认定为浪费 |
| 用六道长任务挑战推断整体能力 | 另建 CSV/CLI、配置解析、过滤分页三个日常开发任务族，独立报告 | 补常见任务分布；全部标为已曝光开发题，不声称新盲测或覆盖已充分 |

**当前效果：**本地回归 **302 项：301 通过、1 跳过**；真实 Host/Docker **9 项通过**；新日常集 oracle **9 次正反校准通过**（每族一份正确实现、两种错误实现）。覆盖登记复用、期望不能偷改、旧接口不能绕过、文件变化使证据失效、错误分类和历史净成本记账。

**边界：**本轮未跑 Luna，因此还不能声称 token、错误次数或结果通过率改善。发票计算、提案 ID、库存原子性等模型产物错误保留为回归，不在 Agent 中加专用答案规则。32 步、旧预算、原分数不变；中途错误继续返回模型。emit 和模型自写验证仍不是独立正确性保证，最终需要外部 oracle。

记录：[本地回归](../../.aster/evals/efficiency-revision-v9-validation.json)、[Host/Docker 检查](../../.aster/evals/efficiency-revision-v9-smoke.json)、[新题校准](../../.aster/evals/everyday-v1-calibration.json)、[日常开发集说明](../../evals/日常开发集说明.md)。

## 14. 验收接口回归简单：最终答案暂存，之后交给 judge（2026-09-06，v10）

**原来：**模型既做题又维护验收合同；补 comparisons/artifacts、改检查编号、输出 observations、修字段绑定都可能报错，正确的业务结果也可能被迫继续返工。

**修改：**只允许 write、bash、read、edit、grep、search、memory、goal、goal_complete、skill。删除模型侧检查点工具和证据重绑定工具；bash 只接收 command/timeout，返回真实输出、退出码与错误。普通最终回答自动暂存；goal_complete 只接收 final_result，停止目标执行，但明确是模型提交、待独立评审。执行日志和预算检查点由系统自动保存，不要求模型填写。

**为什么：**让模型专注读写、开发、测试和回答，不再围绕自建验收格式反复返工。业务正确性移到后置评分，不能因为移除了验收错误就宣称正确率提升。

**当前效果：**46 项针对性本地检查通过，含真实 Docker 普通输出/写入、连续四次命令失败后继续、固定工具名单、旧验收文件不再阻塞、新会话回答暂存、goal 提交、取消和网络恢复。模拟任务验证 20 路同时收集；修正后仅结果评分调用为零，四维程序正常评分，整体 passed 保持 null。旧版本验证接口专用测试仅作为历史记录，不用于要求重新引入已撤掉的协议。

**本轮实测：**boundary-full-v10-jobs20，原 20 题全部完成、Luna 20 路并行、原题预算和输入不变。仅结果维度待后置 LLM judge；过程、效率、安全、可用性由程序正常判定。各题在 run/judge-packets 保存需求、逐阶段最终回答、Trace 路径、工作区和文件哈希。原有权限保护、真实工具错误、32 步上限与断网有限恢复保留。

**评分修正：**初版收集模式误把五维全部置为待评，已修正为只延后结果评分。运行快照和原报告保留不动，校验文件哈希后，从已完成的 Trace、工作区和用量补算四维，不调用模型、不重跑题。补算结果：过程 **18/20**、效率 **16/20**、安全 **19/20**、可用性 **20/20**；结果与五维总通过仍待评。针对性模拟回归通过，确认正确过程能通过、超预算和越权文件会失败、结果判定器未被调用。详见 [四维程序评分](../../.aster/evals/boundary-full-v10-jobs20/run/program-report.json)。

记录：[本地检查](../../.aster/evals/simple-v10-validation.json)、[运行记录](../../.aster/evals/boundary-full-v10-jobs20/execution.json)。

## 15. 真正有效的改动：保留上下文减负，撤掉验收负担（v1～v9 复盘，含 v10 边界）

**先说结论：**最明显的提升是少消耗、少返工，而不是模型突然更会推理。v1～v9 留下了上下文减负的基础；本次跨越还包含 v10 撤掉复杂验收接口，不能把全部收益记到 v9。

**本次实际变化：**结果 **16/20→18/20**，效率 **6/20→16/20**，五维全通过 **5/20→11/20**。本次结果 16/20→18/20，多通过的是审计 CLI 根入口和目录扫描清单两题。新版生成了更符合要求的代码；目前没有消融证明是某个记忆改动使它们通过。库存原子性与提案 ID 两题仍失败。

|---|---:|---:|---:|
| 总 tokens | 5,090,509 | 2,218,747 | -56.41% |
| 未缓存输入 | 3,025,989 | 905,617 | -70.07% |

### 按证据与保留价值排序

**1. 保住已读文件的有效信息，减少压缩后重读（v2）**

- **原来：**压缩后只剩“读过某文件”的摘要，模型为继续工作又把同一文件读一遍。
- **修改：**缓存有大小上限的 read 结果，带文件哈希；内容未变才复用，变更就失效。相同读结果去重，但用户明确发起的 read 仍实际执行。
- **为什么：**让仍然有效的文件内容跨压缩保留下来，模型不用为了恢复工作状态反复读盘；哈希防止把旧内容当新内容。
- **效果：**旧 v1 → v2 的发票、脱敏、运费 read 次数分别 58→5、43→7、31→5。六题总 tokens 352.94 万→173.04 万，减少 51.0%；这是整组改动的实测，不能全部归到读缓存。
- **限制：**当前 20 题 read 总数 233→141，与少重读方向一致；尚无只关闭读缓存的独立对照。

**2. 控制旧工具记录的总大小，并保留可回读原文（v3 → v5）**

- **原来：**只裁剪单条大输出；大量几 KB 的代码、编辑参数和验证命令全部留下，每次请求继续重发。
- **修改：**给已完成的工具调用及结果设置累计预算，超限时替换为原文引用；保留新结果与最近工具对。v5 保持已发送视图稳定，到边界才集中裁剪。
- **为什么：**上下文会被许多小记录一起撑大，因此必须控制累计体积；保留回读入口，避免省掉信息后无法查证。
- **效果：**将 v2 的固定请求交给 v3 投影器重读，库存与配置迁移的历史估算 tokens 分别减少 28.38%、27.60%；其他四题为 0%～4.92%。这是离线重放，未调用模型。
- **限制：**局部输入更短已核验；回放读快照还可能加回内容，应看最终净输入。不能把历史估算降幅当服务商实测账单或正确率提升。

**3. 同一道题使用同一会话身份，避免把自己当外部记忆（v3）**

- **原来：**共用 session.jsonl，却每一轮生成新 session_id；检索只排除本轮 ID，之前轮次摘要又被当成其他会话召回。
- **修改：**共享会话固定 case.id + session_key；自动召回排除当前会话的 episode，过滤当前对话已包含的原文片段。真正隔离的新会话仍可召回。
- **为什么：**排除当前对话已有的信息，减少自我重复与旧结论干扰，不把真正的跨会话记忆一并关闭。
- **效果：**历史三道压缩题的记忆注入曾占主请求输入估算的 34%～37%；快照确认修复从 v3 起生效，当前仍保留。当前三道跨会话召回题两版结果都为 3/3。
- **限制：**修掉重复召回来源有明确代码证据；3/3→3/3 只能说明本组未观察到结果退步，不能说召回能力提升或单项省了多少。

**4. 动态记忆追加到尾部，旧历史尽量不反复改写（v4 → v5）**

- **原来：**最新记忆、检查点放在历史前面，一点状态变化就打断长前缀；逐条裁剪又不断改旧消息。
- **修改：**v4 把变化写成带版本的尾部增量；v5 保存已发送历史视图，在阶段或大小边界再重建。新版保留记忆增量；旧的验收检查点注入已在 v10 删除。
- **为什么：**缓存需要连续前缀匹配；将小变化放在尾部、减少旧历史改写，才有机会复用已有输入。
- **效果：**前缀稳定与撤回逻辑有离线验证。历史 v2→v5 缓存占比 31.25%→57.61%、未缓存输入约降 22.2%，但总 tokens 增 27.3%，效率仍 1/6。
- **限制：**保留减少无谓前缀变化的机制，不能宣传缓存率提升等于整体提速。当前 37.43%→56.44% 同样是多项改动与供应商缓存共同作用。

**5. 按需开放工具，错误正常反馈，成本记录看净值（v2 / v7 / v9）**

- **原来：**普通任务也看到 goal_complete，容易无效调用；三次中间验收错误就暂停；只记裁剪量，看不到读快照加回的成本。
- **修改：**只有活跃 Goal 才开放完成工具；v7 撤销三次中间报错暂停；v9 记录裁剪前、回放前、最终历史 tokens。
- **为什么：**减少无关工具选择，给模型正常修错机会；通过净成本记录识别优化是否只是把开销搬到了另一个位置。
- **效果：**当前 v1 重跑有 2 次无效 goal_complete 调用，新版为 0；v7 有五次报错后仍能修复的本地回归；v9 的净成本字段帮助识别“裁剪了又补回来”。
- **限制：**这是小范围减负、行为修正和诊断能力。两批 20 题均为 0 次暂停、可用性均 20/20，不认领本轮可用性提升。新增统计本身不节省 tokens。

### 本次最重要的新变化其实在 v10

v9 与 v10 的 read_cache、history_budget、working、manager、ContextJournal 五个实现文件哈希完全一致。v10 新做的是撤掉 task_checkpoint、verification_rebind 和模型侧验收合同，改为正常回答后独立评分。历史 v9 有 100 次 task_checkpoint、5 次 rebind；本次 v1 有 73 次 task_checkpoint，新版均为 0。撤掉这些工具直接消除了相应调用和协议返工入口，是本次最有解释力的新增机制；全体 token 降幅仍不能归因于单项。

### 不再当作成功经验的改动

v1～v9 不是越改越好：历史全量 v1→v9 总 tokens 708.10 万→591.34 万，但工具错误 53→128，五维全通过仍 5/20→5/20；加上已发现的队列重复项，结果复核为 17/20→17/20。v8→v9 六题总 tokens 165.59 万→192.81 万、工具错误 30→42。不能把复杂验收协议、字段登记、重绑定、自动附加故障场景或三次报错暂停列为应恢复的成功方案。

BM25/BGE/RRF/重排、grep/search 提速、网络恢复与原文落盘等早期建设，不因名称高级就算成本轮增量；本次没有换检索算法的消融证据。路径和 oracle 纠错提升成绩可信度，不能说它让 Agent 答对更多题。

**结论边界：**本次两批均 20 路、同一组已曝光题、每题一次；没有逐项开关的消融实验，旧六题也存在并发、运行与评分版本差异。历史 .env 未归档。过程 20/20→18/20、安全 20/20→19/20，并非五维全面提升；两道过程失败是压缩次数不足，不能直接说记忆丢失。安全失败仍保留。

**下一步：**如果需要给单项优化填写独立节省比例，应在同一代码基线上逐个关闭读缓存、召回去重、历史预算或尾部增量，并重复采样；本次只做证据复核，不新增跑题。

**面试可以这样说：**“我通过 Eval 定位了重复读文件、同会话重复召回和工具历史累计重放，保留文件哈希校验、召回去重、累计历史预算及稳定请求前缀；复测又发现内部验收协议本身造成大量返工，于是改成提交答案后独立评分。同组 20 题、同为 20 路的单次回归中，总 tokens 降低 56.4%，效率通过从 6/20 到 16/20，结果从 16/20 到 18/20。这是组合改动效果，单项因果尚未拆开验证。”
