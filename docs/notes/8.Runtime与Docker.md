# MiniClaw Runtime 与 Docker 设计

## 1. 结论

MiniClaw 现在把 Runtime 放在 `assistant/tools` 与操作系统之间：

```text
LLM
 ↓
AgentLoop
 ↓
ToolExecutor
 ↓
read / write / edit / grep / bash
 ↓                         ↓
WorkspaceGuard         ToolRuntime
 ↓                         ↓
宿主有效工作区       HostCommandExecutor / DockerCommandExecutor
```

这里借鉴了 pi-mono 最重要的边界，但按 MiniClaw 的 Python 架构重新实现：

- 五个工具的公开名字和参数不变；
- 文件工具不进入 Docker；
- 只有 `bash` 使用 Runtime 选择宿主或容器；
- Runtime 是会话级对象，由 `CodingAssistant` 组装；
- Docker 是可选后端，不是模型、记忆、Goal 或飞书的运行容器；
- 默认使用 `docker + direct`；首次启动前必须准备 `miniclaw-runtime:py311` 镜像，也可以显式传入 `--sandbox host` 临时回退。

## 2. 模块位置

```text
src/MiniClaw/coding_agent/runtime/
├─ config.py       Runtime、Docker、Snapshot 配置
├─ workspace.py    路径映射、越界和敏感路径保护
├─ snapshot.py     安全工作区快照与 manifest
├─ execution.py    Host/Docker 命令执行、超时、容器清理
├─ core.py         会话级 ToolRuntime 组合
└─ __init__.py     对外接口
```

Docker 镜像定义位于：

```text
docker/runtime/Dockerfile
```

`tools` 仍然只负责工具参数、结果和输出策略。它不会自行读取环境变量或创建容器。

## 3. Runtime 与 ToolExecutor 的区别

`ToolExecutor` 管“这次工具调用如何执行”：

- 按名称找到工具；
- 预处理参数；
- 递归校验 JSON Schema；
- 把异常转换成 ToolResult；
- 运行结果转换器；
- 做最终输出长度保护。

`ToolRuntime` 管“工具在哪个工作区、通过什么环境执行”：

- 源工作区与有效工作区的关系；
- 模型看到的执行路径；
- Host 或 Docker 命令后端；
- 默认和最大命令超时；
- Snapshot manifest；
- Docker 资源与网络配置；
- Trace 中的 Runtime 元数据。

因此 Runtime 不替代 ToolExecutor，两者处于不同层次。

## 4. 为什么只有 bash 进入 Docker

文件工具在宿主 Python 进程中实现，原因是它们已经有明确、窄化的操作语义：

- `read` 只能读取一个经过校验的文件；
- `write` 只能写入一个经过校验的路径；
- `edit` 只能进行唯一文本块替换；
- `grep` 只能执行受限搜索，并排除敏感路径；
- `bash` 可以启动任意程序，因此需要更强的进程和资源隔离。

Docker 模式下，两类工具仍操作同一个有效工作区：

```text
宿主：D:\project
容器：/workspace

write("src/a.py")
  → 宿主写 D:\project\src\a.py

bash("python src/a.py")
  → Docker 将 D:\project 挂载为 /workspace
  → 容器读取 /workspace/src/a.py
```

不需要在每次工具调用后复制文件。

## 5. 两种工作区模式

### 5.1 Direct

```text
source workspace = effective host workspace
```

特点：

- 文件工具直接修改真实项目；
- Docker bash bind mount 真实项目到 `/workspace`；
- 宿主和容器修改立即互相可见；
- 适合个人本地 Coding Agent；
- 多会话共享同一项目时仍可能发生并发修改冲突。

Runtime 使用统一路径策略识别常见敏感路径；文件工具每次访问动态判断，Docker 每次启动命令前重新生成遮蔽挂载：

```text
.env / .env.*
.ssh / .aws / .azure / .kube / .gnupg / .docker
credentials / secrets / auth.json
*.pem / *.key / *.p12 / *.pfx
.git/config / .git/credentials*
```

这些路径：

- 被 `read/write/edit/grep` 拒绝或排除；
- Docker Direct 模式中使用空文件或空目录进行只读遮蔽。

MiniClaw 自己的 `.aster` 会话、Trace、Goal 和记忆状态同样被保护；仅保留模型恢复大输出所需的 `tool-output` 与 `context-artifacts` 作为文件工具可读区域。

Host bash 是明确的可信本地执行后端，无法靠 WorkspaceGuard 限制 shell 内部访问。因此对不可信任务应使用 Docker。

### 5.2 Snapshot

```text
source workspace
  ↓ 首次安全复制
<session-dir>/sandbox/workspace
```

特点：

- 每个会话拥有独立有效工作区；
- 文件工具和 bash 都只修改会话副本；
- 后续启动读取 manifest，不重新覆盖已有任务修改；
- 不会自动把结果同步回源项目；
- 适合飞书多会话、Eval、失败复现和不希望直接修改真实项目的任务。

复制时排除：

- 凭据和私钥；
- `.aster` 内部状态；
- `.venv`、`node_modules`、缓存、构建产物；
- 符号链接；
- 超过文件数或总字节限制的工作区。

manifest 记录源目录、任务 ID、复制文件数、字节数、排除项和 Sandbox 配置。

## 6. WorkspaceGuard

`WorkspaceGuard` 同时持有：

```text
host root       D:\project
execution root  /workspace
```

所以 Docker 模式下文件工具同时接受：

```text
src/app.py
/workspace/src/app.py
```

最后都会解析到同一个宿主文件。

防护包括：

1. 拒绝 `..` 越出工作区；
2. 拒绝任意工作区外绝对路径；
3. 解析已有父目录，阻止通过符号链接逃逸；
4. 新文件创建前验证最近存在的父目录；
5. 每次访问按 `read / write / search / execute` 动态判断敏感路径，而不是只依赖 Runtime 启动时的扫描结果；
6. `.aster/**` 只允许内部组件访问，模型只能只读打开已知的 `tool-output` 和 `context-artifacts`；
7. `.git/**` 禁止 Write/Edit 和全文搜索，但允许读取 `.git/HEAD` 等非敏感元数据；
8. 新出现的 `.env`、密钥、凭据会立即被文件工具拒绝，并在每次 Docker 启动前重新加入遮蔽挂载；
9. 为 Docker 生成宿主路径到 `/workspace` 的稳定映射；
10. 为 grep 动态生成敏感路径排除项。

## 7. Docker 每次命令的生命周期

每次 `bash` 调用创建一个新的临时容器：

```text
准备唯一 container name
  ↓
docker run --rm
  ↓
挂载有效工作区到 /workspace
  ↓
sh -c <command>
  ↓
收集 stdout + stderr
  ↓
正常退出或超时清理
  ↓
docker rm -f 兜底
```

容器自身文件系统不会跨命令保留。需要保留的文件必须写入 `/workspace`。

## 8. Docker 安全和资源参数

当前参数包括：

```text
--rm
--pull never
--network none
--cpus 1
--memory 1024m
--memory-swap 1024m
--pids-limit 256
--read-only
--cap-drop ALL
--security-opt no-new-privileges
--tmpfs /tmp:rw,nosuid,nodev,noexec,size=128m
--ulimit nofile=1024:1024
--log-driver none
--workdir /workspace
```

容器只收到固定环境变量：

```text
HOME=/tmp
TMPDIR=/tmp
NO_COLOR=1
CI=1
```

模型 API Key、飞书 Secret 和宿主其他环境变量不会传入容器。

网络默认是 `none`。改为 `bridge` 只代表容器具备网络能力，不代表所有外部写操作天然安全；MiniClaw 当前尚未实现完整的跨平台审批交互，因此开启网络应视为管理员配置决定。

## 9. 超时与输出

Runtime 提供：

- 默认命令超时：120 秒；
- 最大命令超时：900 秒；
- Docker 捕获上限：10 MB，超过后保留尾部；
- 超时或取消时删除容器并终止 Docker CLI 进程树；
- bash 返回最后 2000 行或 50 KB；
- bash 的较大捕获结果仍写入有效工作区的 `.aster/tool-output`。

这里有两层不同限制：

```text
Docker capture limit  防止宿主因无限输出耗尽内存
bash result limit     防止一次 ToolResult 挤爆模型上下文
```

## 10. 配置

```dotenv
MINICLAW_SANDBOX=docker:miniclaw-runtime:py311
MINICLAW_WORKSPACE_MODE=direct
MINICLAW_DOCKER_IMAGE=miniclaw-runtime:py311
MINICLAW_DOCKER_CPUS=1
MINICLAW_DOCKER_MEMORY_MB=1024
MINICLAW_DOCKER_PIDS_LIMIT=256
MINICLAW_DOCKER_NETWORK=none
MINICLAW_DOCKER_TMPFS_MB=128
MINICLAW_SNAPSHOT_MAX_MB=512
MINICLAW_SNAPSHOT_MAX_FILES=50000
MINICLAW_COMMAND_TIMEOUT_SECONDS=120
MINICLAW_COMMAND_MAX_TIMEOUT_SECONDS=900
MINICLAW_COMMAND_MAX_CAPTURE_MB=10
```

Runtime 只接受上述 `MINICLAW_*` 名称，不再维护 pi-mono 环境变量别名。

## 11. 构建与启动

构建 MiniClaw Python Runtime 镜像：

```powershell
docker build -f docker/runtime/Dockerfile -t miniclaw-runtime:py311 docker/runtime
```

Direct Docker：

```powershell
python -m MiniClaw.cli `
  --workspace D:\project `
  --sandbox docker:miniclaw-runtime:py311 `
  --workspace-mode direct
```

Snapshot Docker：

```powershell
python -m MiniClaw.cli `
  --workspace D:\project `
  --sandbox docker:miniclaw-runtime:py311 `
  --workspace-mode snapshot
```

飞书入口同样支持这三个参数：

```powershell
python -m MiniClaw.platforms.feishu.cli `
  --workspace D:\project `
  --env-file C:\path\to\pi-mono\.env `
  --sandbox docker:miniclaw-runtime:py311 `
  --workspace-mode snapshot
```

Docker 镜像必须提前存在。Runtime 不会在 Agent 启动时自动联网拉取镜像，避免不可控下载和启动延迟。

不调用 LLM 的真实容器烟雾测试：

```powershell
python -m MiniClaw.coding_agent.runtime.smoke --image miniclaw-runtime:py311
```

该测试会在系统临时目录创建源工作区和会话 Snapshot，验证：

- 容器能读取挂载输入；
- 容器写入能保留在 Snapshot；
- 源工作区不被修改；
- `.env` 不进入 Snapshot；
- Direct 容器内的 `.env` 被空文件遮蔽；
- Direct 容器修改会落到源工作区；
- 超时命令会被中断且临时容器被删除；
- 容器网络配置保持为 `none`。

## 12. Trace

每个 `run.started` 事件增加 Runtime 元数据：

```json
{
  "runtime": {
    "backend": "docker",
    "workspace_mode": "snapshot",
    "execution_workspace": "/workspace",
    "docker": {
      "image": "miniclaw-runtime:py311",
      "network": "none",
      "cpus": 1,
      "memory_mb": 1024,
      "pids_limit": 256
    }
  }
}
```

Docker bash 的 Tool Result details 还会记录：

- runtime 类型；
- image；
- network；
- container name；
- 捕获是否被截断；
- exit code。

这些字段会自然进入已有统一 Trace，不再恢复独立的 `tool-calls.jsonl` 运行日志。

## 13. 没有照抄 pi-mono 的部分

MiniClaw 保留了 pi-mono 的关键安全边界，但做了以下项目化调整：

- Runtime 是独立 Python package，而不是放进某个平台适配器；
- 使用现有统一 Trace，不重新增加第二套工具审计文件；
- 默认使用 Docker + Direct，在隔离 Bash 执行环境的同时让代码修改直接落入真实工作区；
- 镜像以 Python 3.11 为核心，并预装 git、ripgrep 和构建工具；
- 项目 Runtime 镜像预装 `lark-oapi` 与 `pytest`，其他项目依赖仍应通过自定义镜像固化；
- CLI 和飞书共用同一个 Runtime 配置对象；
- Snapshot 路径跟随 MiniClaw 的 session directory，自然获得会话隔离；
- 不把审批伪装成已完成能力，网络默认关闭，并明确记录当前边界。

## 14. 当前限制

1. Host bash 是真实本地 shell，不是 Sandbox。
2. Direct 模式仍会真实修改项目文件。
3. Snapshot 不自动合并回源项目。
4. Docker 是 Linux 环境，不能替代 Windows/macOS 原生兼容性验证。
5. 容器每次 bash 都重建，镜像内安装的软件保留，但 `/tmp` 状态不保留。
6. 当前没有完整的飞书危险命令审批 UI，Docker 网络默认关闭用于降低风险。
7. Docker bind mount 内的项目文件仍可被命令删除；容器隔离不能替代版本控制和审批。

这些限制被写进文档和配置语义，不会用“用了 Docker 就绝对安全”来夸大能力。
