# v5：减少验收返工与历史前缀改写

2026-09-06。已修改主代码，未改 v2/v3/v4 冻结源码、原始成绩、题目或 Eval 预算。以下记录实施时的机制验证，当时没有调用 Luna 跑题，不能写成六题的节省成绩。

后续六路实跑已完成，见 [v5 与 v2 完整对比](六路Luna-v5与v2完整对比.md)：结果 2/6→4/6、未缓存输入下降 22.2%，但总 tokens 增加 27.3%，验收外壳与字段路径的易错约定仍造成返工。下面的离线验证结果保留，不代替该模型实跑结论。

## 原来与现在

| 问题 | 原来的做法 | 修改后的做法 | 原因 |
|---|---|---|---|
| 验收器要求新格式，系统提示仍教旧格式 | 模型反复手写 task_checks、版本和比较 JSON；比较数据放错层级就再次执行测试 | 新增 `bash.verification` 结构化绑定：命令只输出 observations，运行时绑定当前版本、执行记录、文件与实际比较。旧说明统一到共享协议模块 | 把重复的协议包装交给程序，避免模型边做业务边猜格式 |
| 旧输出中的比较数据位于顶层或 evidence 内部 | 解析器读不到，反复要求重验 | 仅当编号能唯一对应时规范化层级，记录原位置和目标；不补实际值、不猜预期值，歧义或重复仍拒绝 | 兼容已存在的真实证据，不靠偷偷判通过降低错误数 |
| B 项格式错误，A 项的合法结果也没保存 | 整个批次解析完才提交；提前清掉所有本批编号 | 每项独立保留通过、业务失败或协议错误；提交前被拒绝的工具标记 not_started，不让未执行的命令清空旧证明 | 只返工受影响的检查，不让一个坏项拖累全部 |
| 修格式时不断新增编号、升版本 | 模型管理全部版本；略改描述便可能开新清单 | 新编号/版本由运行时补齐；相同明确要求复用编号；进度更新保留既有类型与检查列表。实质修改/撤回须关联更新的用户消息；显示改名使用 label | 分开需求变化、代码变化和验证程序变化 |
| 错误只说“还没验收” | 失败比较细节不进入精简快照 | 返回有限长度的失败编号、实际值、预期值、错误位置；同一协议错误在无工作区进展时连续三次，明确暂停并保存检查点 | 给出可行动信息，阻止无进展循环继续消耗到 32 步 |
| 每请求重裁旧历史 | 为守住小预算不断把不同旧参数/工具结果改成引用 | 保存已经发送的历史视图；同阶段追加保持旧片段稳定。达到高水位时批量归档到低水位；真实新轮次、压缩或状态重置允许重建。重启复用已保存视图 | 不让刚稳定的缓存前缀被另一个裁剪器持续打断 |

高/低水位只控制上下文内部裁剪时机，不改 Eval 的 token 或工具次数预算。低水位沿用原来的 4–16 KiB 工具历史预算，高水位为其两倍；新鲜读取、未决工具和真实错误仍受保护，硬上下文限制与必要压缩保留。因此“阶段内稳定”有明确边界，不是无限堆历史。

用户消息关联来自公开的用户输入入口；Goal 自动继续、网络重试、恢复按钮不会生成新的需求修订凭据。它约束变更来源与时序，**不等于程序已经能完全判断每句自然语言是否授权撤回某个具体要求**。审批、路径防护仍由 Runtime 分别执行。

## 新接口示例

已有一个 criterion `invoice`，要求比较项 `net`。验证程序读取正式输入并输出：

```json
{"observations":{"net":2300}}
```

执行命令时通过 bash 的结构化参数关联：

```json
{
  "command": "python verify_invoice.py",
  "verification": [{
    "criterion_id": "invoice",
    "artifacts": ["input.json", "result.json", "verify_invoice.py"],
    "comparisons": [{
      "check_id": "net",
      "pointer": "/net",
      "expected": 2300,
      "expected_source": "正式输入按交易 ID 去重后的支付减退款"
    }]
  }]
}
```

程序应实际计算 observations，示例数字不是硬编码验证模板。运行时在命令执行前校验绑定并固定需求版本，执行后做严格比较，记录验证器哈希和被测文件内容版本。命令非零退出、缺少要求的字段、越界文件或版本过期都不能通过；完成回复中已绑定的 JSON 字段仍需匹配。

预期值来自模型自写推导时仍属于自测，`expected_source` 只是可追溯来源声明，不是第三方证明。恢复类验收继续要求原有故障阶段证据，不允许用一个普通相等比较替代；现有外部故障探针与独立 Eval 保留。没有给发票或库存题写专用补丁，也不能宣称它们的业务失败已经消除。

## 验证结果

- 最终快速检查共 **266 项：265 通过，1 项因环境条件跳过**，约 **22 秒**。包括验收、历史压缩、恢复、取消、审批、Runtime、会话、Goal 和 Trace。
- 新增针对 v4 问题的检查覆盖：合法同批结果保留、歧义证据拒绝、实际错误拒绝、编号复用、需求来源与版本失效、协议卡住后提前暂停、历史前缀稳定、批量裁剪和重启恢复。
- 实际 Host 命令接入：验证只执行一次；最后 JSON 回答错误后修正，不重放验证命令。非法验证绑定在有副作用的命令执行前拒绝。
- 实际 **Windows + Docker 六项检查通过**：相对路径、`/workspace/` 路径、合法 Windows 宿主绝对路径均能关联同一文件；错误结果、越界路径和非零退出均拒绝。
- 扩展检查首轮发现旧取消测试的假进程缺少 stderr；补齐夹具后通过。没有改运行时来迁就假进程，首轮失败记录保留。
- 真实模型 Eval 请求 **0 次**。原来的 32 步上限、题目和五维预算保持原样；未更改网络失败的评价口径。

复现入口：`scripts/verify_efficiency_v5.py`、`scripts/smoke_verification_v5.py`。机器记录在 `.aster/evals/efficiency-revision-v5-validation.json` 与 `efficiency-revision-v5-smoke.json`；首轮保留为 `efficiency-revision-v5-validation-initial.*`。

## 后续验证顺序

先用一题“产物正确但验收循环”的题确认模型可以使用新接口，再用一题真实业务失败检查边界能力。之后固定并发比较历史投影，观察正确性、未缓存输入、工具数和耗时；这些已曝光题继续作为回归。当前不能承诺节省比例，也不能把格式纠正后的历史数据当作新版模型成绩。
