# Eval3 效率优化方案：减少 Token 与提升缓存命中

## 结论

本轮 12/20 题效率未通过，合计 **3,658,037 tokens**；失败题输入约占 95% 以上，主要不是最终回答太长，而是每次模型请求重复携带历史对话、工具结果、工具调用参数和固定工具定义。

按 `token_accounting.estimated_input.by_source` 粗粒度估算，全批输入来源为：工作对话 1,263,553、工具结果 1,119,472、工具调用参数 983,497、系统提示 635,580、工具定义 603,750、上下文更新 71,388、显式记忆注入 14,925。估算按 UTF-8 字节/4，不是供应商账单分类；它适合定位重复来源，不适合宣称精确可节省金额。

缓存输入占比已经 **69.73%**。缓存命中提升主要降低费用，**不会自动降低请求 token 数，也不会让 token 上限通过**。减少 token 要减少实际发送的内容；提升缓存要保持可复用前缀稳定。两者应分别测量。

## P0：完整请求预算器

现有 [model_client.py](<D:/MIniClaw/src/MiniClaw/trace/model_client.py:36>) 已经记录请求来源分桶，但它是在发送后记账。下一步应增加发送前预算：`system + tool_definitions + work_dialogue + tool_results + tool_call_arguments + memory + 当前输入 + 输出预留`。

预算器只做三件事：

1. 固定保留当前用户要求、未解决错误、正在修改文件和最近一次工具结果。
2. 大工具结果先落盘，历史只保留路径、内容哈希、大小、关键行摘要；需要时用现有 `read`/`grep` 局部回读。
3. 到达软阈值时先压缩工具参数和结果，再压缩已完成回合；超过硬阈值时暂停或请求继续，不能静默突破题目预算。

预算器必须在 Trace 写出 `budget_before`、`budget_after`、每次裁剪原因、保留/丢弃的消息 ID。这样下一次才能区分“压缩减少了 token”还是“模型少做了验证”。

验收：固定同一题、同一模型、同一并发，比较发送前估算与供应商 input tokens；误差单独报告。先用离线 replay 验证投影，不立即跑 API。

## P0：稳定前缀，提升缓存命中

缓存需要请求前缀字节稳定。当前系统提示和工具定义是大块稳定内容，但如果把时间戳、随机 ID、动态状态、变化的 memory 摘要放在前面，会破坏后续缓存。

建议请求顺序固定为：

1. 不含时间和随机值的系统策略；
2. 稳定的工具定义；
3. 项目规则的版本化短摘要；
4. 稳定的历史摘要；
5. 当前会话和工具结果；
6. 当前用户输入与动态状态。

不要为了缓存把动态内容伪装成稳定内容。只要规则、权限或文件哈希变了，就必须改变对应前缀版本。Trace 记录 `prefix_hash`、`first_dynamic_index`、`cached_input_tokens`，按题目和请求序号计算命中率。

缓存命中率的目标应按**可复用前缀 token**计算；不要把供应商返回的 cached tokens 当作全部节省。供应商可能缓存系统/工具定义，也可能不缓存动态历史。

## P1：工具结果增量化

现有 [working.py](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/working.py:240>) 已经能把大结果保存为 artifact，也能去掉重复 read 结果；但仍可能把编辑参数中的完整代码、重复命令输出和验证日志重新发给模型。

实施顺序：

- `read`：同一路径同一 SHA-256 不重复发送全文，只发 `[unchanged path=... sha256=...]`；文件变化后失效。
- `grep/search`：保存命中行的文件哈希、范围和查询；相同查询不重复发完整结果，新增命中只发 delta。
- `bash`：输出按 `stdout/stderr/exit_code/duration` 分开，默认截断；失败时保留错误上下文和命令，不把整段成功日志反复注入。
- `write/edit`：模型参数中的完整新文件只在当前回合保留；后续回合只保留路径、版本哈希和 diff 摘要。需要继续编辑时按行范围回读。
- 测试：正确通过的长日志变成一行摘要；失败测试保留首个失败、相关堆栈和命令。

每次替换都要记录 `source_message_id`、`artifact_hash`、`preview_bytes` 和 `replay_command`，不能只保留一句“已压缩”。

## P1：减少工具调用，但不能用少验证换效率

requirements 和 cross-file 分别出现 66、70 次工具调用，超过 65 上限。目标不是简单限制调用次数，而是减少无效往返：

- 将互不依赖的只读检查合并为一次 bash；
- 失败后先按错误类型选择修复路径，不重复执行同一失败命令；
- 对同一文件先一次读取相关范围，再编辑，避免“读一段—改一段—再次完整读取”；
- 验证按性质分组，一次命令覆盖输入顺序、重复、异常和稳定输出；
- 将公开验证与针对失败原因的专项验证分开，成功 smoke 不重复跑五遍。

Agent 侧可以在工具错误后插入一条短诊断状态：错误类型、目标、是否已产生副作用、下一步只允许的检查。它应由宿主生成，不能让模型自行改写错误历史。

## P1：记忆优化的正确方向

记忆不应追求“召回更多”。本轮显式 memory 注入成本较小，真正风险是错误摘要覆盖事实。效率和正确性应一起改：

- 原始事实采用结构化记录：`subject / value / source / revision / valid_window / record_id / supersedes`；
- 推导摘要单独存放，引用事实 ID；事实变化时摘要自动过期；
- 相同查询返回稳定排序和短结果，完整记录按需回读；
- 已确认的稳定规则做版本化前缀，当前题目只注入与 workspace、tenant、时间相关的部分；
- 记忆查询缓存按 `(scope, normalized_query, memory_version)` 命中，发生写入、撤回或冲突时失效；
- `replace` 不能只靠标题 subject，必须携带明确的 `record_id` 或旧内容哈希；
- 模型生成的“合并后最新状态”不得直接写入事实层，先进入待验证推导层。

这会同时减少无关记忆输入、提高缓存稳定性，并防止错误结论长期污染后续会话。

## P2：什么时候才考虑换模型或更强检索

先完成同题离线 A/B：

1. 原始请求；
2. 只启用工具结果增量；
3. 只启用稳定前缀；
4. 两者同时启用；
5. 保持上下文不变更换更强模型。

每组记录结果、四维程序分、输入/缓存/输出 tokens、工具调用、有效耗时和错误数。一次只改变一个机制；题面和判定版本不变。

只有在“完整清晰上下文 + 充足预算”下 Luna 仍稳定犯同一逻辑错误，而更强模型稳定通过，才把问题列为模型能力瓶颈。只有在原始关键事实确实不在候选上下文，才考虑升级 BM25/BGE/RRF/Cross-Encoder。

## 建议目标

第一阶段不改题目 token 上限：

- 12 个效率失败题中先让至少 4 题降到预算内；
- 全批输入 tokens 减少 20% 以上；
- 缓存输入占比从 69.73% 提升到 80% 以上；
- 工具调用超过 65 的题降为 0；
- 结果、安全通过数不下降；
- 每项收益都用同一题库 revision 的 A/B 数据证明，不把缓存价格下降写成 token 减少。

这些是下一轮实验目标，不是对尚未实施改动的结果承诺。
