# MiniClaw 初版项目详解

> 本文基于当前仓库中的实际代码编写，目标不是只说明“每个文件写了什么”，而是帮助你在实习面试中完整讲清楚：项目解决什么问题、为什么这样分层、一次请求如何流转、当前版本做到了什么、还缺什么，以及面试官可能继续追问什么。

> 更新说明：本文主体保留“最小 Agent 初版”的讲解顺序。当前仓库已经继续加入四层 Memory 和渐进上下文压缩，因此文中“尚未实现 Memory/压缩”的描述只代表初版里程碑；现状请结合 `3.记忆与压缩.md` 阅读。

## 1. 一句话介绍项目

MiniClaw 是一个使用 Python 编写的轻量级编码 Agent 框架。

普通聊天程序通常只完成“用户提问 → 大模型回答”，而编码 Agent 需要形成一个可以反复执行的闭环：

1. 用户提出编码任务。
2. 大模型分析任务并决定是否调用工具。
3. 程序执行文件读取、文件修改、文本搜索或命令运行等工具。
4. 工具结果重新交给大模型。
5. 大模型根据结果继续调用工具，或者给出最终回答。

MiniClaw 初版实现的核心价值，就是把这个闭环拆成边界清晰、可以替换、可以测试的几个模块。

项目不是一个完整的商业级编程助手。目前它更准确的定位是：

- 一个可以运行的最小编码 Agent 原型；
- 一个用于理解 Agent 架构的教学型项目；
- 一个后续可以继续加入流式输出、上下文压缩、沙箱、审批、记忆和多平台接入的基础框架。

## 2. 当前版本包含什么

当前初版已经具备：

- OpenAI Chat Completions 兼容接口接入；
- 模型、消息、工具调用和用量信息的统一数据结构；
- 多轮“模型调用 → 工具执行 → 模型再调用”的 Agent 循环；
- 单次模型回复中多个工具调用的顺序执行；
- 工具注册、参数基础校验、超时控制和输出截断；
- 工作区路径边界检查；
- 文件读取、文件写入、精确替换、文本搜索、命令执行五种工具；
- JSONL 追加式会话保存和启动恢复；
- 命令行交互入口；
- 不依赖真实大模型的离线单元测试。

当前版本暂未实现：

- 真正的 SSE 流式模型响应；
- 工具并行执行；
- 用户取消任务；
- Docker 或其他进程沙箱；
- 高风险命令审批与操作审计；
- 上下文压缩；
- 长期记忆；
- 目标监督和自动恢复；
- Slack、飞书等平台接入；
- 完整的生产级可观测性。

这些功能不是遗忘了，而是有意延后。初版优先验证最核心的 Agent 循环和模块边界。

四个核心包的职责可以概括为：

| 模块 | 核心职责 | 不应该负责的内容 |
|---|---|---|
| llm | 对接大模型供应商，并把不同供应商数据转成统一结构 | 不读写文件，不执行 Agent 循环 |
| agent | 控制模型与工具之间的多轮循环 | 不关心具体是编码助手还是其他 Agent |
| tools | 注册和执行工具，并统一做校验、超时和输出限制 | 不判断用户任务是否完成 |
| assistant | 组装出具体的编码助手产品，并管理会话 | 不直接实现模型协议细节 |

命令行入口 cli 位于最上层，负责接收用户输入并把事件展示出来。

## 4. 整体架构和依赖方向

项目采用单向依赖：

~~~text
cli
 ↓
assistant
 ↓
agent ─────→ tools
 ↓              ↓
llm       具体工具
~~~

可以把四层理解为一家餐厅：

- llm 像翻译员，负责把内部统一语言翻译成不同模型服务能够理解的请求；
- agent 像流程调度员，决定什么时候问模型、什么时候执行工具、什么时候结束；
- tools 像操作规范和执行部门，负责找到工具、安全检查、执行和整理结果；
- assistant 像店长，把模型、工具、提示词和会话管理组装成“编码助手”这个具体产品。

这种设计最重要的好处是降低耦合。

例如，将来要接入另一个模型供应商，理论上只需要新增 ModelClient 实现，不需要修改 AgentLoop。将来增加一个 git_diff 工具，只需要实现 Tool 协议并注册到 ToolExecutor，不需要把工具逻辑写进循环中。

## 5. 一次用户请求的完整执行链路

假设用户输入：“读取 app.py，把 hello 改成 hi，然后运行测试。”

完整流程如下：

~~~text
用户输入
  ↓
cli.interactive
  ↓
CodingAssistant.run
  ↓
AgentLoop.run
  ↓
构造 ModelRequest
  ↓
OpenAICompatibleClient 调用模型
  ↓
模型返回 read 工具调用
  ↓
ToolExecutor 校验并执行 ReadTool
  ↓
文件内容作为 tool 消息加入上下文
  ↓
再次调用模型
  ↓
模型返回 edit 工具调用
  ↓
ToolExecutor 执行精确替换
  ↓
再次调用模型
  ↓
模型返回 bash 工具调用
  ↓
运行测试并把结果返回模型
  ↓
模型不再调用工具，生成最终说明
  ↓
CLI 展示回答，会话消息追加到 JSONL 文件
~~~

注意，“一轮用户请求”不等于“一次模型调用”。

用户只输入了一次任务，但 AgentLoop 可能连续调用模型多次。只要模型回复里仍然包含 tool_calls，循环就会继续；只有模型不再请求工具时，本次 run 才结束。

## 6. cli 模块：程序入口与用户交互

文件：src/MiniClaw/cli.py

### 6.1 核心职责

cli.py 负责：

- 解析命令行参数；
- 从环境变量读取模型配置；
- 创建 OpenAICompatibleClient；
- 创建 CodingAssistant；
- 持续读取用户输入；
- 消费 Agent 事件并打印结果。

它不包含模型协议、工具实现和 Agent 循环，因此入口层比较薄。

### 6.2 配置读取

程序通过环境变量选择模型供应商。默认使用 primary OpenAI 兼容接口和 gpt-5.6-luna：

- MINICLAW_PROVIDER：primary 或 deepseek；
- MINICLAW_PRIMARY_API_KEY：默认供应商密钥；
- MINICLAW_PRIMARY_BASE_URL：默认 https://ai.zxcoding.top/v1；
- MINICLAW_PRIMARY_MODEL：默认 gpt-5.6-luna；
- MINICLAW_DEEPSEEK_API_KEY：DeepSeek 密钥；
- MINICLAW_DEEPSEEK_BASE_URL：默认 https://api.deepseek.com/v1；
- MINICLAW_DEEPSEEK_MODEL：DeepSeek 模型；
- --workspace：Agent 被允许操作的工作区。

CLI 的 --provider、--model 和 --base-url 可以覆盖对应环境变量，但 API Key 只从环境变量读取，不放进命令行参数。

### 6.3 交互循环

interactive 函数中使用一个 while True 循环不断读取输入。

特殊情况包括：

- 空输入：忽略并等待下一次输入；
- 输入 /exit：退出；
- EOF 或 Ctrl+C：正常结束；
- 普通输入：调用 assistant.run。

assistant.run 返回的不是一个最终字符串，而是异步事件流。CLI 只处理其中几类事件：

- text_delta：打印模型文本；
- tool_started：提示正在调用哪个工具；
- error：打印错误。

这说明 UI 与核心逻辑是解耦的。以后即使把 CLI 换成 Web 页面，也可以继续消费同一套 AgentEvent。

## 7. llm 模块：统一模型供应商接口

llm 是最靠近大模型服务的一层，包含 types.py、client.py 和 openai_compatible.py。

### 7.1 types.py：统一领域数据结构

这个文件定义了系统各层共同使用的数据对象。

#### Role

消息角色包含：

- system：系统提示词；
- user：用户消息；
- assistant：模型消息；
- tool：工具执行结果。

#### ToolInvocation

表示模型发起的一次工具调用，包含：

- call_id：本次调用的唯一标识；
- name：工具名称；
- arguments：已经解析成 Python 字典的参数。

call_id 很重要，因为当一次回复中有多个工具调用时，工具结果必须准确对应原来的调用。

#### ChatMessage

表示统一聊天消息，包含：

- role；
- content；
- tool_calls；
- tool_call_id；
- name。

assistant 消息可能带 tool_calls；tool 消息使用 tool_call_id 表示自己是哪次工具调用的返回结果。

#### TokenUsage

记录：

- input_tokens；
- output_tokens；
- cached_tokens。

初版只是保存单次回复的用量，还没有做整次运行的累计统计和成本计算。

#### AssistantReply

表示一次完整的模型回答，包括：

- 普通文本；
- 工具调用列表；
- 停止原因；
- Token 用量；
- 错误信息。

#### ModelProfile

保存模型元数据：

- model_id；
- context_window；
- max_output_tokens；
- supports_tools。

当前实际请求主要使用 model_id 和 max_output_tokens。context_window 和 supports_tools 为后续上下文管理、模型能力判断预留。

#### ModelRequest

是 agent 发送给 llm 的统一请求，包含：

- 模型配置；
- 完整消息上下文；
- 工具定义列表；
- 可选 temperature。

#### ModelEvent

是 llm 向 agent 输出的标准事件，支持：

- text_delta；
- tool_call；
- usage；
- completed；
- error。

虽然当前 OpenAICompatibleClient 还不是真正逐字流式，但接口已经按事件流设计，因此未来替换成 SSE 时，AgentLoop 的主体不需要改变。

### 7.2 client.py：用 Protocol 定义模型接口

ModelClient 是一个 Protocol，只要求实现：

~~~text
stream(request) -> AsyncIterator[ModelEvent]
~~~

Protocol 是 Python 的结构化类型接口。一个类不需要显式继承 ModelClient，只要提供兼容的 stream 方法，就能被 AgentLoop 使用。

这个设计同时提高了：

- 可替换性：可以接入其他模型供应商；
- 可测试性：测试中可以使用假的 ScriptedModelClient；
- 解耦性：agent 不依赖具体 HTTP 实现。

### 7.3 openai_compatible.py：OpenAI 兼容适配器

OpenAICompatibleClient 负责三件事：

1. 把 ModelRequest 转成 Chat Completions 接口请求；
2. 发送 HTTP 请求；
3. 把供应商响应解析成 AssistantReply 和 ModelEvent。

#### 请求构造

发送的数据主要包含：

- model；
- messages；
- max_tokens；
- stream: false；
- tools；
- tool_choice: auto；
- 可选 temperature。

工具定义会被包装成 OpenAI function tool 格式。

#### 为什么使用 asyncio.to_thread

urllib.request.urlopen 是同步阻塞调用。如果直接放在 async 方法中，它会阻塞整个事件循环。

代码通过 asyncio.to_thread 把阻塞的 HTTP 请求放到线程中执行，使外层仍能保持异步接口。

这是一种兼容方案，但不是最理想的生产实现。后续可以换成真正的异步 HTTP 客户端，并支持 SSE。

#### 消息转换

_message_to_wire 把内部 ChatMessage 转成供应商要求的字典：

- assistant 的工具调用要序列化到 tool_calls；
- 工具参数要从字典转成 JSON 字符串；
- tool 消息要携带 tool_call_id。

#### 响应解析

_parse_reply 会：

- 读取第一个 choice；
- 解析模型文本；
- 解析每个工具调用；
- 将工具参数 JSON 字符串转成字典；
- 提取 Token 用量；
- 根据工具调用和 finish_reason 归一化停止原因。

如果接口没有 choices、工具参数不是合法 JSON、参数不是对象，代码会抛出明确错误。

#### 当前的“伪流式”

stream 方法名看起来像流式，但当前流程是：

1. 等待整个 HTTP 响应返回；
2. 解析完整结果；
3. 再一次性发出 text_delta、tool_call、usage、completed 事件。

因此当前 CLI 不能逐 Token 展示模型生成过程。这里实现的是“统一事件协议”，而不是“底层网络真流式”。

## 8. agent 模块：Agent 的核心循环

agent 是整个项目最核心、也最值得在面试中重点讲的模块。

它包含：

- events.py：定义对外事件；
- loop.py：实现模型与工具的循环。

### 8.1 events.py：AgentEvent

AgentEvent 是 agent 对 UI 或上层产品输出的统一事件。

主要事件包括：

| 事件 | 含义 |
|---|---|
| run_started | 一次用户任务开始 |
| turn_started | 一次模型回合开始 |
| message_added | 有消息被加入会话 |
| text_delta | 模型产生文本 |
| tool_started | 工具开始执行 |
| tool_finished | 工具执行结束 |
| turn_finished | 当前模型回合结束 |
| run_finished | 整次用户任务结束 |
| error | 发生错误 |

事件中还可以携带 message、tool_call、tool_result、usage、details 和 is_error。

这种事件驱动设计让核心循环不需要知道前端长什么样。CLI 可以打印事件，Web 服务可以把事件转成 WebSocket 消息，桌面应用也可以用事件更新界面。

### 8.2 AgentLoop 的构造参数

AgentLoop 接收：

- llm：调用哪个模型；
- profile：使用哪个模型及其能力配置；
- tools：有哪些工具以及如何执行；
- system_prompt：系统提示词；
- max_turns：最大回合数，默认 32；
- transform_context：发送给模型前的上下文变换钩子。

AgentLoop 自己不创建模型、不注册文件工具、不管理 JSONL 文件，所以它是一个通用循环内核。

### 8.3 run 方法的核心算法

run 的逻辑可以用伪代码表示：

~~~text
如果已经在运行，拒绝并发启动
标记为运行中
保存用户消息

最多循环 max_turns 次：
    构造上下文和工具定义
    请求模型
    收集模型的完整回复
    保存 assistant 消息

    如果模型没有请求工具：
        结束本次运行

    按顺序执行每个工具调用：
        发送 tool_started
        通过 ToolExecutor 执行
        将结果保存为 tool 消息
        发送 tool_finished

如果超过最大回合数：
    报错结束

无论成功失败：
    清除运行中标记
~~~

### 8.4 为什么要有 _running

同一个 AgentLoop 内部保存了共享的 messages。

如果两个 run 同时修改消息列表，可能出现上下文交叉、工具结果错位等问题。因此初版用 _running 防止同一个实例并发运行。

这只是最基础的并发保护。生产环境通常会为不同会话创建独立 runner，或者使用队列、锁和任务取消机制。

### 8.5 system prompt 如何加入上下文

loop.messages 只保存用户、助手和工具消息。

每次请求模型时，_request_messages 会临时把 system_prompt 放在最前面，因此系统提示词不会重复写入持久化会话。

顺序类似：

~~~text
system
user
assistant（包含工具调用）
tool（工具结果）
assistant
...
~~~

### 8.6 transform_context 的意义

当前版本没有实现上下文压缩，但预留了 transform_context。

发送模型前，可以通过这个钩子：

- 截断过旧消息；
- 总结历史消息；
- 注入检索到的记忆；
- 根据模型上下文窗口控制 Token。

这体现了一个设计原则：上下文管理不应该直接硬编码在 Agent 循环中。

### 8.7 多工具调用如何处理

如果一次 assistant 回复包含多个 tool_calls，runner 使用 for 循环按原始顺序执行，并按相同顺序追加 tool 消息。

优点是行为确定、上下文顺序稳定、容易测试。

缺点是性能不高。互不依赖的读取工具理论上可以并行执行，但写文件和命令类工具可能存在先后依赖，所以以后做并行化时需要先判断工具是否只读、是否存在资源冲突。

### 8.8 错误处理

run 内部的大部分异常都会被转换成：

- error 事件；
- is_error 为真的 run_finished 事件。

这样上层消费事件时，不需要依赖未捕获异常判断任务是否失败。

但当前还有一个值得改进的点：模型客户端已经可能先产生 error 事件，随后 completed 中仍带 error，AgentLoop 又会抛错并产生第二个 error 事件，UI 可能看到重复错误提示。

## 9. tools 模块：工具协议、执行策略与工作区边界

tools 是大模型真正影响本地环境的入口，因此既关系到扩展能力，也关系到安全性。

### 9.1 base.py：工具统一协议

ToolResult 统一工具输出：

- content：给模型看的文本结果；
- is_error：执行是否失败；
- details：结构化附加信息。

Tool Protocol 要求工具提供：

- name；
- description；
- input_schema；
- async execute(arguments)。

大模型通过 name 选择工具，通过 description 理解用途，通过 input_schema 生成参数。

### 9.2 workspace.py：路径边界

WorkspaceGuard 在创建时把根目录转换成绝对规范路径。

resolve 的处理流程是：

1. 用户路径如果是相对路径，就拼接到工作区根目录；
2. 使用 Path.resolve 规范化路径；
3. 用 relative_to 检查最终路径是否仍位于工作区内；
4. 如果逃逸到工作区之外，抛出 PermissionError。

例如，工作区为 D:\project 时：

- src\app.py：允许；
- ..\secret.txt：拒绝；
- 指向工作区外部的绝对路径：拒绝。

这个检查可以阻止最直接的 ../ 路径穿越。

需要注意：它只保护使用 WorkspaceGuard 的文件工具。bash 可以执行任意 shell 命令，当前并没有被真正限制在只能访问工作区，因此项目不能宣称已经有完整沙箱。

### 9.3 executor.py：统一执行边界

ToolExecutor 是所有工具调用的统一入口。

#### 注册

register 根据工具 name 保存工具。重名工具会直接报错，避免后注册工具悄悄覆盖旧工具。

#### 工具定义导出

definitions 把内部工具转换为模型能够理解的结构：

- name；
- description；
- parameters。

这些定义最终由 llm 转成供应商的 function calling 格式。

#### 执行流程

execute 的步骤是：

~~~text
根据名字查找工具
  ↓
调用工具的 prepare_arguments 兼容模型参数
  ↓
递归 JSON Schema 参数校验
  ↓
执行工具；只有显式配置时才使用全局超时
  ↓
捕获超时和普通异常
  ↓
100,000 字符最终兜底限制
  ↓
返回统一 ToolResult
~~~

未知工具不会导致整个 Agent 崩溃，而是返回 is_error 为真的 ToolResult。这个错误结果会继续交给模型，让模型有机会纠正工具名或改用其他方案。

#### 参数校验

_validate 当前递归支持：

- 检查 required 参数是否缺失；
- 检查 string、integer、number、boolean、object、array 等基础类型；
- 检查嵌套 object 和 array items；
- additionalProperties: false；
- minItems 和 minimum；
- 明确拒绝把 Python 的 bool 当作 integer 或 number。

它仍不是完整 JSON Schema 实现，目前没有处理：

- enum；
- 字符串长度；
- oneOf、anyOf 等复杂规则。

如果工具需要更复杂的参数模型，后续可以换成专业 JSON Schema 库或 Pydantic。

#### 超时

ToolExecutor 默认不设置统一超时，因为 pi 的 bash 允许长时间运行，只有调用方传入 timeout 时才应该中止命令。ToolExecutor 仍允许产品层配置全局超时，配置后会使用 asyncio.wait_for。

bash 自己支持可选 timeout，并在 Windows 使用 taskkill、在 POSIX 使用进程组终止整棵子进程树。

#### 输出截断

ToolExecutor 的 100,000 字符限制只是最后一道保险。真正的输出策略由工具自己负责：read 保留头部，bash 保留尾部，grep 同时限制匹配数、总字节数和单行长度。这样比所有工具统一截取前 N 个字符更符合编码场景。

### 9.4 五个独立工具模块

#### ReadTool

文件：tools/read.py。用途：读取工作区内文件。

特性：

- 参数为 path、offset、limit，offset 从 1 开始；
- 默认最多保留头部 2000 行或 50KB；
- 被截断时给出下一次读取使用的 offset；
- offset 超过文件末尾会报错；
- 第一行本身超过 50KB 时不返回半行，而是提示使用 bash；
- 图片会返回类型说明，但当前 Python ToolResult 只能保存字符串，尚不能把图片作为多模态附件传回模型。

read 不添加行号，保持与 pi 返回原始文件内容的方式一致。

#### WriteTool

文件：tools/write.py。用途：创建或完整覆盖 UTF-8 文本文件。

流程：

1. 解析并检查路径；
2. 自动创建父目录；
3. 以 UTF-8 写入内容；
4. 返回实际写入的 UTF-8 字节数；
5. 通过按绝对文件路径划分的修改队列，保证同一个文件的 write/edit 串行执行。

这是高影响工具，因为已有文件会被整体覆盖。系统提示词因此要求模型优先使用 edit 修改已有文件。

#### EditTool

文件：coding_agent/tools/edit.py 和 coding_agent/tools/edit_diff.py。用途：一次调用对一个文件做一个或多个定点替换。

每项 edits 都使用 oldText 和 newText。它要求每个 oldText 在原始文件中恰好出现一次：

- 出现 0 次：报错；
- 出现多次：报错；
- 多个目标互相重叠：报错；
- 只有 1 次且互不重叠：从文件尾向前执行替换。

精确匹配失败后，会像 pi 一样尝试 NFKC、行尾空白、智能引号、Unicode 横线和特殊空格规范化。工具还会保留 UTF-8 BOM 和原文件的 CRLF/LF 风格，并在 details 中返回 diff 与 firstChangedLine。

#### GrepTool

文件：tools/grep.py。用途：通过 ripgrep 搜索工作区文件内容。

它支持：

- pattern 支持正则表达式或 literal 字面量；
- path 指定文件或目录；
- glob 过滤文件；
- ignoreCase 控制大小写；
- context 返回匹配前后的上下文；
- limit 默认最多 100 个匹配。

它遵守 .gitignore，同时搜索隐藏文件。输出格式是 path:line: text，上下文行使用 path-line- text。每一行最多 500 个字符，总输出最多 50KB。

#### BashTool

文件：tools/bash.py。用途：在工作区目录下执行 shell 命令。

它会：

- 把工作区设为 cwd；
- 按产生顺序合并 stdout 和 stderr；
- 根据退出码设置 is_error；
- 支持调用方显式 timeout；
- 超时时终止进程树；
- 输出最多返回尾部 2000 行或 50KB；
- 超长完整输出保存到 .aster/tool-output/，模型可以再用 read 查看。

它是当前能力最强、风险最高的工具。

“cwd 在工作区”不等于“只能访问工作区”。Shell 命令仍可能读取或修改工作区外文件，也可能访问网络或启动其他程序。因此当前 README 明确说明 bash 不是沙箱。

### 9.5 factory.py 与公共辅助模块

factory.py 中的 create_coding_tools 是工具工厂，严格按 read、bash、edit、write、grep 顺序创建五个工具。

它只创建一个 WorkspaceGuard，并让五个工具共享同一个边界，最后返回工具列表，由 CodingAssistant 负责注册。

这种方式避免了每个工具各自解析一个不同的工作区。

truncate.py 统一实现头部截断、尾部截断和 grep 单行截断；mutation_queue.py 保证同文件修改串行；各工具的 Operations Protocol 则为未来远程文件系统或 Docker Runtime 注入执行能力预留边界。

## 10. assistant 模块：组装编码助手产品

assistant 位于通用框架之上，把 llm、agent、tools 和会话能力组装成“编码助手”。

### 10.1 session.py：JSONL 会话持久化

JsonlSessionStore 使用 JSON Lines 格式保存消息，一行对应一条 ChatMessage。

#### append-only 的优点

- 每次只追加一行，逻辑简单；
- 不需要每轮重写完整会话；
- 进程意外退出时，之前已写入的行通常仍可恢复；
- 方便人工检查和后续日志处理。

#### load 的恢复策略

读取时逐行解析。遇到以下坏数据会跳过：

- 不完整 JSON；
- 字段类型错误；
- 缺少必要字段。

注释里写的是“忽略不完整的最后一行”，但实际实现会忽略任何无法解析的行，不仅是最后一行。这提高了容错性，但也可能掩盖中间数据损坏，后续应加入日志或告警。

#### 会话文件位置

CodingAssistant 默认把会话保存在：

~~~text
工作区\.aster\session.jsonl
~~~

工具调用也会被序列化和恢复，因此重启后仍能保留完整对话结构。

当前没有：

- 多会话 ID；
- 会话列表；
- 会话删除；
- 文件锁；
- 并发写保护；
- 会话版本迁移；
- 敏感信息脱敏。

### 10.2 coding.py：Composition Root

CodingAssistant 是整个编码产品的“组装根”。

构造时依次完成：

1. 解析工作区绝对路径；
2. 创建 ToolExecutor；
3. 创建五个标准工具；
4. 注册工具；
5. 创建 JsonlSessionStore；
6. 创建 AgentLoop；
7. 加载历史消息到 loop.messages。

为什么要把组装放在这里？

因为 llm、agent 和 tools 都是通用组件，它们不应该自己决定：

- 编码助手使用哪些工具；
- 系统提示词写什么；
- 会话存在哪里；
- 是否恢复历史消息。

这些都属于具体产品层决策。

### 10.3 系统提示词

系统提示词告诉模型：

- 它是工作在单个仓库中的编码助手；
- 当前工作区是什么；
- 可以使用哪些工具；
- 编辑前先读相关文件；
- 优先精确替换，不轻易覆盖整个文件；
- 修改后运行验证；
- 没有工具结果确认时不能声称操作成功。

这里的提示词属于“软约束”。

例如，“先读再改”主要依赖模型遵守提示词，程序没有强制检查某文件是否已经读过。真正的安全要求不能只依赖提示词，应该在 tools 中实现硬性策略。

### 10.4 run 中的会话保存

CodingAssistant.run 代理 loop.run，并监听 message_added 事件。

每当 runner 加入 user、assistant 或 tool 消息时，CodingAssistant 就把它追加到 JSONL 文件。

这很好地保持了职责边界：

- AgentLoop 只维护内存中的消息；
- assistant 决定消息是否以及如何持久化。

$env:MINICLAW_PRIMARY_API_KEY = "你的 API Key"

## 13. 初版设计中值得讲的亮点

### 13.1 先统一协议，再接具体模型

AgentLoop 只认识 ModelClient 和统一消息对象，不直接依赖 OpenAI 返回格式。这样换供应商不会污染核心循环。

### 13.2 核心循环不绑定编码场景

AgentLoop 不知道 read、write 等具体工具，也不知道会话文件。它只知道模型可能请求工具，ToolExecutor 能执行工具。

因此同一个 AgentLoop 理论上可以用于数据分析 Agent、运维 Agent 或业务流程 Agent。

### 13.3 工具错误会反馈给模型

未知工具、参数错误、超时和工具异常都会被规范化成 ToolResult，并作为 tool 消息送回模型。

这使模型能够自行纠正，而不是任意一个工具错误都让整次任务立即中止。

### 13.4 精确替换避免大面积误改

EditTool 要求每个 oldText 唯一且多个编辑互不重叠，体现了“修改操作应当可定位、可验证”的可靠性思路。

### 13.5 软约束与硬约束分层

- 提示词要求“先读后改、修改后验证”，属于软约束；
- WorkspaceGuard、参数校验、超时和输出限制属于硬约束。

面试中可以强调：安全规则不能全部依赖模型自觉，关键策略必须由程序执行。

### 13.6 通过假的 ModelClient 做离线测试

测试不调用真实大模型，因此：

- 结果稳定；
- 速度快；
- 没有 API 成本；
- 可以精确构造边界场景。

这是 Agent 项目中很重要的工程实践。

## 14. 当前初版的主要问题和改进方向

### 14.1 bash 没有真正沙箱

当前只设置了工作目录，没有限制命令访问工作区外部、网络和系统资源。

改进方向：

- Docker 或受限容器；
- 命令白名单或风险分级；
- 高风险操作人工审批；
- 超时后终止整棵进程树；
- CPU、内存、磁盘和网络限制；
- 命令审计日志。

### 14.2 没有上下文窗口控制

历史会话会不断增长，每次全部发送给模型，最终可能超过上下文窗口，也会增加成本。

改进方向：

- 按 Token 计算上下文预算；
- 保留最近消息；
- 对旧工具输出做摘要；
- 把长期信息保存到独立记忆中；
- 利用 transform_context 实现压缩。

### 14.3 不是真正的模型流式输出

当前需要等完整 HTTP 响应结束后才产生事件。

改进方向：

- 使用异步 HTTP 客户端；
- 解析 SSE；
- 增量拼接文本和工具参数；
- 支持取消请求；
- 处理流中断和重试。

### 14.4 会话存储只适合单用户原型

单个固定 JSONL 文件没有会话 ID、并发锁和索引。

改进方向：

- 每个会话独立文件或数据库记录；
- 增加 session_id；
- 文件锁或事务；
- 消息版本字段；
- 错误行告警；
- 敏感数据处理。

### 14.5 参数校验比较基础

当前只是 JSON Schema 的一小部分。

改进方向：

- 使用 jsonschema 或 Pydantic；
- 拒绝多余参数；
- 支持 enum、范围和嵌套结构；
- 为每个工具增加更严格的业务校验。

### 14.6 缺少任务级统计和可观测性

当前没有完整记录：

- 一次 run 总共调用多少次模型；
- 总 Token 和总成本；
- 每个工具耗时；
- 错误率；
- 每一轮的状态；
- 最终是否真正达到用户目标。

可以在 AgentEvent 基础上增加日志、Trace、指标和运行 ID。

### 14.7 缺少编辑事务和回滚

工具直接修改真实文件。如果后续测试失败，框架不会自动恢复。

改进方向：

- 修改前生成补丁；
- 通过 git diff 展示变更；
- 在临时工作树中执行；
- 通过审批后再应用；
- 支持失败回滚。

## 15. 面试时可以怎样介绍

### 15.1 30 秒版本

我做了一个 Python 的轻量级编码 Agent 框架。它拆成 llm、agent、tools 和 assistant 四层：llm 层屏蔽不同模型供应商协议，agent 层负责模型与工具的多轮循环，tools 层统一处理工具注册、参数校验、超时、输出限制和工作区路径边界，assistant 层再把工具、系统提示词和 JSONL 会话持久化组装成实际的编码助手。初版已经跑通完整工具闭环，并使用假的 ModelClient 做离线单元测试。

### 15.2 2 分钟版本

这个项目的目标不是直接做一个功能很重的编程助手，而是先验证一个最小但边界清晰的 Agent 内核。

用户输入后，AgentLoop 把系统提示词、历史消息和工具定义交给模型。如果模型返回工具调用，ToolExecutor 会找到对应工具，做参数校验、超时控制和异常归一化，再把结果作为 tool 消息加入上下文并重新请求模型。这个过程会持续到模型不再调用工具，或者达到最大回合数。

模型层通过 ModelClient Protocol 解耦，目前实现了 OpenAI Chat Completions 兼容适配器。工具层实现了文件读取、写入、唯一文本替换、搜索和本地命令执行，并通过 WorkspaceGuard 限制文件路径。产品层使用 JSONL 追加保存每条消息，重启后可以恢复上下文。

我比较重视可测试性，所以测试没有调用真实模型，而是使用 ScriptedModelClient 预设回复，验证模型发起工具调用、工具结果回填、模型二次回答的完整链路。当前版本仍然是原型，主要缺口是真流式、上下文压缩、命令沙箱、审批机制和更完整的测试。

## 16. 面试官可能追问的问题

### 问：为什么不把所有逻辑写进一个 Agent 类？

答：模型协议、循环控制、工具安全策略和产品会话是变化频率不同的部分。如果写在一个类里，换模型、加工具或改存储都会影响核心循环，也难以单独测试。分层后每部分都可以替换，测试也能针对单一边界。

### 问：为什么 ModelClient 使用 Protocol？

答：Protocol 支持结构化类型，只要实现同样的 stream 方法就能被 AgentLoop 使用，不需要强制继承。它既降低具体实现之间的耦合，也方便测试中放入假的 ModelClient。

### 问：工具调用为什么还要变成 tool 消息发回模型？

答：模型只负责决策，真正的文件内容和命令结果来自本地 ToolExecutor。只有把结果放回上下文，模型才能根据真实结果继续下一步，并避免凭空假设操作成功。

### 问：为什么 EditTool 要求只匹配一次？

答：编码 Agent 的修改必须尽量可定位。如果旧文本出现多次，模型的修改意图不明确，直接替换可能误伤多个位置。拒绝执行并让模型提供更具体的上下文，比猜测更安全。

### 问：WorkspaceGuard 是否已经足够安全？

答：不够。它能保护文件工具免受直接路径穿越，但 bash 仍可以通过 shell 访问工作区外部，所以当前只能称为路径边界，不是沙箱。生产环境还需要容器、审批、资源限制和审计。

### 问：为什么工具错误不直接终止 Agent？

答：很多错误是模型可以纠正的，例如工具名错误、参数缺失或精确文本没有匹配。把结构化错误作为 tool 消息反馈给模型，可以让模型调整方案。只有模型服务异常、超过最大回合等无法继续的错误才结束整个 run。

### 问：如何避免无限循环？

答：AgentLoop 使用 max_turns，默认最多 32 轮。即使模型一直调用工具，也会在达到上限后产生错误事件并结束。后续还可以增加重复调用检测、Token 预算和总时长预算。

### 问：为什么会话使用 JSONL？

答：初版优先简单和可恢复。JSONL 每条消息独立追加，崩溃时通常只影响最后一行，也方便人工查看。但它不适合多用户并发，后续应升级为带会话 ID、事务和索引的存储。

### 问：真正的流式响应要改哪些地方？

答：主要修改 OpenAICompatibleClient，让它解析 SSE 并逐步发出 text_delta、tool_call 和 completed。因为 agent 已经消费统一 ModelEvent，理想情况下 AgentLoop 的核心流程不需要重写，只需完善增量工具参数组装和取消处理。

### 问：如果要增加新工具，怎么做？

答：

1. 新建一个实现 Tool Protocol 的类；
2. 提供 name、description 和 input_schema；
3. 实现异步 execute；
4. 在 assistant 的组装阶段注册到 ToolExecutor；
5. 为成功、参数错误、权限和超时场景补测试。

核心循环和模型适配器不需要感知具体工具。

## 17. 阅读代码的推荐顺序

第一次看项目时，推荐按以下顺序：

1. README.md：先确认项目目标和范围；
2. llm/types.py：理解统一消息、模型回复和工具调用数据；
3. coding_agent/tools/base.py：理解具体 Coding 工具协议；
4. agent/loop.py：看最核心的模型—工具循环；
5. coding_agent/tools/executor.py：看工具怎样被安全、统一地执行；
6. coding_agent/tools/read.py、bash.py、edit.py、write.py、grep.py：看五个独立工具；
7. coding_agent/assistant/coding.py：看所有组件如何组装；
8. coding_agent/assistant/session.py：看会话如何恢复；
9. llm/openai_compatible.py：看内部协议怎样映射到外部 API；
10. cli.py：最后看用户入口；
11. tests：通过测试确认各模块真实行为。

## 18. 总结

MiniClaw 初版最重要的不是工具数量，而是建立了一个正确的最小骨架：

~~~text
统一模型协议
    ↓
通用 Agent 循环
    ↓
统一工具运行时
    ↓
具体编码工具
    ↓
产品组装与会话持久化
~~~

它已经能够完成最小的编码 Agent 闭环，并且各层职责相对清晰。

面试时应实事求是地描述它：

- 可以说它实现了可运行的模型—工具多轮循环；
- 可以说它重视协议抽象、职责分离和离线测试；
- 可以说文件工具具有工作区路径检查；
- 不应说它已经具备生产级安全沙箱；
- 不应说它已经支持真正流式输出；
- 不应说它已经解决长上下文、长期记忆和多用户并发。

能够明确说明“为什么这样设计、当前限制在哪里、下一步怎样演进”，比单纯罗列功能更能体现对项目的真正理解。
