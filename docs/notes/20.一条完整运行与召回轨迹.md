# MiniClaw：一条完整运行、压缩与多路召回示例轨迹

> 本文使用一条缩短后的虚构轨迹解释当前真实代码行为。文件名、Token 数和业务内容是为了方便理解而简化的，但每一种存储、压缩和召回方式都对应 MiniClaw 当前实现。

## 一、先记住五句话

1. **Working Context 不搜索**：Checkpoint 和近期原文始终直接放在模型上下文中。
2. **Archive 才使用父子节点召回**：先检索 1600 字符左右的子块，再返回最多 5 个父节点及命中块前后文。
3. **Semantic 使用混合检索，但没有父子节点**：每条稳定事实本身就是一个完整检索单元。
4. **Episodic 也使用混合检索，但没有父子节点**：每个历史 Session 摘要是一个完整检索单元，需要时仍可按 Session ID 直接读取。
5. **Skill 不是向量检索**：Skill 名称和描述始终可见，模型选中名称后精确读取对应的 `SKILL.md`。

整条主线是：

```text
用户提出新任务
  ↓
Working 直接提供当前任务状态
  ↓
Semantic / Archive / Episodic 分别召回
  ↓
跨来源 RRF 合并，再基于完整候选统一 rerank，在 15k Token 内自动注入
  ↓
Skill 目录单独注入
  ↓
模型决定是否读取 Skill、Artifact 或完整 Episode
  ↓
调用 Read / Grep / Edit / Bash 等工具完成任务
  ↓
大工具结果立即落盘
  ↓
上下文超过阈值后归档旧工具结果和闭合历史
  ↓
生成 Checkpoint，保留近期原文
  ↓
完整证据进入 Archive，未来通过父子节点召回
```

---

## 二、示例任务的背景

假设 MiniClaw 正在维护一个 Python 项目。用户的新请求是：

```text
修复订单服务偶发重复扣库存的问题，运行测试确认，并记住项目统一使用 pytest。
```

在新请求到达前，工作区里已经有以下记忆。

### 2.1 Semantic Memory 中的稳定事实

文件：

```text
.aster/memory/MEMORY.md
```

内容示意：

```markdown
## project

- 数据库使用 PostgreSQL。
- 订单写入必须在事务中完成。
- 项目统一使用 pytest 执行测试。

## preference

- 用户希望先运行小范围测试，再运行完整测试。
```

这些是短小、独立、可以跨会话复用的事实。

每一条事实就是一个完整检索文档：

```text
Semantic文档1：数据库使用PostgreSQL
Semantic文档2：订单写入必须在事务中完成
Semantic文档3：项目统一使用pytest执行测试
Semantic文档4：用户希望先运行小范围测试
```

它们不会再被切成父节点和子节点。

### 2.2 Episodic Memory 中的历史任务摘要

文件：

```text
.aster/memory/episodes/order-lock-investigation.md
```

内容示意：

```markdown
# Session order-lock-investigation

- Status: completed

## Goal

调查订单并发写入问题。

## Latest Outcome

发现测试环境曾使用SQLite，无法复现PostgreSQL行锁行为。

## Open Work

后续并发测试应连接PostgreSQL测试容器。
```

这是“一次历史经历”的概览，不是完整原始对话。

### 2.3 Procedural Memory 中的项目流程

文件：

```text
.aster/skills/testing/SKILL.md
```

内容示意：

```markdown
---
name: testing
description: 按项目规范运行小范围测试和完整测试。
---

1. 先运行目标模块测试。
2. 修改后运行回归测试。
3. 最终记录退出码和失败数量。
```

启动时不会把整个文件放进 Prompt，只会放入目录：

```text
testing: 按项目规范运行小范围测试和完整测试。
```

### 2.4 Archive Memory 中的旧原始证据

之前某个会话已经压缩过，因此存在：

```text
.aster/memory/archive-index.jsonl
.aster/context-artifacts/old-session/context-transcript-....jsonl
.aster/context-artifacts/old-session/bash-call-....txt
```

旧 Bash Artifact 的内容可能是：

```text
$ pytest tests/test_orders.py -q

test_two_workers_reserve_same_item FAILED

worker-a read stock=1
worker-b read stock=1
worker-a wrote stock=0
worker-b wrote stock=0

AssertionError: reservation_count should be 1, got 2
```

完整文件没有每轮都放入模型上下文，而是被切成约 1600 字符的 Archive 子块等待检索。

## 三、阶段一：新请求到达时，MiniClaw 先从哪里拿信息

用户发送：

```text
修复订单服务偶发重复扣库存的问题，运行测试确认，并记住项目统一使用 pytest。
```

这时还没有执行任何文件工具。MemoryManager 会先构造记忆上下文。

### 3.1 Working Context：直接拿，不搜索

当前会话可能刚开始，因此 Working Context 只有：

```text
[user]
修复订单服务偶发重复扣库存的问题，运行测试确认，并记住项目统一使用 pytest。
```

如果这是恢复中的会话，则还会包含：

```text
[system]
[MiniClaw Working Context Checkpoint]
当前目标：修复订单重复扣库存。
已确认：问题发生在并发预留阶段。
下一步：检查reserve_inventory实现。

[近期未压缩原文]
最近几轮用户、Assistant和Tool消息……
```

这里没有 BM25、向量、RRF，也没有父子节点。

原因是 Working Context 本来就是“当前正在用的内容”，没有必要先把它丢掉再搜索回来。

### 3.2 Semantic：检索稳定事实

查询：

```text
修复订单服务偶发重复扣库存的问题，运行测试确认，并记住项目统一使用 pytest。
```

Semantic 对 `MEMORY.md` 中每条事实执行：

```text
BM25关键词检索
  +
向量语义检索
  ↓
RRF合并两份排名
  ↓
规则rerank
```

可能返回：

```text
Semantic结果1：订单写入必须在事务中完成。
Semantic结果2：项目统一使用pytest执行测试。
Semantic结果3：数据库使用PostgreSQL。
```

这里没有父子节点，因为每条事实已经完整。

模型从 Semantic 得到的关键信息是：

```text
这不是普通内存变量问题，很可能需要数据库事务或锁。
测试命令应优先使用pytest。
```

### 3.3 Archive：通过父子节点找回旧原文

同一个查询也会进入 ArchiveMemoryIndex。

假设旧 Bash Artifact 被分成：

```text
父节点：bash-call-previous.txt

Chunk 0：测试命令和环境信息
Chunk 1：两个Worker读取相同库存的日志
Chunk 2：AssertionError和失败统计
Chunk 3：其他无关测试输出
```

第一步只检索小块：

```text
所有Archive子块
  ↓
BM25 + 向量 + RRF + rerank
  ↓
Chunk 1命中最高
```

第二步恢复父节点关系：

```text
Chunk 1
  ↓
所属父节点 = bash-call-previous.txt
```

第三步展开局部上下文：

```text
Chunk 0 + Chunk 1 + Chunk 2
```

不会返回 Chunk 3，也不会无条件把几十万字符的完整日志塞回 Prompt。

如果多个 Chunk 都来自同一个父节点，它们只占一个父节点名额：

```text
Chunk 1命中
Chunk 2也命中
  ↓
仍然只算一个父节点
```

最终最多选择 5 个 Archive 父节点。

这次可能召回：

```text
Archive父节点1：旧并发测试的Bash Artifact
Archive父节点2：旧会话中关于SQLite无法复现行锁的用户消息
Archive父节点3：旧Assistant对失败原因的分析
```

模型从 Archive 得到的是“原始证据”：

```text
两个Worker确实读到了相同的stock=1。
旧测试环境使用SQLite。
旧测试最终报reservation_count应为1但实际为2。
```

### 3.4 Episodic：混合搜索历史会话

Episodic 不使用父子节点，但和 Semantic、Archive 一样复用统一的 HybridMemoryRetriever。

每个 Episode Markdown 会作为一个完整 MemoryDocument：

```text
subject = Episode中的Goal
content = 完整Episode Markdown
```

然后执行：

```text
BM25关键词检索
＋
本地向量检索
↓
第一级RRF：融合BM25和向量排名
↓
单库rerank
```

可能返回：

```json
{
  "sessionId": "order-lock-investigation",
  "score": 4,
  "preview": "Goal 调查订单并发写入问题……后续并发测试应连接PostgreSQL测试容器……"
}
```

搜索结果同时保留完整正文和约 300 字符调试预览；自动跨来源精排使用完整 Episode 内容，而不是只使用预览。

如果模型认为这个历史任务特别重要，可以再主动调用：

```text
memory(
  action="episode_read",
  sessionId="order-lock-investigation"
)
```

这时按 Session ID 直接读取完整 Episode 文件，不再做搜索。

### 3.5 Procedural Skill：不是检索，而是目录选择

Prompt 中始终存在：

```xml
<available_skills>
- testing: 按项目规范运行小范围测试和完整测试。
</available_skills>
```

模型看到用户要求“运行测试确认”，判断 `testing` Skill 相关，于是调用：

```text
skill(action="read", name="testing")
```

ProceduralMemoryStore 根据准确名称打开：

```text
.aster/skills/testing/SKILL.md
```

这一步没有：

```text
BM25
向量检索
RRF
父子节点
```

模型得到测试流程：

```text
先运行目标模块测试，再运行完整回归测试，并记录退出码。
```

## 四、三路自动召回怎样汇合

自动检索分别得到：

```text
Semantic
├─ 订单写入必须在事务中完成
├─ 项目使用pytest
└─ 数据库使用PostgreSQL

Archive
├─ 旧并发失败日志父节点
├─ 旧SQLite环境讨论父节点
└─ 旧Assistant分析父节点

Episodic
└─ order-lock-investigation会话预览
```

MemoryManager 再做一次跨来源排名融合：

```text
Semantic：权重1.0
Archive：权重1.0
Episodic：权重0.6
  ↓
跨来源RRF
  ↓
去掉内容重复项
  ↓
根据用户问题和完整候选内容统一final rerank
  ↓
在总计15k Token内注入
```

注意：

```text
不是每个Archive父节点拥有15k Token。
不是Semantic、Archive、Episodic分别拥有15k Token。

而是整个 <retrieved_memory> 共享15k Token硬预算。
```

最终自动注入可能类似：

```xml
<retrieved_memory>
- [semantic:...] 订单写入必须在事务中完成。
- [archive:archive_parent_...] 旧测试命令、并发日志、AssertionError……
- [semantic:...] 项目统一使用pytest执行测试。
- [archive:archive_parent_...] SQLite环境无法复现PostgreSQL行锁……
- [episode:order-lock-investigation] 调查订单并发写入问题……
</retrieved_memory>
```

Skill 目录在这个块之外单独追加：

```xml
<available_skills>
- testing: 按项目规范运行小范围测试和完整测试。
</available_skills>
```

## 五、模型拿到这些信息后，怎样做出选择

模型此时掌握：

```text
当前用户要求
├─ 修复重复扣库存
├─ 运行测试
└─ 记住pytest规范

Semantic告诉它
├─ 必须使用事务
├─ 数据库是PostgreSQL
└─ 测试框架是pytest

Archive告诉它
├─ 两个Worker读到了相同库存
├─ reservation_count从1变成2
└─ SQLite测试环境可能不可靠

Episodic告诉它
└─ 以前调查过类似问题，应该用PostgreSQL测试容器

Skill告诉它
└─ 先小范围测试，再完整回归
```

因此模型不会马上随便改代码，而是形成下面的执行决策：

```text
1. 先读取订单预留实现。
2. 搜索reserve_inventory和库存更新SQL。
3. 检查是否存在事务和行锁。
4. 修改后先运行订单模块测试。
5. 再运行完整测试。
6. 将“项目使用pytest”写入Semantic Memory。
```

这里要区分“信息来源”和“最终决定”：

| 信息 | 从哪里得到 | 模型据此做出的选择 |
|---|---|---|
| 必须在事务中写订单 | Semantic | 优先检查事务边界 |
| 旧日志中两个Worker同时读到库存1 | Archive | 怀疑读写竞争 |
| SQLite无法复现PostgreSQL锁 | Episodic | 使用PostgreSQL测试环境 |
| 先跑小测试再跑全量 | Skill | 安排验证顺序 |
| 当前要修重复扣库存 | Working | 决定当前任务目标 |

## 六、阶段二：执行工具时，哪些东西属于“召回”，哪些不是

### 6.1 Read 和 Grep 是读取当前工作区，不是 Memory 召回

模型调用：

```text
grep(pattern="reserve_inventory", path="src")
```

得到：

```text
src/orders/service.py:88:def reserve_inventory(...)
tests/test_orders.py:142:test_two_workers_reserve_same_item(...)
```

然后调用：

```text
read(path="src/orders/service.py", offset=70, limit=80)
```

得到代码：

```python
stock = product.stock
if stock > 0:
    product.stock = stock - 1
    reservation.save()
```

这属于当前工作区文件操作：

```text
Read / Grep
  ↓
WorkspaceGuard
  ↓
当前真实文件
```

它不是 Semantic、Archive、Episodic 或 Skill 检索。

### 6.2 模型修改代码

模型结合当前代码和历史证据，决定使用数据库事务和行锁：

```python
with transaction.atomic():
    product = Product.objects.select_for_update().get(id=product_id)
    if product.stock <= 0:
        raise OutOfStockError()
    product.stock -= 1
    product.save(update_fields=["stock"])
```

调用：

```text
edit(path="src/orders/service.py", ...)
```

这同样不是记忆召回，而是 Tool Runtime 的受控文件修改。

### 6.3 模型精确读取Testing Skill

因为目录中已经显示 `testing`，模型调用：

```text
skill(action="read", name="testing")
```

获得完整测试规范后，先运行：

```text
pytest tests/test_orders.py -q
```

## 七、阶段三：大工具结果立即落盘

假设测试输出达到 22 KiB，超过当前 16 KiB Artifact 阈值。

完整 Tool Result 原本是：

```text
22 KiB测试日志
├─ 环境初始化
├─ 数据库迁移
├─ 146条测试过程
├─ 1条失败堆栈
└─ 最终统计
```

WorkingContext 不把这 22 KiB 全部继续放在每轮 Prompt 中，而是立即保存：

```text
.aster/context-artifacts/order-fix/
└─ bash-call-test-order-a81f....txt
```

当前 Tool 消息被替换成：

```text
[MiniClaw context artifact]
Tool: bash
Full result: .aster/context-artifacts/order-fix/bash-call-test-order-a81f....txt
UTF-8 bytes: 22528
SHA-256: ...

Preview:
日志头部……
... [artifact preview truncated] ...
日志尾部……
```

此时获取完整日志的方法是：

```text
read(path=".aster/context-artifacts/order-fix/bash-call-test-order-a81f....txt")
```

这时还不能把它理解为已经完成父子节点召回：

```text
刚生成的大Artifact
  ↓
当前消息中有路径和预览
  ↓
需要时按路径Read
```

等这条消息以后进入压缩归档，完整 Artifact 才会被加入 Archive Index，之后才能自动父子召回。

## 八、阶段四：上下文增长到 Soft Trigger

任务继续执行，经历多次读取、修改和测试后，当前上下文达到：

```text
82k Token
```

因为：

```text
80k < 82k <= 100k
```

进入 Soft Compaction。

假设这次历史主要是工具日志，确定性 Checkpoint 已经足够小，因此不需要调用摘要模型。

### 8.1 找到闭合切分点

系统优先保留完整回合，不会把一次 Tool Call 和对应 Tool Result 分到两边：

```text
归档侧
├─ 用户旧请求
├─ Assistant Tool Call
├─ Tool Result
└─ Assistant对结果的判断

保留侧
├─ 最近用户请求
├─ 最近Tool Call和结果
└─ 最近Assistant进度
```

### 8.2 旧工具结果落盘

归档侧仍然存在的小 Tool Result 也会被保存为 Artifact：

```text
.aster/context-artifacts/order-fix/
├─ read-call-service-....txt
├─ grep-call-reserve-....txt
└─ bash-call-target-tests-....txt
```

归档消息中的完整 Tool Result 会变成路径引用。

前面已经因为超过 16 KiB 而落盘的大 Tool Result 不会重复制品化；系统识别到 Artifact 标记后会继续复用原路径。

### 8.3 闭合历史完整保存为JSONL

系统把归档侧消息完整保存为：

```text
.aster/context-artifacts/order-fix/
└─ context-transcript-compaction-ab12....jsonl
```

里面仍然保持消息结构：

```json
{"role":"user","content":"修复订单重复扣库存……"}
{"role":"assistant","tool_calls":[...]}
{"role":"tool","content":"[MiniClaw context artifact]..."}
{"role":"assistant","content":"测试证明存在并发竞争……"}
```

这个 JSONL 是完整恢复源，但自动召回不会每次读取整个文件。

### 8.4 写入Archive Index

ArchiveMemoryIndex 会索引两类内容：

```text
1. 闭合历史中的User / Assistant / Tool消息
2. 消息引用的完整Tool Artifact
```

父节点定义为：

```text
一条完整历史消息
或
一个完整Tool Artifact
```

子节点是父节点切分出的约 1600 字符块。

因此以后既可以命中：

```text
Assistant当时为什么做这个决定
```

也可以命中：

```text
完整测试日志里的某段失败堆栈
```

### 8.5 生成确定性Checkpoint

代码根据已知结构提取：

```text
当前用户请求
读取过的文件
修改过的文件
可恢复Tool Artifact路径
完整Transcript Archive路径
前一次Checkpoint
```

生成：

```text
[MiniClaw Working Context Checkpoint]

当前请求：修复订单重复扣库存并运行测试。

已读取文件：
- src/orders/service.py
- tests/test_orders.py

已修改文件：
- src/orders/service.py

可恢复工具结果：
- bash/call-test: .aster/context-artifacts/order-fix/bash-call-test-order-....txt

完整历史：
- .aster/context-artifacts/order-fix/context-transcript-compaction-ab12....jsonl

近期未压缩消息紧随其后，并且优先级更高。
```

### 8.6 压缩后的活动上下文

Soft Compaction 提交后，活动 Prompt 从约 82k 下降到例如 28k：

```text
压缩前活动上下文
├─ 旧原始消息约54k
└─ 近期消息约28k

压缩后活动上下文
├─ 确定性Checkpoint
└─ 近期原文约28k
```

旧原文没有被删除，而是从“每轮都携带”变成“保存在磁盘并按需召回”。

## 九、阶段五：压缩后用户突然询问旧细节

用户接着问：

```text
之前那个并发测试里，两个Worker分别读到了多少库存？
```

Checkpoint 可能只写了“发现并发竞争”，并没有保存两个 Worker 的具体数值。

如果只有摘要，模型可能回答不知道。现在会自动走多路召回。

### 9.1 Working 提供当前状态

Working 直接告诉模型：

```text
当前正在修复订单重复扣库存。
service.py已经修改。
历史日志位于Artifact和Transcript Archive。
```

但没有具体库存数值。

### 9.2 Semantic 搜索

Semantic 可能返回：

```text
订单写入必须在事务中完成。
```

这对解释问题有帮助，但仍然没有 Worker 数值。

### 9.3 Episodic 搜索

Episodic 可能返回历史调查摘要：

```text
发生过并发写入问题。
```

它仍然没有完整日志细节。

### 9.4 Archive父子召回命中原始日志

查询中的关键词：

```text
并发测试 Worker 读取 库存
```

命中 Artifact 的 Chunk 1：

```text
worker-a read stock=1
worker-b read stock=1
```

系统返回同一父节点中的：

```text
Chunk 0：测试名称和环境
Chunk 1：两个Worker读取库存
Chunk 2：最终断言错误
```

模型因此获得完整局部证据：

```text
测试：test_two_workers_reserve_same_item
worker-a读到stock=1
worker-b也读到stock=1
最终出现两条reservation
```

### 9.5 模型做出回答

最终回答：

```text
两个Worker当时都读到了库存1。正因为两边都认为仍有库存，才分别创建了预留记录，最终reservation_count从预期的1变成了2。
```

这里答案真正来自：

```text
Archive中的原始Bash Artifact
```

不是来自：

```text
Checkpoint猜测
Semantic事实
Episode摘要
Skill流程
```

## 十二、阶段七：任务完成后完整轨迹变成什么

模型运行完整测试：

```text
pytest -q
```

结果：

```text
248 passed
exit_code=0
```

Goal Supervisor 验证：

```text
目标代码已修改
目标模块测试通过
完整回归测试通过
验证命令退出码为0
```

Goal 状态变成成功。

需要注意：Goal 状态不是通过记忆检索恢复的。它由 GoalStore 持久化并由外层监督器直接读取。

任务结束时，磁盘可能形成下面的结构：

```text
.aster/
├─ session.jsonl
│  ├─ 所有原始Message事件
│  ├─ Tool Call和Tool Result
│  ├─ 第一次Soft Compaction事件
│  └─ 第二次Hard Compaction事件
│
├─ goal.json
│  └─ Goal状态、验收条件和验证证据
│
├─ trace.jsonl
│  └─ 模型请求、Token、延迟、Tool Call、Compaction和Goal事件
│
├─ context-artifacts/
│  └─ order-fix/
│     ├─ bash-call-test-order-a81f....txt
│     ├─ read-call-service-....txt
│     ├─ grep-call-reserve-....txt
│     ├─ context-transcript-compaction-ab12....jsonl
│     └─ context-transcript-compaction-cd34....jsonl
│
├─ memory/
│  ├─ MEMORY.md
│  ├─ archive-index.jsonl
│  └─ episodes/
│     ├─ order-lock-investigation.md
│     └─ order-fix.md
│
└─ skills/
   └─ testing/
      └─ SKILL.md
```

### 12.1 session.jsonl 保存什么

它是当前 Session 的追加式事件账本。

压缩不会物理删除前面的原始消息，只会追加 Compaction 事件，说明恢复时应该使用哪个 Checkpoint 和从哪条消息开始保留近期原文。

### 12.2 context-artifacts 保存什么

它保存：

```text
超过阈值的大工具结果
压缩时落盘的旧工具结果
每次压缩产生的完整闭合历史JSONL
```

### 12.3 archive-index.jsonl 保存什么

它保存可检索的 Archive Chunk 记录及定位信息：

```text
session_id
source_kind
source_path
role
message_index
chunk_index
content
```

依靠这些字段，命中子块后才能恢复父节点和相邻块顺序。

### 12.4 MEMORY.md 保存什么

它只保存稳定事实。

用户明确说“记住项目统一使用 pytest”，因此可以写入：

```text
[project] 项目统一使用pytest执行测试。
```

临时失败日志、一次测试退出码和中间猜测不会写入 Semantic。

### 12.5 Episode 保存什么

任务结束后可以更新：

```markdown
# Session order-fix

## Goal
修复订单服务并发预留导致的重复扣库存。

## Latest Outcome
使用数据库事务和行锁完成修复，248项测试通过。
```

未来搜索“订单并发修复”时，先返回这个摘要预览；需要完整 Episode 时再按 Session ID 读取。

### 12.6 Skill 保存什么

`testing/SKILL.md` 不会因为本次任务执行而自动改写。

它仍然是一份可复用流程说明，下次模型看到测试任务时继续按名称读取。


模型据此选择：


```text

Procedural告诉模型“应该按什么流程做”
Working告诉模型“现在正在做什么”
```

## 十五、所有“拿信息的方法”最终对照表

| 信息类型 | 存储位置 | 自动还是主动 | 获取方法 | 是否父子节点 |
|---|---|---|---|---|
| 当前请求 | Working Context | 自动 | 直接注入 | 否 |
| 当前Checkpoint | Working Context | 自动 | 直接注入 | 否 |
| 近期原始消息 | Working Context | 自动 | 直接注入 | 否 |
| 稳定项目事实 | Semantic `MEMORY.md` | 自动或主动 | BM25＋向量＋RRF＋rerank | 否 |
| 压缩历史消息 | Archive Index | 自动或主动 | 子块检索→Top-5父节点→相邻块 | 是 |
| 旧Tool Result | Artifact＋Archive Index | 压缩前主动，压缩后可自动 | 路径Read或父子召回 | 压缩后是 |
| 大Tool Result | Artifact | 刚产生时主动 | 路径Read | 尚未归档时否 |
| 已归档的大Tool Result | Artifact＋Archive Index | 自动或主动 | 父子召回或路径Read | 是 |
| 完整闭合Transcript | JSONL Artifact | 主动 | 按路径Read | 文件本身否，索引消息是 |
| 历史任务概览 | Episodic Markdown | 自动 | BM25＋向量＋RRF＋rerank | 否 |
| 完整历史Episode | Episodic Markdown | 主动 | `episode_read(sessionId)` | 否 |
| Skill名称和描述 | Procedural目录 | 自动 | 全目录直接注入 | 否 |
| 完整Skill流程 | `SKILL.md` | 主动 | 按Skill名称精确读取 | 否 |
| Goal状态 | `goal.json` | 自动 | GoalStore直接读取 | 否，也不属于Memory检索 |
| Trace审计数据 | `trace.jsonl` | 分析时主动 | Trace分析器读取 | 否，也不属于Memory检索 |

## 十六、最简单的记忆口诀

```text
Working：现在正在做什么——直接看

Semantic：长期稳定事实是什么——混合搜事实

Archive：以前原文到底说了什么——父子搜原文
```
