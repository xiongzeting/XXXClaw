# MiniClaw 九个工具、审批、WorkspaceGuard 与 Docker 完整执行流程

> 本文以当前代码实现为准，重点回答四个问题：九个工具分别在哪里执行；哪些调用直接通过、需要审批或直接拒绝；八个宿主工具能做什么；Bash 在 Docker 中能做什么。

---

## 一、先记住最终结论

MiniClaw 当前注册了九个模型可调用工具：

```text
基础编码工具（5）
├─ read
├─ write
├─ edit
├─ grep
└─ bash

内部工具（4）
├─ memory
├─ skill
├─ goal
└─ goal_complete
```

它们的执行位置不是“全部经过 Runtime”，而是：

```text
8 个固定能力的 Python 工具在 MiniClaw 宿主进程内执行
├─ read / write / edit / grep
├─ memory / skill
└─ goal / goal_complete

1 个任意命令工具通过 ToolRuntime 进入 Docker
└─ bash
```

这里的“宿主进程内执行”不等于“能任意操作宿主机”。八个工具只能调用预先写好的 Python 方法：

- 文件工具只能访问 WorkspaceGuard 允许的路径。
- Memory 只能调用 Memory Store 定义的动作。
- Goal 只能进行状态机允许的转换。
- Skill 只能读取 Procedural Memory Store。
- 它们都不能接收任意 Shell 命令。

当前完整主流程比下面这句更完整：

```text
Executor → Preflight → Approval → WorkspaceGuard / Docker → 结束
```

准确流程是：

```text
模型产生 Tool Call
  ↓
ToolExecutor 查找工具
  ↓
参数预处理 + 递归 Schema 校验
  ↓
取消信号检查
  ↓
Project Instruction Preflight
  ↓
ApprovalGate Preflight
  ↓
工具自身能力边界
  ├─ 文件工具 → WorkspaceGuard → Host Workspace
  ├─ Bash → ToolRuntime → Docker → /workspace
  ├─ Memory → Memory Store
  ├─ Skill → Procedural Store
  └─ Goal → GoalStore / Verification / Judge
  ↓
ToolResult 标准化
  ↓
Goal / Instruction / Artifact Result Transforms
  ↓
输出上限与截断
  ↓
Trace 记录结果
  ↓
结果返回 AgentLoop，模型决定下一步
```

超时、取消和 Trace 不是一扇单独的门，而是贯穿这条链路的横向控制。

## 二、审批到底如何工作

### 2.1 经过 ApprovalGate 不等于询问用户

九个工具都会调用 `ApprovalGate.authorize()`，但 ApprovalGate 会先进行风险分类：

```text
没有 RiskFinding
  → 直接返回
  → 不产生审批请求

存在 RiskFinding
  → 检查项目白名单
  → 再根据 allow / ask / deny 策略处理
```

三种项目策略：

| 策略 | 发现风险后的行为 |
|---|---|
| `allow` | 自动允许，但仍记录审批事件 |
| `ask` | 暂停等待用户；超时自动拒绝 |
| `deny` | 不询问，直接拒绝风险操作 |

当前默认策略是 `ask`，默认审批等待上限是 300 秒。

如果项目白名单同时覆盖本次调用产生的全部风险能力，则直接放行。只覆盖其中一个风险不够。

### 2.2 “直接接受”是什么意思

直接接受只是表示 ApprovalGate 不阻止调用。它后面仍可能被以下环节拒绝：

- Schema 参数不合法。
- 项目指令需要刷新。
- WorkspaceGuard 阻止路径。
- Memory 冲突规则拒绝写入。
- Goal 状态机拒绝状态变化。
- Goal 完成证据不足。
- Docker 中命令不存在、越权、联网失败或退出码非零。
- 超时或用户取消。

### 2.3 “直接拒绝”有两种

第一种是审批策略拒绝：

```text
发现风险 + policy=deny
  → APPROVAL_REQUIRED

发现风险 + policy=ask + 用户拒绝
  → APPROVAL_DENIED

审批超时
  → APPROVAL_TIMEOUT

没有可用审批入口
  → APPROVAL_UNAVAILABLE

审批后 Tool Call 被改变
  → APPROVAL_CALL_CHANGED
```

第二种是硬安全边界拒绝。这类拒绝与用户是否同意无关，例如路径逃逸、受保护文件访问和 Goal 验收失败。

## 三、九个工具的审批总表

| 工具 | 常规调用 | 会触发审批的情况 | 不由审批决定的硬拒绝 |
|---|---|---|---|
| `read` | 直接通过 | 当前没有 | 工作区外、符号链接逃逸、敏感或受保护路径、目标不是文件 |
| `grep` | 直接通过 | 当前没有 | 工作区外、受保护搜索范围、路径不存在、`rg` 不可用 |
| `edit` | 普通项目文件直接通过 | 修改审批配置或敏感文件 | 工作区外、`.aster/**`、`.git/**`、密钥路径、文件不存在、文本匹配不唯一或重叠 |
| `write` | 新建普通文件直接通过 | 完整覆盖已有文件；修改审批配置或敏感文件 | 工作区外、`.aster/**`、`.git/**`、密钥路径、符号链接逃逸 |
| `bash` | 未命中风险规则时直接通过 | 删除、覆盖、联网、外部写入、危险 Git、系统修改、数据库破坏等 | Docker 网络/文件系统/资源限制；命令不存在；超时；取消 |
| `memory` | 查询操作直接通过 | `remember / replace / forget / conflict_resolve` | 参数不合法、记忆冲突、记录不存在、Store 规则失败 |
| `skill` | `list / read` 直接通过 | 当前没有 | Skill 或资源不存在、Procedural Store 拒绝 |
| `goal` | 全部 action 直接通过审批 | 当前没有 | 没有 Active Goal、缺少 summary、非法状态转换 |
| `goal_complete` | 直接通过审批 | 当前没有 | 没有新鲜成功验证、验收证据不完整、Judge 拒绝或失败关闭 |

需要注意：`edit` 修改普通已有代码不需要审批，但 `write` 完整覆盖普通已有文件会产生 `file-overwrite` 中风险。当前实现按工具语义区分，不是所有文件写入都会询问。

## 四、八个宿主工具分别能做什么

八个宿主工具是：

```text
read、write、edit、grep、memory、skill、goal、goal_complete
```

它们运行在 MiniClaw 的 Python 进程中，但每个工具只有固定能力，不存在可供模型填写的任意 `command` 字段。

### 4.1 read

合法示例：

```json
{"path":"src/app.py"}
```

```json
{"path":"README.md","offset":101,"limit":80}
```

可以：

- 读取工作区内普通文件。
- 读取 `.git/HEAD` 等少量非敏感 Git 元数据。
- 只读访问开放给模型的 `.aster/tool-output/**`。
- 只读访问开放给模型的 `.aster/context-artifacts/**`。
- 使用 `offset` 和 `limit` 分段读取大文件。

不能：

- 读取工作区外文件。
- 通过 `..`、绝对路径或符号链接逃逸到工作区外。
- 读取 `.env`、凭据、私钥及敏感目录。
- 读取 `.aster/goal.json`、Trace、内部 Memory 等私有状态。
- 读取 `.git/config` 或 Git 凭据。
- 将目录当作文件读取。

Read 默认只返回前 2000 行或 50KB；更大的内容需要继续分段读取。这是输出控制，不是 Token 上下文压缩。

### 4.2 grep

合法示例：

```json
{"pattern":"ToolExecutor","path":"src","glob":"*.py"}
```

可以：

- 在工作区普通文件中执行正则或字面量搜索。
- 设置 glob、大小写、上下文行和结果数量。
- 搜索隐藏文件，但仍遵守 `.gitignore`。
- 默认返回最多 100 个匹配。

不能：

- 搜索工作区之外。
- 搜索 `.aster/**`、`.git/**`、凭据及敏感路径。
- 借搜索结果绕过保护；每个结果路径还会再次检查。

Grep 在宿主机启动固定参数的 `rg` 子进程，但模型只能提供搜索模式和有限选项，不能将其变成任意 Shell 命令。

### 4.3 edit

合法示例：

```json
{
  "path":"src/app.py",
  "edits":[
    {"oldText":"debug = True","newText":"debug = False"}
  ]
}
```

可以：

- 修改工作区内已经存在的普通文件。
- 一次执行多个不重叠文本替换。
- 保留 UTF-8 BOM 和原有 CRLF/LF 换行风格。
- 使用原子写入和文件级串行队列降低半写入及并发覆盖风险。

不能：

- 新建不存在的文件。
- 修改工作区外路径、敏感文件、`.aster/**` 或 `.git/**`。
- 在 `oldText` 不唯一、不存在或多个 Edit 互相重叠时强行修改。

普通 Edit 当前不触发审批。修改 `.env` 等路径即使被风险分类为需要审批，也会在后续 WorkspaceGuard 处硬拒绝，因此“用户批准”不能突破路径边界。

### 4.4 write

合法示例：

```json
{"path":"docs/design.md","content":"# Design\n"}
```

可以：

- 在工作区创建普通文件。
- 自动创建普通父目录。
- 完整替换允许访问的普通文件。
- 使用原子写入避免留下半个文件。

审批行为：

- 新建普通文件：不审批。
- 覆盖已经存在的普通文件：`file-overwrite`，中风险。
- 修改 `.miniclaw/approval.json`：`approval-policy-change`，严重风险。
- 修改 `.env`、私钥等：`sensitive-file`，高风险。

不能：

- 写到工作区外。
- 写入 `.aster/**`、`.git/**`、敏感路径。
- 通过符号链接写到工作区外。

### 4.5 memory

Memory 是一个工具，其中包含多个 action。

直接通过的只读动作：

```text
read
search
conflict_list
archive_search
episode_list
episode_search
episode_read
```

会修改长期语义记忆、但不触发人工审批的 action：

| action | 作用 |
|---|---|
| `remember` | 新增长期语义记忆 |
| `replace` | 替换已有长期事实 |
| `forget` | 删除已有长期事实 |
| `conflict_resolve` | 按明确 resolution 处理冲突事实 |

Memory 工具不能：

- 访问任意宿主文件。
- 保存 Schema 没有定义的字段。
- 直接运行检索引擎之外的命令。
- 绕过冲突策略静默覆盖事实。

Memory 的所有 action 都不再弹出人工审批。写入安全由 Semantic Store 的 Secret/临时内容拒绝、重复检测和冲突处理负责；压缩归档、Working Context 和 Episode 的系统内部自动维护同样不会暂停 Goal 等待审批。

### 4.6 skill

Skill 当前只有：

```text
list
read
```

它只能读取 `.aster/skills` 对应的 Procedural Memory Store，不提供 create、write、delete 或 execute，因此没有审批风险分类。

### 4.7 goal

Goal action：

```text
status
checkpoint
waiting_for_user
failed
```

Goal 不触发人工审批，因为这些是监督器内部状态，而不是外部副作用。

它仍然会被 GoalStore 约束：

- `status` 只读取状态。
- 没有 Active Goal 时不能修改状态。
- `checkpoint / waiting_for_user / failed` 必须提供 summary。
- 状态转换必须符合六状态状态机。

因此 Goal 自动 checkpoint 和外层续跑不会要求用户蹲在电脑前反复确认。

### 4.8 goal_complete

`goal_complete` 不走 Human-in-the-loop 审批，但必须满足：

1. 存在 Active 或 Verifying Goal。
2. 之前运行过新鲜的真实 Bash 验证。
3. 验证退出码为 0。
4. 每条验收标准都有对应证据。
5. 开启独立 Judge 时，Judge 必须批准。
6. Judge 异常时失败关闭，不能将任务误标为完成。

这是“正确性验收”，不是“权限审批”。如果让 `goal_complete` 每次都等人工批准，Goal 自动监督就会失去意义。

## 五、WorkspaceGuard 究竟保护什么

WorkspaceGuard 是文件边界，不是人工审批器。

```text
ApprovalGate
  → 这件危险操作是否获得授权？

WorkspaceGuard
  → 这条路径是否属于工具能够访问的范围？
```

文件工具每次执行都会按访问类型调用：

```text
read  → resolve(access="read")
grep  → resolve(access="search")
edit  → resolve(access="write")
write → resolve(access="write")
```

主要保护内容：

- 将模型路径规范化为真实绝对路径。
- 确保真实路径仍位于工作区。
- 检查已有父目录，阻止利用新路径和符号链接逃逸。
- 动态发现运行期间新创建的敏感文件。
- 按 read、write、search、execute 区分权限。
- 保护 `.aster/**`、`.git/**`、`.env`、密钥、凭据和敏感目录。
- 仅对 Artifact 目录开放必要的只读访问。

WorkspaceGuard 的拒绝不应该被审批放开。例如用户即使批准 `edit .aster/goal.json`，Edit 执行时仍会被 WorkspaceGuard 拒绝。

## 六、Bash 的审批：什么命令直接通过

Bash 是唯一接受任意命令字符串的工具，因此必须同时使用风险分类和 Docker。

当前风险分类器没有命中规则时，ApprovalGate 会直接放行。常见例子：

```bash
pwd
ls
find . -maxdepth 2 -type f
rg "ToolExecutor" src
python -m pytest
python -m compileall src
ruff check src
git status
git diff
git log -5 --oneline
git add src/app.py
git commit -m "fix runtime"
```

这些命令是否最终成功，还取决于 Docker 镜像中是否安装对应程序、Git 身份是否配置，以及工作区内容是否满足要求。

需要特别注意：当前分类器不会因为“命令会修改文件”就全部审批。例如测试、格式化工具、代码生成器或者普通 Python 脚本可能修改 `/workspace`。风险分类主要覆盖明确的危险语法，不是完整的 Shell 语义证明器。

## 七、Bash 的审批：什么命令会产生风险

### 7.1 外部写入：critical

示例：

```bash
git push origin main
curl -X POST https://example.com/api -d @result.json
gh pr create
scp report.txt user@example:/tmp/
```

能力标签：`external-write`。

### 7.2 文件系统破坏：critical

示例：

```bash
rm -rf build
Remove-Item -Recurse output
del report.txt
python -c "import os; os.remove('a.txt')"
```

能力标签：`destructive-filesystem`。

如果用户批准，且路径位于可写 `/workspace`，删除会真实反映到宿主项目，因为当前使用 direct workspace。

### 7.3 Git 破坏：critical

示例：

```bash
git reset --hard HEAD~1
git clean -fd
git checkout -- src/app.py
git restore src/app.py
git push --force
git branch -D feature
git rebase main
```

能力标签：`destructive-git`。

### 7.4 数据库破坏：critical

示例：

```sql
DROP TABLE users
TRUNCATE TABLE events
DELETE FROM users
```

能力标签：`database-destruction`。

### 7.5 修改敏感文件：high

示例：

```bash
echo "TOKEN=x" > .env
Set-Content credentials.json $value
```

能力标签：`sensitive-file`。

即使审批通过，Docker 中对应受保护路径通常还会被空文件或空目录遮蔽，因此审批不保证命令一定能够完成。

### 7.6 系统修改：high

示例：

```bash
sudo apt install package
chmod -R 777 .
chown -R user .
taskkill /F /IM process.exe
systemctl stop service
```

能力标签：`system-change`。

### 7.7 网络访问：high

示例：

```bash
curl https://example.com/file
git clone https://github.com/example/repo
git fetch origin
pip install package
npm install package
Invoke-WebRequest https://example.com
```

能力标签：`network-access`。

默认 Docker 网络为 `none`。因此这类命令即使获得审批，通常仍会因为容器没有网络而失败。要真正联网还必须由项目配置将 Docker 网络改为 `bridge`。

### 7.8 Shell 直接覆盖文件：medium

示例：

```bash
echo value > config.txt
echo value >> config.txt
Set-Content config.txt value
Copy-Item source target
Move-Item source target
```

能力标签：`filesystem-overwrite`。

一条命令可以同时产生多个能力。例如：

```bash
curl -X POST https://example.com -d @data.json && rm data.json
```

会同时得到：

```text
external-write
network-access
destructive-filesystem
```

白名单必须覆盖全部能力才能自动执行。

## 八、什么 Bash 命令会被直接拒绝或最终失败

### 8.1 ApprovalGate 直接拒绝

当命令产生风险且策略为 `deny`，命令不会进入 Docker。

当策略为 `ask` 时，以下情况也不会进入 Docker：

- 用户拒绝。
- 300 秒内没有响应。
- CLI/飞书入口没有审批处理器。
- 批准后 Tool Call 内容发生变化。

### 8.2 Docker 边界导致失败

即使 ApprovalGate 放行，Docker 还具有以下限制：

```text
镜像：miniclaw-runtime:py311
工作目录：/workspace
网络：none（默认）
CPU：1
内存：1024MB
PID：256
根文件系统：只读
Linux capabilities：全部移除
no-new-privileges：开启
/tmp：128MB tmpfs，nosuid/nodev/noexec
最大文件描述符：1024
```

因此以下操作通常无法完成：

- 读取宿主机 `/workspace` 之外的真实文件。
- 写入容器系统目录，例如 `/usr`、`/etc`。
- 使用默认配置联网。
- 在容器中提升权限。
- 使用被移除 capability 的系统操作。
- 访问被 mask mount 遮蔽的 `.aster`、`.git` 敏感区域和密钥文件。
- 创建超过内存、PID、tmpfs 或文件描述符限制的负载。
- 使用镜像中不存在的命令。

### 8.3 命令超时和取消

- Bash 默认命令超时：120 秒。
- 模型指定的 Bash timeout 最大不能超过 900 秒。
- 超时后删除容器并终止 Docker 客户端进程树。
- 用户取消会贯穿 AgentLoop、ToolExecutor 和 Docker 进程。
- 取消结果在 Trace 中记为 cancelled，而不是普通失败。

### 8.4 Docker 保护不了什么

当前默认是：

```text
backend = docker
workspace_mode = direct
```

宿主项目会可写挂载到：

```text
Host Workspace ↔ Docker /workspace
```

所以 Docker 不能自动撤销以下操作：

- 删除 `/workspace` 中普通项目文件。
- 覆盖 `/workspace` 中普通项目文件。
- 修改工作区 Git 内容。
- 测试或脚本产生的真实项目副作用。

这也是 ApprovalGate 和 WorkspaceGuard 仍然必要的原因。Docker 主要保护宿主系统、网络、进程和敏感路径，不代表项目文件天然只读。

## 九、Project Instruction Preflight 负责什么

Project Instruction Preflight 不是安全沙箱，也不是 Human-in-the-loop。

它只针对：

```text
read / write / edit / grep
```

作用是根据目标路径激活对应层级的 `AGENTS.md` 等项目指令。

- Read/Grep：发现目标路径对应的新规则并为后续模型轮次激活。
- Write/Edit：如果即将修改的目标存在尚未注入的新规则，则先阻止本次修改，让模型读取刷新后的规则再重试。
- Bash、Memory、Goal、Skill：当前不进行目标文件级 Instruction Preflight。

因此 Preflight 回答的是：

> 模型在修改这个目标前，是否已经看到适用于该路径的项目规则？

它不回答：

> 这个操作危险不危险？路径会不会逃逸？命令是否应该进 Docker？

## 十、执行完成后还发生什么

工具返回后不是立即结束，还要执行三个 Result Transform：

### 10.1 Goal Transform

- 成功的 Edit/Write 会使旧的 Goal 验证失效。
- 带 `goal_verification=true` 的 Bash 会记录真实退出码和验证输出。

这样可以防止：

```text
先跑测试成功
  ↓
又修改代码
  ↓
仍拿旧测试结果宣称完成
```

### 10.2 Instruction Transform

Grep 返回的目标文件会激活对应路径规则，使下一轮系统指令包含新发现的局部 `AGENTS.md`。

### 10.3 Artifact Transform

大工具结果会被 Working Context 制品化，完整内容落盘，当前上下文只保留引用和有限预览。

### 10.4 输出上限

- ToolExecutor 最终通用上限：100,000 字符。
- Read/Grep/Bash 自身通常先按约 50KB 做专用截断。
- Docker 原始捕获上限默认 10MB，只保留尾部。
- Bash 大输出会保存到 `.aster/tool-output/**`，模型可通过 Read 只读查看。

### 10.5 Trace

Trace 记录：

- 工具名、参数和 Tool Call ID。
- 开始、结束和延迟。
- 成功、失败、阻止或取消。
- Approval 请求、能力集合和决定。
- Bash Runtime、退出码、Docker 容器信息。
- Goal 状态变化和验证结果。
- Artifact、Compaction 和模型指标。

## 十二、面试时最简洁的解释

可以这样回答：

> MiniClaw 向模型暴露九个工具。所有工具统一经过 ToolExecutor 的参数校验、项目指令预检和 ApprovalGate，但只有命中风险分类的调用才会真正要求审批。Read、Write、Edit、Grep 等固定能力工具运行在宿主 Python 进程中，每次文件访问必须经过操作感知的 WorkspaceGuard；Memory、Skill 和 Goal 则由各自 Store 与状态机限制能力。Bash 因为接受任意命令，额外通过 ToolRuntime 进入受限 Docker，容器采用只读根文件系统、默认断网、能力移除和 CPU/内存/PID 限制，同时将受保护路径遮蔽。工具结束后还会统一执行取消、错误归一化、输出制品化、Goal 验证失效与 Trace 记录。

如果面试官问“为什么不是所有写操作都审批”，可以回答：

> 审批保护的是权限扩张和高风险副作用，而不是机械判断有没有写入。普通项目修改属于用户下达编码任务时已经授权的能力；删除、凭据修改、外部上传、危险 Git 和长期记忆替换才需要额外确认。路径逃逸和内部状态篡改则属于不可审批的硬边界，直接由 WorkspaceGuard 拒绝。

## 十三、当前实现需要诚实说明的边界

1. Bash 风险识别基于多能力规则匹配，不是完整 Shell 语义分析。
2. `python script.py`、`make target` 等间接副作用不一定能从命令字符串识别。
3. 当前普通 Edit 不审批，但 Write 覆盖已有文件会审批，两者仍存在语义不完全一致。
4. Docker direct 模式会真实修改宿主工作区，不提供自动回滚。
5. Bash 不会对命令中的每个路径逐个调用 WorkspaceGuard；它依靠工作目录挂载、受保护路径遮蔽和 Docker 边界。
6. ToolExecutor 当前没有统一全工具超时配置；Bash 由 Runtime 单独提供 120 秒默认、900 秒硬上限，审批等待默认 300 秒。
7. Goal 状态变化不要求人工审批，这是为了保证外层监督器可以自动续跑；真正外部副作用仍由对应 Tool Call 的 ApprovalGate 决定。

这些边界并不否定当前安全链路，但说明它采用的是“固定能力工具 + 路径硬边界 + Bash 风险审批 + Docker 隔离”的分层防御，而不是声称能够静态理解所有程序行为。
