# Luna 效率复测：降了一半，为什么还超预算

分析日期：2026-09-06。读取本轮最终结果、实际发送给模型的请求、工具返回和冻结源码；未重跑模型，未修改运行产物或评分。

**结论：优化有效，但只解决了一部分浪费。6 题总 token 从 3,529,367 降到 1,730,372，减少 51.0%；仍有 5/6 超 token 预算。剩余主因是同题历史被重复召回、旧摘要与当前验收状态冲突、验证协议返工，以及大量小命令历史不断重发。直接生成摘要只占本轮总 token 的 4.1%，不是目前最大的直接开销。**

## 1. 最终结果与口径

15:27 启动，15:50 完成，2 路 Luna、6 题各一次，墙钟约 23.8 分钟。使用效率修复时冻结的版本；后续非效率修复不在本批内。

| 题目 | 原来 tokens | 本轮 tokens | 变化 | 预算 | 本轮结果验收 |
|---|---:|---:|---:|---:|---|
| 原子批量预留 | 1,176,232 | 169,253 | −85.6% | 130,000 | 新增提交故障检查未过 |
| 阶梯发票 | 890,612 | 323,281 | −63.7% | 240,000 | 税额舍入错误 |
| 脱敏优先级 | 600,890 | 374,092 | −37.7% | 240,000 | 通过 |
| 运费上限 | 498,101 | 445,486 | −10.6% | 240,000 | 漏规则、非法输入保护未过 |
| 配置迁移 | 234,090 | 300,089 | **+28.2%** | 130,000 | 修订版判定器通过 |
| 依赖锁撤回 | 129,442 | 118,171 | −8.7% | 240,000 | 提案 ID 输出错误 |

只有依赖锁题的效率全过，但它的结果没过；配置迁移、脱敏的结果过了，效率没过。因此五维全通过为 **0/6**，结果严格全通过为 **2/6**，效率严格全通过为 **1/6**。

报告显示的效率 **58.3%**、结果 **41.7%** 是子检查平均分，不能读成题目通过率。

本批效率检查实际只有 `total_tokens` 与 `tool_calls ≤ 65`，6 题工具次数都在限制内；**没有单独设置耗时判错项**。不能把“未出现时间失败”当成时间门槛通过。单题墙钟分别约 279、490、554、751、374、217 秒。没有步数暂停；网络波动按既定规则单独保留，不据此判能力失败。

原子预留增加了旧评分没有覆盖的故障检查，配置迁移修订了合法接口判定，因此不能把结果差异全部归因于 Agent 版本。每题仅一次，51.0% 是本次观测，不是稳定收益或单因素消融结论。

## 2. 已经改善了什么

| 题目 | read 次数（前→后） | 全部工具（前→后） | 主模型请求（前→后） | 成功压缩（前→后） |
|---|---:|---:|---:|---:|
| 阶梯发票 | 58→5 | 106→25 | 72→27 | 47→11 |
| 脱敏优先级 | 43→7 | 67→28 | 52→32 | 36→17 |
| 运费上限 | 31→5 | 67→40 | 45→40 | 23→21 |
| 原子预留 | 12→10 | 51→23 | 50→16 | 0→0 |
| 配置迁移 | 17→16 | 41→41 | 26→29 | 0→0 |

以前明显的“压缩后反复 read”减少了，本轮按成功 read 的相同参数、相同返回内容统计，额外重复为 0。这个口径不等于完全没有语义重复，例如同一代码可能同时存在于 write 参数、read 返回和记忆摘要。

运费题最能说明问题：read 已从 31 次降到 5 次，主模型请求却只从 45 次降到 40 次。节省下来的读取没有转化为同等幅度的收尾减少。

## 3. 第一优先：同一题被拆成不同会话身份，重复召回自己的历史

**通俗讲：压缩刚把旧记录收起来，检索又把它当成“别的会话的有用经验”搬回来。**

冻结版 `evaluation/runner.py` 使用同一个 `eval-sessions/shared/session.jsonl` 保存多轮对话，但每轮初始化 Assistant 时传入不同的 `session_id=case_id-turnN`。记忆层自动检索只排除与当前 `session_id` 完全相同的 episode；前面的 turn1、turn2 等因此仍可命中，还会继续带出对应 archive 原文。

实际发票 turn6 的请求中，一个检索块约 **16.3 KB**，包含 turn1、turn2、turn3 的 episode 和 archive。多个 episode 重复描述开头的只读检查、stub、旧目标和工具活动。当前用户消息、压缩摘要、已读片段之外，又带着这些重复资料。

按 Trace 现有的 UTF-8 字节数除以 4 估算，累计记忆注入占主请求输入组成：

| 题目 | 记忆注入估算 tokens | 占该题主请求输入估算 |
|---|---:|---:|
| 阶梯发票 | 108,578 | 35.7% |
| 脱敏优先级 | 132,536 | 36.5% |
| 运费上限 | 144,058 | 33.9% |

这是实际请求的来源估算，**不是供应商逐字段计费，也不代表这些 token 可以全部删除**。历史规则仍有用，问题是按错误的会话身份重复提供，而不是应该关闭历史记忆。

**建议：**共享对话使用稳定 conversation/session 身份，phase/run 单独标识；自动检索按同一对话的归属及已覆盖内容去重，显式跨会话任务继续按真实会话隔离。已在当前上下文或最新摘要覆盖的历史不再次自动注入；仍允许按需查原文。优先修身份与内容覆盖，不先推倒 BM25/BGE/RRF/重排。

证据：冻结版 `evaluation/runner.py:351,379`；`memory/manager.py:448,691`。发票请求事件 `e18d31f9-d1af-4bb8-ae0b-d9ef72c6d3c2`。

## 4. 第一优先：旧压缩摘要仍叫它继续检查，当前验收却已经通过

**通俗讲：一份清单说“检查通过了”，旁边另一份旧清单还说“没检查，继续检查”。**

运费 turn7 在检查点事件 `cbc02fdf-664d-4f04-a052-a9c205698bd9` 时，四项自验已经都有证明，`remaining=[]`。紧随其后的实际请求同时包含：

- 当前 TaskProgress：`Final task verification passed`，四项 verified。
- 旧压缩摘要：`Actual file contents and modification state still need inspection`，以及重新检查文件、解决旧断言、重新运行验证的 Next Steps。

旧摘要通过 system 角色注入；当前 TaskProgress 是 user 角色的运行记录。不能让旧模型笔记靠更高消息角色影响当前真实状态。旧摘要还出现把“生成压缩检查点”的工作指令当成 Current User Request 的内容。

这之后同阶段又发生 **7 次主模型请求，82,186 tokens**；脱敏 turn7 同样在自验清单齐全后还有 **4 次、47,952 tokens**。这些数字包含正常最终回复，不全是可省成本；但多次重新验证与格式返工确实存在，期间没有新的运费实现写入。

冻结版确定性摘要把完整 Previous Checkpoint 嵌入下一份，实际请求中最多嵌套 3 层；运费摘要最大约 **7.7 KB**。它保留了过期 Next Steps，而不只是当前状态。

**建议：**当前 TaskProgress 与文件版本作为任务状态依据，压缩摘要只保留历史证据和无法从结构化状态恢复的信息；旧待办依据验收项 ID/version 淘汰，不能无限套 Previous Checkpoint。模型摘要不要以 system 角色承载可执行任务指令。满足已登记验收后进入明确交付状态；文件或要求变化才重新开放对应验证。

这里的自验齐全不等于独立结果正确。运费题本身仍漏规则，不能通过强制结束掩盖真实错误；应同时补可信字段验收。

证据：下一请求 `b4863d06-efe5-48b2-b27d-a2e306ac70b4`；冻结版 `memory/working.py:642,649,576`。

## 5. 第一优先：验证协议反复写错，验证代码也越来越多

本轮共记录 **8 次验收协议错误**：运费 3、发票 2、配置迁移 2、原子预留 1。这些不等于工具进程退出失败，因此只看 `tool_errors` 会漏掉。

典型情况：

- 运费和发票使用 `python ... 1>&2`，把整份验收 JSON 发到了 stderr，stdout 为空，Runtime 无法读取。
- 配置迁移在 JSON 后面又输出 `SMOKE_OK`，整份 stdout 不再是一个 JSON 对象。
- 运费提供对象格式 evidence，旧协议只接受非空字符串；于是重新写一遍大脚本。
- 原子预留的验收编号格式错误，被协议拒绝。

运费在最后一次写入实现之后，同轮还有 **17 次主请求、188,771 tokens**。这包含合理测试和交付，不应全部叫浪费；但该阶段的大量活动都已转为验证脚本、错误预期修正、协议修正和重复确认。

**建议：**提供小而稳定的结构化验证输出适配器，把业务测试、命令日志和验收结果分开传递；不要每次让模型手拼数千字命令和包装 JSON。验证格式不合格应给明确修复位置，仅使对应证明失效。合法的结构化证据可按正式 schema 验证，而不是仅因不是字符串就要求重跑业务测试。测试程序本身和中间比较还需可信来源，不能为了省调用接受口头成功。

后续非效率修复已经补了部分逐字段比较和局部失效，但**没有解决以上全部问题**，也不在本批冻结版里。

## 6. 第二优先：许多“小片段”累积成巨大历史，单条阈值没有命中

**配置迁移是本轮唯一涨价题。**主模型请求 26→29，平均每次输入约 8,618→9,929 tokens，两个因素共同推动总量上涨 28.2%。

这题 29 次请求的 `raw_history_tokens` 与 `request_history_tokens` 均相同，投影没有缩短历史。冻结代码主要在单段约 8 KB 时才转换为引用；本题的 write、edit、bash 参数多为约 1～3 KB，单条不大，累计却很大。

配置迁移累计输入来源估算中，工具调用参数约 **122,539 tokens**，工具结果约 **63,299 tokens**。此前整段 write 代码、旧 edit 前后文本、多个长验证命令都持续存在。第二阶段 10 次主请求消耗 **168,411 tokens**，超过第一阶段 19 次请求的 **131,678 tokens**，说明后面每一步带的包袱更重。

**建议：**增加针对已闭合工具历史的总预算，考虑内容新旧、当前任务相关性和文件版本，按累计大小收缩，而不只看单条是否超过阈值。当前结果完整消费一次；旧成功命令保留短结论、文件版本及可回读原文。最近失败的有效诊断继续保留。

原子预留也有类似结构：第二阶段只用 7 次请求却消耗 110,302 tokens。缓存降低重复读取，并不会自动去掉旧写入参数和旧验证命令。

## 7. 次要因素及不能误判的部分

- **摘要生成直接成本较小。**总输入 1,644,982 tokens，占总量 95.1%；全部 compaction 请求 71,018 tokens，占总量 4.1%。即使只算主 Agent 请求，5 道超预算题仍超。应区分摘要生成本身、摘要重放和摘要过期引发的额外操作。
- **片段复用并非免费。**运费在 35/40 次主请求中自动注入已读片段，累计约 59 KB；脱敏约 61 KB、发票约 50 KB。它减少了 read，但仍应按当前所需文件和已覆盖内容挑选，不能每次都塞同一份公开验证文件。这是次要增量，不能单独解释几十万超支。
- **固定请求开销会随回合放大。**本轮主请求的系统与工具定义累计估算约 549k tokens，约占输入来源估算的 31.9%。这些功能有必要，不能盲删；最直接的降本仍是减少不必要请求，再考虑按角色开放工具及精简重复约束。
- **前六轮本来就要求接收长归档。**三道旧压缩题前六轮约各消耗 71k～73k tokens；turn7/8 才集中实施与核验。turn8 是原题要求的新输入与 CLI 复查，不能全部删掉当优化。
- **耗时主要在模型请求阶段。**按 Trace 的请求 duration 累计，约占各题 run 时长的 94.6%～99.3%；里面包含模型计算、传输与重试等待，不能把这些统称为纯推理时长。实际工具执行并非这批的主要墙钟开销。
- **不是把 VPN 波动改判成能力差。**保留本批 14 次请求重试和运费 1 次摘要网络错误的记录；各阶段最终均有交付，无步数暂停。输入重复和验收返工有独立 Trace 证据，不靠网络错误次数推断能力。
- **工具错误指标还有盲区。**有命令前面的 Python 已 AssertionError，后面的 smoke 成功让整条 shell 最终退出 0。配置迁移虽统计 `tool_errors=0`，不代表验证过程中没有错误。应在验证执行器中逐子进程记录退出码、可靠传播失败，不能用全文包含 error 单词判失败。

## 8. 结果错误说明：不能只追求更便宜的错误答案

- 发票旧的“免税变免费”不再是本次首个失败；现在是 50 分税基、7% 税率应半分向上为 4 分，实际使用向下取整得到 3 分。模型自己的测试也用了同样的向下取整预期。
- 运费漏了易碎费：2000g、remote、fragile 应为 1150 分，实际 1000 分；非法输入还会覆盖既有输出。代码与部分自验共同漏了规则。
- 依赖锁仍把 `V1` 输出为约束表达式，最终 ID 规则未满足。
- 原子预留在第一个文件替换后异常，状态成了库存 9、记录 0；这个新增独立检查拒绝了半次提交。

这些结果说明要修的是“当前要求、有效证据和交付状态如何对齐”。新增更多散落的自验或提示词，可能增加 token，却不补上独立正确性。

## 9. 建议执行顺序与验收

1. **稳定共享会话身份，阻止同题历史被当跨会话重复召回。**用离线实际请求检查覆盖内容去重，保留真正跨会话召回；不需要先换检索算法。
2. **消除过期摘要待办与当前验收的冲突，明确进入交付阶段。**已通过项、文件版本、要求版本只有一套当前状态；避免带着三层旧计划继续验收。
3. **固定验证输出通路，并逐子进程记录失败。**用真实成功/失败/日志混杂/部分验证场景测试，减少格式错误导致的重跑；不能放松字段与安全验收。
4. **对已闭合工具历史设置总预算。**重点覆盖许多小 write/edit/bash 的累积，不只测试单个超大输出。追踪请求实际缩短量与可回读能力。
5. **再调片段复用与固定工具开销。**先用当前需要的文件范围过滤，观察真实正确率与成本，再决定进一步精简。

验证先用本批冻结 Trace 做离线请求投影和状态回放，不调用模型；随后新冻结一版，优先少量复测运费、配置迁移及一题正确的脱敏对照。维持原题、结果标准及预算。离线估算节省不等于真实模型节省，应分别报告，不能把修改后会通过当成既成事实。
