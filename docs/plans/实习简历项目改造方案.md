## 1. 我的结论：保留底座，重构任务交付与验证链路，收缩功能战线

MiniClaw 已经超过“调用模型 API＋几个工具”的入门项目。原生 SSE、取消传播、工具协议、工作区边界、Goal 状态、记忆检索、Trace 和 Eval 都有实际实现，还有相当数量的离线测试。这些值得保留。

但以高水平实习简历为目标，当前最大的短板是：**功能清单很长，能独立证明真实编码能力、可靠性和成本收益的证据还不够集中；几个跨模块边界还存在会破坏可信度的问题。** 继续增加模型、聊天入口、Benchmark 名称，优先级低于修复这些问题。

我最推荐的项目定位是：

> **MiniClaw：面向真实代码仓库的可恢复 Coding Agent，在隔离工作区完成修改与验证，交付可审查补丁，并通过可复现实验衡量成功率、可靠性和成本。**

简历只保留三条技术主线：

1. **可靠执行**：流式模型协议、任务状态、取消、故障恢复、资源预算。
2. **可信交付**：独立工作区、补丁审查、绑定代码版本的验证证据。
3. **效果证据**：真实 Coding 任务、成对消融、Trace 到回归用例。

长期记忆是可以深挖的专项，但要回答“它是否让代码维护任务更成功或更便宜”，再决定是否占据简历核心篇幅。

**不建议全量推倒重写，也不建议为简历更换技术栈。** 推荐保留 `llm → agent → coding_agent` 的依赖方向，较大地重构 Task、Workspace、Verification、持久状态和评测协议；按实验结果删掉没有收益的复杂机制。

本文默认目标岗位是 **AI 应用 / Agent 工程实习**，其次适用于 **Python 后端 / AI Infra 实习**。如果投模型算法岗，现有工程项目不能替代训练、算法和严谨实验经历；可以把“代码版本感知记忆与成本控制”发展成研究型子方向，但不要包装成模型训练项目。

## 5. P0：先修复会损害项目可信度的问题

### P0-01：Windows 进程存活检测可能终止被检测进程

**证据**：`runtime/state.py` 的 `_process_alive` 在非当前 PID 分支调用 `os.kill(process_id, 0)`；`recover_interrupted` 用它判断上一运行是否仍存在。

POSIX 下它常被用作存在性检查，但 Python 官方文档明确说明：Windows 下除 `CTRL_C_EVENT` 与 `CTRL_BREAK_EVENT` 外，其他信号值会调用 `TerminateProcess`。因此，在另一个任务进程仍存活或 PID 被重用时，恢复检查可能终止那个进程。当前进程有提前返回分支，不能夸大成“每次恢复必然杀进程”。

**修改方法**：区分平台。Windows 使用无副作用的进程查询 API，或明确引入 `psutil`；进程身份同时保存 PID 与创建时间，避免 PID 重用。权限不足应返回“未知”，不要直接判死后接管。

**验收**：创建受控子进程，分别检查存活、退出、身份不匹配、权限异常，确认检测前后子进程状态不被改变；Windows 与 Linux 都进 CI。测试必须只管理测试自己创建的进程。

**面试价值**：这是一个具体的跨平台生产边界问题，能展示你如何从语义差异找到 bug，并建立回归。

参考：[Python 3.11 `os.kill` 文档](https://docs.python.org/3.11/library/os.html#os.kill)。本次已通过 HTTPS 核对原文。

### P0-02：让“验证通过”绑定当前代码，而不是一段成功输出

**已确认的问题**：

- `assistant/coding.py:456` 附近只对 `edit` / `write` 更新验证状态。普通 `bash` 也能修改源码，却可能保留旧 `last_verification`；这一绕过已离线复现。
- 默认独立 Judge 关闭。通用 criterion 主要检查名称与非空证据文本，特殊客观检查集中在覆盖率；一次退出码为 0 的命令不等于需求完成。
- 关键状态更新处于可降级的结果转换链中，转换失败可能被记录后继续返回成功。不能让验证失效更新与附加日志享有相同的失败语义。

**推荐设计**：

1. 引入结构化 `VerificationResult`：任务 ID、验收项 ID、起始版本、代码内容指纹、验证命令、退出码、原始日志引用、时间、执行环境、评判器版本。
2. 所有可能改变工作区的操作都推进 mutation revision。不能可靠判定 Bash 是否只读时，先保守地使验证失效。
3. 最终完成门禁再检查当前工作区指纹；这也覆盖外部编辑器和另一进程的修改。只靠工具事件计数不够。
4. 验证命令及隐藏测试由用户/任务定义/独立评测环境提供。Agent 可以建议命令，但不能只靠自己生成的“通过证据”完成任务。
5. Agent 自建测试作为补充；补丁外的独立 grader 在干净环境执行，不能允许 Agent 修改唯一判定依据来获得通过。
6. 状态落盘失败或副作用无法确认时进入 `uncertain` / `needs_review`，不允许显示 `completed`。

**建议边界**：不追求自动证明任意自然语言需求。明确区分“机器检查通过”“需要人工确认的验收项”和“模型建议已完成”。Judge 可以辅助检查描述性条件，不能替代独立测试。

**验收**：先验证后经 Bash 改坏代码、外部进程改文件、验证时并发修改、命令成功但需求未完成、删除测试骗通过、验证状态写入失败，均不能获得可信完成状态。每个漏洞都要有负向回归。

### P0-03：个人身份、共享会话、任务工作区必须分别隔离

**证据**：飞书 `router.py:289` 命中缓存时直接复用 assistant；`:313` 创建时绑定首位发言者 user scope。群线程能多人共用，而记忆管理器依赖该固定身份选择个人存储。因此后续发言者可能沿用首位发言者的个人记忆范围。

另外，飞书默认最多 8 个并发会话；默认 Docker＋Direct 让不同会话使用同一源工作区。文件级 `write/edit` 锁不等于任务隔离，也不能隔离 Bash 修改和测试。

**两个合理方案，优先选 A 先交付**：

| 方案 | 改法 | 适用情况 |
|---|---|---|
| A：明确单用户自托管 | 限定可访问用户；群共享线程禁用个人记忆；同源 Direct 写任务互斥 | 实习作品快速收口，减少错误承诺 |
| B：支持多人共享 | 当前 actor 随每次 turn 传入；分离个人与共享记忆；每任务独立工作区 | 远程协作确有需求且有时间验证 |

两种方案都建议默认独立 Snapshot / Git worktree。Git worktree 适合干净版本仓库；对已有未提交修改，要么建立包含当前内容的隔离快照，要么明确选择基准，不能静默丢掉脏工作区。

**验收**：A、B 同一线程交替发言不串个人偏好；B 的事实不会落入 A 的目录；两任务同时改同一文件和运行测试互不污染；取消一个任务不影响另一个；同源 Direct 模式第二个写任务应排队或拒绝。

**不要宣传**：“会话目录不同”不等于多租户隔离，“用了 Docker”不等于文件工具都在容器里。

## 6. P1：形成能打动面试官的完整项目

### P1-01：从“能调用编辑工具”升级为“交付可审查代码变更”

**这应是最优先补齐的产品能力。** 当前有编码工具、Snapshot、Goal 和 Trace，Code-Compression 评测侧也已有工作区、补丁生成与 grader 链路；CLI 缺完整 session/patch 交付流程。优先提取可复用能力，不另写一套补丁实现。

新增一个轻量 Task 契约，统一 `task_id`、来源、actor、session、工作区基准、预算、状态、验证结果、产物和 Trace 引用。先用现有 Python 包组合，不拆微服务。

建议用户流程：

```text
创建任务与验收条件
  → 捕获基准版本及当前未提交变更
  → 建立独立工作区
  → Agent 定位、修改、测试
  → 独立验证当前补丁
  → 展示 diff、测试证据、耗时与失败说明
  → 导出 patch
  → 用户明确选择后再应用到原工作区
```

建议 CLI 表面可以是 `run`、`sessions list/resume`、`diff`、`export-patch`、`apply`；这是拟议接口，当前并不存在完整实现。优先统一行为和退出码，不纠结命令名称。

**必须处理**：源工作区在任务执行期间又发生修改；补丁冲突；未跟踪文件；删除/重命名；受保护路径；中途取消；验证后再改代码。Apply 之前重新检查基准，不直接覆盖新变更。

**验收产物**：3 个真实仓库任务，每个有基准 commit、原始失败、最终补丁、独立测试、完整运行记录和一条复现命令。招聘者可以拿一个小仓库真实试用。

### P1-02：用真实 Coding 任务替换“主要靠记忆问答证明 Coding Agent”

22 条工程回归继续保留。它们用于守住已知能力，不承担主榜单成绩。

主基准从真实 Issue / 仓库维护任务中选择：跨文件修复、接口变更、回归修复、配置迁移、带测试的小功能。先做 5–10 个高质量任务把协议跑通，再扩到 30–50 个任务作为起点。预算足够时扩大样本，而不是凑任务数。

可以使用 SWE-bench 等公开 Coding 基准的合适子集，也可以使用固定版本的开源真实任务。项目的 `code_compression.py` 已有原生 Coding 运行、`capture_patch`、预测文件生成和 `grade_patch` 官方 grader 接入，另有 SWE-bench harness 的 Windows 换行兼容包装；本地也存在真实成功补丁。**优先审计并复用已有链路，补齐未评分任务、同任务配对实验、冻结主基准与统一报告，避免重复造轮子。** 已检查的 9 份任务汇总并不是完整配对消融，不能从其中少数完成评分的案例推断整套成功率。

**每个任务应具备**：固定 repo/base commit、可复现环境、任务描述、Agent 看不到的最终判定依据、补丁应用规则、独立测试、超时和成本预算、标准化失败原因。

**划分原则**：按仓库/Issue 家族切分；同一问题的不同表述或攻击载体不能跨开发/保留集。公开数据也可能已被模型训练见过，因此“开发者未曝光”与“模型从未见过”必须区分。

**基线**：相同模型＋相同工具的精简 Agent 是首要基线。再选一个配置固定的公开 Agent 作为外部参照，写清版本、预算和工具差异。不能只和一个明显被削弱的基线比。

**验收**：任何 resolved 结果都能定位到补丁、原始测试输出和独立 oracle；失败要区分基础设施错误、模型失败、工具失败、验证失败、预算耗尽。没有 oracle 的案例只做 demo，不计主成功率。

### P1-03：做成对消融，然后让数据决定复杂度

先比较少数能解释的实验组，不立即铺开所有组合：

| Arm | 启用机制 | 回答的问题 |
|---|---|---|
| A：精简基线 | 同模型、工具、权限、预算；最小上下文管理 | 基本 Agent 能做到什么 |
| B：A＋Artifact/压缩 | 大工具输出恢复、必要的上下文压缩 | 成本变化来自哪里，有无信息损失 |
| C：B＋跨会话记忆 | 可追溯的历史证据与失效处理 | 历史维护任务是否更成功或更省定位成本 |
| D：C＋精排 | 混合召回后可选 Cross-Encoder | 精排收益是否覆盖延迟、依赖和维护成本 |

这是分阶段对比，不足以单独识别所有交互效应。如果要精确归因某个组件，再围绕该组件做“只切换这一项”的配对实验。

**实验约束**：相同题目、模型、任务预算、权限、grader；随机化组别执行顺序；区分冷/热缓存；跨会话任务只给各组按协议允许的历史。不能在 A 没有历史信息、C 获得额外答案的情况下把差异叫检索算法收益。

**至少报告**：成功率及区间、逐任务配对差异、每次尝试成本、总花费/成功任务数、输入输出 Token、真实延迟分布、检索开销、失败类别。重复运行同一题不当作多个独立问题。

**机制触发证明**：记录 L1/L2/L3 是否触发、归档是否读回、注入证据是否被用到、模型后端是否真实启用。没有触发压缩的任务不能用于证明压缩策略优越。

**删减门槛**：若 CE 或某组启发式规则没有稳定增益，默认关闭或移入实验配置；如果质量下降，只能报告质量/成本权衡，不能用 Token 下降遮住失败。

### P1-04：统一资源预算、大文件 I/O 与取消语义

**当前缺口**：

- Goal 的次数、时间和费用判断主要在 attempt 前后；单个 attempt 内可以跑很多模型/工具轮次，因此是软边界。
- Host executor 使用 `process.communicate()` 全量缓冲输出；Docker 有 capture 上限。模型可见输出截断不等于宿主内存占用有界。
- `read` 即使给 offset/limit 仍先读完整文件。大文件只返回 50KB，不代表只读了 50KB。
- `asyncio.to_thread` 取消不会停止工作线程；原子写清理可能先于线程结束，已复现临时文件残留。

**修改方法**：增加每次模型/工具边界都可查询的 BudgetController，统一 deadline、Token 预算、单输出上限、进程数量、磁盘与产物配额。费用只能在供应商信息与预估范围内控制，要标明估算和未知成本。

Host 输出按块读取并滚动落盘，保留有界尾部；文本文件支持流式行读取，二进制/异常大文件先检查；原子写的后台任务必须由生命周期管理器持有，在取消后等待安全清理点或登记待清理产物。

**验收**：大输出子进程不会随输出量线性占满内存；取消后不再启动后续工具；关闭任务后子进程和临时资源得到回收；预算耗尽有稳定终态和原因。对费用超调报告实测上界，不承诺无法控制的绝对账单上限。

### P1-05：从“有 JSON 状态文件”升级为“定义清楚的恢复语义”

现有 run-state、Goal、transcript 和 Trace 是好底座。下一步要解决的是：文件修改、工具结果和状态落盘之间的崩溃窗口，而不是再加一个状态文件。

**建议状态语义**：任务执行、工具准备、执行中、结果已确认、待验证、完成、失败、取消、未知副作用。进程死亡时不能默认重放最后一个写操作。

**具体改法**：

1. 为工具操作建立稳定 operation ID，保存准备记录、参数摘要、工作区 revision、结果引用和恢复策略。
2. 只读操作可重试；可验证文件写入先核查结果再决定；不可判定副作用进入人工审查。幂等 ID 并不能让任意 Shell 天然幂等。
3. 增加任务/工作区租约，防止两个进程同时恢复同一任务。记录进程创建时间，不能只依赖 PID。
4. `MemoryFileLock` 当前按文件年龄超过 30 秒就删除，没有 owner 生存与令牌校验；慢操作时有错误接管风险。用可靠 OS 文件锁或事务存储替代，或者至少补 ownership、租约和释放验证。
5. 可将 Task、operation、outbox 元数据集中到 SQLite 事务中；transcript、Trace 和大日志保留追加文件/Artifact。迁移收益是原子状态变更，不是“用了数据库更高级”。
6. 恢复后重新核对 workspace 与验证指纹。状态显示“模型回复完成”不能替代任务真正完成。

**验收**：在“写文件后、结果落盘前”“收到模型回复后、工具开始前”“验证后、完成前”强制中断；重启后不重复副作用、不丢失已知变更、不伪造完成。增加两进程竞争恢复、锁持有超时、PID 重用的受控测试。

### P1-06：重构要围绕不变量，不能只把大文件切碎

保留通用 `AgentLoop` 和 provider 抽象。将 `CodingAssistant` 留作组合入口，把执行流程交给清楚的协作者。

推荐分离：TaskCoordinator、WorkspaceSession、VerificationService、BudgetController、MemoryContextProvider、RunEventSink。优先用现有接口与普通 dataclass，不引入庞大依赖注入框架。

**最关键的一刀**：把必须成功的状态维护与可降级观察分开。当前 `result_transforms` 同时处理验证状态、指令和 memory，`ToolExecutor` 捕获转换异常后继续返回结果。应明确：

| 类别 | 示例 | 失败时行为 |
|---|---|---|
| 执行前必须满足 | 工作区授权、参数校验、指令刷新 | 不执行副作用 |
| 执行后必须确认 | 变更 revision、操作结果、验证失效 | 标记 uncertain，阻止完成与盲目重试 |
| 可降级附加服务 | 部分展示统计、可选检索精排 | 标记降级，按策略继续 |

注意：不是所有 Trace 都可以丢。如果 Trace 被当作发布结果和关键操作的唯一证据，就必须有独立的持久审计记录，不能仅靠 best-effort 日志。

**验收**：为每个关键边界注入失败，证明不变量仍成立；架构测试检查绝对和相对导入，避免只匹配绝对模块名。重构前后同一 fixture 的工具决策、状态和交付行为保持一致，除非是明确修复。

### P1-07：长期记忆转向代码版本和证据来源

当前检索很丰富，但通用文本问答的启发式优化未必是 Coding 项目的最佳投入。

**第一步：代码事实版本化。** 增加 repo ID、commit、文件内容 hash、symbol、证据位置、观察工具、验证结果、有效范围和状态。当前 evidence 结构没有完整承载这些字段。用户偏好、历史观察、当前代码事实与“测试已通过”使用不同失效规则。

**第二步：来源约束。** 自动蒸馏目前校验 exact quote，但引用来自混合 user/assistant/tool 文本；“文本里出现过”不等于“结论有支持”。引用绑定具体消息 ID、role 和原文跨度；偏好需用户确认，环境事实来自实际观察，成功流程绑定验证。助手猜测不能直接升级为可信经验。

**第三步：优化检索，但先测。** 当前 ANN 只是稠密召回的一部分；scope 文本/key、词法统计和 BM25 仍会遍历，不能宣传整个系统已变为次线性。对 1k/10k/100k 文档测冷启动、增量更新、热查询、内存和磁盘；再决定倒排索引、增量统计或分区索引是否必要。

**第四步：明确后端与缓存身份。** 缺模型可降级有利于产品使用，但 benchmark strict 模式必须要求对应组件实际启用。索引身份加入模型 revision/权重摘要、编码配置、schema 与分词版本，避免同名权重命中旧向量。

**验收**：重命名函数、删除配置、跨 commit 更新事实后不会继续盲用旧记忆；不可信工具输出不会把恶意指令或无依据结论写成稳定事实；记录 stale-memory 命中率、错误引用率、重复定位开销和跨会话任务成功率。

**小改路线**：先做路径＋文件 hash＋证据失效，关闭复杂自动蒸馏。**大改路线**：在明确收益后再做结构化事实、符号范围和增量索引。不要一开始就上图数据库。

### P1-08：Trace → Eval 需要工作区和判定依据

当前 `create_eval_case` 已能生成失败签名与模型边界重放，但实现自己也说明：成为完整任务正确性评测之前还要添加 workspace fixture 和确定性检查。这应保留为“候选用例提取”，不能宣传完全自动生成完整回归。

建议固定流程：

```text
真实失败 Trace
  → 脱敏和失败聚类
  → 最小工作区 fixture
  → 人工确认预期与独立 oracle
  → 旧版本复现
  → 修复版本通过
  → 纳入回归并记录来源
```

优先收集自己的真实使用：错误完成、取消残留、恢复冲突、记忆过期、规则不生效、补丁应用失败。每个案例保存原问题、根因、修复、回归、影响范围。

Trace 导出要区分本地完整记录与可公开证据，现有正则脱敏不能保证任意业务数据都可直接发布。增加保留期限和导出预览即可，不必扩成独立合规平台。

**验收**：至少 5 类真实失败能定位到旧版复现、修复版结果与脱敏证据；不能只是“从失败日志提取了一个 JSON”。

### P1-09：真实运行展示比继续美化架构图更重要

当前 `frontend` 是 SVG 架构查看器，服务端是静态文件服务器；它不是 Coding 工作台。保留它作为架构说明，停止将其当核心产品前端优化。

**推荐小版本**：优先复用现有 HTML Dashboard，增加单次任务页：目标、时间线、变更 diff、验证命令与原始输出、审批、取消/恢复、Token/成本、失败原因。先读已生成的脱敏 Task/Trace，不必立刻做实时 Web 服务。

**有余力的大版本**：轻量本地任务工作台，只做提交、流式进度、diff、审批、取消、恢复。避免同时做账号系统、在线 IDE、团队管理和复杂权限。

首页控制在 90 秒可读：一句定位、三个亮点、30–60 秒演示、3 步启动、一张带版本的结果表、已知限制和文档入口。将 33 份根目录 Markdown 中的历史讲解迁入 docs 的主题导航/历史记录，保留当前实现的唯一说明入口。

**五分钟面试演示**：真实失败测试 → Agent 定位与修改 → diff 与验证 → 取消或模拟中断 → 恢复 → 查看 Trace 与相关 regression。准备已录制备用视频和离线 replay，清楚注明 replay，不用录制内容冒充现场生成。

**验收**：不了解项目的人能够在 10 分钟左右按文档运行离线示例；面试官能从结果点到具体补丁和验证证据；演示不依赖临时修文件、隐含环境或个人目录。

### P1-10：飞书做一个可靠的可选入口，不另造平台

如果时间有限，把它界定为单用户远程发起/通知入口，身份和并发问题修完即可。若作为正式亮点，则补下列跨边界能力：

- 发送重试复用稳定的远端幂等键。当前传输每次生成随机 UUID；持久 outbox 只提供进程内重试与成功记录去重。
- 启动扫描待投递项；明确 transient/permanent 失败；不可恢复项进入可查看的失败队列。
- 测试服务端已接收但本地超时、发送后落盘前退出等窗口。对外说明实际 at-least-once / 去重语义，不能承诺任意情况下 exactly-once。
- 仅任务 owner 或明确授权角色可以取消；共享会话权限先简单化。
- 为队列和 assistant 缓存增加总量限制、闲置回收；多个进程不应依赖当前仅在本实例内判断的 inbox claim。
- 如承诺实时进度，节流更新步骤和审批状态；现有飞书不是模型 Token 实时输出。产物需上传或提供真正可访问的交付方式，服务器本地路径不是远程文件交付。

**验收**：重启后待投递结果可恢复；远端成功但本地状态未知时不会无界重复；任务执行与消息投递状态分离；所有保证与实现一致。

### P1 横向要求：安全限制必须由执行边界兜底

这一项与 P0-03、P1-01/04 同步实施，不另起“安全平台”。

本次已复现：一个通过 Python 解释器写文件的命令字符串没有命中风险规则，即使设置 `deny` 也被放行。准确结论是 **deny 拒绝已识别风险；正则没有能力穷举任意 Shell 的副作用**。不应通过不断增加命令正则来声称解决任意代码执行安全。

建议明确三种运行模式：

| 模式 | 保证和使用前提 |
|---|---|
| 默认受限任务 | 独立工作区；最小挂载；网络与资源由执行环境限制；结果通过补丁交付 |
| 受控 Direct | 明确任务互斥和真实工作区副作用；适合本人信任的项目 |
| Host 调试 | 任意命令具有宿主用户权限；审批是辅助，不宣称沙箱隔离 |

当前只有 Bash 进入 Docker，文件工具运行在宿主并受 WorkspaceGuard 限制。文档已经部分说明这一点，简历与演示也要保持一致。

若未来要承接不可信多人仓库，把所有写操作统一放进一个可强制约束的工作区执行服务，并复查 symlink、TOCTOU、挂载和运行身份。当前 Dockerfile 没有设置非 root 用户，执行参数也未显式指定用户；公开环境需验证生成文件所有权和最小权限。原子替换也应验证 Linux 可执行位等元数据是否保留。

安全实验同时报告正常任务成功率和攻击成功率；把所有写操作都拒绝而得到“零攻击成功”没有实用意义。未知命令、解释器、子进程、文件内容中的提示注入、路径跳转都应在受控 fixture 中测试。

## 7. P2：哪些新功能值得加，什么时候才加

### 7.1 Repository Map / 符号检索：有条件推荐

**触发条件**：真实 Coding 基准显示主要失败来自定位不到正确文件、跨文件调用关系或改错接口，而不是模型本身不会修。

先做文件树、符号定义/引用、路径与错误码精确匹配、受预算控制的局部上下文。可以用 Tree-sitter 或语言服务器，但先选项目最常用的一种语言，不直接支持十几种语言。

**验收**：定位正确文件的比例、修改前搜索轮数、注入上下文 Token、最终任务成功率发生可测变化。只有检索指标改善、任务结果没变时，不夸大成编码能力提升。

### 7.2 受控并行 / 多 Agent：有条件推荐

**触发条件**：任务确实存在可独立的仓库调查、方案审查或测试诊断，且单 Agent 基线已经稳定。

第一版只允许只读调查并行；写入仍由一个执行者管理。另一种合理扩展是让独立验证者执行固定验收。不要先做自由分工的 Agent 群、自动角色社会或无限互相反思。

限制子任务数量、总预算、上下文和超时；结果必须带证据。若多个执行者需要写，必须各有独立工作区，并解决冲突和验证失效。

**验收**：相同总预算下，相比单 Agent，在哪些任务上成功率或时间更好；报告协调开销与冲突率。若只是花两倍 Token 获得同等结果，不作为核心亮点。

### 7.3 标准工具互通：可选，不以协议数量作为成果

当确有外部工具需求时，再增加标准化工具接入（例如 MCP 适配层）。复用 ToolManager 的 schema、审批、超时、取消和 Trace，不让外部工具绕过边界。

验收关注协议兼容、权限最小化、工具定义变更、连接中断与幂等，而不是“支持某协议”四个字。当前项目不需要为了简历再造插件市场。

### 7.4 规模化存储与服务：只在测出瓶颈后做

单机自托管优先用 SQLite、文件锁、任务租约和明确队列。只有并发、容量或跨机部署需求被测出后，再讨论服务拆分和外部数据库。

不建议现在引入 Redis、Kafka、Kubernetes、分布式向量库、全套 OpenTelemetry 后端。可以让事件格式方便后续导出，但不要让基础设施掩盖 Agent 的核心问题。

### 7.5 模型优化或训练：研究方向的另一个项目阶段

先冻结数据和可靠基线，再讨论路由、蒸馏或微调。如果没有足够独立数据、计算预算与对照，仅增加一个训练脚本不能使项目成为算法项目。

更适合当前阶段的研究问题是：**历史代码证据何时失效、哪些记忆值得保留、在给定上下文预算下如何选择证据。** 可以形成一个定义清楚、可消融的小论文式实验。

## 8. P3：明确删除、降级或冻结什么

这里的“删除”指未来经过版本归档后从默认产品与主展示中移出；本次没有执行任何删除。

| 项目 | 建议 | 原因 |
|---|---|---|
| Slack、微信、更多聊天适配器 | 冻结 | 不增加主编码链路深度，增加配置和投递维护 |
| 完整在线 IDE、多租户 SaaS、账号与团队平台 | 冻结 | 一名实习候选人难同时证明所有承诺 |
| 架构 SVG 的额外交互与装饰 | 保留现有，停止主投入 | 当前更需要真实任务证据 |
| 多个 Benchmark 的等权维护 | 主线保留 1 个 Coding、1 个记忆诊断、1 个安全、现有回归；其他移 experiments | 适配器数量不等于能力证据 |
| `external` 上游源码、虚拟环境、大型结果与本机研究产物 | 放受控下载/缓存目录，不进入默认发布包 | 减少克隆负担，明确原创边界与许可 |
| 未证明收益的 CE、规则重排、自动记忆蒸馏 | 默认关闭或列 experimental | 降低延迟、依赖和错误来源 |
| 零散“第 N 版”设计与面试问答 | 迁 docs/history、保留主题索引 | 避免过时说法和当前实现混在一起 |
| 只测字符串包含某功能名的测试 | 保留必要静态契约，替换虚弱能力证明 | 测试名称和字数不证明行为 |
| 大规模微服务、消息中间件、插件市场 | 不做 | 当前问题能用更小的系统解决 |
| “生产级”“完全自主”“百分百安全”“无限上下文”表述 | 删除 | 现有证据不支持这些无边界承诺 |

`.gitignore` 已忽略 `.aster`、`.env` 等，但未覆盖所有外部与研究产物。正式初始化或同步仓库前，先确定发布白名单、依赖下载清单和实验归档策略；不要直接把整个当前目录上传。

## 9. 推荐目标架构与不可破坏的约束

### 9.1 保留现有依赖方向，补齐任务层

```text
CLI / 可选飞书 / 轻量任务查看页
                │
        TaskCoordinator + AppSettings
                │
    ┌───────────┼────────────┐
WorkspaceSession      VerificationService      BudgetController
    │                   │                         │
    └────────── CodingAssistant ─────────────────┘
                         │
                    AgentLoop
                    /       \
              ModelClient   ToolExecutor
                               │
                 明确的前置门禁 / 执行 / 状态确认
                               │
                      Host 或受限 Runtime

MemoryContextProvider 负责证据选择、预算与来源，不决定任务完成。
Task/Operation Store 负责关键状态；Trace 负责可观察证据与诊断。
Eval 在独立工作区应用补丁并判定，不依赖 Agent 自述。
```

这是目标职责划分，不要求按框名创建同名目录。优先让调用关系和失败语义清楚。

### 9.2 八条不变量

1. `completed` 必须对应当前代码内容的有效验收；自然停止只表示一轮模型交互结束。
2. 同一工作区同一时间只有一个有权提交变更的任务，或每个任务各自隔离。
3. 个人身份随当前请求确定，不随“第一个创建缓存的人”固定。
4. 不可信历史、仓库文字和工具输出只能作为证据，不能自行提升为系统权限或可信长期事实。
5. 取消到达后不启动新副作用；已发生的副作用与未执行的操作必须区分。
6. 进程中断后的未知操作不自动重放；恢复前先核查状态和结果。
7. 实验中的每项组件、数据、模型、成本与判定依据可追溯；降级不能静默改变实验含义。
8. 发布的数字能回到具体任务、配置、原始证据和计算口径。

## 10. 怎样设计最终能写进简历的实验

### 10.1 最小完整实验包

建议输出一个独立 `release-results` 目录，包含：

| 产物 | 内容 |
|---|---|
| Run manifest | 代码版本、依赖、模型目的地/标识、Prompt、工具、预算、数据与 grader 版本 |
| Task manifest | repo/base commit、划分、任务家族、测试 oracle、运行环境 |
| 原始逐题结果 | patch、验证日志、状态、失败原因、Token、费用、延迟与后端 |
| 聚合报告 | 同一协议生成的成功率、成本、延迟、分层结果与区间 |
| 消融表 | 配对任务差异、机制触发和实际质量/成本权衡 |
| 局限性 | 小样本、公开数据曝光、供应商用量缺失、未覆盖语言/平台 |
| 复现入口 | 无密钥的结构检查；需要密钥的执行命令；预期运行时间和预算 |

公开包只放允许再分发的数据与脱敏证据。大型上游数据用 URL、版本和下载校验清单表达。

### 10.2 指标定义不要模糊

| 指标 | 建议定义 |
|---|---|
| 任务成功率 | 独立验收全部通过的任务数 / 所有纳入该评测的任务数 |
| 误报完成率 | Agent 标记完成但独立验收失败的次数 / Agent 标记完成的次数；同时报分子分母 |
| 有效修复成本 | 该组所有尝试的总成本 / 成功任务数；零成功时为不可定义，不填 0 |
| 恢复成功率 | 预定义故障点注入后，恢复并通过独立验收的任务比例 |
| 取消延迟 | 收到取消到相关进程停止/任务进入稳定终态的时间；分别报告 |
| 副作用重复率 | 故障恢复后重复发生的受跟踪写操作 / 相应故障测试操作数 |
| 记忆过期错误率 | 因过期历史证据导致错误决策的案例比例，配合人工核对口径 |
| 检索 Recall@k | 在有证据标注的诊断集上，Top-k 覆盖所需证据的比例 |
| 延迟 p95 | 指定范围全部原始样本的 95 分位；任务墙钟与请求延迟分开 |
| Token / 费用 | Agent 与辅助调用分账，总账合计；真实 usage 和估算区分 |

同一任务重复 3–5 次适合观察随机性；同题重复不是新增独立样本。置信区间和配对分析以任务为单位，必要时按仓库/家族聚类，避免得到虚假的精确性。

### 10.3 验收目标如何设

下面是建议门槛，不是本项目已经达到的数字：

- P0 缺陷对应的负向回归全部通过，不以整体平均成功率抵消严重错误。
- 核心恢复/取消协议在受控故障矩阵中无未解释的状态；已知限制写入文档。
- 主结果至少包含精简基线和一个完整方案，协议、预算与任务配对一致。
- 至少有一项改造能展示有解释的成功率提升或成本下降；若区间很宽，明确结果尚不确定。
- 至少 3 个可完整追查的真实仓库案例、5 类由真实失败转来的回归案例。
- 性能阈值先测基线再冻结。例如选择某硬件上取消 p95、最大内存、热检索延迟的目标，而不是凭空宣称“毫秒级”或“百万级”。

不建议预设“必须成功率 90%”。难度、模型和预算不同，绝对百分比不具可比性。高水平来自协议清楚、难度真实、结果可复查和改进有因果解释。

## 11. 三条实施路线：按时间与方向选择

### 11.1 只剩约一周：收口版

目标是消除致命问题并形成诚实可展示的版本，**不是一周完成全部 P0/P1**。

| 时间 | 工作 | 完成标志 |
|---|---|---|
| 第 1–2 日 | Windows 探测、过期验证；固定负向回归 | 两个高危逻辑有复现与修复证据 |
| 第 3 日 | 暂时收窄单用户、Direct 互斥；修多行输入和配置路由 | 不再承诺未实现的隔离，文档示例可用 |
| 第 4 日 | 环境约束、CI 依赖、快速开始 | 新环境离线测试/演示路径可走通 |
| 第 5 日 | 修最关键指标错误，冻结当前可用结果，标记其余未验证项 | 不把计划执行数和错误百分位写进简历 |
| 第 6–7 日 | 整理 1–3 个真实任务案例、演示和 README | 能讲具体问题、改法和证据 |

此版本可以开始投递，但简历重点写工程实现与故障修复，不宣称广泛泛化效果。若 P0 修复超时，减少展示范围或推迟相关承诺，不用赶工掩盖。

### 11.2 约四周：最推荐的实习简历版

| 周 | 主目标 | 验收交付 |
|---|---|---|
| 第 1 周 | P0：正确性、隔离、配置与可复现环境 | 缺陷回归、明确运行边界、可用安装 |
| 第 2 周 | Task/Workspace/Verification/Patch 主链路 | 3 个真实仓库任务能交付补丁 |
| 第 3 周 | 修正评测协议、建立主基准、做最小消融 | 可追溯逐题结果、失败分析和初步对照 |
| 第 4 周 | 补关键恢复/取消问题，冻结结果、演示与简历 | 一个版本化发布、一次完整技术讲解 |

四周不适合同时做完整多人飞书、全套记忆大改和新前端。优先使用现有 CLI、Snapshot 和 Dashboard，选择一个专项深挖。

### 11.3 六至八周以上：冲刺更强项目

四周主线通过后，在下面两条中选一条，而不是全做：

| 方向 | 核心问题 | 应深入的工作 |
|---|---|---|
| Agent 可靠性 / 后端方向 | 中断、并发、取消后如何保证任务和副作用正确 | 事务状态、租约、故障矩阵、独立验收、消息投递语义 |
| 记忆 / 检索研究方向 | 哪些历史证据有效，怎样以更低预算帮助代码维护 | 版本化事实、失效、来源支持、规模曲线、配对消融与泛化 |

后续再扩大未见任务和真实使用案例，先冻结协议再运行发布用保留集。实验没有收益时就收缩机制；这也是可以讨论的工程结论。

### 11.4 如果决定大改

允许大改不意味着整套系统必须重写。最合理的大改边界是：

1. 保留 LLM transport、AgentLoop、基础文件工具和已有回归。
2. 把 Task/Operation 元数据与恢复语义统一起来。
3. 把工作区隔离、补丁和独立验证变成产品中轴。
4. 把复杂记忆变成可插拔实验组，默认保留有收益的部分。
5. 最后迁移 CLI/飞书，保持入口共用同一配置与服务。

每步都应能用同一批任务验收。禁止同时换语言、换存储、换 Agent 框架、换前端、换评测，导致任何结果变化都无法归因。

## 13. 面试必须准备的十个追问

| 问题 | 应当拿出的证据 |
|---|---|
| 为什么模型说完成不代表任务完成？ | 旧验证漏洞复现、工作区指纹与独立测试 |
| SSE 已输出一部分后为什么不直接重试？ | 当前可见输出后的停止重试策略、断流测试 |
| 取消为什么不只是设置一个标记？ | 模型流、审批、工具、进程、线程写入的生命周期 |
| 进程崩溃在写文件后、写结果前怎么办？ | Operation 状态与 uncertain 分支，防重复副作用案例 |
| Docker 为什么不能直接等于安全？ | 挂载、宿主文件工具、网络、身份、资源和审批边界 |
| 为什么记忆可能降低成功率？ | 过期事实、错误来源、注入预算、重复检索和完整消融结果 |
| BM25＋向量＋精排各解决什么？ | 分组件检索指标、端到端成本与任务结果，而不是算法定义背诵 |
| 你的数字如何复现？ | 固定 manifest、任务 oracle、逐题结果、真正的总体 p95 |
| 为什么没有引入多 Agent / Redis / 微服务？ | 当前瓶颈、范围选择与对应的测量；如果引入，要证明收益 |
| 哪个问题最难，哪些代码是你负责的？ | 一条由你解释清楚的复现→定位→修复→回归→效果证据链 |

至少准备 3 份短 ADR：任务完成与验证；持久 transcript 与可压缩 context；副作用恢复与投递语义。每份写背景、候选方案、选择、代价、验证，不要重复功能手册。
