原来 → 修改 → 实测
01

压缩与召回：减少反复读取同一份内容

核心不是删掉记忆，而是让模型少读重复内容。

成本优化

原来的做法

旧历史刚压成摘要，又被记忆搜索自动塞回当前对话；摘要还可能再抄一份已保留的用户要求。每次请求都重复读，累计 token 很高。

修改后的做法

自动召回跳过本次会话的历史归档；摘要去重，只补充进展和约束。达到最低节省要求才采用压缩。原始记录仍保存，需要时可以主动回读。

为什么这样改

把厚资料做成一页笔记后，就不用每次再把整叠资料发一遍。总结本身也有成本，没变短就不反复总结。

02

文件搜索提速：知道路径，就按路径找

对应《问题.md》“搜索太慢”：减少无关遍历与重复安全检查。

搜索优化

原来的做法

已经知道文件名和目录，也可能扫描整个项目；遍历无关文件时，仍逐个做昂贵的完整路径检查。依赖和项目越多，等待越长。

修改后的做法

完整路径直接检查；指定目录只查该目录；必须全局找时，先匹配文件名，再对匹配结果做完整安全检查。

为什么这样改

知道书架就不用翻完整个图书馆。优化无关文件的检查成本，受保护目录、链接和返回结果的安全检查仍保留。

这些是已有前端实测中的单次工具耗时，不是整轮模型回复时间，也不是相同条件下的前后加速比。对应整轮回复约 25～30 秒；全局无结果依然最慢。验证同时检查直接路径不启动递归、指定目录不越出范围，以及受保护文件不会被返回。

03

第二轮效率修复：读过的内容少读，旧记录少重发

2026-09-06 · 6 道已曝光原题，两路 Luna 各复测一次。

已完成实测

原来的做法

文件刚读完就可能变成简短引用，压缩后又重新读取；旧工具记录和完整工具说明重复发送，任务越长，累计 token 越高。

修改后的做法

新片段先完整使用一次，旧的相同读取去重；保留少量已读片段，文件内容改变就失效。按真实工具失败保留报错，完整工具说明只发一份，并检查压缩是否有收益。

为什么这样改

已经翻过的资料，内容没变就不必重新找；需要的原文仍可回读。优先减少重复工作，让模型把调用用在实施和有效验收上。

实际效果：发票、脱敏、运费的 read 次数分别从 58→5、43→7、31→5；没有步数暂停。还有什么限制？结果全过 2/6，五维全过 0/6；单次复测且包含其他改动，不能归因于单一优化。本批未设置时间判错项。

已定位、尚待修复：同题每轮更换会话 ID 导致历史重复召回；旧摘要与当前验收冲突；验证格式返工；许多小工具记录累计重发。摘要生成只占总 token 约 4.1%，下一步优先解决重复输入和无效回合。详见《Luna 效率复测结果与超预算根因》。

04

Goal 按需开放：普通任务不再反复调用完成工具

对应《问题.md》第 6 节：减少无效收尾，保留正常任务验收。

完成流程优化

原来的做法

普通任务也向模型提供 goal_complete。没有显式 Goal 时，模型仍可能反复调用，增加工具说明和收尾消耗。

修改后的做法

只有显式 Goal 处于执行或验收状态时才开放 goal_complete；其他状态从工具定义和系统工具列表移除，并禁止执行。普通任务通过验收后直接回复。

为什么这样改

需要目标监督时才走对应完成流程。普通任务不用多办一次“完成手续”，同时仍须检查交付结果，不能跳过验收。

实际效果：看板第一阶段原题复测中，goal_complete 调用从 5 次→0 次，从触顶暂停变为正常收尾，独立功能检查 8/8 通过。离线检查确认工具随 Goal 状态开放。

还有什么限制？这是一个阶段的观察，5→0 只统计该完成工具，不是全部工具调用；具体节省多少 token 尚未单独测量，也不代表全部长任务都已解决收尾问题。
