# MiniClaw 四层记忆与上下文压缩

本文专门解释 MiniClaw 的 Memory 设计。实现参考了 pi 的 `pi-coding-agent` compaction 和 `mom` progressive context compaction，但改写为 Python，并保持 MiniClaw 自己的分层边界。

## 1. 为什么不能只保存一个 messages 数组

编码 Agent 会不断累积用户请求、模型分析、工具调用和工具结果。如果全部原样发送给模型，会出现三个问题：

1. 上下文最终超过模型窗口；
2. 很早以前的大段命令输出会反复计费；
3. 对话越长，真正重要的当前任务越容易被旧信息淹没。

MiniClaw 将“磁盘上的完整历史”和“本轮发给模型的工作上下文”分开：

```text
完整 JSONL 事件日志：长期保留、append-only、可审计
                 ↓ 派生
模型工作上下文：checkpoint + 最近原始消息
```

压缩只改变第二部分，不删除第一部分。

## 2. 四层 Memory

| 层 | 保存内容 | 生命周期 | 默认位置 |
| --- | --- | --- | --- |
| Working Context | 当前 checkpoint、近期消息、工具结果引用 | 每轮自动维护 | `.aster/session.jsonl` |
| Episodic Memory | 一次 Session 的目标、结果和状态 | 每次 run 完成后更新 | `.aster/memory/episodes/*.md` |
| Semantic Memory | 用户偏好、项目事实、环境和稳定事实 | 仅显式写入 | `.aster/memory/MEMORY.md` |
| Procedural Memory | Skill 名称、简介和操作指南 | 文件维护、按需读取 | `.aster/skills/*/SKILL.md` |

四层不能合并，因为它们的写入条件和遗忘方式不同。当前工具输出适合 Working Context，但不应该自动成为长期事实；一个测试修复过程适合 Episode，但不应该每轮全部放进提示词；Skill 是操作流程，也不属于聊天历史。

### Memory 工具和自动压缩不是一回事

项目里确实有 `memory` 工具，但模型不靠它触发上下文压缩：

```text
memory 工具
  → 模型主动 search / remember / replace / forget
  → 管理长期语义事实和历史 Episode

MemoryManager.maybe_compact
  → CodingAssistant 在每轮 turn_finished 后自动调用
  → 管理本次会话发给模型的 Working Context
```

因此即使模型从不调用 `memory`，80k/100k 的自动压缩仍然会工作。反过来，调用 `memory(remember)` 只表示保存稳定事实，不会立即压缩当前 messages。模型看到的是程序组装后的 checkpoint + 近期原文；磁盘里的原始 JSONL 仍然追加保留。

## 3. Working Context 的四阶段渐进压缩

### 阶段一：大型实时工具结果制品化

工具刚执行完、进入消息历史之前，MiniClaw 计算结果的 UTF-8 字节数。默认达到 16KB 时：

1. 完整结果写到 `.aster/context-artifacts/<session>/`；
2. 记录相对路径、字节数、SHA-256 和时间；
3. 模型上下文只保留头尾预览与引用。

这一步最省钱，因为大型日志不会在后续每一轮中重复发送。工具调用消息和工具结果消息仍然成对存在，只替换结果正文。

### 阶段二：旧工具结果引用化

有些工具结果产生时没有超过 16KB，但会在长会话中逐渐变成低价值旧信息。压缩开始后，凡是即将离开近期窗口的旧 Tool Result，只要还不是 artifact 引用，就会把完整内容落盘，并在归档副本中改为引用。

原始 JSONL 中的 Tool Result 不修改，因此仍保留完整审计历史。

### 阶段三：闭合历史确定性归档

MiniClaw 从最新消息向前估算 Token，尽量保留最近 20k。切点优先放在 user 消息前，因此一个完整回合中的 Assistant Tool Call 和 Tool Result 不会被拆到两侧。

被移出的闭合历史写成 JSONL artifact，checkpoint 保存：

- 当前用户请求的精确原文；
- 上一次 checkpoint；
- 最近的用户/助手语义台账；
- 归档路径和 SHA-256；
- 可恢复的工具结果制品；
- read/grep 读取过的文件；
- write/edit 修改过的文件；
- 恢复优先级规则。

这一步不调用模型，结果确定、便宜且容易测试。

### 阶段四：模型摘要兜底

只有到达硬触发线，并满足以下任一条件时才调用模型做摘要：

- 被归档的非工具语义内容超过 4.5k Token；
- 确定性 checkpoint 加近期消息仍超过 30k 目标。

模型摘要会合并上一次 checkpoint，但“当前用户请求”仍由程序从原始 user 消息精确提取，不让摘要模型猜测。

## 4. 评测档为什么这样设

实现机制跟随 pi，但阈值改为更适合控制评测成本的工作集：

```text
80k soft trigger   → 只允许确定性压缩，失败就暂缓
100k hard trigger  → 允许模型摘要兜底
30k target         → 压缩后的目标上限
20k recent budget  → 原样保留的近期消息
动态 reserve        → 至少覆盖模型最大输出，并受窗口限制
4.5k semantic      → 确定性语义密度预算
```

这组值的主要评测意义是：在输入达到 80k 时就能观察确定性压缩，到 100k 时能稳定覆盖模型摘要兜底，而压缩后回到约 30k，避免为了触发一次压缩构造 200k 以上输入。这样更便于分别统计“无压缩成本、确定性压缩成本、模型摘要成本”。

当前默认 `ModelProfile` 是 128k，可以直接使用完整评测档：

```text
80k soft trigger
100k hard trigger
30k target
20k recent budget
12.8k reserve
4.5k semantic budget
```

若模型窗口更小，四条水位线会按比例安全降低。模型窗口与最大输出可以通过环境变量覆盖：

```dotenv
MINICLAW_CONTEXT_WINDOW=128000
MINICLAW_MAX_OUTPUT_TOKENS=8192
```

## 5. Append-only 与重启恢复

`session.jsonl` 包含三类记录：

```json
{"type":"message", "id":"...", "message":{}}
{"type":"compaction", "summary":"...", "first_kept_message_id":"..."}
{"type":"recovery", "compaction_id":"...", "restored_messages":12}
```

重启时读取最后一个 compaction，然后构造：

```text
Working Context Checkpoint
+ first_kept_message_id 开始的原始消息
+ 压缩后继续追加的新消息
```

连续第二次压缩会把 previous checkpoint 合并进新 checkpoint，而不是遗忘第一次压缩已经提炼的信息。

## 6. Episodic Memory

每次 `CodingAssistant.run` 结束后，会将当前 Session 写成 Markdown Episode，状态为 completed 或 failed。它保存最近用户目标、最近助手结果和恢复提示。

`memory` 工具提供：

- `episode_list`：查看最近 Session；
- `episode_search`：按词频进行可解释搜索；
- `episode_read`：读取指定 Session。

Episode 不自动注入每一轮提示词，避免旧任务干扰当前任务。模型需要时再搜索和读取。

## 7. Semantic Memory

Semantic Memory 只允许通过 `memory` 工具显式修改，分类为：

```text
preference / project / environment / fact
```

保护规则包括：

- 拒绝 API Key、Token、Password 等 secret-like 文本；
- 拒绝“本轮、临时、刚刚”等短期信息；
- 大小写不敏感去重；
- `key: value` 冲突必须精确 replace；
- 单条最多 2,000 字符，文件最多 32KB；
- 只修改 managed markers 中的内容，保留人工笔记。

与当前请求相关的稳定事实会以 `<long_term_memory>` 数据块进入 system prompt，并明确当前请求和系统规则优先。

相关事实不再使用简单关键词计数。当前实现采用 BM25 主检索、向量辅检索、加权 RRF 融合和第二阶段 rerank，具体见 `5.长期记忆检索.md`。

同一主题出现新旧不同值时不会静默覆盖，而是产生持久化 conflict ID，要求显式选择保留旧值、替换或并存。文件级写锁和原子替换还会防止飞书多会话并发写入造成更新丢失。

## 8. Procedural Memory

程序扫描 `.aster/skills/*/SKILL.md`。System Prompt 中只放 Skill 名称和一句简介；真正需要使用某个流程时，模型调用 `skill` 工具读取正文或同目录 reference。

路径经过 resolve 和 relative 校验，不能用 `../` 越过 Skill 目录；单个资源最大 64KB。

这就是渐进加载：目录常驻、正文按需、附件再按需，避免把所有操作手册永久塞进上下文。

## 9. 模块边界

Memory 没有写进通用 `AgentLoop`。`AgentLoop` 仍然只负责模型与工具循环，`CodingAssistant` 在产品组装层完成：

```text
CodingAssistant
├─ AgentLoop
├─ ToolExecutor
├─ MemoryManager
│  ├─ WorkingContext
│  ├─ EpisodicMemoryStore
│  ├─ SemanticMemoryStore
│  └─ ProceduralMemoryStore
└─ read / bash / edit / write / grep / memory / skill
```

大型工具结果的转换通过 ToolExecutor 的通用 result transform 注入。这个扩展点不认识 Memory，未来也可以用于审计、脱敏或远程制品存储。

## 10. 评测建议

至少分别记录四组指标：

1. 不压缩时每轮累计 input token；
2. 只开启大型工具结果制品化后的累计 input token；
3. 开启确定性归档后的累计 input token 与磁盘 artifact 大小；
4. 触发模型摘要后的摘要调用 input/output token 与后续节省量。

测试中应构造大量重复工具输出，而不是只堆用户文本。前者更能体现渐进压缩相对“每次都让模型总结”的成本优势。

## 11. 当前测试覆盖

离线测试已覆盖：

- 80k/100k 评测触发配置和不同模型窗口安全降级；
- 大型实时 Tool Result 制品化；
- append-only compaction 与重启恢复；
- Tool Call/Result 不跨压缩切点；
- 闭合历史 JSONL 归档；
- 硬阈值模型摘要 fallback；
- Semantic secret、临时信息、重复与冲突拒绝；
- Episode 搜索；
- Skill 渐进读取与路径逃逸拒绝。
