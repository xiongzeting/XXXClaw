# 9. 危险操作审批系统

## 1. 这一层解决什么问题

Docker 只能限制命令运行的位置和资源，不能替用户判断一个操作是否应该发生。例如：

- 容器仍可能挂载可写工作区；
- 开启网络后，命令可能上传代码或调用外部接口；
- Host Runtime 可以直接影响本机文件、进程和服务；
- `write` 可以完整覆盖已有文件；
- 长期记忆修改会影响后续会话。

因此 MiniClaw 在工具参数校验之后、工具真正执行之前增加统一 Approval Gate。它属于工具执行边界，而不是 LLM 层，也不是 AgentLoop 的任务规划逻辑。

```text
模型产生 Tool Call
        ↓
ToolExecutor 查找工具并规范化参数
        ↓
递归 Schema 校验
        ↓
Approval Gate 风险识别
        ↓
白名单 → allow / ask / deny
        ↓
批准：执行工具
拒绝：返回结构化 ToolResult，文件和命令都不执行
```

所有入口共享同一个 Gate，因此不会出现 CLI 有审批、飞书却能绕过审批的情况。

## 2. 三种策略

### `allow`

识别到危险操作后直接允许，但仍写入：

- `approval.requested`
- `approval.decision = allowed-by-policy`
- 后续 `tool.call`执行结果

它适合完全可信、已经有外部隔离的评测环境，不适合作为日常默认值。

### `ask`

默认策略。危险操作暂停，等待当前任务的用户明确批准或拒绝。超过审批时间后自动拒绝。

### `deny`

危险操作一律不执行，返回 `[APPROVAL_REQUIRED]`。项目白名单可以为非常具体的已知操作提供例外。

## 3. 当前风险分类

| 风险 | 级别 | 典型情况 |
|---|---:|---|
| `destructive-filesystem` | critical | 删除、格式化、`Remove-Item`、`rm`、`diskpart` |
| `destructive-git` | critical | `reset --hard`、`clean -f`、强推、删除分支 |
| `database-destruction` | critical | `DROP`、`TRUNCATE`、无条件删除数据 |
| `external-write` | critical | 上传文件、HTTP 写请求、`git push` |
| `approval-policy-change` | critical | 修改 `.miniclaw/approval.json` |
| `sensitive-file` | high | 修改 `.env`、证书、私钥、credentials |
| `system-change` | high | 全局安装、权限、服务、关机和进程终止 |
| `network-access` | high | 下载、拉取仓库、安装远程依赖、访问 URL |
| `filesystem-overwrite` | medium | Shell 直接覆盖文件 |
| `file-overwrite` | medium | `write`完整替换已存在的文件 |

一个 Shell 命令可以同时保留多个能力，例如 `curl POST ... && rm file` 会得到 `external-write + network-access + destructive-filesystem`。界面仍以最高级别作为主风险展示，但审批、白名单和 Trace 都保存完整 `capabilities`；白名单只有覆盖全部能力时才会放行。

普通 `read`、`grep`、新建文件、常规源代码 `edit` 和所有 `memory` action 不要求审批。长期记忆写入由 Memory Store 的 Secret 拒绝、去重和冲突处理约束；`edit` 修改敏感文件或审批配置时仍会被拦截。

## 4. CLI 审批

CLI 遇到危险操作会显示：

```text
需要审批 `A1B2C3`
工具：bash
风险：high / network-access
原因：命令可能联网、下载不受信任内容或读取远程资源
预览：
git fetch origin main

批准请输入：批准 A1B2C3
拒绝请输入：拒绝 A1B2C3
```

审批 ID 必须完全匹配。英文 `approve A1B2C3`和 `deny A1B2C3`也可以使用。Windows 控制台使用非阻塞轮询读取，超时后不会留下继续读取下一条用户输入的后台线程。

CLI 参数：

```powershell
python -m MiniClaw.cli --workspace D:\project --approval-policy ask --approval-timeout 300
```

## 5. 飞书审批

飞书通过相同的六位审批 ID 处理：

```text
批准 A1B2C3
拒绝 A1B2C3
```

实现中特别处理了会话队列死锁问题：

```text
原任务占用会话 Worker，等待审批
                    ↑
审批回复在 submit 阶段优先解析，不进入普通任务队列
                    ↓
直接唤醒原任务的 Future
```

如果审批消息也进入普通队列，它会排在正在等待的原任务之后，两边会永久互相等待。

飞书还限制：

- 审批必须来自同一会话；
- 默认只有发起当前任务的用户能够审批；
- 已超时或已处理的 ID 不可复用；
- 审批消息本身不会再发送给 LLM。

## 6. 项目级白名单

默认配置位置：

```text
<workspace>/.miniclaw/approval.json
```

示例：

```json
{
  "policy": "ask",
  "timeout_seconds": 300,
  "allowlist": [
    {
      "tool": "bash",
      "risk": "network-access",
      "command_glob": "git fetch origin *"
    },
    {
      "tool": "write",
      "risk": "file-overwrite",
      "path_glob": "docs/**"
    }
  ]
}
```

支持字段：

- `tool`：必填，工具名或 Glob；
- `risk`：风险类别 Glob；
- `command_glob`：仅匹配 Bash 命令；
- `path_glob`：仅匹配文件工具路径。

一个规则中的字段是 AND 关系。上面的第一条只允许 `bash + network-access + git fetch origin *`，不会顺便允许 `git push`。

白名单匹配前还会执行两项收紧：

- 文件路径先通过 WorkspaceGuard 解析为真实、规范化的工作区相对路径；含 `..` 或符号链接逃逸歧义的原始路径不能命中白名单；
- 宽泛 `command_glob` 不能借助 `&&`、`;`、管道、重定向、命令替换等额外 Shell 结构承载第二个操作，除非规则本身明确写出了该结构。

审批请求会记录规范化 Tool Call 的 SHA-256。等待用户期间如果调用内容发生变化，返回 `APPROVAL_CALL_CHANGED`，不执行工具。

不要使用过宽的规则，例如：

```json
{"tool": "bash", "risk": "*"}
```

审批配置自身被标记为 critical，避免模型静默把策略从 `ask`改为 `allow`。

## 7. 环境变量

```text
MINICLAW_APPROVAL_POLICY=ask
MINICLAW_APPROVAL_TIMEOUT_SECONDS=300
MINICLAW_APPROVAL_CONFIG=D:\project\.miniclaw\approval.json
```

审批配置只接受上述 `MINICLAW_*` 名称，不再维护 pi-mono 环境变量别名。

优先级为：

```text
CLI 显式参数
  > 环境变量
  > 项目 approval.json
  > 默认 ask / 300 秒
```

## 8. Trace 记录

每次危险操作至少产生三类信息：

```text
approval.requested
  approval_id / tool_call_id / risk / capabilities / level
  normalized_call_hash / reason / preview

approval.decision
  approved / denied / timeout / unavailable
  allowed-by-policy / allowed-by-whitelist / denied-by-policy

tool.call
  success 或 error、耗时、参数、结果与审批 details
```

预览和 Trace 都会隐藏 API Key、Bearer Token 和常见 Secret 环境变量。审批失败会作为工具错误返回给模型，模型可以向用户解释，但系统提示明确禁止模型换工具绕过拒绝。

## 9. 关键失败关闭原则

- `ask`但当前入口没有审批能力：`APPROVAL_UNAVAILABLE`；
- 用户拒绝：`APPROVAL_DENIED`；
- 超时：`APPROVAL_TIMEOUT`；
- `deny`策略命中：`APPROVAL_REQUIRED`；
- 审批后调用内容变化：`APPROVAL_CALL_CHANGED`；
- 所有上述结果都发生在真实工具执行之前；
- Approval Gate 自己异常时不默认放行。

这使审批系统成为真实执行边界，而不是日志字段或 UI 提示。
