# MiniClaw 工具系统详解

> 更新说明：原有五个 pi 风格编码工具保持 `read → bash → edit → write → grep`，默认工厂现增加独立、无 Shell 的 `search` 文件发现工具。产品层使用角色感知的 `ToolManager` 注册这些工具以及 `memory`、`skill`、`goal`、`goal_complete`，并支持会话级角色注入、allow/deny、动态启停与注销。本文正文仍重点解释原有五个工具的实现细节。

> 本文专门讲解 MiniClaw 的工具层。目标是让你不仅知道五个工具“怎么用”，还能够在实习面试中说明：为什么这样拆分、一次工具调用如何执行、哪些行为参考了 pi、Python 移植时做了哪些取舍，以及未来 Docker Runtime 应该放在哪里。

## 1. 工具层解决什么问题

大模型本身只会生成文本。它不能直接读取本地代码、修改文件或运行测试。

编码 Agent 要真正完成任务，必须为模型提供一组受程序控制的工具：

| 工具 | 作用 |
|---|---|
| `read` | 读取文件内容 |
| `bash` | 执行工作区命令 |
| `edit` | 对已有文件做精确的局部修改 |
| `write` | 新建文件或完整覆盖文件 |
| `grep` | 搜索仓库中的文本 |

工具层位于“模型决策”和“操作系统能力”之间：

~~~text
模型生成工具调用
        ↓
ToolExecutor 统一校验和执行
        ↓
read / bash / edit / write / grep
        ↓
文件系统、ripgrep、Shell
        ↓
ToolResult 返回给模型
~~~

它有两个核心目标：

1. 把操作系统能力包装成模型能够理解的稳定接口。
2. 在真正执行前后实施路径检查、参数校验、输出限制和错误归一化。

## 2. tools 和 assistant 模块有什么区别

这是非常容易混淆、也很适合面试追问的问题。

### 2.1 tools 是“能力层”

tools 只回答：

- 系统有哪些工具？
- 每个工具接受什么参数？
- 参数是否合法？
- 文件路径是否位于工作区？
- 工具如何执行？
- 执行结果怎样限制大小并返回？

tools 不应该决定：

- 用户任务是否已经完成；
- 模型下一步应该调用哪个工具；
- 系统提示词怎么写；
- 会话存在哪里；
- 历史上下文什么时候压缩。

### 2.2 assistant 是“产品组装层”

assistant 负责把通用组件组装成一个具体的编码助手：

- 选择并注册哪些工具；
- 设置系统提示词；
- 创建 AgentLoop；
- 选择模型；
- 保存和恢复会话；
- 未来接入上下文压缩、长期记忆和目标监督。

可以把两者类比成：

- tools 是工具箱以及工具使用规范；
- assistant 是拿着工具箱完成用户任务的产品经理和组装者。

因此，`GrepTool` 的实现属于 tools；“先 grep，再 read，修改后 bash 验证”这样的工作习惯属于 assistant 的系统提示词或 Agent 策略。

## 3. 为什么从 builtin.py 拆成独立模块

初版把五个工具全部写在 `builtin.py` 中。代码量少时可以工作，但继续发展会出现几个问题：

- read、grep、bash 都有不同的截断规则，公共逻辑难以维护；
- edit 的匹配、换行、BOM、diff 已经不是一个简单 replace；
- bash 需要进程树终止和完整输出落盘；
- 单文件越来越长，测试和定位问题困难；
- 未来为 Docker 或远程执行注入 Operations 时边界不清晰。

现在的目录结构是：

~~~text
src/MiniClaw/coding_agent/tools
├─ __init__.py
├─ base.py
├─ workspace.py
├─ executor.py
├─ truncate.py
├─ mutation_queue.py
├─ edit_diff.py
├─ read.py
├─ bash.py
├─ edit.py
├─ write.py
├─ grep.py
└─ factory.py
~~~

这与 pi 的思路一致：每个工具独立，公共机制再放入小型辅助模块，而不是继续堆在一个“大而全”的工具文件中。

## 4. 与 pi 的对应关系

本次 Python 实现主要参考：

~~~text
pi-mono/packages/coding-agent/src/core/tools
├─ read.ts
├─ bash.ts
├─ edit.ts
├─ edit-diff.ts
├─ write.ts
├─ grep.ts
├─ truncate.ts
└─ file-mutation-queue.ts
~~~

MiniClaw 中的对应关系：

| pi | MiniClaw Python |
|---|---|
| `read.ts` | `read.py` |
| `bash.ts` | `bash.py` |
| `edit.ts` | `edit.py` |
| `edit-diff.ts` | `edit_diff.py` |
| `write.ts` | `write.py` |
| `grep.ts` | `grep.py` |
| `truncate.ts` | `truncate.py` |
| `file-mutation-queue.ts` | `mutation_queue.py` |

“参考 pi”主要体现在工具名称、参数结构、截断策略、edit 匹配规则、同文件串行修改和错误提示思路上。

MiniClaw 没有直接复制 TypeScript 代码，而是使用 Python 的 `asyncio`、`pathlib`、`difflib`、`subprocess` 和 Protocol 完成移植。

## 5. 工具统一协议：base.py

### 5.1 ToolResult

所有工具最终返回同一种结果：

~~~python
@dataclass(slots=True)
class ToolResult:
    content: str
    is_error: bool = False
    details: dict[str, Any] = field(default_factory=dict)
~~~

字段含义：

- `content`：直接交给模型看的文本；
- `is_error`：本次工具调用是否失败；
- `details`：给程序使用的结构化附加信息。

例如 bash 可以在 details 中保存退出码、截断信息和完整输出路径；edit 可以保存 diff 和第一处修改行号。

为什么不把所有信息都塞进 content？

因为模型需要的是可读文本，而 UI、日志和后续自动化更适合读取结构化字段。两者分开后，既方便模型理解，也方便程序处理。

### 5.2 Tool Protocol

一个工具需要提供：

- `name`；
- `description`；
- `input_schema`；
- 异步 `execute(arguments)`。

模型看到的是前三项，程序真正调用的是 execute。

使用 Protocol 的好处是工具不必继承某个重量级基类。只要结构兼容，就可以注册到 ToolExecutor。

## 6. ToolExecutor：统一执行边界

`executor.py` 不实现具体工具能力，而是负责所有工具共同的执行流程。

### 6.1 完整执行流程

~~~text
收到 ToolInvocation
  ↓
根据 name 查找已注册工具
  ↓
可选调用 prepare_arguments
  ↓
递归校验 JSON Schema
  ↓
执行 tool.execute
  ↓
捕获超时和异常
  ↓
执行最终 100,000 字符兜底限制
  ↓
返回 ToolResult
~~~

### 6.2 为什么需要 prepare_arguments

真实模型有时不会严格按照 Schema 输出参数。

pi 的 edit 工具兼容两种常见情况：

1. 模型把 `edits` 数组错误地输出为 JSON 字符串；
2. 模型仍使用旧版顶层 `oldText` 和 `newText`。

EditTool 的 `prepare_arguments` 会先把这些输入转换成标准结构，再进行 Schema 校验。

标准参数仍然是：

~~~json
{
  "path": "src/app.py",
  "edits": [
    {
      "oldText": "old",
      "newText": "new"
    }
  ]
}
~~~

这是一种“边界处兼容，内部保持统一”的设计。

### 6.3 递归参数校验

当前校验支持：

- required；
- string、integer、number、boolean、object、array；
- 嵌套 object；
- array items；
- additionalProperties: false；
- minItems；
- minimum。

还专门处理了 Python 的一个陷阱：

~~~python
isinstance(True, int)  # True
~~~

虽然 bool 是 int 的子类，但 Schema 中的 integer 和 number 不应该接受布尔值，所以执行器会明确拒绝。

### 6.4 为什么取消默认 60 秒超时

旧版 ToolExecutor 对所有工具统一设置 60 秒超时，这会破坏 pi 的 bash 语义。

例如构建大型项目可能需要几分钟。如果用户没有要求超时，框架不应该在第 60 秒强行取消。

现在的规则是：

- ToolExecutor 默认没有全局超时；
- 产品层如果确实需要，可以显式配置；
- bash 参数中可以由模型或调用者传入 `timeout`。

### 6.5 为什么仍保留 100,000 字符兜底

五个内置工具已经有自己的输出限制，但未来第三方工具可能忘记限制输出。

因此 ToolExecutor 保留一个较大的最终保险，防止异常工具一次把超大文本塞入模型上下文。这个限制不应该替代工具自己的语义化截断。

## 7. WorkspaceGuard：文件路径硬边界

所有文件工具共享同一个 WorkspaceGuard。

它的规则是：

1. 相对路径基于工作区解析；
2. 绝对路径只有在工作区内部才允许；
3. 解析后的真实路径必须仍是工作区的子路径；
4. `../` 逃逸会被拒绝。

例如工作区是：

~~~text
D:\MIniClaw
~~~

那么：

| 输入 | 结果 |
|---|---|
| `src/MiniClaw/cli.py` | 允许 |
| `D:\MIniClaw\README.md` | 允许 |
| `../secret.txt` | 拒绝 |
| `C:\Windows\system.ini` | 拒绝 |

这比原生 pi 的本地文件路径行为更严格，是 MiniClaw 有意保留的安全差异。

但必须注意：WorkspaceGuard 只直接保护 read、write、edit、grep 的路径解析。bash 能执行任意 Shell 命令，所以“bash 的 cwd 位于工作区”并不等于“bash 只能访问工作区”。完整隔离仍需要 Docker 或系统沙箱。

## 8. truncate.py：不同工具需要不同截断方向

公共常量与 pi 一致：

~~~python
DEFAULT_MAX_LINES = 2000
DEFAULT_MAX_BYTES = 50 * 1024
GREP_MAX_LINE_LENGTH = 500
~~~

### 8.1 truncate_head

保留内容头部，适用于 read 和 grep。

read 文件时通常先看开头；grep 结果则按匹配顺序返回。因此超限时保留前面的完整行。

规则：

- 行数和字节数哪个先达到，就按哪个截断；
- 不返回半行；
- 如果第一行本身超过 50KB，返回空内容并标记 first_line_exceeds_limit。

### 8.2 truncate_tail

保留内容尾部，适用于 bash。

命令失败原因、测试汇总和异常堆栈通常出现在输出末尾。如果统一保留头部，模型可能看到启动日志，却看不到真正的错误。

特殊情况：如果最后一行本身超过 50KB，bash 可以保留这一行最后面的合法 UTF-8 字节片段，并标记 last_line_partial。

### 8.3 truncate_line

grep 的一条匹配可能来自压缩后的 JSON、锁文件或生成代码，单行可能特别长。

因此 grep 每行最多显示 500 个字符，超出后添加：

~~~text
... [truncated]
~~~

这三个函数共同体现了一个重要设计原则：输出限制不只是“切字符串”，而要根据工具用途保留最有价值的信息。

## 9. mutation_queue.py：为什么同一文件必须串行修改

假设两个工具几乎同时修改同一个文件：

~~~text
任务 A 读取旧内容
任务 B 读取旧内容
任务 A 写入新内容
任务 B 写入自己的新内容
~~~

任务 B 可能覆盖任务 A 的结果，这就是经典的丢失更新问题。

MiniClaw 按规范化后的绝对文件路径维护 `asyncio.Lock`：

- 同一个文件的 write/edit 串行执行；
- 不同文件仍可以并行；
- 所有等待者离开后清理无用锁。

为什么不能只给 EditTool 自己加锁？

因为 write 和 edit 都会修改文件。它们必须使用同一套队列，才能避免 write 与 edit 互相覆盖。

## 10. read 工具

文件：`tools/read.py`

### 10.1 参数

~~~json
{
  "path": "src/MiniClaw/agent/loop.py",
  "offset": 1,
  "limit": 200
}
~~~

- `path`：必填；
- `offset`：可选，从 1 开始；
- `limit`：可选，最多读取多少行。

### 10.2 执行流程

~~~text
WorkspaceGuard 解析路径
  ↓
确认目标是文件
  ↓
读取 bytes
  ↓
判断是否为图片
  ↓
文本按 UTF-8 解码并根据 offset/limit 选行
  ↓
truncate_head 限制 2000 行或 50KB
  ↓
返回内容与继续读取提示
~~~

### 10.3 offset 和 limit 的区别

offset 决定从哪里开始，limit 决定最多主动取多少行。

例如文件有 1000 行：

~~~json
{"path": "a.py", "offset": 101, "limit": 50}
~~~

表示读取第 101 到 150 行。如果后面仍有内容，会提示：

~~~text
[850 more lines in file. Use offset=151 to continue.]
~~~

### 10.4 为什么不再给每行添加行号

旧版 read 输出 `1: ...` 这样的人工行号。pi 的 read 返回原始文本，并通过 offset 告诉模型当前范围。

保持原始内容有两个好处：

- 模型复制 oldText 给 edit 时不会误把行号复制进去；
- 文件内容与磁盘内容更一致。

### 10.5 超大单行

read 不返回半行，因为半行可能破坏 JSON、压缩文本或代码结构。

如果第一个目标行本身超过 50KB，工具提示使用 bash 检查有限字节范围。

### 10.6 图片差异

pi 的 ToolResult 支持文本块和图片块，read 可以把图片作为附件交给视觉模型。

MiniClaw 当前的 ToolResult.content 是字符串，因此第一版只能：

- 检测常见图片 MIME；
- 返回图片类型说明；
- 明确说明当前尚不能附加图片。

这是已知的类型系统差异，不应该在面试中宣称已经完全支持多模态读图。

## 11. write 工具

文件：`tools/write.py`

### 11.1 参数

~~~json
{
  "path": "src/new_module.py",
  "content": "print('hello')\n"
}
~~~

### 11.2 行为

- 自动创建父目录；
- 文件不存在时创建；
- 文件存在时完整覆盖；
- 使用 UTF-8 编码；
- 返回实际写入字节数；
- 与 edit 共享同文件修改队列。

### 11.3 为什么返回字节数而不是字符数

英文字符通常是 1 字节，但中文 UTF-8 通常是 3 字节。

~~~python
len("中")                  # 1 个字符
len("中".encode("utf-8")) # 3 个字节
~~~

pi 返回的是字节数，因此 Python 移植也使用 UTF-8 编码后的长度。

### 11.4 什么时候用 write，什么时候用 edit

适合 write：

- 创建新文件；
- 文件很小且确实要完整重写；
- 生成配置文件或固定内容。

适合 edit：

- 修改已有代码的一小部分；
- 希望保留未涉及区域；
- 希望得到清晰 diff。

系统提示词要求优先 edit 修改已有文件，是为了降低整文件覆盖造成的信息丢失风险。

## 12. edit 工具

文件：`tools/edit.py`、`tools/edit_diff.py`

edit 是五个工具中逻辑最复杂、最值得在面试中重点讲的一个。

### 12.1 参数

~~~json
{
  "path": "src/app.py",
  "edits": [
    {
      "oldText": "def old_name():",
      "newText": "def new_name():"
    },
    {
      "oldText": "old_name()",
      "newText": "new_name()"
    }
  ]
}
~~~

一次调用可以包含多个 edits，但必须满足：

- edits 至少有一项；
- oldText 不能为空；
- 每个 oldText 必须唯一；
- 不同 edits 不能重叠或嵌套；
- 替换后必须真的发生变化。

### 12.2 所有 edits 都匹配原始文件

假设原文件是：

~~~text
A B C
~~~

两个 edit 都先在同一个原始文本中定位，而不是第一个替换完后再让第二个匹配新文本。

这样做的好处是一次工具调用具有明确、可预览的语义，不会因为前一个 replacement 改变后一个 replacement 的搜索空间。

### 12.3 为什么从文件尾部向前替换

假设两个匹配位置分别是 10 和 100。

如果先修改位置 10，文本长度可能变化，原来的位置 100 就不再准确。

因此 edit 会：

1. 先在原始文件中找到所有起止位置；
2. 检查唯一性和重叠；
3. 按位置倒序执行。

先改后面的文本不会影响前面文本的下标。

### 12.4 唯一匹配

如果 oldText 出现多次，工具拒绝猜测：

~~~text
Found 2 occurrences ... Each oldText must be unique
~~~

模型需要读取更多上下文，把函数名、周围代码或完整代码块一起放进 oldText，使目标唯一。

这比默认替换第一处更安全，也比全局替换更可控。

### 12.5 重叠检测

原文：

~~~text
abcde
~~~

如果一个 edit 匹配 `abc`，另一个匹配 `bcd`，两个范围重叠。

工具会拒绝执行，并要求调用者把它们合并为一个 edit。否则修改顺序会导致语义不明确。

### 12.6 pi 风格模糊规范化

精确匹配失败后，edit 会尝试以下规范化：

- Unicode NFKC；
- 去除每行末尾空白；
- 智能单引号转普通单引号；
- 智能双引号转普通双引号；
- 多种 Unicode 横线转 `-`；
- 不换行空格等特殊空格转普通空格。

这是为了处理模型输出与真实文件之间常见的排版差异。

需要注意：只要某个 edit 使用了模糊匹配，操作会进入规范化文本空间，因此文件中相关格式可能被统一。这与 pi 当前行为一致。

### 12.7 保留 BOM 和换行风格

edit 读取文件后会：

1. 分离 UTF-8 BOM；
2. 检测原文件主要使用 CRLF 还是 LF；
3. 在 LF 规范化空间中匹配和生成 diff；
4. 写入前恢复原换行；
5. 把 BOM 加回文件头。

这避免了只改一行代码却把整个 Windows 文件的换行全部改成 LF，也避免了无意删除 BOM。

### 12.8 diff 和 firstChangedLine

成功后 details 包含：

~~~json
{
  "diff": "-10 old\n+10 new",
  "firstChangedLine": 10
}
~~~

diff 便于 UI 展示和审计，firstChangedLine 可以让未来编辑器直接跳到第一处变化。

### 12.9 同文件队列

edit 的“读取旧内容 → 计算新内容 → 写回”必须作为一个完整临界区放进修改队列。

如果只在写入那一步加锁，两个 edit 仍可能先读取同一份旧内容，最后互相覆盖。

## 13. grep 工具

文件：`tools/grep.py`

### 13.1 为什么使用 ripgrep

历史版本中负责内容搜索的 SearchTool 使用 `Path.rglob` 遍历文件，再用 Python 逐行匹配；这里描述的是被 `grep` 替代的旧实现，当前 `search` / `SearchTool` 负责按路径发现文件。

这在小目录中能工作，但大型仓库会有明显问题：

- 性能较慢；
- 不自然地支持正则；
- 不自动遵守 .gitignore；
- 很难正确处理隐藏文件、glob 和二进制文件。

pi 使用 ripgrep，MiniClaw 也通过 `shutil.which("rg")` 查找本机 rg。

当前实现不会自动联网下载 rg。如果环境没有安装，会返回明确错误。

### 13.2 参数

~~~json
{
  "pattern": "class .*Tool",
  "path": "src",
  "glob": "*.py",
  "ignoreCase": false,
  "literal": false,
  "context": 2,
  "limit": 100
}
~~~

参数含义：

- `pattern`：正则或字面量；
- `path`：搜索文件或目录，默认工作区；
- `glob`：文件过滤；
- `ignoreCase`：忽略大小写；
- `literal`：把 pattern 当普通字符串；
- `context`：匹配前后显示多少行；
- `limit`：最多返回多少个匹配，默认 100。

### 13.3 为什么使用 rg 的 JSON 输出

普通 rg 文本输出需要自己解析冒号、路径和行号，Windows 盘符中的冒号还会增加歧义。

JSON 模式会为每个匹配返回结构化事件，包括：

- 文件路径；
- 行号；
- 匹配行文本。

Python 只需解析事件，不必猜测字符串格式。

### 13.4 输出格式

匹配行：

~~~text
src/app.py:20: class App:
~~~

上下文行：

~~~text
src/app.py-19- @dataclass
src/app.py:20: class App:
src/app.py-21-     ...
~~~

冒号表示真正匹配，横线表示上下文。

### 13.5 三层输出限制

grep 同时限制：

1. 默认最多 100 个匹配；
2. 总输出最多 50KB；
3. 单行最多 500 字符。

如果达到匹配上限，会提示提高 limit 或缩小 pattern；如果单行被截断，会提示使用 read 查看完整内容。

### 13.6 .gitignore 与隐藏文件

rg 默认遵守 .gitignore，命令中加入 `--hidden` 搜索隐藏文件，但被 ignore 规则排除的文件仍不会返回。

这适合代码仓库：既可以搜索 `.github` 等隐藏目录，又不会把大量依赖和构建产物无条件塞进结果。

## 14. bash 工具

文件：`tools/bash.py`

### 14.1 参数

~~~json
{
  "command": "python -m unittest discover -s tests -v",
  "timeout": 120
}
~~~

- `command`：必填；
- `timeout`：可选，单位秒。

### 14.2 stdout 和 stderr 合并

测试工具经常把普通进度写到 stdout，把警告或错误写到 stderr。

MiniClaw 将 stderr 重定向到 stdout，按进程产生数据的顺序收集，避免最后返回两个彼此割裂的区块。

### 14.3 非零退出码

退出码不是 0 时：

- 保留命令输出；
- 在末尾添加 `Command exited with code N`；
- ToolResult.is_error 设为 true。

这样模型既知道失败了，也能看到失败原因。

### 14.4 可选 timeout

未提供 timeout 时，bash 不设置默认命令期限。

提供 timeout 后，超时会：

- Windows 调用 taskkill 终止 PID 对应的整棵进程树；
- POSIX 终止新建的进程组；
- 返回清晰的超时错误。

只杀死 Shell 父进程是不够的，因为测试、构建工具或脚本可能已经启动子进程。

### 14.5 为什么保留输出尾部

例如测试输出可能是：

~~~text
前面 5000 行构建日志
...
FAILED tests/test_app.py::test_x
AssertionError: ...
~~~

模型最需要最后的失败摘要和堆栈，所以 bash 使用 `truncate_tail`，保留最后 2000 行或 50KB。

### 14.6 完整输出落盘

如果输出超限，完整 bytes 会保存到：

~~~text
.aster/tool-output/bash-<随机ID>.log
~~~

ToolResult 会给出相对路径。模型如果需要更早的日志，可以继续使用 read 分段查看。

为什么不使用系统临时目录？

因为 WorkspaceGuard 不允许 read 访问工作区外路径。把文件保存在工作区内部，既能继续读取，也便于项目级清理和审计。

### 14.7 bash 不是沙箱

当前 LocalBashOperations 直接使用本机 Shell。

因此它仍可能：

- 访问工作区外文件；
- 访问网络；
- 启动其他程序；
- 消耗大量 CPU、内存或磁盘。

目前只能说它有 cwd、timeout、进程树清理和输出限制，不能说它有生产级安全隔离。

## 15. Operations Protocol 与 Docker Runtime 放哪一层

pi 的工具普遍允许注入 operations，把“工具语义”和“实际执行位置”分开。

MiniClaw 已为 read、write、edit、bash 定义 Operations Protocol，例如：

~~~text
BashTool
  ↓ 调用 BashOperations.run
LocalBashOperations
  ↓ 本机 Shell
~~~

未来接入 Docker 时，推荐结构是：

~~~text
assistant / composition root
        ↓ 选择运行环境
tools 语义层
        ↓ Operations Protocol
runtime 层
├─ LocalRuntime
└─ DockerRuntime
        ↓
Docker Engine
~~~

也就是说：

- DockerRuntime 不应该写进 AgentLoop；
- 不应该让 assistant 自己拼 docker exec 命令；
- 不应该在每个工具里重复一套 Docker API；
- 应该由独立 runtime 包实现工具需要的读、写、执行等 operations；
- assistant 只在组装时选择 Local 还是 Docker 实现并注入工具。

推荐未来目录：

~~~text
src/MiniClaw
├─ runtime
│  ├─ base.py
│  ├─ local.py
│  └─ docker.py
├─ tools
│  ├─ bash.py
│  ├─ read.py
│  └─ ...
└─ assistant
   └─ coding.py
~~~

runtime 与 tools 属于相邻层：

- tools 定义“read/edit/bash 应该具有什么语义”；
- runtime 定义“这些操作在本机、Docker 或远程主机上怎样落地”。

当前 BashOperations 已经是最明显的 Docker 注入点。read/write/edit 的 Operations 也可以在后续统一到一个更完整的 WorkspaceRuntime Protocol。

## 16. factory.py：工具组装顺序

`create_coding_tools` 创建一个 WorkspaceGuard，并让五个工具共享这个边界。

注册顺序严格为：

~~~text
read → bash → edit → write → grep
~~~

这个顺序跟随 pi 的常用 coding tool 集合，也会成为发送给模型的工具定义顺序。

工具本身不应该创建 AgentLoop，也不应该读取模型配置。factory 只负责构造工具，不负责整个产品。

## 17. 一次真实工具调用怎样流转

以 edit 为例：

~~~text
模型返回：
name = edit
arguments = {path, edits}
        ↓
AgentLoop 创建 ToolInvocation
        ↓
ToolExecutor 查找 EditTool
        ↓
prepare_arguments 兼容模型输出
        ↓
递归 Schema 校验
        ↓
WorkspaceGuard 验证路径
        ↓
mutation_queue 获取该文件的锁
        ↓
读取文件，分离 BOM，检测换行
        ↓
唯一匹配、模糊规范化、重叠检查
        ↓
逆序应用 edits，恢复换行和 BOM
        ↓
写回文件并生成 diff
        ↓
ToolResult 返回 AgentLoop
        ↓
作为 tool 消息加入模型上下文
~~~

模型只有看到真实 ToolResult 后，才能声称修改成功或决定下一步运行测试。

## 18. 安全边界总结

当前已经具备的硬边界：

- 文件路径限制在工作区；
- 拒绝 `../` 逃逸；
- 工具参数递归校验；
- edit 唯一匹配和重叠检查；
- 同文件修改串行；
- bash 可选超时和进程树终止；
- 工具输出按用途截断；
- 超长 bash 输出保存到可追踪文件。

当前尚未具备：

- Docker 沙箱；
- 命令风险审批；
- 文件修改审批；
- 网络访问控制；
- CPU、内存、磁盘配额；
- 完整审计日志；
- 自动回滚。

面试中最重要的是准确区分“工作区路径保护”和“完整执行沙箱”。前者已经实现，后者没有。

## 20. 面试时怎么讲

### 20.1 30 秒版本

MiniClaw 的工具层参考 pi 拆成 read、bash、edit、write、grep 五个独立 Python 模块。ToolExecutor 负责工具注册、参数兼容、递归 Schema 校验和异常归一化；WorkspaceGuard 限制文件路径；每个工具再负责自己的语义化输出策略。read 保留文件头部，bash 保留命令尾部并把完整超长输出落盘，grep 使用 ripgrep，edit 支持多个唯一且不重叠的 replacement，并保留 BOM 和换行格式。同一个文件的 write/edit 通过异步锁串行执行。

### 20.2 2 分钟版本

工具系统位于 AgentLoop 和操作系统之间。模型只产生结构化工具调用，真正执行统一经过 ToolExecutor。执行器会先做参数预处理，例如兼容 edit 的字符串化 edits 和旧版 oldText/newText，然后递归校验 Schema，再执行具体工具并把异常转换成 ToolResult。

五个工具不是简单封装系统 API，而是分别实现了适合编码 Agent 的可靠性规则。read 支持从 1 开始的 offset 和 limit，输出最多 2000 行或 50KB；grep 使用 ripgrep，遵守 .gitignore，并限制匹配数、总字节和单行长度；bash 合并 stdout/stderr，保留错误更常出现的输出尾部，超长完整输出写入工作区；edit 会把所有 oldText 相对原文件唯一匹配，拒绝重叠，从后向前应用，并保留 CRLF 和 BOM；write 自动建目录。write 和 edit 共享按文件路径划分的修改队列，避免并发丢失更新。

当前文件工具有工作区路径边界，但 bash 仍在本机执行，所以不是完整沙箱。未来会在 tools 下方增加独立 runtime 层，通过 Operations Protocol 注入 DockerRuntime，而不是把 Docker 逻辑塞进 AgentLoop。

## 21. 面试官可能追问

### 问：为什么 read 和 bash 的截断方向不同？

答：读文件通常先理解定义、导入和开头结构，所以保留头部；命令错误、测试总结和堆栈通常在最后，所以 bash 保留尾部。统一截断前 N 个字符会丢失 bash 最有价值的错误信息。

### 问：为什么 edit 不直接使用 str.replace？

答：编码修改必须可定位。直接 replace 无法可靠处理多次出现、多个编辑重叠、换行差异、BOM、智能引号和 diff。当前实现先定位所有编辑并做唯一性、重叠检查，再逆序应用，语义更明确。

### 问：为什么 grep 不直接遍历 Path.rglob？

答：ripgrep 对大型仓库更快，原生支持正则、glob、.gitignore、隐藏文件和二进制过滤。使用 JSON 输出还避免了手工解析路径与行号。

### 问：为什么同文件修改队列按路径划分，而不是一个全局锁？

答：全局锁会让修改不同文件的操作也互相等待，降低并发能力。按绝对路径划分可以保证同文件一致性，同时允许不同文件并行。

### 问：ToolExecutor 为什么没有默认超时？

答：不同工具合理时长不同，特别是构建命令可能超过 60 秒。pi 的 bash 只在显式提供 timeout 时限制。产品层仍可以按部署要求配置统一上限。

### 问：WorkspaceGuard 能阻止 bash 删除工作区外文件吗？

答：不能。WorkspaceGuard 保护的是由框架解析的文件路径，Shell 命令仍能自己访问其他路径。解决这个问题需要 Docker、受限账户、审批或系统级沙箱。

### 问：Docker Runtime 为什么不放进 assistant？

答：assistant 只应该选择运行环境并组装依赖。具体的文件读写和命令执行属于 runtime 能力。如果 Docker 逻辑写进 assistant，工具无法复用，测试和远程运行也会变得困难。

### 问：为什么还需要 details？

答：content 给模型阅读，details 给程序消费。比如 UI 可以用 edit.details.diff 展示修改，用 firstChangedLine 跳转，用 bash.details.fullOutputPath 提供“查看完整日志”入口，而不需要从自然语言中反向解析。

1. `tools/base.py`：理解工具协议和 ToolResult；

## 23. 总结

MiniClaw 当前的工具系统已经从“一个文件里的五个简单函数”演进成了边界清晰的工具运行层：

~~~text
Tool 协议
  ↓
ToolExecutor 统一执行
  ↓
WorkspaceGuard + 参数校验
  ↓
五个独立工具
  ↓
截断、修改队列、edit diff 等公共机制
  ↓
本机文件系统 / ripgrep / Shell
~~~

最值得强调的不是工具数量，而是每个工具都具有适合编码 Agent 的可靠性语义：

- read 可以继续分段读取；
- bash 优先保留错误尾部；
- edit 拒绝不明确和重叠修改；
- write 与 edit 避免同文件并发覆盖；
- grep 快速、结构化并尊重仓库忽略规则；
- 所有文件路径受到工作区边界保护。

它仍不是生产级安全沙箱，但已经为后续 Docker Runtime、审批、审计和远程执行留下了清晰的注入位置。
