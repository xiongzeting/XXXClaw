日期：2026-09-07。依据：本次 Luna 20 路、20 题各一次、121 阶段的冻结交付与 Trace。本文是下一轮实施方案；Dashboard 接入与报告归档已实施，下面的 Agent 改动尚未实施。

结果维度的进一步 Trace 归因见 [模型与 Agent 责任分析](./Eval3结果失败归因-模型与Agent.md)：9 道非隔离会话失败题的完整用户题面仍在最终请求中，未发现压缩事件；记忆题已定位到错误推导写入事实记忆。结果改进应先防止记忆污染、补契约验证，不应从这些失败直接推断需要重写压缩或升级检索。

我建议先做**阶段权限、有效契约与反例验证、完整请求预算**。这三项最贴近本轮失败，也容易用状态、代码和实验解释。暂时不增加 Agent 数量、不升级检索模型、不继续堆监督提示词。

## 3. P0：先让评测本身可信

这不是降难度，而是让难点来自问题本身，避免模型猜没有发出的规则。

- shipping：在下一 revision 补齐被构建器漏掉的基础费率、remote、零重量约定。当前失败只依赖公开的 amendment 排序反例，不追溯改变 r1 成绩。
- release：故障注入必须确认实际命中读取路径；允许 `open`、`read_bytes` 等正确实现。断言旧文件原字节不变，并分别检查参数错误 2、运行失败 1。
- cross-file：参考解先验证所有 `(tenant,id,revision)` 冲突，再选最高修订。加入“高版本先到、低版本内部冲突”的独立反例，避免候选与参考解共享盲点。
- transaction：明确 P2 的业务状态或净贡献，不依赖未定义的数量/单价拆解。现有 r1 按确定的总额 48 判断。

每个隐藏条件都要能指向公开要求。加入“独立人写的正确解通过、最小业务缺陷被抓到”的校准；不依赖复制参考解生成测试。已看过的题进入回归，新变体单列为保留测试，不能再说未见。

## 4. P0：把“这轮只读”落实到执行层

### 证据与判断

9 个实际违规案例：migration、audit、protocol、parser、invoice、upgrade、cross-file、extract、authorization。它们跨任务类型出现，说明仅在提示词里声明只读不足以防止副作用。授权题还在第一轮调用 API，却把参数中的阶段填成 turn3/turn4；阶段标签不能由模型自己证明。

现有 [ToolExecutor](<D:/MIniClaw/src/MiniClaw/coding_agent/tools/executor.py:61>) 已有执行前检查入口；[instruction preflight](<D:/MIniClaw/src/MiniClaw/coding_agent/assistant/coding.py:346>) 主要保证相关文件规则先注入模型，不能把它当作完整阶段授权。运行环境入口是 [ToolRuntime](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/core.py:20>) 与 [Docker 执行器](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/execution.py>)。

### 最小方案

由宿主维护当前请求的 `read_only`、可修改路径、不可读取路径与权限版本。模型仍只有既有 10 种工具；不新增权限登记工具或验收 JSON。Eval 阶段权限来自运行器配置，产品里的权限来自真实用户请求/界面状态；工具输出、检索记忆和模型自己填写的参数均不能扩大权限。

`write/edit` 在执行前检查当前权限。只读阶段的 bash 使用只读工作区视图；确需运行测试时只允许临时目录和缓存目录写入。不要用“命令包含 cat/echo/rm”这类黑名单代替隔离，因为 Python、重定向和子进程都能绕过。保护文件不挂载进模型执行视图，并在 read/search/grep 入口执行相同路径策略；宿主 Trace 目录也不能作为可写业务挂载暴露给候选。

可写阶段若先采用整工作区可写挂载，只能声称阶段只读得到保证，不能声称任意 bash 都受细粒度路径控制。精确范围可用独立可写工作副本加宿主受控回写，或按目录配置挂载；这部分可作为第二步，避免第一版造复杂文件系统。

权限检查与写入要绑定同一版本，串行化阶段切换和在途变更，避免并行调用在权限收紧后继续写入。操作日志由宿主自动补入阶段、调用 ID、目标和结果；模型可以提出业务参数，不能提交审计身份。审计继续记录写后删除，最终目录干净不等于从未违规。

### 怎么验收

保留 9 个原始违规反例，增加 read、write、edit、bash 内 Python、写后删、并行调用、路径链接、嵌套规则和“下一轮授权后允许写入”的小测试。只读业务文件字节与生命周期无变更，保护文件内容不可取得；合法读取/计算/获准修改均完成。拒绝事件和副作用事件分别记数，绝不隐藏真实工具错误来提过程分。

目标是消除当前可观测越权，同时保持合法结果通过率；“全部拒绝工具”不算成功。

## 5. P1：保留有效契约，让验证发现真实遗漏

本轮结果失败里，多项不是算法没写出来，而是接口和规则边界偏离：旧 `transform` 被删、合法 item 版本覆盖失效、修订顺序依赖输入顺序、旧 revision 内冲突被跳过、退出码混淆、`after_version` 拼错、擅自保留 `before_` 前缀、重复 ID 测试缺失。

从现有 [assistant prompts](<D:/MIniClaw/src/MiniClaw/coding_agent/assistant/prompts.py>) 和 [working context](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/working.py:240>) 入手：保留一个简短的“当前仍有效要求”段落，涵盖公开接口、优先级、例外、异常与交付范围；每条带原始消息或文件来源。新阶段只修改真正被更新的要求，不把旧要求全覆盖，也不能从助手自己的猜测生成新规则。先做普通内部文本，必要时回读原始来源；不要恢复 checkpoint、verification_rebind 等面向模型的登记协议。

验证围绕要求中的风险点生成少量反例，而不是再要求多跑一次 smoke：

| 公开契约 | 最小反例 / 不变量 |
|---|---|
| 保留旧接口 | 用原调用方式实际 import 并调用旧函数；新入口正常不代表兼容 |
| 单项覆盖全局 | 顶层版本非法 + 单项版本合法；该项仍按自己的版本处理 |
| 修订重放有序 | 同一组 amendments 的排列变化不影响最终业务结果 |
| 同修订冲突 | 最高修订先到，后面两个低修订互相冲突，也必须报错 |
| 故障点与回滚 | 精确故障标识触发后，验证异常类型和新进程恢复终态 |
| 测试充分性 | 正确实现通过；去掉重复 ID 校验后测试必须失败 |

验证命令、返回码与文件变化自动从 Trace 收集，最终自然语言回答照常保存。公开 `verify.py` 运行成功仍仅证明执行了它，不能当作结果维度通过。验收证据与候选文件哈希绑定，修改后旧证据标为过期，避免改完代码仍沿用之前的“通过”。

第一步只把这些能力做成可解释的小流程，不建设全自动形式化规范系统。当前错误已曝光，用相同规则、不同 ID/顺序/数值的变体检验泛化，禁止针对题名分支写补丁。

## 6. P1：效率优化先看完整请求，而不是缓存率

实测输入 4,314,256，占总 tokens 约 95.31%。缓存命中 69.73% 主要改善价格，不会让累计 token 验收自动通过。12 个 token 失败中，shipping 481,089、invoice 477,908、resolution 413,275、cross-file 394,801 最高。protocol 和 cross-file 同时工具调用超预算，不能只压缩输入后忽视执行次数。

读取本轮 `token_accounting.estimated_input.by_source` 后，得到按 UTF-8 字节/4 估算的累计输入分布：

| 来源 | 估算累计 tokens | 优化含义 |
|---|---:|---|
| 工作对话 | 1,263,553 | 大段要求与历史回答反复随请求发送，先核验哪些仍需原文 |
| 工具结果 | 1,119,472 | 检查重复回读、重复完整测试输出与超大结果 |
| 工具调用参数 | 983,497 | 写文件/编辑参数里的完整代码也占历史预算，不能只截断工具结果 |
| 系统提示 | 635,580 | 稳定前缀可利于缓存，缩短要验证行为不退步 |
| 工具定义 | 603,750 | 固定成本；不通过删除必需工具降低任务能力 |
| 上下文更新 | 71,388 | 集中在 memory 题，需检查同一信息是否反复注入 |
| 显式记忆注入 | 14,925 | 不是全批最大输入来源，当前不支持优先升级检索模型 |

这些是粗粒度估算，不是供应商计费分类，也不直接证明哪一项可删除。估算总和 4,692,165 与实测输入不同属正常估算误差；同一消息被多次发送会累计记账。重现入口：`python scripts/eval3_hardened/analyze_improvements.py`，只读 Trace，不调用 API。

在 [history_budget](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/history_budget.py>)、[working](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/working.py:240>) 与 [完整请求记账](<D:/MIniClaw/src/MiniClaw/trace/model_client.py:36>) 基础上做：

1. 发送前预算包含 system、工具定义、历史调用参数、结果、当前输入与输出预留。不要仅按 messages 的正文判断是否该压缩。
2. 优先保留当前有效要求、未解决错误、正在修改文件的必要内容；旧代码/大结果保留路径、哈希和短摘要，需要时用现有 read/memory 回读。
3. 按内容哈希与版本识别重复回读和重复注入。文件变更或权限变更时失效，不能把过期文件摘要当作当前内容。
4. 同一文件版本与同一验证输入不反复跑完整检查；修复后跑相关检查，交付前做一次适当回归。省略验证不能作为效率改进。

离线重放请求投影可先证明输入字节减少，不能证明模型成绩不退步。之后固定模型、预算、题目 revision 和并发做 A/B；先分开开关“工具参数历史预算”和“上下文增量”，再决定组合。主指标同时包含结果/安全、总 token、未缓存输入、已知费用、有效耗时；首字延迟与供应商等待单列。

## 7. P1：记忆与撤回，先区分信息丢失和错误使用

memory 题最终在 9 月 20 日选择 verbal 7777，而有效 lab-log 5432 优先。transaction 题撤回 P3 后仍保留其放大贡献，算成 56 而不是 48。这证明最终推导错了，但尚不足以证明 RRF、重排或压缩算法就是根因。

先沿 Trace 找三件事：原始规则是否保存、最终请求是否包含足够来源、模型是否在信息完整时仍算错。如果召回没有带回关键证据，修 [memory manager](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/manager.py:437>) 的覆盖与裁剪；如果信息已在上下文，改冲突核验步骤，不升级 BGE 或 Cross-Encoder。

最小机制是事实携带来源、作用域、有效区间、替代/撤回关系。检索相关性用于找候选，不能替代来源权威或时间有效性。回答有来源冲突时先核对有效窗口，再按用户指定优先级选择；缺证据就回读，不能用更近的低优先级口头信息覆盖记录。

撤回计算采用事件重放或依赖失效后的重算：保留“P2 净新增 8”的原始关系，撤回 P3 时撤销它及依赖贡献，保留独立 P5 的新增 10。允许用 bash 中短程序验证金额不变量，不要求模型提交内部验收字段。先服务本轮两种真实场景，不做通用知识图谱。

验收：同一租户/不同租户、有效区间右端点、unknown 到期、低优先级新记录、高优先级旧有效记录、撤回后独立分支保留，全部用不同数据检验。压缩前后答案一致，同时记录 token 增减。

## 8. P1：过程质量，少犯重复错误并保留宿主证据

cross-file 真实工具错误 6 次；下一步逐次分类是语法、路径、断言失败还是真实系统故障，不能统称“不会用工具”。在 [ToolExecutor](<D:/MIniClaw/src/MiniClaw/coding_agent/tools/executor.py>) 和 [Agent loop](<D:/MIniClaw/src/MiniClaw/agent/loop.py>) 给最近同类错误一个短诊断提示：说明错误种类、失败命令/目标，促使读取相关局部信息后再试。第一版不增加自动修复 Agent，也不固定循环次数放大总步数。

区别“运行测试成功发现缺陷”和“工具本身调用失败”，但既有 r1 分数不追溯重写；如要修订未来评分定义，提前冻结规则，并让两组对照都使用同一规则。

授权题的阶段由宿主分配，操作日志以真正发生的 write/delete 为准，完整留存拒绝、尝试、成功与失败；修改最终日志不能覆盖独立审计。程序依靠实际事件判分，不依赖模型说“已按顺序完成”。

## 9. P2：可用性已通过，下一步补边界证据

继续沿用 [模型恢复](<D:/MIniClaw/src/MiniClaw/llm/recovery.py>)、[请求实现](<D:/MIniClaw/src/MiniClaw/llm/openai_compatible.py>) 和 [取消传播](<D:/MIniClaw/src/MiniClaw/cancellation.py>)。本轮两次 `MODEL_TOTAL_TIMEOUT` 为供应商流超过 120 秒，不应直接叫作 VPN 问题。恢复请求仍共用原预算，保留之前工具结果；有缓冲输出但尚未执行工具时可丢弃缓冲后重试。

用离线模拟服务构造：首字前断开、输出中断、工具参数 JSON 截断、429/5xx、不可重试错误、用户取消和重试额度耗尽。分别检查重试次数、累计等待、是否暂停、恢复后是否交付；未知尝试用量继续标 unknown。

模型请求恢复和工具副作用恢复是两件事。工具执行状态不确定时先核验文件/持久化状态；不因请求重试重新跑写入。对“写入已完成但结果尚未保存”的窗口做一次进程故障测试，确认能说明恢复边界。取消时检查 Docker/子进程实际退出和锁释放，不以 Python 协程取消返回作为全部完成证据。

目标维持可用性 20/20 并扩充故障覆盖；不能用无限重试、整批重跑或提高预算换分。

## 10. 实施与复测方法

建议第一轮只实施阶段权限，第二轮有效契约/反例流程，第三轮请求预算。每轮先跑相关的廉价离线回归，确认后才做 API 对照；本次接 Dashboard 没有新增模型评测费用。

每次记录源码/题库/模型参数/并发/预算/判定版本哈希，复用这次最终报告的数据形状。五维全部保留；结果由后置助手判断，其他四维程序验收。原始失败、修正记录和费用缺口单独保存，不覆盖上一版。

只对同一题库 revision 的同等配置讨论改动收益。改过题面/探针后，先运行新 revision 的基线，再跑改动版；不要把修题带来的变化归因于 Agent。重复采样可先覆盖关键题族并记录波动，20 题单次差 1 题不要包装成稳定提升。

两周内最值得在简历里讲的闭环是：**发现“最终文件正确但早期越权”的问题 → 宿主阶段权限阻止副作用 → Trace 回归证明合法交付仍完成**；其次是**发现历史调用参数也在反复消耗上下文 → 完整请求预算 → 同题同预算消融证明成本降低且结果不退步**。实际完成并测得数据后再写具体提升百分比。
