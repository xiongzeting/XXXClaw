# MiniClaw Cross-Encoder 重排

## 先说结论

MiniClaw 现在不是让 Cross-Encoder 扫描整个记忆库，而是让它只处理 BM25、向量检索和 RRF 已经召回的小候选集：

```text
记忆文档库
  ├─ BM25 Top-24，负责关键词和精确实体召回
  └─ 向量 Top-24，负责语义近似召回
             ↓
      加权 RRF 合并，最多 48 个候选
             ↓
    确定性规则分数筛选与兜底
             ↓
 Cross-Encoder 同时阅读 Query + Document
             ↓
 70% Cross-Encoder + 30% 确定性分数
             ↓
          最终 Top-K
```

默认模型为：

```text
cross-encoder/ms-marco-MiniLM-L6-v2
```

该模型只从本机 Hugging Face 缓存加载。依赖、模型或缓存不存在时，不会在 Agent 运行中临时联网下载，而是自动退回原来的 BM25＋向量＋RRF＋确定性 rerank。

## 1. 为什么还需要 Cross-Encoder

原来的检索链已经包含 BM25、向量、RRF 和规则 rerank，但这些步骤都有局限：

- BM25 擅长关键词匹配，不真正理解问题和证据之间的语义关系。
- 当前向量通道主要用于扩大召回，无法精细比较两个非常相似的候选。
- RRF 只融合名次，不会重新阅读候选内容。
- 确定性 rerank 主要看词覆盖、主题短语和来源特征，解释性强，但语义能力有限。

Cross-Encoder 会把问题和一条候选证据一起送入同一个 Transformer：

```text
[Query, Candidate Document] → Transformer → 相关性分数
```

它比把 Query 和 Document 分别编码的 Bi-Encoder 更慢，但能看到二者之间的逐词交互，更适合处理：

- 问题和证据词面不完全一致。
- 多个候选都含有相同实体，但只有一个真正回答问题。
- 否定、条件、动作结果和流程关系。
- BM25 与向量召回意见不一致的候选。

## 2. 为什么不能让它扫描全库

Cross-Encoder 每比较一条文档，都要执行一次联合 Transformer 推理。若对两万条记忆逐条打分，CPU 延迟和计算量都不可接受。

因此 MiniClaw 把检索拆成两个阶段：

```text
第一阶段：Recall
目标：快，尽量别漏掉正确证据
方法：BM25 + 向量 + RRF

第二阶段：Precision
目标：从少量候选中选出最相关证据
方法：Cross-Encoder
```

当前 BM25 和向量通道各取 Top-24，并集最多 48 条。Cross-Encoder 只处理这 48 条，不接触其余文档。

## 3. 三种记忆来源怎样使用 Cross-Encoder

MiniClaw 自动召回时有三个历史来源：

- Semantic：稳定事实、项目约束和用户明确要求记住的信息。
- Archive：压缩前保存的完整对话、工具结果和 Artifact 原文。
- Episodic：历史任务的 Goal、结果、错误和经验摘要。

当前采用“各来源先召回，最终只做一次 Cross-Encoder”的结构：

```text
Semantic：BM25 + 向量 + 来源内 RRF ─┐
Archive： BM25 + 向量 + 来源内 RRF ─┼─→ 跨来源 RRF
Episodic：BM25 + 向量 + 来源内 RRF ─┘       ↓
                                      Cross-Encoder 一次重排
                                               ↓
                                           最终 Top-K
```

没有在三个来源内部各执行一次 Cross-Encoder，再在外面重复执行一次。这样可以：

- 避免同一请求运行三到四次神经重排。
- 让不同来源的候选在同一语义尺度上直接竞争。
- 保留来源内 BM25＋向量＋RRF 的召回能力。
- 让 Trace 中的最终分数更容易解释。

模型主动调用 `memory.search`、`memory.archive_search` 或 `memory.episode_search` 时，只搜索一个指定来源，因此该次搜索默认可以直接执行 Cross-Encoder。

## 4. Archive 为什么只重排命中的子块

Archive 使用父子召回：先命中约 1600 字符的子块，再把同一消息的相邻块展开，作为完整证据注入模型。

```text
前一子块 + 命中子块 + 后一子块 = 注入给回答模型的父节点
```

但 Cross-Encoder 的最大输入为 512 Token。如果直接把整个父节点送入重排，前一子块可能占满输入，使真正命中的子块被截断。

当前处理方式是：

```text
用于排序：命中子块 anchor
用于回答：anchor 前后相邻块组成的完整父节点
```

也就是说，排序阶段优先保证相关证据可见，回答阶段仍给模型连续上下文。为了避免超长 Goal 挤占正文，Cross-Encoder 输入中的 subject/Goal 前缀还限制为最多 400 字符。

## 5. 最终分数怎样计算

RRF 候选先得到确定性分数，包含：

- RRF 名次分数。
- Query 词覆盖率。
- Subject 词覆盖率。
- 完整 Query 短语。
- 有意义的连续多词主题短语。
- 少量类别特征。

Cross-Encoder 输出原始 logit 后，先用 sigmoid 映射到 0～1：

```text
ce_score = sigmoid(cross_encoder_logit)
```

最终分数为：

```text
final_score = 0.70 × ce_score
            + 0.30 × normalized_deterministic_score
```

保留 30% 确定性分数的原因是：

- Cross-Encoder 模型主要在英文搜索数据上训练，不应完全覆盖中文和代码标识符的词面证据。
- 精确文件名、错误码、函数名和版本号通常更适合 BM25。
- 模型不可用时，可以无损退回确定性排序。

## 6. 运行时与性能控制

实现包含以下控制：

- 惰性加载：第一次真正需要重排时才加载模型。
- 类级模型缓存：同一进程中的多个 MemoryManager 复用模型实例。
- Pair 分数缓存：相同 Query＋Document 不重复推理，最多缓存 20,000 对。
- 批处理：默认每批 16 个候选。
- 推理锁：避免多个线程同时驱动同一个本地模型造成资源竞争。
- 本地限定：只读取本机缓存，不在在线任务中隐式下载。
- 自动降级：模型或依赖缺失时继续使用原确定性排序。
- 候选上限：最多重排 48 条，不随记忆库体积无限增长。

本机烟雾测试中：

- 第一次模型加载约 5～9 秒。
- 模型加载后，24 个短候选的纯重排约 0.05 秒。
- LongMemEval-V2 的候选更长，平均 Cross-Encoder 阶段约 1.84 秒。

长候选和短候选的延迟不能直接比较；真正影响推理量的是候选数量和截断前文本长度。

## 7. 为什么保留 48 个候选

同一批 40 题做过不调用回答模型的候选池对照：

| 配置 | 正确答案短语进入 Top-1 | 进入 Top-5 | CE 平均耗时 |
|---|---:|---:|---:|
| 无 Cross-Encoder | 9/40 | 13/40 | 0 |
| Cross-Encoder，24 候选 | 10/40 | 12/40 | 约 1.03 秒 |
| Cross-Encoder，最多 48 候选 | 11/40 | 14/40 | 约 1.84 秒 |

这里的“答案短语进入证据”是一个可重复的检索代理指标，不等同于最终回答正确率。它说明 24 候选虽然更快，但会在部分问题上过早截断召回候选，因此当前保留 48。

## 8. LongMemEval-V2 同批结果

同一随机种子、同一批 40 题、同一回答模型的结果：

| 指标 | 原确定性 rerank | Cross-Encoder |
|---|---:|---:|
| 正确率 | 9/40，22.5% | 10/40，25.0% |
| Unknown | 14 | 14 |
| 模型错误 | 0 | 0 |
| 平均检索耗时 | 2.50 秒 | 4.39 秒 |
| 检索中位数 | 1.63 秒 | 3.28 秒 |
| 输入 Token | 327,924 | 345,019 |
| 总运行时间 | 493.87 秒 | 498.65 秒 |

逐题变化为新增 4 题通过、3 题回归，净增 1 题。由于远程回答模型即使温度为 0 也可能存在输出波动，不能把净增全部归因于 Cross-Encoder。

当前可以可靠表达的结论是：

- Cross-Encoder 已完整接入真实检索链和 Trace。
- 检索代理指标的 Top-1、Top-5 均有小幅提升。
- 最终回答正确率有净提升，但样本较小，暂不能宣传为稳定显著提升。
- CPU 检索延迟明显增加，因此它是可配置能力，而不是不可关闭的硬依赖。

## 9. 配置方法

安装可选依赖：

```text
pip install -e ".[rerank]"
```

环境变量：

```ini
MINICLAW_MEMORY_CROSS_ENCODER_ENABLED=true
MINICLAW_MEMORY_CROSS_ENCODER_MODEL=cross-encoder/ms-marco-MiniLM-L6-v2
MINICLAW_MEMORY_CROSS_ENCODER_CANDIDATES=48
MINICLAW_MEMORY_CROSS_ENCODER_WEIGHT=0.70
MINICLAW_MEMORY_CROSS_ENCODER_BATCH_SIZE=16
MINICLAW_MEMORY_CROSS_ENCODER_MAX_LENGTH=512
```

代码默认是 opt-in：如果调用方没有加载 `.env`，Cross-Encoder 不会自行开启。MiniClaw 的项目 `.env` 和 `.env.example` 已显式开启，因此正常 CLI、飞书和 Benchmark 启动会使用它。

关闭方式：

```ini
MINICLAW_MEMORY_CROSS_ENCODER_ENABLED=false
```

## 10. Trace 记录什么

每次重排会记录：

- `cross_encoder_enabled`：是否配置了重排器。
- `cross_encoder_applied`：本次是否实际成功执行。
- `cross_encoder_model`：模型名称。
- `cross_encoder_candidates`：实际重排候选数。
- `cross_encoder_seconds`：重排耗时。
- `cross_encoder_load_error`：加载或依赖错误。
- `deterministic_score`：原确定性分数。
- `cross_encoder_score`：Cross-Encoder 归一化分数。
- `final_rerank_score`：最终融合分数。

这使后续 Eval 可以区分：

```text
候选根本没被召回
Cross-Encoder 排错了
正确证据已进入 Top-K，但回答模型没用对
模型未加载，实际走了降级链路
```

## 12. 降级与兼容性

MiniClaw 保留了旧自定义 Retriever 的兼容性：

- 旧 Retriever 没有 `use_cross_encoder` 参数时，仍可继续搜索。
- 旧 Retriever 没有 `rerank_documents` 时，最终层自动使用确定性 rerank。
- Cross-Encoder 返回失败时，不改变原确定性顺序。
- 新增的分数字段带默认值，不破坏旧 RetrievalHit 构造代码。

当前全项目为 187 项单元测试通过，新增测试覆盖：

- Cross-Encoder 能把相关候选提升到第一名。
- 只处理配置的候选池。
- 来源内关闭时不重复运行。
- 模型缺失时确定性降级。
- 环境变量边界校验。
- Archive 最终重排使用 anchor，而不是被展开父节点前缀截断。

## 13. 面试常问问题

### Q1：为什么已有向量检索还要 Cross-Encoder？

向量检索适合从大库快速召回，Cross-Encoder 适合在小候选集内精排。前者解决“别漏”，后者解决“谁更相关”，两者不能互相替代。

### Q2：为什么放在 RRF 后面？

BM25 和向量先把两万级文档缩小到最多 48 条，Cross-Encoder 才有可接受的 CPU 成本。若放在 RRF 前面对全库推理，延迟会随文档量线性爆炸。

### Q3：为什么三个来源不各跑一次？

各来源只负责召回，跨来源 RRF 后统一重排，能减少重复推理，也能让 Semantic、Archive 和 Episode 在同一个语义尺度上竞争。

### Q4：Cross-Encoder 挂了会不会导致记忆不可用？

不会。它是精排增强层，不是召回依赖。模型、依赖或缓存缺失时，系统继续使用 BM25＋向量＋RRF＋确定性 rerank，并在 Trace 中记录降级原因。

### Q5：为什么不是 100% 使用 Cross-Encoder 分数？

当前模型偏英文通用检索；代码符号、路径、版本号、中文实体更依赖 BM25 和确定性特征。保留 30% 确定性分数，可以降低领域偏差和模型误排风险。

### Q6：当前最大问题是什么？

40 题样本中最终正确率只净增 1 题，说明 Cross-Encoder 只能重排已经召回的候选，无法修复“正确证据根本不在候选集”或“父节点缺少完整状态链”的问题。后续应分别测候选召回率、重排 NDCG/MRR 和最终答案正确率，不能只看一个端到端成功率。
