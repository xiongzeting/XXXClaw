## 0. 先读这一页：你在面试中的定位

### 0.1 面试官对你的第一判断

如果我是这个岗位的面试官，我会把你定位成：

> **软件工程背景、能把 Agent 做成工程系统，同时真正跑过 LoRA SFT 与在线 GRPO 的硕士候选人。**

你的简历最有价值的不是“写了很多名词”，而是出现了两条互相补强的证据链：

```text
购物项目：数据 → SFT → Reward → 在线 GRPO → Harness → Benchmark
MiniClaw：模型协议 → Agent Loop → Tool Runtime → Memory → Eval
```

前一条证明你接触过后训练和 Agentic RL；后一条证明你理解模型之外的执行、上下文、安全和评测。面试时不要把两个项目讲成两个孤立 Demo，要反复回到这句话：

> 模型负责提出决策，环境和 Runtime 负责执行边界，评测负责证明结果，数据闭环负责下一轮改进。

### 0.2 星级含义

每个问题前面的星级是面试优先级，不是问题难度。

| 标记 | 含义 | 准备要求 |
|---|---|---|
| ★★★★★ | 必问、决定是否进入下一轮 | 必须脱稿，能接至少三层追问 |
| ★★★★☆ | 高频深挖 | 能讲实现、取舍和边界 |
| ★★★☆☆ | 常见扩展 | 能给出结构化回答，不必背全部细节 |
| ★★☆☆☆ | 可能的交叉追问 | 先掌握结论和一个例子 |
| ★☆☆☆☆ | 低概率或开放题 | 知道定义，避免说错即可 |

### 0.3 统一答题公式

任何项目问题都优先按下面五步回答，避免一上来倾倒名词：

1. **结论**：我解决的具体问题是什么。
2. **机制**：系统/算法如何工作，关键数据如何流动。
3. **证据**：一个数字、一个 case 或一个测试入口。
4. **取舍**：为什么这么设计，放弃了什么。
5. **边界**：当前版本没有证明什么，下一步怎么验证。

示例：

> 我用动态 Tool Schema 和 Action Guard 降低长程购物中的非法动作。Schema 根据最新页面只暴露可执行动作，Guard 在执行前再次校验 ASIN、规格 ID 和按钮状态。旧版 Final-240 的 Guard 拒绝次数从 82 降到 25，但这一组同时换了 Harness，因此我把它作为完整系统收益，不声称是单独 Schema 的因果消融。当前顺序候选版本又改变了收敛方式，旧版“模型从候选列表挑一个”的说法已经不适用。

### 0.4 面试官最想确认的五件事

| 面试官要确认什么 | 你的证据 | 最容易失分的说法 |
|---|---|---|
| 你是否真的做过训练 | Teacher 筛选、Action-only SFT、GRPO rollout、Reward 设计 | “veRL 帮我自动训练，所以我做了 GRPO” |
| 你是否理解 Agent 系统 | MiniClaw 三层架构、Loop、Runtime、Memory、Trace | “Agent 就是模型调用工具” |
| 你是否能做数据闭环 | 三层质量门、纠错轨迹、冻结评测、Bad case 回流 | “数据越多越好” |
| 你是否有评测意识 | 固定分母、确定性成功、Rubric、Judge、资源指标 | 只报最好看的成功率 |
| 你是否诚实可靠 | 版本差异、无消融、无实时淘宝、未做的算法 | 把历史文档或框架能力说成当前实测 |

## 2. 开场必问：自我介绍、动机与项目主线

### ★★★★★ Q1：请你做一个 60 秒自我介绍

**面试官想听什么：**学历匹配、方向匹配、真实项目、可到岗性；不是听完整技术名词清单。

**推荐回答：**

> 您好，我叫熊泽廷，目前是中国科学技术大学软件工程硕士在读，本科就读于河海大学软件工程。我主要关注 Agent 工程和大模型后训练，最近做了两个相关项目。
>

## 3. 按简历第一段逐词拆解：购物 Agent 项目

### 3.1 项目一句话必须讲清

> 基于淘宝真实商品快照环境，把 Qwen3.5-2B 从不会稳定完成工具交互的 Base，通过 Teacher 数据、LoRA SFT、在线 GRPO、Reward 和 Harness 优化，训练成能搜索、比较、核验规格并购买的长程 Agent，并用固定 240 题评测结果、过程质量和资源成本。

这句话里有六个面试入口：

1. ★★★★☆ “淘宝真实商品快照”——是不是实时淘宝？
2. ★★★★☆ “长程”——为什么不是一次分类？
3. ★★★★★ “SFT-GRPO”——两阶段各解决什么问题？
4. ★★★★★ “Agent”——动作、状态、Observation 如何循环？
5. ★★★★★ “正确率”——Gold、Valid、Partial 怎么定义？
6. ★★★★☆ “优化”——究竟是模型、Reward、Harness 还是评测改变？

### ★★★★★ Q8：这个购物环境到底是什么？是真实淘宝吗？

**推荐回答：**

> 不是直接操作线上淘宝，而是 ShopSimulator 中基于真实商品快照的可复现交互环境。商品标题、品牌、属性、价格和多规格尽量保留真实业务复杂度，但商品库、任务、搜索结果和状态转移是冻结的。这样可以让训练和评测重复执行，避免线上库存、价格和页面变化破坏对比。

**追问（沿用 Q8：★★★★★）：为什么不用线上淘宝？**

> 线上环境不可控，存在登录、反爬、库存、价格变化、隐私和真实购买副作用；研究后训练需要确定性和可审计。快照环境牺牲了部分现实动态性，换来可复现、可回放和安全。

**追问（沿用 Q8：★★★★★）：快照环境会不会过拟合？**

> 会有风险，所以要做 task/family 零重叠、固定 held-out、Challenge 切片和不同搜索位置分布；但它仍不能证明线上客服泛化，需要额外的时间切分、多语言和真实流量回放。

### ★★★★★ Q9：为什么叫“长程购物 Agent”？长在哪里？

**推荐回答：**

> 长程不只是步数多，而是一个动作会改变下一步合法动作和可见证据。模型要先理解自然语言约束，再搜索、翻页、打开候选、核对公开属性、逐轴选择规格、确认最终 variant 价格，最后才能购买。中间任何一步都可能造成状态变化，不能把所有动作并行或脱离最新页面执行。

可以把一条轨迹抽象为：

```text
用户 Query
  → search_products
  → open_product
  → select_option × n
  → buy_now / back_to_search
  → terminal Reward
```

### ★★★★★ Q10：为什么 Base 是 0%？这是不是基线故意做差？

**推荐回答：**

> 0% 是特定模型、工具协议、上下文和成功定义下的结果，不等于 Base 完全不懂商品。小模型在未经后训练时会出现非法工具、错误参数、重复动作、没有完成规格选择或在终局前停下。基线和后训练模型使用同一固定题集、同一环境和同一分母，Base 的失败轨迹也保留下来做诊断。
>
> 我会重点检查 Base 是否使用了正确 Chat Template、同样的工具 Schema、相同预算和正确的 Observation，而不是用接入错误制造零分。当前数据里 Base 的 Guard 拒绝和非法动作很多，说明协议学习是第一瓶颈；SFT 后才转向候选比较和证据核验。

### ★★★★★ Q11：为什么选 Qwen3.5-2B，而不是直接用更大的模型？

**推荐回答：**

> 2B 的优势是训练和 rollout 成本可控，而且能清楚暴露数据、协议和 Reward 是否真的有效。大模型可能掩盖 Harness 和数据问题。Qwen3.8-27B 作为同协议外部 Actor 对照，用来观察模型规模和后训练的相对作用，而不是证明 2B 在所有任务上超过 27B。

**追问（沿用 Q11：★★★★★）：2B 的限制是什么？**

> 长上下文、复杂否定、近似价格、多规格和候选比较仍容易失败；它对 Prompt 和工具反馈很敏感。后续可以做更大模型蒸馏、模型规模对照和跨域测试。

### ★★★★★ Q12：Agentic RL 与普通文本分类/生成有什么不同？

**推荐回答：**

> 普通生成通常一次输出，标签或文本可以直接和答案比较；Agentic RL 中，模型的输出是动作，动作进入环境后改变状态，环境再返回 Observation，最终 Reward 依赖整条轨迹。奖励可能只在购买或终止时产生，因此要处理长程信用分配、非法动作、重复循环和样本有效性。

**不要说：**“每生成一个 token 就直接得到一个业务奖励。”本项目主要是终局 Reward，工具结果作为下一步上下文。

### ★★★★☆ Q13：为什么 SFT 在前、GRPO 在后？能不能直接 GRPO？

**推荐回答：**

> Base 的非法动作和无效终局太多，直接 GRPO 会得到大量常数或不可验证的 Group，优势接近零，训练信号很差。SFT 先教模型基本工具协议、页面状态和成功轨迹，让在线 rollout 能进入有效区域；GRPO 再利用当前策略采样的成功/失败差异优化候选决策、证据核验和停止时机。

**追问（沿用 Q13：★★★★☆）：SFT 是否只是模仿，不能泛化？**

> 是的，SFT 主要覆盖示范分布；它能降低冷启动难度，但不能穷举所有搜索改写和候选组合。GRPO 的价值是让策略在环境反馈下探索未被示范覆盖的决策，但它也依赖 Reward 质量和组内差异。

### ★★★★☆ Q14：项目中的“正确购买”到底指什么？

**先给简历口径，再给当前口径：**

> 简历里的“购买成功”采用当时评测的 Gold＋Valid 购买成功口径，即严格目标商品或满足公开约束的有效替代商品都可以计入；严格 Gold 则只认目标 ASIN 和完整约束。当前 Reward v4 又进一步要求可评分 Hard 和 Soft 都通过才进入 Gold；scored Soft 可验证地失败会成为 Partial，Soft 不可核验会标成 `reward_unverifiable`，Hard 失败会成为 Wrong。所以我报告数字时一定同时说明 Reward、Harness 和版本。

## 4. 简历核心技术逐词解释：Agentic RL、Qwen、LoRA、SFT、GRPO、veRL、vLLM

### ★★★★★ Q15：请分别解释你简历里的七个核心技术名词，并说它们在项目中各自负责什么

| 名词 | 一句话 | 项目位置 | 不负责什么 |
|---|---|---|---|
| Agentic RL | 在环境交互轨迹上用反馈优化动作策略 | GRPO rollout 与 Reward | 不等于普通聊天 SFT |
| Qwen3.5-2B | 被优化的基座语言模型 | Actor/Policy | 不是训练框架 |
| LoRA | 在冻结基座上学习低秩增量矩阵 | SFT 与 GRPO 可训练参数 | 不会自动减少所有激活/KV 显存 |
| SFT | 用示范动作监督模型 | Teacher→训练集→模型 | 不负责在线探索 |
| GRPO | 通过同一输入多条轨迹的相对奖励更新策略 | 在线训练 | 不负责定义业务正确性 |
| veRL | 编排 rollout、Reward、优势和训练更新 | 训练基础设施 | 不会自动设计 Harness/Reward |
| vLLM | 高效生成 rollout 的推理引擎 | 采样执行 | 不做梯度更新 |

**口语串联：**

> Qwen3.5-2B 是 Actor，LoRA 是参数更新方式；SFT 用 Teacher 轨迹解决冷启动，GRPO 在环境中在线采样并比较组内 Reward；vLLM 负责生成动作，veRL 组织采样和训练，Harness 把动作送进 ShopSimulator，Reward 再把结果反馈给 GRPO。

### ★★★★☆ Q16：Qwen3.5-2B 的“2B”是什么意思？

> 2B 通常指约 20 亿量级参数，不是上下文长度、显存大小或训练步数。实际可用显存还包括权重精度、激活、KV Cache、LoRA、框架缓冲和 rollout 并发。不能用“2B×4 bytes”直接当作完整训练显存。

### ★★★★☆ Q17：LoRA 的原理和公式是什么？

冻结原权重 `W`，只学习低秩更新：

$$
W' = W + \Delta W,\qquad \Delta W = \frac{\alpha}{r}BA
$$

其中 `A∈R^{r×d_in}`、`B∈R^{d_out×r}`，`r` 远小于原矩阵维度，`α` 控制缩放。前向可以理解为原线性层加一个低秩旁路。

**项目回答：**

> 我用 LoRA 是为了在 2B 模型上降低可训练参数和优化器状态，方便 SFT 与 GRPO 迭代；基础权重仍参与前向，长上下文激活和 vLLM KV Cache 仍可能成为显存瓶颈。训练结束可以把 LoRA 增量合并到基座生成 HF 权重，但合并前必须确认基座、Tokenizer、dtype 和 checkpoint lineage 一致。

### ★★★★☆ Q18：LoRA 的 rank、alpha、target modules 怎么选？

> rank 决定适配子空间容量，越大参数和表达能力越高但成本也高；alpha 是缩放，不等于 rank；target modules 决定哪些线性变换可适配。我的项目以配置和显存为约束做选择，不能声称当前值在所有数据上最优。应通过固定验证集比较成功率、Reward、稳定性和资源，而不是只看训练 loss。

### ★★★★☆ Q19：SFT 的 loss 是什么？和预训练有什么区别？

自回归语言模型的 token 级交叉熵可写成：

$$
\mathcal L=-\sum_t m_t\log p_\theta(y_t\mid y_{<t},x)
$$

预训练通常对大规模无标注文本的下一个 token 计算损失；SFT 使用任务示范，`m_t` 可以只选择需要学习的 Assistant 动作 token。购物项目重点是让模型学会在 Observation 后输出合法动作，而不是重新学习商品文本。

### ★★★★☆ Q20：GRPO 和 PPO 的核心区别是什么？

> PPO 通常需要 Critic 或价值估计，并用 old policy/reference 等机制限制更新；GRPO 以同一 prompt 的多条 rollout 奖励构造组内基线，减少单独 Critic 的依赖。两者都可以使用 clipped policy objective，但数据组织、优势估计和工程实现不同。我的实践是在线 GRPO，不是完整 PPO 训练。

### ★★★★☆ Q21：veRL 和 vLLM 的边界是什么？

> vLLM 解决“如何高效生成模型输出”，关注 KV 管理、调度和吞吐；veRL 解决“如何组织强化学习训练流程”，包括 rollout、Reward、优势、梯度更新和权重同步。一个是推理执行引擎，一个是训练编排/框架。vLLM 生成出来的动作还要经过 Harness 和环境，veRL 不会替它判断商品是否合适。

### ★★★★☆ Q22：rollout.n=4 是四张 GPU 吗？

> 不是。它表示每个输入采样四条轨迹，用于组内 Reward 比较。GPU 数量、并发 worker、batch size、group size 是不同概念。四条轨迹仍可能由调度器在一个或多个设备上执行。

### ★★★★☆ Q23：为什么不能把 vLLM 带来的速度提升直接写成正确率提升？

> vLLM 主要改变推理执行效率和调度，正确率主要由模型参数、Prompt、工具协议、Reward 和环境决定。采样速度变化可能间接影响训练吞吐，但需要同硬件、同请求分布、同采样配置的对照才能归因。

```text
结果层：终局是否真的满足任务
        ↓
过程层：动作、工具、状态和证据是否可重放
        ↓
行为语义层：是否存在循环、近似购买、无意义探索等模式
        ↓
长度/难度/能力覆盖配平
        ↓
600 条正常轨迹 + 400 条纠错轨迹
        ↓
30K token 合同、assistant-only labels、LoRA SFT
```

### ★★★★★ Q24：8,708 条 Teacher 候选是怎么来的？是不是 8,708 条都拿去训练？

**推荐回答：**

> 8,708 是多来源生成和采集后的候选池，不是最终训练集。先按结果、过程和行为语义三层质量门审计，再按轨迹长度、检索难度、能力类型和 bad case 做配平，最后形成 600 条正常与 400 条纠错的 1,000 条 SFT 数据。面试时我会明确“候选池”和“最终训练数据”两个分母，避免把数据规模夸大。

**追问（沿用 Q24：★★★★★）：为什么不直接用全部候选？**

> 低质量或重复轨迹会把错误动作、错误工具参数和单一模板写进策略；过多短轨迹会让模型只会最容易的路径；包含隐藏目标或不可重放状态的样本还可能造成泄漏。

### ★★★★★ Q25：三层筛选分别筛什么？请给一个会被拒绝的例子

| 层 | 问题 | 例子 |
|---|---|---|
| 结果层 | 最终是否完成公开任务 | 买错品类、Hard 约束失败、没有合法终局 |
| 过程层 | 轨迹是否可重放、动作是否基于当时页面 | 用历史 option ID、工具参数错、多个动作无法配对 |
| 行为语义层 | 行为是否值得教给模型 | 重复搜索、无进展循环、近似商品却直接购买、先说完成后未核验 |

**口语回答：**

> 结果正确是必要条件，但不是充分条件。一条轨迹可能碰巧买到 Gold，却经过大量 Guard 拒绝或没有核验最终规格；如果把它直接做 SFT，模型会学到脆弱甚至错误的行为。所以我把“结果能不能交付”和“过程值不值得模仿”分开。

### ★★★★★ Q26：600 条正常＋400 条纠错，为什么这样配？

> 正常轨迹提供稳定的基础动作分布，纠错轨迹覆盖循环、近似商品、错误规格、搜索改写和终局犹豫等困难状态。比例是工程配额，不是经过完整消融证明的最优比例；如果面试官要求严谨结论，我会说需要比较 800/200、600/400、400/600 等配比，并按难度分层报告结果。

### ★★★★★ Q27：纠错轨迹是不是把失败动作直接当成监督答案？

> 不是。纠错轨迹可以包含错误尝试，但最终必须恢复并完成严格成功；写入 SFT 时会删除可安全清洗的 Guard 拒绝 assistant/tool 对，保留恢复后的合法动作与 Observation 对齐，不把非法调用本身当监督目标。纯失败轨迹更适合做偏好数据、失败分析或在线 RL 的负反馈，不能不加筛选地做 SFT 正例。

### ★★★★★ Q28：你说“处理循环、近似商品购买等 bad case”，具体怎么处理？

**推荐回答：**

> 对循环，我关注同一搜索词、同一 canonical action、同一页面状态是否反复出现，并保留能从错误中恢复的示范；对近似商品购买，我检查它是否满足 Hard 约束、是否只在 Soft 偏好上让步，以及购买前是否核对公开证据。最终不是简单删除所有长轨迹，而是让数据覆盖“发现问题—改变策略—完成任务”的恢复过程。

### ★★★★☆ Q29：为什么要配平轨迹长度？长轨迹是不是一定更好？

> 长度只是难度的一个代理，不等于质量。全是短轨迹会让模型缺乏长程状态经验；强行拉长又会诱导无意义探索。更合理的是联合任务难度、Gold 检索位置、候选数量、规格轴和行为类型做分层配额，长度只作为一个约束。项目早期尝试过强行拉长，后来转向任务难度和能力覆盖驱动。

### ★★★★☆ Q30：怎样避免训练集和评测集泄漏？

> 至少检查 task ID、family、Query 近似、轨迹 ID 和商品/任务来源集合；SFT、GRPO probe 与 Final-240 分开建池。只检查字符串不够，因为同一个任务可能换措辞后仍然泄漏；但过度删除所有语义相近 Query 又会损失真实泛化分布，需要记录规则和误删风险。

### ★★★★★ Q31：30K 上下文下，超长轨迹怎么处理？

> 先保留完整 Assistant Tool Call 与对应 Tool Result 的协议单元，不能从中间截断成半个调用。超过训练合同的样本整条拒绝或回到候选池补采；同时做 token audit，检查 tokenizer、特殊 token、Tool Call JSON 和 Observation 是否都计入。30K 是合同上限，不代表每条样本都接近 30K。

### ★★★★★ Q32：assistant-only Loss 是什么？为什么适合 Tool Calling？

**推荐回答：**

> 输入里仍包含 System、User、环境 Observation 和 Tool Result，但 label mask 只在 Assistant 需要学习的动作 token 上为 1，其他位置设为 `-100`。这样模型能读取环境信息，却不会把长商品页面、Teacher 的私有解释或工具返回文本当成需要逐字复制的目标。

简化代码：

```python
loss = cross_entropy(
    logits[:, :-1],
    labels[:, 1:],
    ignore_index=-100,
)
```

**追问（沿用 Q32：★★★★★）：为什么不监督 Observation？**

> Observation 是环境给出的条件，不是策略要生成的动作；监督它会浪费容量，也可能把环境文本模板化。它仍然保留在上下文中影响下一步策略。

### ★★★★☆ Q33：为什么不训练 Teacher 的完整思维链？

> Teacher 思维链可能含隐藏目标、冗余描述或模型特有表达；当前任务更关心可执行动作和证据。Action-only 让部署输出与训练目标一致，也降低答案泄漏。若要训练 reasoning，需要单独定义隐私、质量和可验证性边界，不能默认把长 CoT 全部蒸馏。

### ★★★★☆ Q34：SFT 训练 loss 下降但成功率不升，可能是什么原因？

按顺序排查：

1. label mask 错，把 Tool/Observation 也算进 loss；
2. Chat Template 或 special token 不一致；
3. 数据结果正确但过程高度重复、难度过低；
4. train/validation 泄漏或验证集分布不匹配；
5. 模型学会格式，却没有学会当前页面 grounding；
6. 评测 Reward/工具 Schema 与训练合同不一致。

### ★★★☆☆ Q35：为什么 1,000 条数据也可能有效？

> 目标不是学习通用世界知识，而是固定环境里的工具协议和行为模式；高质量、覆盖多种困难的 1,000 条可能比大量重复短轨迹有效。但不能据此断言 1,000 是最优规模，仍需规模、配比、去重和跨任务消融。

## 6. Reward 与 GRPO：面试官会从数学追到业务语义

### 6.1 先记住当前 Reward v4 的决策树

```text
任一 scored Hard 失败
        → wrong_purchase (-1.00)
没有 Hard 失败但任一 scored Hard/Soft 不可核验
        → reward_unverifiable (0, valid=false)
Hard 全过、scored Soft 可验证且至少一项失败
        → partial_alternative_purchase (0.50 + 0.30×soft_score)
Hard/Soft 全过 + 目标 ASIN
        → gold_purchase (1.00)
Hard/Soft 全过 + 替代 ASIN
        → valid_alternative_purchase (0.80)
```

另有 `early_abstain=-0.40`、`repeat_loop=-0.60`、`assistant_final=-0.80`、`guard_rejection=-0.80`、`max_steps=0`（再叠加步数惩罚）等终局。第 16 个已执行工具步骤起有分段递增的累计步数惩罚；按当前函数逐段相加到 45 步约为 `-1.05`，部分历史说明写成约 `-1.06`，面试时以对应代码/运行 artifact 为准。

### ★★★★★ Q36：为什么要把用户 Query 编译成 Hard/Soft 约束？

> 自然语言里的“必须”“不超过”“最好”“左右”“尽量”强度不同。如果把所有条件都当硬门，系统会拒绝合理替代；如果全部软化，超预算、错品类和明确型号冲突可能被高分掩盖。因此先保留 Query 原文 span，再把可确定性比较的要求编译成 Hard、Soft、Ignore 或 Needs Review，并在终局逐项核验。

### ★★★★★ Q37：预算到底是 Hard 还是 Soft？

> 取决于原话。明确“不超过 500 元”通常是 Hard；“预算 500 左右”“最好 500 内”更可能是 Soft。不能只看字段名或 Gold 商品价格，也不能让模型自己决定约束强度。语义编译要保留证据、操作符、期望值和实际值来源，歧义要求可以 `audit_only`，避免制造错误负样本。

### ★★★★★ Q38：为什么目标 ASIN 也不能免检？

> Gold 身份只说明它是任务标注的目标，不说明用户 Query 的每个公开条件都满足。若目标商品违反 Hard，直接给 Gold 会让 Reward 鼓励错误购买；若 scored Soft 有可靠证据且失败，当前 v4 降为 Partial；若 Soft 无法核验则是 `reward_unverifiable`。这样能避免评测和训练对隐藏 Gold 的投机。

### ★★★★★ Q39：Hard、Soft、Partial、Valid、Gold 如何区分？

| 类型 | 语义 |
|---|---|
| Hard | 不可妥协且可确定核验的要求；失败即 Wrong |
| Soft | 可让步偏好；可验证地失败且 Hard 全过则 Partial，不可核验则 invalid |
| Gold | Hard/Soft 全过且目标 ASIN 正确 |
| Valid alternative | Hard/Soft 全过但不是目标 ASIN |
| Partial alternative | Hard 全过且至少一个 scored Soft 有可验证证据但失败，目标/替代都适用 |
| Wrong | 任一 scored Hard 失败 |
| Unverifiable | 评分证据未知，不能把未知当满足 |

**面试陷阱：**当前候选收敛阶段只允许模型依据 Hard 拒绝候选，Soft 失败不能直接 `back_to_search`；这是为了避免候选阶段因软偏好过早放弃，终局 Reward 仍然严格检查 Soft。见 Q53。

### ★★★★★ Q40：递增步数惩罚为什么不是每步固定扣分？

> 固定每步扣分会让短但错误的轨迹和长但最终正确的轨迹之间难以平衡。前期允许模型探索，超过合理步数后逐渐增加成本，鼓励尽快收敛但不把必要的多步核验直接打成负分。惩罚只对 `reward_valid=true` 的有效终局叠加（包括有效的 wrong/repeat/assistant_final/guard 等负样本）；`reward_unverifiable` 或基础设施无效不加，步数边界和 Environment 的无进展终止仍是独立机制。

### ★★★★☆ Q41：步数惩罚会不会导致模型过早购买？

> 会有风险。模型可能为了避免惩罚而跳过候选比较、规格核验或选择错误商品，所以必须同时看严格 Gold、约束状态、证据核验、错误购买和终止效率，而不是只看平均步数。Reward 设计要让“少做无意义动作”和“少做必要核验”可区分。

### ★★★★★ Q42：什么是 on-policy？你的 GRPO 为什么是 on-policy？

> on-policy 指训练数据由当前或近似当前策略与环境交互产生。每轮 GRPO 用当前 Actor 通过 vLLM 采样多条购物轨迹，按最新 Reward 计算组内优势，再更新策略；更新后重新采样。旧策略数据不能无限复用，否则会产生分布偏移，需要记录 policy/checkpoint 和采样时间。

### ★★★★★ Q43：GRPO 的组内优势怎么计算？

最简形式是对同一 prompt 的 `G` 条轨迹奖励做中心化：

$$
A_i = R_i - \frac{1}{G}\sum_{j=1}^{G}R_j
$$

某些实现再除以组内标准差；本项目配置关闭 `norm_adv_by_std_in_grpo`，保留中心化但不做标准差归一化。

例：奖励 `[0.2, 0.4, 0.8, 1.0]`，均值 `0.6`，中心化优势为 `[-0.4,-0.2,0.2,0.4]`。

### ★★★★☆ Q44：为什么关闭组内标准差归一化？代价是什么？

> 低方差 Group 中，极小的奖励差除以很小的标准差会被放大，可能让噪声主导更新；关闭后优势仍反映同组相对好坏，尺度更接近原始 Reward。代价是不同 Group 的梯度尺度可能更不均匀，对 Reward 标定和学习率更敏感。项目借鉴 Dr.GRPO 的关键思路，不声称完整复现论文全部设置。

### ★★★★★ Q45：为什么需要动态重采样？

> 如果一组轨迹全部失败、全部成功或 Reward 几乎相同，中心化后优势接近零，采样算力不能带来有效学习信号。动态采样会检查至少有成功购买、Reward range 超过阈值等条件，不满足时有限补采；仍无有效差异就丢弃或跳过更新。它不是“只保留高分”，而是保留可比较的成功/失败差异。

### ★★★★☆ Q46：动态采样会不会造成选择偏差？

> 会。它改变了训练 prompt 和 Group 的分布，可能过度集中在容易产生差异的题，忽略全失败但重要的能力。解决办法是记录丢弃原因、保留率和题族覆盖，并在独立 held-out 上评测；不能只报告留下的 Group。

### ★★★★☆ Q47：为什么无 KL？无 KL 会不会让策略崩掉？

> 当前配置关闭 KL Reward 和 KL Loss，是为了直接观察任务 Reward 对 SFT Policy 的作用，并减少参考模型开销。它不是没有约束：仍有 LoRA、较小学习率、PPO-style clip、有限训练步和独立评测。但无 KL 会增加策略漂移和 Reward hacking 风险，项目中也观察到成功任务回退，因此需要有无 KL、不同系数和多随机种子消融。

### ★★★★☆ Q48：日志里为什么还有 PPO KL？

> `actor/ppo_kl` 可以是诊断策略偏移的监控指标，不代表它进入优化 Loss。要看 `use_kl_loss`、`kl_loss_coef`、`use_kl_in_reward` 等配置。监控 KL 和施加 KL 惩罚是两件事。

### ★★★★☆ Q49：Reward 提高但严格成功率不提高，可能为什么？

1. Reward 软分或步数分提高，但 Hard 仍失败；
2. Reward 允许替代商品，购买成功率提高但 Gold 不变；
3. Reward 与真实业务目标错位，模型学会投机；
4. 评测样本、Harness 或版本发生变化；
5. 方差、随机种子或样本量造成偶然波动。

### ★★★★☆ Q50：GRPO Loss 不下降是不是训练失败？

> 不能单看 Loss。GRPO Loss 不是固定标签的交叉熵，在线采样和优势分布一直变化，可能围绕零波动。应同时看 Reward、严格成功、Group 保留率、KL 诊断、梯度、终局类型、独立验证和 bad case。

### ★★★☆☆ Q51：PPO、DPO、GRPO、RLHF 的关系怎么讲？

| 方法 | 数据/反馈 | 你项目中的位置 |
|---|---|---|
| RLHF | 人类偏好→Reward Model→RL | 简历写熟悉原理，不声称完整实践 |
| PPO | 典型 clipped policy optimization，可配 Critic/KL | 用于理解 GRPO 对照 |
| DPO | 直接用 chosen/rejected 偏好对优化 | 未做主训练链，准备原理 |
| GRPO | 同一 prompt 多轨迹组内相对奖励 | 实际在线训练 |

推荐说法：

> 我的实操集中在 LoRA SFT 和在线 GRPO；PPO、DPO、经典 RLHF 我能解释目标、数据需求和稳定性差异，但没有把它们都跑成独立端到端实验。

## 7. Harness：简历里最容易被低估、也最容易被问穿的部分

### 7.1 先把 Harness 的职责边界说对

```text
模型：决定下一步想做什么
Harness：把决策变成受约束、可追踪的动作
环境：维护页面/状态并执行动作
Reward：按公开约束评估终局
```

Harness 不是推荐系统，不替模型挑商品，也不是 Reward 的另一个实现。它负责协议、状态同步、Observation 投影、动作安全、候选记忆、循环/步数控制和轨迹记录。

### ★★★★★ Q52：Harness 到底是什么？为什么不直接让模型调用环境？

**推荐回答：**

> Harness 是模型和 ShopSimulator 之间的执行控制层。模型输出 Tool Call 后，Harness 先按当前请求的 Schema 校验工具和参数，再用 Action Guard 检查 ASIN、规格 ID、按钮和页面状态，只有合法动作才进入环境。环境执行后，Harness 将公开状态渲染成 Observation v2，按预算投影，记录轨迹、错误、步骤和终局，再交给模型下一轮。
>
> 如果直接把模型输出交给环境，历史页面上的 ASIN、过期 option ID、多工具调用和过长 Observation 都可能污染状态或训练数据。Harness 的价值是让“模型看到的可执行目标”“Guard 允许的目标”和“环境实际能执行的目标”保持一致。

### ★★★★★ Q53：当前公开的 8 个购物工具是什么？每个工具做什么？

| 工具 | 参数 | 作用 | 当前边界 |
|---|---|---|---|
| `search_products` | `query: string` | 提交有区分度的搜索词 | 只能在可搜索页面调用 |
| `open_product` | `asin: string` | 打开最新结果页可见商品 | ASIN 必须来自最新页 |
| `select_option` | `value: string` | 选择最新详情页的稳定 `option_id` | 不能填自然语言颜色/尺寸代替 ID |
| `next_page` | `{}` | 翻到下一页 | 当前必须存在 Next |
| `prev_page` | `{}` | 返回上一页 | 当前必须存在 Prev |
| `back_to_search` | `{}` | 从详情回搜索，候选阶段表示拒绝当前候选 | 语义随阶段受限 |
| `buy_now` | `{}` | 购买完整 variant 并终止 | 需要当前状态允许购买 |
| `finish_without_purchase` | `reason=no_suitable_product` | 主动结束且不购买 | 普通阶段才有意义 |

`view_description`、`view_features`、`view_reviews`、`view_attributes`、`think`、`reopen_candidate` 不属于当前公开 8 工具。历史 SFT 轨迹中可能仍出现旧工具名，那是历史数据分布，不代表当前 Schema。

### ★★★★★ Q54：为什么只允许一个 Assistant 回合执行一个 Tool Call？

> 多个调用往往基于同一个旧 Observation 生成。第一个调用可能改变页面、搜索结果或已选规格，后面的调用就可能变成 stale action。单步单工具让每次动作都在最新状态上重新决策，便于追踪和 Reward 归因。
>
> 这不是 Tool Calling 协议的普遍限制，而是本购物 Harness 的执行策略。MiniClaw 的通用 AgentLoop 可以接收多个调用，但只对明确只读工具做相邻并行；购物环境有共享状态，所以适合串行。

### ★★★★★ Q55：动态 Tool Schema 和 Action Guard 是不是重复？

> 两者是“减少错误”和“最后兜底”的两层防线。动态 Schema 根据最新页面 footer 和候选阶段，尽量不把当前不可执行的工具展示给模型；Action Guard 不信任模型输出，即使模型手写了隐藏工具或旧页面目标，也在执行前再次拒绝。Schema 面向生成，Guard 面向安全执行，不能只保留其中一个。

### ★★★★★ Q56：Action Guard 具体检查什么？不检查什么？

**检查：**

- 工具名、必填参数、类型、额外字段和空值；
- `open_product` 的 ASIN 是否出现在最新搜索结果；
- `select_option` 的 stable `option_id` 是否存在于最新详情且尚未选择；
- `next/prev/back/buy` 按钮是否在最新 Observation 中真实可用；
- `finish_without_purchase` 是否使用唯一合法 reason；
- 连续拒绝次数，达到 3 次终止为 `guard_rejection`。

**不检查：**

- 商品是否满足用户语义；
- 价格是否符合 Hard/Soft 约束；
- 哪个候选最优；
- Reward 是否应该为 Gold。

这些由模型决策、环境状态和终局 Reward 负责。

### ★★★★☆ Q57：为什么 `option_id` 比“蓝色 XL”更可靠？

> 商品详情中的规格可能有同名、层级、编码或变体映射；稳定 `option_id` 是当前页面为某个可选值提供的机器可校验标识。自然语言值可能歧义，且选择后 variant 价格可能变化，所以每次选择后要重新读取详情并核验已选轴和最终价格。

### ★★★★☆ Q58：Observation v2 是什么？为什么不是直接把原始网页全文给模型？

> Observation v2 是环境结构化状态经过统一 renderer 和预算投影后的模型可见视图。搜索结果页预算约 2,560 token，详情页约 3,072，普通页/信息页约 512，候选记忆另有 2,048 的附加预算。详情页优先保留价格、品牌、品类、公开属性、已选规格、可选规格和按钮。
>
> 原始页面可能包含大量重复描述和低价值文本；每轮完整发送会造成成本、延迟和上下文溢出。投影可以压缩文本，但不能静默删除当前页 ASIN、option ID、价格轴或可执行按钮，否则模型看得见却无法操作，属于基础设施错误。

### ★★★★★ Q59：Observation 投影会不会把正确答案删掉？

> 这是投影器必须守住的不变量：当前页所有可操作商品边界、ASIN、规格目标和 footer 都必须完整保留；只能压缩低优先级长文本。项目有投影一致性测试，比较原始可执行集合、模型可见集合和 Guard 允许集合；如果预算内无法安全表示整页，应标记基础设施无效，而不是偷偷截掉候选。

### ★★★★★ Q60：当前候选收敛机制和旧版有什么不同？

**这是必须更新的旧问题。**

> 旧版候选列表阶段会把候选列表交给模型，让模型选择并调用 `open_product`。当前顺序候选版本不再这样做：达到 6 步无实质进展，或普通探索执行到 30 步仍未结束后，Harness 清空普通探索上下文，进入候选专用阶段，按稳定编号 C1→C4 自动逐个重新打开候选。模型不再调用 `open_product` 选择候选，候选之间硬重建上下文。

**为什么改：**

1. 避免模型在长历史里重复比较、迟迟不收敛；
2. 让每个候选都有同样的核验机会，减少候选列表展示顺序和上下文残留的影响；
3. 把“候选顺序控制”从概率决策变成可审计的 Harness 流程；
4. 让候选阶段只暴露与当前状态匹配的工具。

**代价和风险：**固定顺序可能引入 C1 优先偏差，且自动重开会增加环境动作和上下文重建成本。因此必须报告候选顺序、各候选拒绝原因、收敛触发原因，并做不同候选顺序的消融。

### ★★★★★ Q61：当前候选记忆保存什么？为什么固定 C1-C4？

> 候选记忆只保存模型已经看到的公开信息：ASIN、标题、品牌、品类、当前价格、已选规格、关键公开证据、来源搜索词、页码和 rank。它不保存 Gold 身份、Reward、Hard/Soft 判定或匹配分，因此不是答案泄漏通道。
>
> 当前评测运行时固定保留最先核验的 4 个候选，编号 C1-C4；达到 4 个后不替换，重访同一 ASIN 只更新原记录。固定上限能控制上下文大小并让轨迹可比较；不替换可以避免后面候选把早期证据挤掉。通用函数仍可能有兼容默认值，但运行合同以 `runtime_contract.py` 的 4 为准。

### ★★★★★ Q62：为什么候选阶段只允许 Hard 判定，Soft 失败也不能直接拒绝？

> 候选阶段的目标是避免把“偏好不完全满足”误当成“没有可买商品”。因此当规格还未闭合时只暴露 `select_option/back_to_search`，闭合后只暴露 `buy_now/back_to_search`；`back_to_search` 表示永久拒绝当前候选，只有明确 Hard 失败才允许拒绝。只要规格闭合且全部 Hard 满足，下一步必须 `buy_now`；即使 Soft 可验证地失败、或 Soft 暂时不可核验，也不能用 `back_to_search` 淘汰。终局时，scored Soft 可验证且失败才记为 Partial；Soft 不可核验则是 `reward_unverifiable`，两者都不是候选阶段的拒绝理由。
>
> 终局 Reward 仍会严格检查 Soft：Hard 全过但 Soft 失败是 Partial，Hard/Soft 全过才是 Gold 或 Valid。候选阶段的 Hard-only 是搜索策略边界，终局的 Hard+Soft 是业务评分边界，二者并不矛盾。

### ★★★★☆ Q63：为什么 30 步就进入候选阶段，而最大步数仍是 45？

> 30 步是“开始收敛”的提前恢复阈值，给模型留下候选核验和购买的尾部预算；45 步仍是环境的硬上限，防止永不终止。两个阈值职责不同：30 步触发流程切换，45 步触发 `max_steps` 终局。把 30 步说成任务直接失败是错误的。

### ★★★★☆ Q64：连续无进展如何定义？提醒是否直接改变 Reward？

> 环境根据是否获得新候选、新商品证据、新规格状态或其他实质进展累计 no-progress；连续 3 步可以给循环提醒，连续 6 步触发候选恢复或 `repeat_loop`。精确相同 canonical action 达到当前 `exact_repeat_limit=2` 会直接以 `exact_action_repeat` 终止，不经过候选恢复；这条规则和 no-progress 恢复不能混为一谈。35/40 步提醒和候选 Prompt 只改变模型可见上下文，不直接加减 Reward；真正的 `repeat_loop`、`max_steps` 和步数惩罚由终止/Reward 合同决定。

### ★★★★☆ Q65：候选之间为什么要硬重置上下文？会不会损失信息？

> 硬重置是为了防止上一个候选的 option ID、结论和犹豫污染当前候选。每个候选上下文只包含候选专用 System、原始用户需求和当前候选完整详情，规格未闭合时保留连续状态，候选之间不带旧候选的可执行动作。
>
> 代价是丢失跨候选比较的即时文本，因此比较信息要落在公开候选记忆和来源位置中；但候选记忆不能写入满足度或答案。若要证明硬重置更好，需要对比保留历史、摘要重置和当前重置的成功率、重复动作与上下文成本。

### ★★★★☆ Q66：你简历里的“17 条循环→11 条正确购买＋6 条部分满足”现在还能直接讲吗？

> 不能把它当作当前顺序候选版本的全量结果。这个数字来自旧候选列表版的特定循环子集；当前报告已经改变候选恢复流程，且有不同的 r4/r5 子集统计。面试时可以说“旧版专项分析显示部分无进展轨迹可被候选收敛挽救”，同时明确版本、子集和统计口径；如果要求当前数字，就引用当前 `audit-report.md` 与对应 run summary，不把旧数字外推。

### ★★★★☆ Q67：平均步数从 15.9 到 10.1，能否证明 Harness 一定更好？

> 只能说明那两次运行的动作尝试或工具步骤减少。因为同时可能变化了模型 checkpoint、Prompt、Tool Schema、候选流程和 Reward，不能把下降单独归因于 Harness。还要看严格成功率、Hard/Soft 约束、错误购买、Guard 拒绝、P50/P95 和稳定性；过早购买也可能让步数变短但质量变差。

## 8. MiniClaw：简历第二个项目的逐层面试稿

### 8.1 先用一句话定位 MiniClaw

> MiniClaw 是一个 Python Coding Agent 框架：`llm` 统一模型协议，`agent` 实现通用模型—工具循环，`coding_agent` 负责把工具、Runtime、审批、Memory、Goal、指令和 Trace 组装成可运行的编码产品。

它的目标不是训练一个新模型，而是让一个概率模型在长任务中更能持续执行、少产生危险副作用、能处理中断和上下文压力，并且把失败变成可复现的 Eval。

### ★★★★★ Q68：MiniClaw 的整体架构是什么？为什么分成 `llm`、`agent`、`coding_agent`？

**推荐回答：**

```text
入口（CLI / Feishu / Eval）
          ↓
coding_agent：产品装配层
  Runtime / Approval / Memory / Goal / Tools / Trace
          ↓
agent：通用 AgentLoop
          ↓
llm：Provider-neutral 请求、响应、事件、SSE
```

> `llm` 只知道模型协议和 Usage，不知道工作区和 Goal；`agent` 只知道如何请求模型、执行抽象工具、追加结果，不知道具体文件工具或 Docker；`coding_agent` 是 composition root，负责把具体服务组装起来。这样可以替换供应商、Runtime 或产品策略而不改通用 Loop，也便于用假模型和临时工作区做单元测试。

**容易说错：**简历写了 `agent_core`，源码包名实际是 `MiniClaw.agent`；面试时可以说“Agent Core 层”，不要声称仓库有一个名为 `agent_core` 的独立包。

### ★★★★★ Q69：MiniClaw 的 Agent Loop 一轮具体怎么走？

```text
追加用户消息
  → 构造当前 system prompt / context / tool definitions
  → 调 LLM（可能是 SSE 流）
  → 累积文本与 Tool Call
  → 追加 assistant 消息
  → ToolExecutor 校验、审批、执行、变换结果
  → 按 call_id 追加 tool result
  → 下一轮模型请求
  → 无 Tool Call、预算耗尽、取消或错误时结束本次 run
```

> “一次模型自然停止”只代表一次 Agent run 或 Goal attempt 结束，不自动等于业务任务完成。是否继续由产品层 Goal/状态策略决定。

### ★★★★★ Q70：`llm` 模型适配层统一了什么？

统一内部数据类型：

- `ModelRequest`：profile、messages、tools、metadata、取消信号；
- `AssistantReply`：文本、Tool Calls、stop reason、Usage、error；
- `ModelEvent`：text delta、tool call、completed、error、transport；
- `ToolInvocation`：call id、工具名、参数；
- `TokenUsage`：输入、输出、缓存 token。

> 不同供应商的 HTTP 字段、SSE 事件和 Tool Call 格式先转换成这些内部协议，AgentLoop 不必知道 OpenAI-compatible 和 Anthropic 的差异。

### ★★★★★ Q71：SSE 流式 Tool Call 为什么难？你如何组装碎片？

**推荐回答：**

> 流式响应中的工具名、call ID 和 JSON 参数可能分散在多个 chunk，不能收到第一片就执行，否则会执行半个 JSON 或错误动作。我按 call index 保存每个调用的累积状态，持续拼接参数片段；只有收到完整终止事件并成功解析 JSON 后，才生成 `ToolInvocation` 交给 AgentLoop。文本 delta 可以流式交付，但未完成 Tool Call 保持内部缓冲。

**追问（沿用 Q71：★★★★★）：流中途断了怎么办？**

> 如果还没有向用户或执行器暴露可执行结果，可以对当前逻辑请求做有限重试或 fallback；一旦已经发出可见文本/工具决策，就不能无条件重放，避免重复文本或副作用。当前 Trace 会区分一个逻辑 `model.request` 和多个 `model.transport` attempt。

### ★★★★★ Q72：超时为什么要分 connect、first-token、idle、total？

> 连接建立慢、服务端迟迟不出首 token、流中间长时间无数据和整次请求超时是不同故障。分开设置可以让错误可诊断，也避免把慢首 token误判为连接失败。总超时仍是硬上限；取消信号要能打断当前读操作和重试等待。

### ★★★★☆ Q73：模型重试怎样避免重复副作用？

> 模型请求的重试边界和工具调用的重试边界分开。模型请求只在尚未交付可见输出时重试；工具只有幂等/只读调用允许有限网络重试，非幂等写入在“执行后失去响应”时不自动重放，而是标记 `uncertain_side_effect`，要求核实当前状态。审批只对一个逻辑调用授权一次，重试不重复弹审批。

### ★★★★★ Q74：ToolExecutor 的统一生命周期是什么？

```text
received
  → validated
  → preflighted（指令刷新 / 审批 / 路径策略）
  → started
  → succeeded / failed / timed_out / cancelled
  → transformed（Artifact / 输出边界）
  → delivered（只回传一次）
```

> 把所有工具放到一个执行边界，才能统一参数 Schema、错误码、取消、重试、输出裁剪和 Trace；否则每个工具各自处理，容易出现权限和错误语义不一致。

### ★★★★☆ Q75：为什么 ToolExecutor 没有运行时 `register` 或随意 `enable/disable`？

> 工具集合在 CodingAssistant 装配时固定，模型请求可以按当前状态生成一个广告视图，但执行器仍检查调用是否属于固定集合、是否在本次请求被允许。这样组合职责与执行职责分离，避免模型或插件在运行中悄悄注入未审计工具。当前 `goal_complete` 是状态相关的展示例外：没有 Goal 时从请求定义隐藏，手写调用仍会被 `TOOL_UNAVAILABLE` 拒绝。

### ★★★★☆ Q76：MiniClaw 的 read-only 工具能并行吗？和购物项目有什么不同？

> 通用 AgentLoop 对相邻且明确只读的 `read/grep/search/ls/find` 调用可以用 `asyncio.gather` 并行，但按模型原顺序回填结果；写、edit、bash、memory、goal 仍串行。购物环境共享页面状态，当前 Harness 更保守地每回合只执行一个动作。因此“支持多个 Tool Call”和“所有工具都并行”不是一回事。

### 8.2 Runtime、Docker、审批和路径安全

### ★★★★★ Q77：MiniClaw 是否所有工具都进入 Docker？

> 不是。当前只有 `bash` 通过 session Runtime 选择 Host 或 Docker 后端；`read`、`write`、`edit`、`grep`、`search`、`ls`、`find` 在 Python 进程中执行，并由 WorkspaceGuard 约束路径。默认通常是 Docker + Direct 工作区，Host 是显式开发 fallback，Snapshot 是一次安全拷贝且后续修改不自动回写源目录。

### ★★★★★ Q78：Docker 在项目里具体提供了哪些隔离？

Docker 命令参数包括：

- 每次命令一个临时容器，结束/超时/取消后清理；
- 工作区绑定到 `/workspace`；
- 根文件系统只读，`/tmp` 受限 tmpfs；
- `network`、CPU、内存、PID、文件描述符上限；
- `cap-drop ALL`、`no-new-privileges`；
- 动态敏感路径 mask mount；
- 取消时移除容器并终止本地 Docker CLI 进程。

> 这不是绝对安全保证。挂载的工作区仍可能被命令修改，Docker 不理解用户意图，也不能代替审批、路径检查和结果验收。

### ★★★★★ Q79：WorkspaceGuard、ApprovalGate、Docker 各自解决什么问题？

| 层 | 解决的问题 |
|---|---|
| WorkspaceGuard | 路径是否在有效工作区，是否存在 `..`/symlink 逃逸，读写/执行 ACL 是否允许 |
| ApprovalGate | 这个动作是否需要用户确认，allow/ask/deny 如何处理，超时是否 fail-closed |
| Docker Runtime | 命令在哪个环境执行，能用多少资源、网络和权限 |
| 结果验收 | 运行后是否真的满足业务目标 |

### ★★★★★ Q80：`allow / ask / deny` 怎样判断？审批后如何防参数被改？

> 先对工具和参数做规范化，再做多能力风险分类、项目 allowlist（规则按 AND 匹配）和策略判断。`allow` 直接执行，`ask` 生成带预览和六字符 ID 的审批请求，`deny` 不启动工具；审批等待超时或处理器不可用时 fail-closed。请求里保存 normalized call hash，审批返回时比对哈希，防止用户批准 A 后模型把参数改成 B。

### ★★★★☆ Q81：为什么路径校验不能用 `startswith`？

> `/workspace/project2` 会错误地通过 `/workspace/project` 的字符串前缀判断；大小写、分隔符、`..` 和符号链接还会造成更多绕过。应先规范化/resolve，再用路径对象的父子关系判断；对已有路径逐段跟随 symlink，并在每次访问重新做 ACL。即使通过路径检查，业务上写错文件仍可能是结果错误。

### ★★★★☆ Q82：取消是如何贯穿整条链路的？

> 一个 attempt-scoped `CancellationToken` 从 AgentLoop 传给 LLM、审批、ToolExecutor、Host/Docker 命令、压缩和 Goal Judge。取消时模型读取停止，未启动的后续 Tool Call 记录为 cancelled 且不执行；Host 终止进程树，Docker 删除容器；write/edit 在临时文件完成后、`os.replace` 前再次检查取消，降低后台写入晚到的风险。

### ★★★★☆ Q83：能否保证 exactly-once？

> 不能对任意外部副作用做强保证。对于本地 staged write/edit 和幂等只读调用，可以设计原子提交和有限重试；如果非幂等操作已提交但响应丢失，系统只能标记不确定并要求核实，不能盲目重放。面试时主动承认这一边界比说“有重试所以 exactly-once”更可信。

### 8.3 当前 Goal 语义：必须避免旧文档陷阱

### ★★★★★ Q84：GoalSupervisor 为什么在 AgentLoop 外？

> AgentLoop 的职责是一次模型—工具执行；Goal 是产品级长任务状态。模型自然停止可能只完成一半，因此 GoalSupervisor 把一次自然停止当作一次 attempt，读取持久化状态，在 `active` 或 `verifying` 时按预算继续下一次 attempt；`waiting_for_user`、`failed`、`cancelled` 等状态由外层处理。这样通用 Loop 不需要知道验收清单、会话目录或平台入口。

### ★★★★★ Q85：当前 `goal_complete` 是否代表任务已被独立验证？

**这是必须纠正的旧说法。**

> 当前公开 `goal_complete` 主要是提交 `final_result`，把 Goal 标为 complete，并记录 `judge_status=pending`、`completion_basis=model_submission`，随后交给后置独立评审。它本身不等于已经通过 fresh verification，也不等于所有 Acceptance Criteria 有外部证据。`GoalStore.complete/validate_completion` 仍保留严格 fresh-verification 路径和兼容测试，但不是当前公共提交工具的充分条件；旧架构文档把两条路径混在一起，不能直接当作当前公共协议。

**更好的设计理由：**让模型先提交结果、系统再独立评审，避免模型既做业务又维护复杂验收 JSON，减少协议返工和自证偏差。

### ★★★★☆ Q86：Goal 状态和 run 状态有什么区别？

> Goal 是用户任务层的生命周期，如 active、verifying、complete、waiting_for_user、failed、cancelled；run-state 是一次运行/进程层的 waiting_model、executing_tool、finalizing、paused、interrupted 等。一个 Goal 可以有多个 run attempt；进程崩溃可把 run 标为 interrupted，但不能直接把 Goal 宣布完成。

### 8.4 Memory 与上下文压缩：按当前源码回答

### ★★★★★ Q87：MiniClaw 当前的上下文压缩到底是软硬两级还是单一策略？

> 当前运行时是 **单一 progressive hard-only 管线**，不是旧笔记里的 soft trigger + closed-history 多阶段生产算法。provider 单次请求输入达到约 40K hard trigger 才自动压缩；先找安全切点、准备 Artifact、生成结构化 continuation summary，再原子提交压缩视图并恢复。旧配置字段和文档名称可能保留兼容标签，但不能说当前运行同时执行独立 soft archive pass。

### ★★★★★ Q88：硬压缩保留什么、删除什么？

> 原始 session JSONL 和 Trace 追加保存，不物理删除；模型可见视图保留结构化 checkpoint、最近约十分之一的原始历史和必要的工具调用/结果边界。Assistant Tool Call 与 Tool Result 不能被拆开。成功的大工具结果达到约 8 KiB 时先落成 content-addressed Artifact，模型只看路径、大小、SHA256 和约 256 字符预览，需要时再显式 read。

### ★★★★☆ Q89：为什么要用文件 Hash 恢复 Read 结果？

> 压缩后重新注入旧文件内容有风险：文件可能已经改变。ReadSnapshotCache 记录路径、内容和 SHA256；恢复前再次读取并比较 hash，未变化才最多重放一次，变化则失效并要求重新读取。这样可以减少重复读，又不把旧内容误当当前事实。

### ★★★★☆ Q90：当前有几个 Memory？哪些会自动召回？

> 从产品概念看有 Working Context、Episodic、Semantic 和 Procedural workflow；但职责不同。Working 是当前会话视图，Episodic 保存每个 session 的总结并支持 memory search，Semantic 保存用户确认的稳定事实并作为稳定 prompt prefix，Procedural 主要用于选择/加载技能，不应被说成普通记忆检索源。Artifact 和证据日志是支撑记录，不是额外的公开 Memory 类型。
>
> 当前公开 `memory` 工具主要是 `search`（查 episodic）、`remember/replace/forget`（改 semantic）；不能把旧版 archive_search 或自动把所有工具输出写成长期事实说成现状。

### ★★★★★ Q91：语义记忆怎样防止把临时信息、密码或错误事实写进去？

> Semantic store 校验类别、长度、secret-like pattern 和 transient pattern；偏好写入要求精确用户原话，自动 consolidation 会拒绝 assistant-only 的一次性断言、工具/技能输出回声和文件完成快照。相同实体有 revision、record ID、乐观冲突检测和 conflict log；新值冲突时默认不自动覆盖，等待明确解决。详细内容放 topic file，`MEMORY.md` 只是短索引。

### ★★★★☆ Q92：BM25、BGE、RRF、Cross-Encoder 当前到底能不能说“都启用了”？

> 只能分层说。源码支持混合检索：词法/BM25、精确代码符号、向量、RRF 和可选 Cross-Encoder；持久化缓存和 FAISS HNSW 也有实现。但当前默认环境可能关闭向量和 Cross-Encoder，使用 local hash fallback。因此面试时说“我实现并支持这条检索链，默认配置按环境可能降级”，不要无条件说本次每次运行都用了 BGE-M3/FAISS 或已有单项收益。

### ★★★★☆ Q93：如何保持记忆更新又不破坏模型前缀缓存？

> 把动态内容变成 append-only delta，由 `ContextJournal` 在完整工具批次后追加；达到更新数或字节边界才折叠成一个 state。稳定的 system、工具定义和语义 memory prefix 尽量不改，动态证据放在后部。`PrefixDiagnostics` 只比较精确前缀的 SHA/字节变化，是诊断工具，不等同于服务商报告的 cache token。

### 8.5 Eval、Trace 与指标

### ★★★★★ Q94：MiniClaw 的五维 Eval 分别是什么？

| 维度 | 问题 | 示例 |
|---|---|---|
| outcome | 最终结果对不对 | 文件、命令、JSON、正则或后置 LLM rubric |
| process | 过程是否按合同发生 | 工具序列、Goal、指令注入、Memory、Compaction |
| efficiency | 资源是否可接受 | token、请求、缓存、费用估算、TTFT、耗时 |
| safety | 是否越权或产生禁止副作用 | 工作区 diff、审批、敏感路径、Docker 边界 |
| reliability | 重复/故障后是否仍能工作 | 重跑、取消、重试、fallback、重启恢复 |

### ★★★★★ Q95：当前五维是不是全部由 LLM Judge 自动评分？

> 不是。当前 `outcome` 可以延后交给独立 LLM rubric；`process/efficiency/safety/reliability` 主要由程序、Trace、workspace/oracle 和预算检查。结果待 judge 时，case 的总 `passed` 应保持 pending/null，不能把未评写成通过。旧版复杂的模型侧验收合同已经撤掉。

### ★★★★★ Q96：你简历里的 Token 减少 56.41% 是怎么算的？

> 同组已曝光 20 题、20 路并发、每题一次的 v1→v10 组合回归：总 tokens 从 5,090,509 降到 2,218,747，计算为 `1 - 2,218,747 / 5,090,509 ≈ 56.41%`。同时未缓存输入下降约 70.07%，费用是按配置费率估算约下降 66.16%。这是多项改动和 v10 撤掉复杂验收协议的组合结果，不是单独读缓存或某一个 Memory 模块的消融。

### ★★★★★ Q97：缓存命中“提升 19.01%”应该怎样说？

> 原始输入缓存占比从 37.43% 到 56.44%，增加 **19.01 个百分点**；相对增幅约 50.79%。我会优先报两端值和百分点，避免把百分点说成相对百分比。缓存和费用缺失时系统标记 unavailable，不会把未知当零成本。

### ★★★★☆ Q98：Trace 记录了哪些东西？估算 token 和真实 usage 如何区分？

> 每个 session 有 append-only `trace.jsonl`，记录逻辑 model request、transport attempt/retry/fallback、provider usage、工具生命周期、审批、Goal、Compaction、取消和完成状态。provider 上报的 input/output/cached token 是实际响应 usage；按 UTF-8/4 的估算分桶只用于定位上下文来源，不能当服务商计费。费用按配置费率估算，也不是发票；重试和缺失 usage 要单独标记。

### ★★★★★ Q99：为什么要把失败 Trace 沉淀成 Eval，而不是只看日志？

> 日志适合人工浏览，不能稳定复现。Trace 能保留清洗后的模型边界、工具事件、工作区和用量；评测 Case 再在独立 fixture/workspace 中执行真实 Agent，分别检查结果、过程、效率、安全和可靠性。模型边界 replay 只重放请求，不执行历史工具，适合安全比较模型/Prompt，但不能替代完整 workspace 集成测试。

### ★★★★☆ Q100：你是否能说 MiniClaw 当前所有测试都通过？

> 不能这样说。部分新增针对性回归和历史阶段的测试通过，但当前工作树处于接口迁移，旧测试仍传已删除的 `soft_trigger_tokens` 等参数，聚焦全量运行并非全绿；一次 130 项聚焦运行出现 8 个 error、2 个 failure，另一个旧架构集合也有接口不一致，动态召回路径还需要继续补回归。当前没有把真实模型 Eval 说成已重跑。面试时我会报告具体通过的测试文件、失败原因和未运行项，不把旧设计测试的绿色结果冒充当前默认路径稳定。

## 9. Transformer、RoPE、KV Cache、Flash Attention：简历写了就会被问公式

### ★★★★★ Q101：Transformer 的核心思想是什么？为什么适合 LLM？

> Transformer 用 self-attention 在序列位置之间建立动态依赖，再用前馈网络做逐位置的非线性变换。训练时已知整段 token，可以通过 causal mask 并行计算所有位置的 next-token loss；推理时下一个 token 依赖前一个生成结果，所以仍然是自回归。相较 RNN，它更容易并行训练、长距离依赖路径更短；代价是标准全注意力随序列长度呈平方增长。

### ★★★★★ Q102：请写出 scaled dot-product attention 公式并解释 Q/K/V

$$
Q=XW_Q,\quad K=XW_K,\quad V=XW_V
$$
$$
\operatorname{Attention}(Q,K,V)=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}+M\right)V
$$

> Q 表示当前位置想查询什么，K 表示每个位置可被匹配的特征，V 是真正被聚合的信息；`M` 是因果或 padding mask。点积得到相关性，softmax 变成权重，再加权汇总 V。Q/K/V 是可训练投影后的表示，不是手工定义的“问题/答案/值”。

### ★★★★☆ Q103：为什么除以 `sqrt(d_k)`？

> 如果 Q、K 各维近似独立、方差为 1，点积方差大约随 `d_k` 增长，维度越大 logits 越容易变得极端，softmax 过尖导致梯度变小。除以 `sqrt(d_k)` 是控制尺度的初始化稳定化。它不是对最终概率做除法。

### ★★★★☆ Q104：MHA、MQA、GQA 有什么区别？

| 结构 | Q 头数 | K/V 头数 | 主要取舍 |
|---|---:|---:|---|
| MHA | H | H | 表达最灵活，KV Cache 大 |
| MQA | H | 1 | KV 最省，可能损失表达 |
| GQA | H | G（1＜G＜H） | 质量与 KV 成本折中 |

> GQA 主要降低 Decode 阶段的 KV 存储和带宽；它与 Flash Attention 不同，前者改变头共享结构，后者改变计算/内存实现。面试被问到 Qwen 的精确头数时，以本地模型 `config.json` 为准，不凭其他 Qwen 版本猜。

### ★★★★☆ Q105：Attention 后为什么还要 FFN？SwiGLU 是什么？

> Attention 负责跨 token 混合信息，FFN 在每个位置独立地做更高维的非线性组合。SwiGLU 可写为：

$$
W_{down}\big(\operatorname{SiLU}(W_{gate}x)\odot W_{up}x\big)
$$

> 门控分支决定哪些特征通过。不能把 Transformer 的所有算力都归因于 attention；长序列下 FFN 的 `O(Ld^2)` 也可能占主导。

### ★★★★★ Q106：训练时为什么能并行，生成时却不能完全并行？

> 训练时真实目标 token 已知，位置 `t` 的输入可以同时准备，只用 causal mask 阻止看未来；生成时 `x_{t+1}` 依赖刚得到的 `x_t`，存在条件依赖。Batch/continuous batching 可以并行不同请求或不同序列的当前 decode，但不能消除单条序列的自回归依赖。

### ★★★★☆ Q107：Pre-Norm、Post-Norm、RMSNorm 怎么答？

> 残差让每层学习增量并改善梯度路径；Pre-Norm 先归一化再进入子层，深层训练通常更稳定；Post-Norm 在残差后归一化。RMSNorm 主要按均方根缩放，不做 LayerNorm 的均值中心化：

$$
\operatorname{RMSNorm}(x)=g\odot\frac{x}{\sqrt{\frac1d\sum_jx_j^2+\epsilon}}
$$

> 具体模型可能采用混合结构，不能只凭“Transformer”断言所有层完全相同。

### ★★★★★ Q108：为什么需要位置编码？RoPE 的直觉是什么？

> Self-attention 本身对 token 集合近似置换等变，不知道顺序；位置编码注入相对/绝对位置信息。RoPE 将 Q、K 的二维子空间按位置角度旋转，使 `q_m^T k_n` 自然包含相对位置 `m-n` 的相位关系，而 V 通常不旋转，因为位置关系主要通过注意力权重体现，旋转 V 会改变被聚合内容的表示。

二维旋转：

$$
R(\theta_p)=\begin{bmatrix}\cos\theta_p&-\sin\theta_p\\\sin\theta_p&\cos\theta_p\end{bmatrix},\quad q_p'=R(\theta_p)q_p
$$

### ★★★★☆ Q109：RoPE 为什么能表达相对位置？

利用旋转矩阵的正交性：

$$
(R_mq)^T(R_nk)=q^TR_m^TR_nk=q^TR_{n-m}k
$$

> 点积只依赖角度差，因而把相对位置信息带进 attention score。这里是数学结构，不保证无限长度外推都稳定。

### ★★★★☆ Q110：RoPE 外推为什么会失效？

> 训练时模型只见过有限位置范围，继续外推会让旋转频率、相位分布和注意力模式超出训练分布，出现高频混叠或远距离关系失真。位置插值、NTK-aware、YaRN 等方法调整频率或缩放位置，但要配合训练/评测验证，不能只改 `max_position_embeddings` 就宣称支持更长上下文。

### ★★★★★ Q111：KV Cache 缓存什么？为什么不缓存 Q？

> 在逐 token Decode 时，历史 token 的 K/V 对未来查询仍会被使用，可以缓存；历史 Q 只在它生成当时用于计算过去位置的注意力，不会再作为未来位置的查询，所以通常不需要保存。每层、每个请求的 KV Cache 占显存，GQA/MQA 能减少 K/V 头数。

### ★★★★☆ Q112：有 KV Cache 后 attention 是 O(1) 吗？

> 不是。对新 token 来说，避免了重新计算历史 K/V 投影，但它仍要与长度为 `L` 的历史 K 做匹配并聚合 V，单步注意力仍随上下文长度增长；只是避免了重复工作。完整序列的理论关系和实际吞吐还受 batch、kernel、带宽和缓存布局影响。

### ★★★★☆ Q113：Prefill 和 Decode 的瓶颈有什么不同？

> Prefill 一次处理整段输入，计算密集，长 Prompt 会显著增加延迟；Decode 每次生成少量 token，常受内存带宽、KV 读取和调度影响。购物 rollout 和 MiniClaw 长上下文都要区分“输入很长”与“输出很长”，不能只看总 token。

### ★★★★★ Q114：Flash Attention 优化了什么？是不是把复杂度变成线性？

> Flash Attention 使用 tiling、片上 SRAM 和在线 softmax，避免把完整 `L×L` attention matrix 写回显存，减少 HBM 读写和峰值显存；精确全注意力对序列长度的算术复杂度仍有平方项。它是 kernel/IO 优化，不是摘要压缩，也不是稀疏注意力。

### ★★★★☆ Q115：FlashAttention、PagedAttention、KV Cache 有什么区别？

| 名词 | 解决什么 |
|---|---|
| KV Cache | 避免逐 token 重算历史 K/V |
| Flash Attention | 以更少中间显存和 IO 执行精确 attention |
| PagedAttention | 将 KV 按块管理，降低动态请求的碎片/预留浪费 |

> vLLM 可能使用 PagedAttention 和连续批处理；这不等于它自动删掉上下文。MiniClaw 的 context compaction 改变发送给模型的内容，属于另一层。

### ★★★★☆ Q116：Prompt Cache、KV Cache 和项目里的 Read Cache 有什么关系？

> KV Cache 是一次模型推理过程中历史 token 的中间状态；Prompt/Prefix Cache 是跨请求复用相同 token 前缀的服务能力；MiniClaw ReadSnapshotCache 是应用层文件内容快照，靠路径和 SHA256 判断能否恢复。三者都叫 cache，但生命周期、键和失效条件完全不同，不能把“文件 hash 命中”报成 provider KV 命中。

### ★★★☆☆ Q117：30K 上下文为什么仍可能 OOM？

> 上下文长度只约束 token 数，不包含模型权重、梯度、优化器、激活、KV Cache、LoRA、并发序列和框架临时 buffer。训练时反向激活尤其昂贵，推理时多路 rollout 也会叠加 KV。需要通过 batch、梯度检查点、精度、并发和 max sequence 共同控制。

## 10. PyTorch、Python、异步和数据结构：把“了解”答成可执行能力

### ★★★★★ Q118：PyTorch 的 Tensor、autograd、backward、step 分别做什么？

> Tensor 是带 device/dtype/shape 的多维数组；autograd 记录带梯度的运算图；`loss.backward()` 按链式法则把梯度累积到参数的 `.grad`；`optimizer.step()` 根据梯度更新参数；`zero_grad()` 清理上一步累积。在线训练还要注意 `detach()`，不能把不需要反传的环境 Reward 或旧策略概率意外接进图。

### ★★★★☆ Q119：`train()`、`eval()`、`no_grad()`、`inference_mode()` 区别？

> `model.train()/eval()` 切换 Dropout、BatchNorm 等模块行为；`torch.no_grad()` 关闭梯度记录但不改变模块模式；`inference_mode()` 进一步减少 autograd 开销并限制某些 tensor 变更，适合纯推理。评测前要 `eval()`，不能只写 `no_grad()`。

### ★★★★☆ Q120：`detach`、`item`、`clone`、原地操作的坑？

> `detach()` 切断梯度但可能共享存储；`item()` 把单元素 Tensor 转 Python 标量并同步设备；`clone()` 复制数据仍可能保留梯度关系；原地操作可能覆盖 autograd 需要的中间值，导致 backward 报错或静默错误。日志记录 Reward 时常用 `detach().cpu().item()`，但不要在训练主路径频繁同步 GPU。

### ★★★★☆ Q121：BF16、FP16、FP32 和混合精度如何取舍？

> FP32 精度和动态范围最好但显存/吞吐成本高；FP16 更省显存但指数范围小，容易 underflow/overflow；BF16 指数范围接近 FP32，训练稳定性通常更好。混合精度让部分算子低精度、敏感累加保留高精度；具体仍取决于 GPU、框架和模型实现。LoRA 不会让所有权重都变成低精度。

### ★★★★☆ Q122：Python 的 `asyncio`、线程、进程怎么选？

> `asyncio` 适合大量 I/O 协作（SSE、网络、等待工具）；线程适合阻塞 I/O 或库不支持 async 的情况；进程适合 CPU 密集任务或隔离资源，但序列化和进程管理成本更高。Python GIL 限制同一进程线程执行 Python 字节码的并行度，但不代表线程对网络 I/O 没用。MiniClaw 的模型流、审批和工具生命周期以 async 为主，命令进程由子进程执行。

### ★★★★☆ Q123：`asyncio.gather` 并发时如何保证结果顺序？

> `gather(*aws)` 返回结果顺序与传入 awaitable 顺序一致，即使完成顺序不同；因此可以并发只读工具，再按原 Tool Call 顺序回填消息。共享状态、写操作、取消和异常传播仍需单独设计，不能因为结果有序就认为执行无副作用。

### ★★★★☆ Q124：幂等性是什么？为什么工具重试必须区分？

> 幂等操作重复执行后的最终状态与执行一次相同，例如读取文件；写入、下单、扣款可能不是幂等。网络错误发生在副作用之后时，客户端不知道服务端是否已提交，盲目重试可能重复副作用。MiniClaw 对只读/标记幂等调用有限重试，非幂等不自动重放并记录不确定状态。

### ★★★☆☆ Q125：JSON、JSONL、SQLite 各适合什么？

> JSON 适合小型整体配置；JSONL 适合 append-only Trace/会话，单条损坏不必丢整文件；SQLite 适合需要索引、并发和增量查询的本地状态。写入重要状态时使用临时文件加原子替换或事务，避免进程崩溃留下半份结果。

### ★★★★☆ Q126：LRU、Top-k、RRF 在项目中分别怎么用？

> LRU 以最近使用淘汰缓存，适合有容量上限的文件/结果；Top-k 保留排序前 k 个候选；RRF 根据多个排序名次融合，典型形式 `Σ 1/(k+rank)`，避免 BM25 分数和向量相似度尺度不一致。RRF 不是重新训练模型，最后仍需去重、权限过滤和预算裁剪。

### ★★★☆☆ Q127：路径边界判断的复杂度和常见坑？

> 先做规范化/resolve，再用 `relative_to` 或父子关系判断，避免字符串前缀误判；还要考虑符号链接、大小写和 TOCTOU。复杂度通常是路径深度加文件系统解析，不能只靠一次 `startswith`。

## 11. Agent、ReAct、RAG、Memory、Tool Calling：岗位要求的应用能力

### ★★★★★ Q128：Agent 和普通聊天机器人/工作流有什么区别？

> 普通聊天通常是输入到输出的一次生成；固定工作流由程序预先决定步骤；Agent 则由模型根据当前状态选择下一步动作，并通过工具或环境反馈闭环。真正的 Agent 仍需要程序定义状态、工具、权限、预算和终止，不是把一段 Prompt 叫作 Agent。

### ★★★★★ Q129：ReAct 是什么？你的项目如何体现？

> ReAct 把 reasoning 和 acting 交替组织：模型根据当前观察形成下一步判断，调用工具，读取 observation，再继续。购物项目中的搜索→打开→核验→选规格→购买就是环境化的 ReAct；MiniClaw 的请求—工具—结果循环也是同类执行结构。当前 SFT 主要监督可执行 Assistant 动作，不把私有思维链作为必须输出的协议。

### ★★★★☆ Q130：ReAct 常见失败有哪些？

1. 工具名/参数格式错误；
2. 依据旧 Observation 使用 stale ID；
3. 重复搜索或无进展循环；
4. 看到局部证据就过早终止；
5. 工具结果过长导致上下文遗忘；
6. 把外部工具文本当成高优先级指令；
7. 失败后盲目重试非幂等副作用。

> Harness、ToolExecutor、Memory 和 Goal 分别处理其中不同层面，不能靠一条“不要犯错”的 Prompt 解决。

### ★★★★★ Q131：Tool Calling 是什么？模型真的执行了函数吗？

> Tool Calling 是模型按约定输出工具名和结构化参数，应用解析、校验、授权并执行，再把结果按 call ID 回传。模型只提出动作建议，不直接获得 Python 进程、磁盘或网络权限；执行器是实际边界。

### ★★★★☆ Q132：JSON 输出和真正 Tool Calling 有什么区别？

> 只生成一段 JSON 还缺少工具注册、Schema 校验、调用 ID 配对、权限/审批、执行、错误反馈和循环控制。真正的 Tool Calling 是一个端到端协议，不是“让模型输出看起来像 JSON”。

### ★★★★☆ Q133：MCP 和你项目的 Tool Schema 是什么关系？

> MCP 是一种更广的模型工具/资源连接协议，规定发现、调用和上下文交换的标准；项目当前实现的是自有的 provider-neutral ToolInvocation、JSON Schema 和 ToolExecutor/Harness，不应声称已经接入 MCP。若接入 MCP，我会在适配层把远端工具映射成内部 ToolSpec，并重新做权限、超时、来源可信度和结果大小控制。

### ★★★☆☆ Q134：Skills 和 Tools 有什么区别？

> Tool 是一次可执行动作，例如 read、bash、search；Skill 是针对任务的流程/知识指引，通常是 Markdown 或配置，不应自动获得执行权限。当前 MiniClaw 有内部 procedural skill 选择/加载逻辑，但没有把 `skill` 当成普通公开执行工具；加载内容仍受 system policy 和项目指令约束。

### ★★★★★ Q135：RAG 是什么？和 Memory 有什么关系？

> RAG 是检索相关外部知识再注入上下文，让模型基于证据生成；Memory 更关注跨回合/跨会话保存和恢复状态。两者都包含“存储—检索—注入”，但数据生命周期、权限、更新和可信度不同。MiniClaw 的 Episodic/Semantic Memory 是产品记忆；如果接入商品知识库，还要单独处理文档版本、租户权限和时效。

### ★★★★☆ Q136：RAG 的标准链路怎么设计？

```text
文档采集 → 清洗/切分 → 元数据与权限 → embedding/词法索引
→ query rewrite（可选）→ 召回 → 融合/重排 → 证据截断
→ 注入上下文 → 生成 → 引用/事实核验 → 反馈回流
```

> 召回率、精确率、nDCG、答案 groundedness、延迟和成本都要评估；只看最终回答不够。

### ★★★★☆ Q137：BM25 和向量检索为什么要混合？

> BM25 对错误码、文件名、型号、精确词很敏感；向量检索能补充同义改写和语义相近。两者分数尺度不一致，常按 rank 用 RRF 融合，再在小候选集上做 Cross-Encoder 精排。代价是索引维护、延迟和权限过滤更复杂。

### ★★★★☆ Q138：Cross-Encoder 为什么比 Bi-Encoder 慢？

> Bi-Encoder 先独立编码 query 和 document，可预计算文档向量并用 ANN 召回；Cross-Encoder 把 query 和每个 document 拼接后联合编码，交互更充分但每个候选都要计算，因此适合小候选精排而不是全库检索。

### ★★★★☆ Q139：Memory 什么时候应该写入？

> 只有稳定、可复用、用户明确确认或有可靠来源的事实才进入 Semantic；本轮命令输出、一次性完成快照、模型自己的推测应留在 Working/Episodic。写入前做 secret、transient、重复和冲突检查，保留来源和版本；宁可少写，也不要把错误事实长期污染后续会话。

### ★★★★☆ Q140：Memory 检索结果能覆盖系统提示吗？

> 不能。检索结果是低优先级的历史证据，应作为 untrusted user-level context 注入；system policy、用户当前明确请求和项目规则优先。外部文档可能包含 Prompt Injection，执行端仍要重新做工具权限和路径校验。

### ★★★☆☆ Q141：如果检索很准，模型仍答错，怎么定位？

按链路分层：

1. 召回是否包含正确证据；
2. 重排/过滤是否删错或超预算；
3. 注入位置和优先级是否被历史内容淹没；
4. 模型是否读懂证据；
5. 工具动作是否基于最新状态；
6. 最终判断/Reward 是否与业务定义一致。

> 用 Trace 和分层 Eval 记录每一层，不能只调 embedding。

### ★★★☆☆ Q142：多 Agent 什么时候值得用？

> 当任务有清晰的角色隔离、可并行子任务、独立上下文和汇总协议时才值得；否则多个 Agent 会增加通信、重复上下文和冲突状态。当前两个项目的核心是单 Agent 长程闭环，不能为了迎合岗位名词声称已经实现复杂多 Agent 协作。

## 12. 评测、Benchmark、Rubric、Judge：把“准确率”讲成科学实验

### ★★★★★ Q143：Core-180 和 Challenge-60 怎么设计？

> Final-240 由 Core-180 和 Challenge-60 组成。Core 覆盖九个商品领域的常见任务；Challenge 分为 search reformulation、candidate comparison、price semantics、multi-option、evidence verification、long-horizon 六类，每类 10 题。训练池与评测 task/family 零重叠，任务哈希和分母冻结。

### ★★★★★ Q144：为什么固定 240 题分母？缺失任务怎么算？

> 如果缺失任务从分母删除，系统故障或难题超时会被掩盖，成功率会被抬高。因此缺失按失败或单独的基础设施无效状态记录，但不悄悄删分母；Judge 未返回也要标记 `not_judged`，不能写成通过。

### ★★★★★ Q145：Reward、Rubric、LLM Judge 三者如何分工？

| 组件 | 最适合判断 |
|---|---|
| Environment Reward | 终局、目标/替代、Hard/Soft 约束、可验证性 |
| Deterministic metrics | 工具合法性、步骤、重复、Guard、Token、耗时、文件/状态 |
| Rubric Curator | 从 Query 中选择真正表达的约束并冻结 |
| Trajectory Judge | 搜索策略、候选利用、证据核验、决策和终止质量 |

> 严格成功由代码和 Reward 合同决定，Judge 用于语义过程诊断，不能互相覆盖。

### ★★★★★ Q146：为什么 Judge 必须盲评？它看不到什么？

> 如果 Judge 看到 Gold ASIN、Reward 或隐藏商品字段，就可能沿着答案打分，无法判断模型是否真的从公开证据做出决策。当前 Judge 只看 Query、冻结 Rubric、Actor 可见轨迹、Guard 事件和白名单行为指标；不看 Gold、Reward、隐藏字段和未投影页面。

### ★★★★☆ Q147：为什么不做一个综合总分？

> 综合分需要主观权重，可能用高结果分掩盖安全或成本问题。项目保留结果/约束、轨迹质量、资源效率等独立面板，让面试官或业务方按目标解释；如果业务确实需要单指标，应先公开权重、敏感性和门槛。

### ★★★★☆ Q148：1,769 条 Rubric 是什么单位？

> 是 240 道任务中冻结的逐约束条目数，不是 1,769 道题。每条记录约束类型、期望值、操作符、Query 原文 span、Hard/Soft/审计状态和实际证据。状态 `satisfied/violated/unknown/not_applicable` 统计的是条目，不应与任务成功率混用。

### ★★★★☆ Q149：Rubric Curator 会不会把 Gold 商品的所有属性都加成要求？

> 不会。候选约束先由 Query 和公开任务信息生成，Curator 只选择 Query 明确表达的要求，禁止新增期望值；Gold 的私有属性只作审计参考。否则模型可能因为不知道隐藏条件而被不公平扣分，也会造成答案泄漏。

### ★★★★★ Q150：pass@4 和 pass^4 怎么解释？

> `pass@4` 是四次尝试中至少一次成功的任务比例，衡量覆盖能力；`pass^4` 是四次都成功的任务比例，衡量稳定性。它们分别对应并集和交集，不是把单次成功率简单四次方。若四次结果有相关性，独立 Bernoulli 的近似也不成立。

### ★★★★☆ Q151：四轮都用 temperature=0，为什么结果还可能不同？

> 温度为 0 不保证整个系统完全确定：服务端 tie-breaking、并发调度、网络重试、工具/环境状态、浮点和不同 Prompt/版本仍可能产生差异。要比较稳定性，固定模型、Prompt、环境、顺序和版本，并记录每轮轨迹。

### ★★★★☆ Q152：Qwen3.8-27B 72.92% 和你的 2B 77.08% 怎么解释？

> 先说明这是旧版同协议的 Gold＋Valid 购买成功口径，且两者是不同 Actor/不同规模的对照。2B 在这个固定环境中可能因 SFT、GRPO 和 Harness 更贴合任务；27B 有更强通用能力但未必适配当前工具策略。不能据此说 2B 全面优于 27B，要看严格 Gold、Challenge 切片、稳定性、成本和当前版本。

### ★★★★☆ Q153：Judge 五维均分高 0.02 有多大意义？

> 评分范围是 0—2，0.02 是很小的描述性差异，可能受 Judge 方差影响。应报告样本数、置信区间、重复 Judge 一致性和逐题迁移；没有统计检验和多次采样时，不说“显著提升”。

### ★★★★☆ Q154：怎样证明一次改动真的有效，而不是模型/题目变化？

> 冻结同一 task ID、环境、Prompt、模型、采样和分母，做 paired comparison；最好做单因素开关消融、多随机种子和置信区间。记录失败→成功、成功→失败、工具错误、资源和行为指标，而不是只比较两个总成功率。当前购物的 GRPO230 与 Harness 同时变化，因此只称完整系统收益。

### ★★★☆☆ Q155：如何防止 Final-240 评测集泄漏？

> 在 rollout 前检查训练/评测 task、family、Query/商品近似和轨迹 ID 的交集；用 `evaluated=false`、task/slice/data hash 和 blind guard 限制训练脚本读取；Rubric/Judge 不根据 Actor 结果反向修改。历史失败题一旦用于调参，应移入回归集并换新的 held-out，不能继续把它称为未见测试。

### 13.1 AI 应用全生命周期

### ★★★★★ Q156：如果把你的购物项目映射到“业务—模型—反馈”闭环，完整链路是什么？

> 先把业务目标定义为“在公开商品信息和规格状态下满足用户约束并完成购买”；再把它拆成动作协议、数据、Reward 和评测指标。Teacher/ SFT 解决冷启动，在线 GRPO 从当前策略采样，Harness 记录行为和环境状态，终局 Reward 给出可计算反馈，Rubric/Judge 诊断过程，失败轨迹再回流到纠错数据或回归集。每一轮都要保留版本、哈希和失败原因，才能知道反馈是否来自模型、环境还是评分器。

### ★★★★☆ Q157：真实客服场景比你的商品快照多哪些问题？

> 多语言和混合语言、订单/物流/售后知识时效、用户身份与隐私、工具权限、情绪和澄清、多轮会话隔离、在线延迟和峰值流量。我的项目主要验证长程工具决策、约束满足和可审计评测，不能直接声称覆盖这些线上问题；但 MiniClaw 的会话、Trace、Approval、Memory 和 Eval 设计可以作为迁移基础。

### 13.2 数据飞轮与合成数据

### ★★★★★ Q158：合成数据怎样保证不是“模型自嗨”？

> 生成器只负责扩大候选，质量门和独立环境负责验收。对轨迹做结果、过程、行为语义三层过滤；用确定性环境/Reward 检查终局，用 task/family 和近似 Query 做泄漏检查，用覆盖率、长度、错误类型和动作序列多样性做数据集级审计。Judge 可以辅助语义诊断，但不能代替外部 oracle。

### ★★★★☆ Q159：Teacher 选强模型还是选真实用户轨迹？

> 强模型适合产生规范动作和覆盖边界，真实轨迹更贴近用户分布但噪声和隐私风险更高。可以混合来源，但必须统一 Tool Schema、Observation 和结果门，并记录来源、模型版本和清洗规则。不能因为 Teacher 模型强就跳过过程门。

### 13.3 评测体系

### ★★★★★ Q160：如果业务只给你一个“解决率”，你会怎样拆指标？

> 先保留主业务成功率，再拆 Hard 约束满足、Soft 偏好满足、工具合法率、证据核验率、过早终止、循环、平均/P95 延迟、Token/成本、安全拦截和重复稳定性。每个指标绑定可复现的事件或 oracle，避免一个综合数掩盖风险。购物项目的 Final-240 和 MiniClaw 五维 Eval 都采用这种拆解思想。

### 13.4 Reward 与可控性

### ★★★★★ Q161：为什么不直接用 LLM 当 Reward？

> LLM 对开放语义判断有价值，但对价格、ASIN、规格、步数和终局等可确定字段不如代码稳定；它还可能受提示、泄漏和评分偏差影响。我的做法是代码确定性 Reward 负责硬事实，Rubric/Judge 负责过程语义诊断，并做盲评和校准。若必须使用 LLM Reward，要固定输入、禁止隐藏字段、校准一致性并保留原始判断。

### ★★★★☆ Q162：Hard/Soft 约束如何防止 Reward Hacking？

> Hard gate 先阻断不可接受错误，Soft 只能在 Hard 全过后贡献部分分；未知证据不当作满足；目标 ASIN 不免检；步数惩罚不能覆盖硬错误。再用独立 Rubric 和失败迁移检查模型是否通过“早买、少核验、标题关键词投机”等方式拿到高 Reward。

### 13.5 外部能力：RAG/Memory/MCP/多 Agent

### ★★★★☆ Q163：如果让你给天猫客服加 Memory，你会保存什么？

> 保存经用户确认、可长期复用且不含敏感信息的偏好，例如语言、尺码偏好或配送约束；订单事实应有时效和权限，不能当永久语义记忆。每条记忆要带来源、时间、版本和租户/会话边界，支持替换、删除和冲突处理。一次性工具输出、模型推测和密码不进入长期记忆。

### ★★★★☆ Q164：如果接入 MCP，最先做哪三层防护？

> 工具发现与 schema 白名单；调用前的租户/用户授权、风险分类和参数校验；调用后的超时、结果大小、来源标记、审计和取消。远端 MCP 工具的返回仍是外部数据，不能直接提升为系统指令；非幂等调用要有幂等键或人工确认。

### ★★★☆☆ Q165：多 Agent 客服如何避免互相覆盖状态？

> 明确每个 Agent 的职责和可写状态，使用共享任务 ID、版本号/乐观锁和事件日志；只让一个协调器提交最终副作用，其他 Agent 返回带证据的建议。并行只用于独立只读检索，涉及订单修改、退款或购买必须串行和审批。

## 14. 现场白板与算法题：按岗位高频排序

### ★★★★★ Q166：手写稳定 Softmax，并说明为什么要减最大值

```python
import math

def stable_softmax(xs: list[float]) -> list[float]:
    if not xs:
        return []
    if not all(math.isfinite(x) for x in xs):
        raise ValueError("logits must be finite; an all-masked row needs a separate policy")
    m = max(xs)
    exps = [math.exp(x - m) for x in xs]
    total = sum(exps)
    return [x / total for x in exps]
```

> 减去最大值不改变归一化后的概率，因为分子分母同时乘同一个常数；可以防止 `exp(1000)` 溢出。全 `-inf` 的 mask 行不能直接套这个函数，生产代码要显式定义处理策略。时间复杂度 O(n)，空间 O(n)。

### ★★★★★ Q167：手写带因果 mask 的单头 attention

```python
import math
import torch

def attention(q, k, v):
    # q/k/v are torch.Tensor; production code should vectorize the mask.
    # q: [Tq, d], k/v: [Tk, d]
    scores = q @ k.T / math.sqrt(q.shape[-1])
    # 只允许查询位置 i 看见 key 位置 <= i（示例假设 Tq == Tk）
    mask = torch.triu(torch.ones_like(scores, dtype=torch.bool), diagonal=1)
    scores = scores.masked_fill(mask, float("-inf"))
    weights = torch.softmax(scores, dim=-1)
    return weights @ v
```

> 现场可先写伪代码，说明真实 PyTorch 应用 `masked_fill` 和向量化，不要在生产代码里用双重 Python 循环。复杂度标准 attention 约 O(T²d)。

### ★★★★★ Q168：手写 RRF 排名融合

```python
from collections import defaultdict

def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    score = defaultdict(float)
    for ranking in rankings:
        for rank, item in enumerate(ranking, start=1):
            score[item] += 1.0 / (k + rank)
    return [item for item, _ in sorted(score.items(), key=lambda p: (-p[1], p[0]))]
```

> RRF 只依赖名次，避免把 BM25 与向量分数直接相加；真实系统还要在融合前做权限过滤、去重和来源限制。

### ★★★★☆ Q169：手写一个带容量和 Hash 失效的 Read Cache

```python
from collections import OrderedDict

class ReadCache:
    def __init__(self, capacity: int = 5):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, path: str, current_sha: str):
        item = self.data.get(path)
        if item is None or item[0] != current_sha:
            self.data.pop(path, None)
            return None
        self.data.move_to_end(path)
        return item[1]

    def put(self, path: str, sha: str, content: str):
        self.data[path] = (sha, content)
        self.data.move_to_end(path)
        while len(self.data) > self.capacity:
            self.data.popitem(last=False)
```

> 重点是“命中前再次确认 hash”，否则缓存只按路径会把旧文件内容误当新事实。若多进程使用，还要加锁或改用 SQLite。

### ★★★★☆ Q170：手写组内 Advantage，并处理全相同 Reward

```python
def group_advantages(rewards: list[float]) -> list[float]:
    if not rewards:
        return []
    mean = sum(rewards) / len(rewards)
    return [r - mean for r in rewards]
```

> 全相同奖励时所有优势为 0，说明这一组没有学习信号，不应伪造正负标签；动态采样可以有限重采样，仍无差异就跳过该组。若再做标准差归一化，要处理零方差。

### ★★★★☆ Q171：手写异步并发，并保证最多 N 个任务

```python
import asyncio

async def bounded_map(coros, limit: int = 8):
    semaphore = asyncio.Semaphore(limit)

    async def run_one(coro):
        async with semaphore:
            return await coro

    return await asyncio.gather(*(run_one(c) for c in coros))
```

> 还要说明取消、超时和异常策略；共享写状态不能只靠 semaphore 保证正确。真实实现应保存任务对象，在一个协程失败或取消时清理未完成任务；MiniClaw 只对明确只读工具并行，结果按原顺序回填。

### ★★★★☆ Q172：手写路径是否位于工作区内

```python
def inside(root: Path, candidate: str) -> Path:
```

### ★★★★☆ Q173：写一个最小的 PPO clipped objective

$$
L^{CLIP}(\theta)=\mathbb E_t\left[\min(r_t(\theta)A_t,\operatorname{clip}(r_t(\theta),1-\epsilon,1+\epsilon)A_t)\right]
$$

其中 `r_t=π_θ(a_t|s_t)/π_old(a_t|s_t)`。`A_t>0` 时不让概率无限增大，`A_t<0` 时不让概率无限减小；clip 和 KL 监控/惩罚不是同一件事。

### ★★★☆☆ Q174：如何解释 DPO loss？

> DPO 使用 chosen/rejected 偏好对和参考模型 log-prob，把“更偏好 chosen”写成一个二分类式目标，不需要在线环境 rollout 和独立 Reward Model。它适合已有偏好对；购物项目的优势在于环境可交互、可计算终局反馈，所以主链使用 on-policy GRPO。我的 DPO 是原理准备，不声称主项目端到端实践。

## 15. 把购物动作链逐步讲明白：搜索、比较、核验、规格、购买

### ★★★★★ Q175：一次完整购物任务从 Query 到购买是怎样的？

**推荐回答：**

> 首先从 Query 中提取品类、预算、品牌/型号、功能和规格约束，但这些隐含约束只用于模型理解和终局公开证据核验。模型在搜索页提交简洁且有区分度的 query，读取当前页商品的 ASIN、标题、价格和属性；再打开当前页可见的候选，核对详情和公开证据；如果有多规格，逐个使用当前详情页的 stable option ID，选择后重新确认 variant 价格；最后只有在当前页面、规格和证据都闭合时调用 `buy_now`。每一步的下一组工具都由最新页面状态决定。

### ★★★★★ Q176：为什么搜索词不能直接复制整句用户需求？

> 整句 Query 可能包含否定、预算和背景叙述，直接复制会降低搜索区分度或让索引把无关词当主要词。应保留核心品类、品牌/型号和区分属性，必要时做有实质变化的改写；改写后要检查新结果是否带来候选或新证据，避免机械重复搜索。

### ★★★★☆ Q177：候选比较看哪些维度？顺序为什么重要？

> 先看品类和不可妥协 Hard，再看预算/价格语义，再看品牌、型号和核心功能，最后核对规格和 variant 实际价格。顺序能减少“标题很像但核心约束不满足”的误购；但它是决策启发式，不是把所有商品评分公式硬编码给模型。当前 Reward 和 Judge 会分别检查 Hard/Soft 约束与候选利用质量。

### ★★★★★ Q178：详情核验和搜索结果浏览有什么区别？

> 搜索页适合发现候选，字段通常是摘要；详情页才有完整公开属性、规格轴、已选值和当前 variant 价格。不能仅凭搜索标题购买，尤其是多规格、按包/瓶/平方米计价和否定条件。当前 `select_option` 后必须重新看详情，确认选择和价格没有变化。

### ★★★★☆ Q179：为什么要核验“最终 variant 价格”，而不是商品起价？

> 商品详情的起价可能对应另一个规格或数量；用户买的是选择完成后的 variant。Reward v4 用完整 variant 的实际价格和公开字段逐约束核验，必要时按包/瓶/面积等基准换算。否则模型可能选了一个满足功能但超预算的规格，却因为页面起价低而被错误判成功。

### ★★★★☆ Q180：什么是“近似商品购买”？怎样判定是合理替代还是错购？

> 先判断品类和所有 scored Hard 是否满足；Hard 全过且 scored Soft 有可靠证据但未全满足，属于 Partial；Hard/Soft 全过但不是目标 ASIN，属于 Valid Alternative；任一 Hard 失败则 Wrong；Hard/Soft 证据不可核验则是 `reward_unverifiable`。不能因为标题相似、价格接近或目标 ASIN 正确就免检，也不能把无法核验当作满足。

### ★★★★☆ Q181：为什么 `finish_without_purchase` 不能随便调用？

> 主动放弃是一个终局动作，当前统一记为 `early_abstain`，不能替代充分搜索或候选阶段的 Hard 判断。普通探索阶段只有在确实没有合适候选、并且符合环境规则时才考虑；进入顺序候选阶段后不再把它作为候选决策工具，候选被拒绝通过 `back_to_search` 进入下一个候选，全部拒绝再按触发原因终止。

### ★★★☆☆ Q182：为什么不公开 `view_reviews`？

> 工程上判断 Reviews 这类页面长、主观、与当前结构化 Reward 关键字段关系较弱，可能带来额外循环，因此当前移除低频 `view_*` 信息工具，并把非空描述/Features/Attributes 合并到详情 Observation，减少工具数量和页面往返；“噪声是主因”是设计假设，不是独立消融结论。若业务必须使用评价，应设计受控、一次性、带预算和证据来源的工具，而不是简单开放所有页面。

## 16. 训练和评测数字的逐字解释

### ★★★★★ Q183：0%→64.58%→69.17%→77.08% 每个箭头代表什么？

**按简历口径回答：**

> 0% 是 Base；64.58% 是加入 SFT 后的购买成功率，对应 155/240；69.17% 是 GRPO100，对应 166/240；77.08% 是旧版 Harness 改善后 GRPO230，对应 185/240。这里的“购买成功”是 Gold＋Valid 口径，分母固定为 240；严格 Gold 另有一列，不应混成同一个指标。

**随后主动补边界：**

> 这些箭头跨越了模型训练、Reward 聚合和 Harness 版本变化。8/26 旧候选列表流程的 raw summary 是 GRPO230 176/240 strict Gold、195/240 Gold＋Valid；同批冻结轨迹经 8/31 Reward v4 overlay 重算为 169/240 strict Gold、185/240 Gold＋Valid。9/1 后才改为 C1→C4 顺序自动重开，当前没有同条件完整 Final-240 结果。因此若要复现实验，我会先锁定 run manifest、task hash、Reward contract 和 Harness commit，不把这些 artifact 拼成一条曲线。

### ★★★★★ Q184：为什么 SFT 的 64.58% 不是严格 Gold 64.58%？

> 因为简历把“正确购买”写成 Gold＋Valid 购买成功；旧表中 SFT 严格 Gold 是 137/240=57.08%，Valid Alternative 另有 18 条。面试中必须先说指标名称和分子，不只报百分比。

### ★★★★☆ Q185：Reward 0.3033→0.3945 是什么提升？

> 这是特定历史运行中平均 Final Reward 的变化，不是成功率，也不是每条轨迹都提高。Reward 由终局类别、Hard/Soft 约束和步数惩罚组成；平均值可能受替代购买、Partial、错误和轨迹长度共同影响。比较时要锁定 Reward 版本、题集、模型和是否回放重算。

### ★★★★☆ Q186：P50 31.8→17.6 秒怎么计算？

> 对每条任务记录从开始到终局的端到端耗时，按 240 条排序取中位数；它包含模型等待、工具和环境执行、重试以及调度，不是单 token 延迟。当前不同 Harness/Actor 版本的 P50 不能跨表直接相减；同时应报告 P95，避免长尾被中位数隐藏。

### ★★★★☆ Q187：pass@4=84.17% 与 pass^4=65.42% 为什么都要报？

> 前者回答“多试几次能不能覆盖到一次成功”，后者回答“每次都成功是否稳定”。如果 pass@4 高而 pass^4 低，说明策略有覆盖能力但方差大；线上客服通常更关注稳定性，训练探索则可能关注覆盖。两者都基于同一四轮任务结果，不能用一个替代另一个。

### ★★★★☆ Q188：Rubric “增加 56 条”是什么意思？

> 是与 Qwen3.8-27B 对照相比，满足的逐约束条目数多 56 条（例如 1,611 对 1,555 的历史表），不是多完成 56 道任务，也不是成功率增加 56 个百分点。条目数分母是 1,769 条冻结约束，任务成功分母是 240，必须分开。

### ★★★★☆ Q189：Judge 五维均分高 0.02 是怎么算的？

> Judge 对搜索策略、候选利用、证据核验、决策质量、终止效率分别给 0/1/2 分，先按任务求均值，再比较两个 Actor；“高 0.02”是平均分差，规模很小且没有完整显著性证据。它用于过程诊断，不覆盖代码判定的严格成功。

### ★★★★☆ Q190：为什么严格 Gold 可能比购买成功低？

> 购买成功允许满足公开约束的替代商品，严格 Gold 还要求目标 ASIN；另外当前 Reward v4 对 Soft 和可验证性有更细分类。一个轨迹可以是 Valid Alternative 或 Partial，说明用户需求部分满足，但不应包装成目标商品严格命中。

## 17. 当前源码变化引出的新追问（必须优先复习）

### ★★★★★ Q191：为什么 Reward v4 最近要求目标商品也通过 Soft？

> 旧逻辑容易把目标 ASIN 当作免检通道，导致它即使违反用户“最好/预算左右”等公开偏好也拿到 Gold。现在目标和替代都先过 Hard，再检查 Soft：可验证的 Soft 失败进入 Partial，Soft 不可核验进入 `reward_unverifiable`，只有 Hard/Soft 全过的目标才是 Gold。这样评测语义更接近用户要求，也减少 Gold 身份造成的奖励投机。

### ★★★★★ Q192：为什么 Hard 失败要优先于“不可核验”？

> 如果已经有明确证据证明品类、强制价格或规格不满足，就应判 Wrong，而不能因为另一个字段未知而把整条标成 Unverifiable。否则错误购买会被错误地从训练/统计中排除。当前 Reward 先检查可确认 Hard 失败，再处理不可核验状态，并保留逐约束证据。

### ★★★★☆ Q193：为什么要给 Reward contract 做 SHA 校验？

> Query 语义编译、任务修复、商品数据和 Reward 代码任何一个版本变化，都可能改变终局分类。把 instruction/config/constraint contract 的 hash 写入轨迹，评测时先核对，能防止用新规则重算旧轨迹却把结果当同一实验。hash 不能证明语义本身正确，但能证明“你知道自己比较的是哪一版”。

### ★★★★☆ Q194：Task 363 的语义别名修复说明了什么？

> 标题关键词的部分匹配可能误把“AI”“儿童”“彩色贴片”等词当成满足条件，但当前选中的规格或数量仍可能冲突。项目把别名和任务修复表版本化，并用 instruction SHA 绑定；回归测试验证明确 Hard 失败时必须 Wrong，不能被标题别名覆盖。这是数据/Reward 语义修复，不是给模型写答案规则。

### ★★★★☆ Q195：搜索 BM25 权重修复为什么不能直接说模型变聪明？

> FTS5 的 `bm25()` 权重按列位置解释，若漏掉未索引的 ASIN 首列，title/model/brand 等权重会错位。修复索引和 manifest 后，检索排序本身改变；要证明收益，应在固定模型/Prompt/Harness 下做检索结果和端到端配对实验，不能把搜索修复后的成功率提升归因于 SFT/GRPO。

### ★★★★☆ Q196：训练数据里还有旧 `view_*` 动作，当前怎么处理？

> 历史数据是当时 Harness 的真实分布，不能假装不存在；但当前公开 Schema 已移除 `view_*` 和 `think`，非空信息并入详情 Observation。若继续使用旧轨迹，需要做动作迁移/过滤并重新过 schema、token 和过程门；历史 SFT 结果不能直接证明当前 Schema 的行为完全一致。

### ★★★★☆ Q197：GRPO Probe 的“三批重采样”和训练的“两批重采样”为什么不同？

> 离线 Probe Gate 的 `max_rounds` 是数据准入诊断，训练配置的 `max_num_gen_batches` 是在线算力预算，两者服务不同阶段。不能把 Probe 尝试次数直接当成正式训练每组的采样次数。回答时要引用对应配置文件和运行 manifest。

### ★★★★☆ Q198：当前候选恢复的顺序偏差怎么验证？

> 固定 C1→C4 虽然可审计，但可能让早期候选获得更多注意。应记录候选来源 rank、触发原因和每候选结果，做候选顺序随机置换、按 rank 分层和不同上下文策略的配对消融；只看总成功率不能排除顺序偏差。

### ★★★★☆ Q199：GRPO 的 45 步、vLLM 180 秒和上下文 30K 是同一个预算吗？

> 不是。45 步是环境/Agent 动作上限；vLLM 180 秒是单次模型请求或 runtime 超时配置；30K 是模型序列长度/训练上下文合同。还要区分单步生成长度、总轨迹时间、Provider token 和候选恢复阈值 30 步。预算名称相似但资源维度不同。

## 18. “训练数据构造、Checkpoint 评估、Badcase 迭代”三个短语的深挖

### ★★★★★ Q200：你如何评估一个 SFT/GRPO checkpoint，而不是只看训练 loss？

> 我会固定评测协议，至少看：严格 Gold/Gold＋Valid、Reward 有效率、Hard/Soft 约束、工具非法/Guard 拒绝、重复动作、平均和 P95 步数/耗时、上下文使用、Group 保留率以及 Challenge 分层。Checkpoint 评估要保留模型权重、Tokenizer、Prompt、Harness、Reward、题集 hash 和运行配置，避免“同名 step”实际使用不同版本。

### ★★★★☆ Q201：step50、step100、step230 为什么不能只按数字比较？

> step50/100/230 表示训练 checkpoint 或阶段，但 step230 还同时包含 Harness 改善和 Reward/评测版本变化。step 数增加不保证泛化更好；应做同协议 paired comparison，报告成功→失败回退、Reward 类型、行为指标和置信区间。简历数字来自特定冻结快照，不能把 step230 的所有收益归因于多训练 130 步。

### ★★★★★ Q202：你发现一个 Badcase 后，如何从现象走到修复？

```text
定位：读取逐步 Trace 与终局证据
→ 分类：模型决策 / Tool 协议 / Harness / Reward / 数据 / 评测器
→ 构造最小可复现 case
→ 选择修复层（Prompt、数据、Reward、Runtime 或评测）
→ 添加固定回归
→ 在不接触 held-out 的开发集复测
→ 检查副作用与回退，再决定是否进入训练/发布
```

> 例如“买到正确品类但超预算”：先确认是 Query 语义、variant 价格、Reward comparator 还是模型没核验；不能看到结果变好就盲目加一个关键词规则。

### ★★★★★ Q203：你怎样区分模型问题和 Harness 问题？

| 证据 | 更可能的归因 |
|---|---|
| 模型想调用当前页不存在的 ASIN，Guard 拒绝 | 模型 grounding/协议学习，但 Guard 保护了环境 |
| Observation 没有暴露本来可执行的按钮 | Harness 投影/Schema 问题 |
| 商品证据公开且完整，模型仍买错 | 策略/训练/Reward 归因 |
| Reward contract hash 不一致或证据不可验证 | 评测/基础设施，不应当作普通模型失败 |
| 旧验证结果在修改后仍被复用 | Runtime/验收新鲜度问题 |

> 需要用同一版本的 replay、Trace 和独立 oracle，不凭一条自然语言回答归因。

### ★★★★☆ Q204：训练中的 checkpoint 如何安全合并和导出？

> 先确认基座权重、LoRA adapter、Tokenizer、dtype、模型配置和训练 lineage；合并 `W + ΔW` 后做加载、参数非零、输出和工具协议 smoke test，再进入固定评测。不能把“文件成功保存”当作模型已正确更新，也不能混用不同基座的 adapter。

### ★★★★☆ Q205：如果 SFT 后非法动作减少但重复搜索增加，你会怎么处理？

> 这说明协议格式学会了，但搜索策略或停止策略变差。先看绝对步数和成功率，确认不是 Base 因为早停导致重复次数看起来少；再按 Search Rank、query canonicalization、候选比较和终止效率分层。修复可以补充有实质改写的纠错轨迹、调整 Prompt/Reward 的重复惩罚，或改 Harness 提醒，但要防止过早终止和过拟合。

### ★★★★☆ Q206：为什么不能只用最终购买是否成功来筛 Teacher？

> 最终成功可能是偶然命中、经过多次非法动作后碰巧购买，或者利用了隐藏信息；这样的轨迹会教模型错误过程。结果门保证交付，过程门保证可重放和工具合法，行为门保证没有明显循环/泄漏/无意义探索，三者共同决定是否值得监督。

### ★★★☆☆ Q207：你会怎样设计一个最小消融实验？

> 固定数据、模型、环境、Prompt、seed 和评测集，只开关一个机制；例如同一 checkpoint 比较有/无候选记忆、不同候选顺序、Hard/Soft Reward、去标准差、动态采样。每个条件至少多 seed，报告均值、区间、逐题迁移、资源和失败类别。当前项目的完整系统对比没有做到所有机制逐项消融，所以我会明确这是下一步，而不是假装已有。

## 21. 专业技能逐字卡：简历写“了解/熟悉”时的最低回答线

这一节不是让你把所有知识讲成论文，而是规定面试官突然点名一个词时，至少要能说出“定义—项目连接—边界”。

### ★★★★☆ Q221：Python 在你的项目里具体用来做什么？

> Python 负责 Agent 编排、异步模型请求、工具执行、数据清洗、Reward/评测脚本和 Trace 处理。它的优势是生态和开发效率，代价是动态类型和 GIL 需要靠类型检查、测试、进程/异步边界补足。我的回答不能停在“会写语法”，要能解释异常、资源清理、并发和文件原子写入。

### ★★★☆☆ Q222：生成器、异步生成器和装饰器有什么用？

> 普通生成器按需产出值，节省内存；异步生成器适合逐步消费 SSE/AgentEvent；装饰器可以在不改业务函数的情况下包裹 Trace、重试或权限逻辑。要注意装饰器会改变调用栈/元数据，异步函数不能被同步 wrapper 误调用。

### ★★★☆☆ Q223：Python 异常为什么不能全部 `except Exception: pass`？

> 吞掉异常会把真实失败伪装成成功，尤其是 Reward、文件写入和安全校验。应在边界处记录结构化错误、清理资源并决定可恢复/不可恢复；只有明确的可选诊断或缓存优化才可以降级，而且要保留状态。

### ★★★★☆ Q224：PyTorch 里的 mask 有哪几种？

> causal mask 防止当前位置看未来；padding/attention mask 忽略无效填充；loss label mask（如 `-100`）决定哪些 token 参与监督。三者作用位置不同，不能因为都叫 mask 就混用。购物 SFT 的 assistant-only 是第三种，环境 Observation 仍作为输入。

### ★★★★☆ Q225：CrossEntropyLoss 为什么通常不先 softmax？

> PyTorch 的 `CrossEntropyLoss` 通常内部组合 `log_softmax + NLLLoss`，直接传 logits 数值更稳定，也避免重复计算。若手动先 softmax 可能造成数值下溢和梯度问题；计算 perplexity 时才从平均负对数似然取指数。

### ★★★★☆ Q226：梯度累积、梯度裁剪和 gradient checkpointing 分别解决什么？

> 梯度累积用多次小 batch 的梯度模拟更大有效 batch；梯度裁剪限制异常大梯度，减少训练爆炸；gradient checkpointing 只保存部分激活，反向时重算以省显存换计算。它们不能互相替代，也不能把训练 batch size、GRPO group size 和 rollout 并发混为一谈。

### ★★★★☆ Q227：RLHF 的经典流程怎么讲？

> 先用 SFT 得到初始策略，再收集人类偏好训练 Reward Model，最后用 PPO 等 RL 方法优化策略并用 KL 约束不要偏离参考模型。现代也有 RLAIF、DPO 和可验证 Reward。我的购物项目跳过独立人类 Reward Model，直接使用环境可计算终局 Reward 做 GRPO；这属于不同反馈来源。

### ★★★★☆ Q228：PPO 的 clip 为什么能稳定更新？

> 它限制新旧策略概率比 `r_t` 在 `1±ε` 附近，取 clipped 与 unclipped 目标的较小值，防止一次更新让高优势动作概率暴涨或低优势动作概率骤降。Clip 不会自动保证语义正确，也不等于 KL 惩罚；还要配合 Advantage、batch、学习率和评测。

### ★★★★☆ Q229：DPO 为什么不需要在线 rollout？

> DPO 直接使用 chosen/rejected 响应的相对 log-prob 和参考模型，优化隐式偏好目标；它适合已有偏好对，训练数据分布固定。GRPO 直接从当前策略与环境交互，能利用终局和状态反馈，但采样成本高、Reward 设计难。购物项目选择 GRPO 是因为环境能明确判定动作后果。

### ★★★★☆ Q230：on-policy GRPO 的数据为什么不能长期缓存？

> 策略更新后，旧轨迹的动作分布不再代表当前策略；无限复用会产生 off-policy 偏差。工程上可以保留 checkpoint/轨迹用于诊断或有限 replay，但训练 admission 要记录生成策略、时间、Reward contract 和有效性，不能把历史成功样本无限当当前策略数据。

### ★★★☆☆ Q231：Tokenizer、BPE 和特殊 Tool Token 为什么会影响结果？

> token 数决定上下文预算、训练 loss 和成本；同一个中文/JSON 字符串在不同 tokenizer 下 token 数不同。Tool Call 的特殊 token、角色标记和 chat template 必须和推理一致，否则 assistant-only mask 对不上，模型可能学不会合法调用或把 Observation 当答案。

### ★★★☆☆ Q232：Temperature、top-p 和 greedy 有什么区别？

> Temperature 调整 logits 分布的尖锐程度；top-p 从累计概率最小集合采样；greedy 取最大概率 token。评测常设 temperature 0/greedy 以减少随机性，训练 rollout 会保留探索温度；但并发、服务端 tie-breaking 和环境仍可能导致差异。

### ★★★★☆ Q233：RAG 的 chunk size/overlap 怎么选？

> chunk 太小会丢上下文，太大会降低召回精度和增加注入成本；overlap 用来保留跨边界语义，但过大造成重复。应按文档结构、查询粒度、模型窗口和评测数据调参，并用 recall@k、答案 groundedness、延迟和成本做联合选择，不存在通用最优值。

### ★★★☆☆ Q234：Query Rewrite 会不会改变用户意图？

> 会有风险。改写应保留否定、数值、实体和约束强度，并记录原 Query 与改写结果；搜索改写只用于扩大召回，不应覆盖原始业务约束。Reward/评测仍以用户原话和冻结 Rubric 为准。

### ★★★★☆ Q235：RAG/Memory 如何处理权限和多租户？

> 权限过滤必须在召回前或至少在结果注入前做，不能只依赖模型拒绝；索引、缓存键、会话 ID 和 Artifact 路径都要带租户/用户 scope。跨会话召回要显式授权，删除和过期要能传播到索引和缓存。MiniClaw 当前用 user/channel/session scope 和 untrusted context 边界，不能把所有业务多租户问题说成已完成。

### ★★★★☆ Q236：Flash Attention 的“在线 softmax”如何避免一次保存全部矩阵？

> 将 Q/K/V 分块处理，维护每行当前最大值和归一化累积量；新块到来时用尺度因子更新旧累积，得到与完整 softmax 等价的结果。这样中间 attention score 不必完整落到显存，减少 IO；数值稳定性来自 max-shift 和累积更新。

### ★★★☆☆ Q237：GIL 对你的 Agent 有实际影响吗？

> 模型网络、SSE、文件等待属于 I/O，asyncio/线程可以提高并发；CPU 密集的 Python 解析或计算受 GIL 影响，可考虑进程、原生库或向量化。真正的模型推理通常在外部服务/GPU，不应把 GIL 当作所有延迟的解释。

### ★★★☆☆ Q238：数据结构里 set 和 dict 为什么常用？

> set 适合去重和 O(1) 平均成员判断，例如已见 ASIN、call ID；dict 适合按 ID 映射状态、缓存和证据。要注意哈希对象不可变、顺序需求和最坏情况；需要稳定输出时要显式排序，不能依赖偶然插入顺序。

### ★★★☆☆ Q239：BFS/DFS/状态机与 Agent 有什么联系？

> 多步 Agent 的环境状态可以看作图节点、工具动作是边；BFS 适合按层找最短路径，DFS 适合深度探索，状态机适合约束明确的生命周期。购物 Harness 不是让模型遍历完整搜索树，而是用当前页面和阶段限制合法动作；Goal/Runtime 也用状态迁移而不是无限递归。

### ★★☆☆☆ Q240：如何解释“了解数据结构算法”而不被现场题击穿？

> 至少能讲复杂度、哈希/排序/堆、队列、图遍历、LRU、二分和区间合并，并能写出边界测试。不会的题先澄清输入、约束和输出，再给朴素解、复杂度和优化，不要直接套项目名词。

## 22. 系统设计与压力面：把两个项目迁移到真实客服

### ★★★★★ Q241：如果让你从零设计天猫国际 AI 客服 Agent，你会先画什么？

```text
用户/会话入口
  → 会话与租户隔离
  → 意图/约束解析
  → Memory + RAG（权限、时效、来源）
  → Policy / Tool Schema
  → Agent Loop / 状态机
  → 审批与副作用工具
  → 结果核验 / 转人工
  → Trace / Eval / 数据飞轮
```

> 我会先定义业务成功和不可妥协的安全边界，而不是先选模型。高风险退款、改地址、下单需要授权、幂等键和人工兜底；检索、工具、模型、Reward 和评测都要有版本与可观测事件。

### ★★★★★ Q242：如何让客服 Agent 不会因为“看起来完成”就结束？

> 把自然语言停止和业务完成分开：用状态机、待办/证据清单、工具结果和后置核验决定是否结束，没有必要证据就继续或转人工。MiniClaw 的 GoalSupervisor 提供了外层 attempt 监督和提交后独立评审思路；当前公共 `goal_complete` 是模型提交并置 `judge_status=pending`，底层仍保留严格完成 API，但线上最终仍需业务 oracle。

### ★★★★★ Q243：如何防 Prompt Injection？

> 文件、网页、商品描述、记忆和工具返回都标为不可信数据，与 system policy、项目规则和用户请求分层；模型输出必须经过 Schema、权限、审批和运行时 Guard。即使模型被诱导，执行端也不能允许未授权副作用。评测要加入工具结果含恶意指令的固定夹具，并检查泄密、越权和错误引用。

### ★★★★☆ Q244：如何把线上成本再降 30%，且不损失正确率？

> 先用 Trace 分解固定 Prompt、历史、检索、输出、重试和辅助模型成本；再尝试稳定前缀、Artifact、Hash Read Cache、按需工具、摘要/检索预算和模型路由。每项改动都做质量—成本 Pareto 对照；MiniClaw 的 56.41% 是组合回归，必须做单项消融后才能归因。

### ★★★★☆ Q245：如何设计线上发布门禁？

> 回归集阻断已知错误，开发集定位新问题，held-out 检查泛化，线上 canary 观察真实指标。发布前至少检查业务成功、Hard 约束、安全、P50/P95 延迟、Token/成本和重复稳定性；模型、Prompt、Tool Schema、Reward、索引和数据都要锁版本 hash，异常可回滚。

### ★★★★☆ Q246：Reward 变更后成功率上升但用户投诉增加，怎么办？

> 先冻结版本，回放投诉样本，比较新旧 Reward 的逐约束分类和轨迹；重点查 Hard/Soft 是否反了、未知是否被当满足、是否鼓励早买。把投诉转成独立回归，不在投诉题上无限调参；必要时增加真实满意度面板，而不是硬改成功率。

### ★★★★☆ Q247：如何处理多语言和跨境价格/单位？

> Query 解析保留原文、语言、否定、数值、币种和单位；标准化和比较都记录证据。商品/订单知识要带地区、时间、汇率和版本；“左右/大约”不能自动变成严格上限。先做多语言数据和单位转换的独立 Eval，再进入训练。

### ★★★★☆ Q248：工具成功但响应丢失，能否自动重试？

> 先按幂等性和副作用分类。只读或带幂等键的调用可以有限重试；下单、退款、写入先查询状态或转人工，记录不确定副作用，不能盲目重复。重试次数不是可靠性的唯一指标。

### ★★★☆☆ Q249：如何监控 Agent 健康度？

> 业务看解决率、转人工、误购/误答；过程看工具合法、循环、证据覆盖；资源看 P50/P95、输入/输出/缓存 token、费用；安全看审批拒绝、越权、敏感数据；可靠性看重试、取消、重启恢复。按模型、版本、场景、租户分层，避免总体均值掩盖风险。

### ★★★☆☆ Q250：什么情况下不用 Agent，而用固定工作流？

> 如果步骤和规则稳定、风险高且不需要开放探索，固定工作流更可控、便宜、易验收；Agent 适合需求多变、需要根据证据选择动作的部分。实际常用混合架构：Agent 做检索/解释，状态机和策略层控制高风险副作用。

## 23.5 追加高频边界追问

### ★★★★★ Q251：8 KiB、128 KiB、10 MiB 这三个输出阈值分别解决什么问题？

> 8 KiB 是成功大工具结果实时落盘为 Artifact 的阈值，解决后续上下文反复携带全文；约 128 KiB 是 ToolExecutor 对模型可见普通成功结果的最后字符上限，防止没有自有输出策略的工具失控；约 10 MiB 是 Host/Docker 底层捕获上限，防止命令持续输出耗尽进程内存。三者分别属于上下文治理、模型视图边界和底层资源保护，不能把 8 KiB 说成 Runtime 只捕获 8 KiB，也不能把 Artifact 说成丢弃原文。

### ★★★★☆ Q252：Verification cache 的 key 为什么包含 command、mutation epoch 和文件 hash？

> 仅按命令字符串缓存不安全：命令依赖的文件可能已变化，或者前一次 write/edit 已改变工作区。key 同时包含规范化命令、涉及文件内容 hash 和 mutation epoch；成功的幂等/验证调用才可复用，任何写/edit 都推进 epoch 使旧证据失效。当前 fingerprint 只会哈希从命令 token 中识别到的工作区文件，不是完整 Shell 依赖图；动态路径、环境变量和网络输入可能漏检，所以它是降本优化，不是正确性证明。错误、非幂等副作用或不确定结果不能当作通过缓存。

### ★★★★☆ Q253：ContextJournal 和 PrefixDiagnostics 各自做什么？

> ContextJournal 把动态 Memory/phase 信息记录为 append-only delta，在完整工具批次后追加，达到更新数或字节边界才折叠，避免每轮重写整个上下文；PrefixDiagnostics 比较模型、工具定义和消息的精确稳定前缀，输出 SHA/字节诊断。后者只是客户端诊断，不等于服务商已经报告的 prefix-cache token。

### ★★★★☆ Q254：Snapshot 工作区和 Docker Direct 工作区有什么取舍？

> Direct 将实际工作区挂载给运行时，交付修改直接落在源目录，适合明确授权的开发；Snapshot 在会话目录先复制一份，通常跳过 symlink、`.git`、`.aster` 等内部/敏感内容，后续修改不自动回写，适合评测和试验。Snapshot 增加复制成本且需要显式导出结果；Docker 只改变命令执行环境，不能替代工作区边界。

### ★★★★☆ Q255：为什么模型请求已经有重试，工具还要单独设计重试？

> 两者失败语义不同。模型请求重试的是未交付的生成边界，必须处理已输出片段和 Tool Call 是否可执行；工具重试涉及真实副作用，要依据幂等性、审批和提交不确定性决定。统一“网络错误就重试”会重复写入、下单或扣款，因此分别记录 request/transport 和 tool attempt。

### ★★★★☆ Q256：Shopping 搜索索引为什么要锁 schema、权重和商品 hash？

> 搜索结果依赖字段、分词、权重、商品内容和 tie-break 规则。当前 SQLite FTS5 索引对 title/model/brand/category/attributes/options/bullets 使用固定权重，并修复了 ASIN 未索引列导致的 `bm25()` 权重错位；manifest 记录 schema、权重、tokenizer、商品 SHA 和排序规则。这样才能判断排序变化来自索引修复，而不是模型或题集变化。

### ★★★★☆ Q257：如果当前 GRPO230 v3 summary 出现 context ratio>1 或一条 truncation，你怎么回答？

> 我不会宣称全程没有截断。先区分本地 pre-request 估算和 provider 实际 `prompt_tokens`：当前 summary 的旧估算可能超过预算，而校正文件按真实 provider usage 得到另一组分位数。再定位具体 task 的 raw/visible Observation、模型调用和 contract hash，确认是统计口径、单条投影边界还是实际溢出；必要时重跑独立回归。成功率和效率结论要把这条边界写进版本说明。

### ★★★★★ Q258：简历写“蒸馏 DeepSeek”，你做的是哪一种蒸馏？

> 这里主要是 trajectory/behavior distillation：用 DeepSeek Teacher 生成或修正可执行购物轨迹，再经过环境终局、过程和行为语义质量门，筛成 Qwen 的 SFT 示范。我没有做 logit-level knowledge distillation、温度蒸馏或把 Teacher 的私有思维链直接复制给学生。强 Teacher 负责扩大候选和覆盖难例，最终监督目标仍必须来自公开 Observation、合法 Tool Call 和可审计结果。

**追问（沿用 Q258：★★★★★）：为什么不直接用 Teacher 的答案？**

> Teacher 也会犯工具、状态和语义错误；直接复制会把错误放大。环境重放和三层门把“会说”变成“真的能执行”，同时保留来源、版本和失败原因。

### ★★★★☆ Q259：你怎样证明 Teacher 轨迹不是只记住了题目答案？

> 检查 task/family/Query 近似和商品池重叠，隐藏 Gold 不进入 Observation；训练和 Final-240 零重叠；再在不同检索 rank、多规格和 Challenge 题上看动作协议、约束满足和证据核验，而不是只看目标 ASIN 命中。若 Teacher 轨迹携带了 target 或 Reward 字段，应在数据门直接拒绝。

### ★★★★☆ Q260：SFT 产物里的历史 `reward-v3.2` 字段和当前 Reward v4 矛盾时怎么办？

> 不覆盖历史 metadata，也不把它倒写成当前训练合同。先记录该 SFT 产物生成时的 contract/version，再用当前 Reward v4 做独立离线重放或评测，结果另存并带新的 hash。简历里 600/400 和 30K 描述的是数据组成与训练合同，不能因为后续 Reward 更新就声称原始 SFT 已按 v4 生成。

### ★★★★☆ Q261：Qwen3.5-2B 的具体结构你能讲到什么程度？

> 以本地实际 `config.json` 为准：当前合并权重对应 `Qwen3_5ForConditionalGeneration`，文本主干约 24 层、hidden size 2048、intermediate size 6144，8 个 Query heads 与 2 个 KV heads（GQA），按 `full_attention_interval=4` 周期插入 full-attention 层、其余为 linear-attention，RoPE 只作用于部分维度，权重常用 BF16。这里的版本字段和具体数值必须现场打开配置核对；不同 Qwen 版本不能互相套用。简历只写 2B 时，我不会主动把未核对的架构细节说成项目贡献。

### ★★★★☆ Q262：SFT 和 GRPO 的 LoRA 配置为什么可能不一样？

> 当前 SFT 脚本默认 `r=16`、`alpha=32`、`dropout=0.05`，target 包括 attention/FFN 以及 Qwen3.5 线性注意力投影，学习率约 `1e-4`；GRPO 配置是 `r=16`、`alpha=32`、`target_modules=all-linear`、学习率约 `1e-6`，并启用 gradient checkpointing/FlashAttention 2。两阶段目标不同：SFT 需要较快吸收示范，GRPO 要避免在线策略剧烈漂移。回答具体数值时必须标明阶段和配置文件，不能把两套参数拼成一套。

### ★★★★☆ Q263：`loss_agg_mode=seq-mean-token-mean` 解决了什么偏置？

> 先对每条 response 的 token loss 求均值，再对序列求均值，让长短轨迹的权重更接近按“每条轨迹一次”计算。否则一个长循环失败轨迹因为 token 多，可能支配 Actor 更新。它和 `norm_adv_by_std=false` 不同：前者控制 loss 聚合权重，后者控制组内优势尺度；动态采样则控制哪些 Group 进入更新。当前配置如此，历史 checkpoint 需查各自 config。

### ★★★★☆ Q264：SFT 你实际跑了哪些训练规模和资源？

> 以已保存的 SFT 产物快照为准：1,000 条数据按 900 train/100 validation，3 epochs，记录约 339 个 optimizer steps，最大 train/validation 样本长度约 29,533/29,994 token；LoRA 可训练参数约 1,681.9 万，占 2.230B 基座约 0.7542%，训练约 43.8 分钟，峰值显存约 89.64 GiB。BF16、FlashAttention/Liger 等以该 run record 为准。训练本身完成不等于所有收尾审计脚本都成功；遇到收尾脚本/环境错误时，要把训练状态和审计状态分开报告。

### ★★★★☆ Q265：当前 GRPO 配置里最重要的工程参数是什么？

> 当前 `configs/grpo.yaml` 的一组可核对参数是：每个 prompt `n=4`，异步 vLLM、8 个 Agent workers，LoRA `r=16/alpha=32`，Actor 学习率约 `1e-6`，clip ratio ±0.20，rollout temperature 0.7、top-p 0.9，max model length 30K，动态采样初始加最多一次重试（`max_num_gen_batches=2`），Reward range 容忍阈值 0.025，环境最大步骤 45。验证时要说明这是当前配置，不把它无条件套到所有历史 checkpoint。

### ★★★★☆ Q266：1,000 条最终 SFT 数据内部还有哪些质量门？

> 600/400 是行为组成，900/100 是 train/validation 划分，二者不是同一层。数据门还会检查 `trajectory_id` 唯一、train/validation 与 Final-240 的 task/family 零交叉、Gold 检索位置覆盖、搜索改写、候选比较、多规格、证据核验、Guard recovery 和长轨迹比例，并做 token audit 和动作序列去重。比如 metadata 中的历史 contract 可能仍写 reward-v3.2，回答时要把“产物当时的字段”和“后续 Reward v4 重放”分开。
