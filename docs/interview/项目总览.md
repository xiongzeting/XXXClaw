MiniClaw 是一个 Python Coding Agent 框架：把用户任务转成“请求模型 → 调用工具 → 接收反馈 → 继续处理”的循环，并围绕这个循环提供会话、记忆、执行边界和可追溯评测。

代码分成三层：`llm` 统一模型接口与流式事件；`agent` 提供通用循环；`coding_agent` 组装工具、记忆、指令、审批、Runtime 和可选 Goal。CLI、前端等入口使用这套产品能力，Trace 记录过程，Eval 检查是否真的完成任务。

## 图一：沿着一个任务看系统如何变化

示例任务是“修复金额计算，保留 CSV 字段”。图中为了展示完整机制，假设历史已有相关约定，且执行过程中上下文增长到压缩条件。**这是教学轨迹，不是实测日志；短任务可能完全不发生压缩。**

![MiniClaw 典型任务轨迹：工具注册、历史召回、安全执行、结果回写、压缩与跨会话复用](/D:/MIniClaw/docs/interview/MiniClaw典型任务轨迹.svg)

从图中记住三个连接关系即可：

- **当前对话与历史证据一起供模型决策。** Working 保存当前活动上下文；Semantic 保存稳定信息；Episodic 保存历史会话摘要；Procedural 保存技能。Archive 提供归档证据，不额外算一个核心记忆模块。
- **模型提出调用，程序负责执行边界。** 工具注册发生在会话组装时；每次调用再经过参数、项目指令、审批以及具体工具的边界检查。文件工具通过 WorkspaceGuard 访问有效工作区，bash 才选择 Host 或 Docker。
- **结果返回后，既更新任务状态，也可能改变下一轮上下文。** 大结果可以先制品化；历史过长时生成检查点并保留近期完整消息；缺少细节时再查归档和原文。任务结束也不会把所有对话自动变成长期事实。

当前本地前端使用 `host · direct`。图中的 Docker 表示可选命令后端，不能据此声称当前前端已经在容器中执行。`direct / snapshot` 决定用哪份工作区，`Host / Docker` 决定命令在哪里运行，这是两组独立配置。

Goal 是可选的持续任务监督层，不是每次聊天都会创建；`run.completed` 表示一轮运行结束，任务验收仍要看文件、测试和其他证据。

## 图二：同一条轨迹怎样被 Eval 判定

Eval 不只检查最后一句回答。它把初始条件、用户输入、最终文件、工具轨迹、记忆事件和消耗放在一起，再按事先确定的规则判分。

![MiniClaw Eval 总览：数据用途、能力题型、评分维度、执行流程与指标](/D:/MIniClaw/docs/interview/MiniClawEval总览.svg)

读报告时先问三个问题：**这批题用于开发还是独立验收？它主要考什么能力？通过是依据哪种证据？** 一道压缩题也必须检查最终答案，一道安全题也可能同时统计工具行为和成本。

再核对指标口径：Case 与 Attempt 的分母不同；一次成功与重复全部成功不同；工具耗时与整轮耗时不同；召回条数与召回正确率不同。离线测试、原生 Agent Eval、公开 benchmark 的结果也不能直接混成一个通过率。各套件的实际划分和限制以对应 manifest 为准。

## 面试时的一分钟讲法

> 我做的是一个 Python Coding Agent。模型只负责提出行动，产品层负责会话和记忆，工具执行层负责参数、审批、工作区与命令后端。一次任务开始时先按问题召回历史证据，模型读文件、改代码、运行测试；结果回写后继续循环。上下文过长时，把旧历史保存为可检索归档，下一轮只保留检查点和近期消息，需要细节再恢复。整个过程有 Trace，因此 Eval 可以同时检查交付结果、执行过程、安全边界、资源消耗和重复稳定性。改进时先校准判断器，再在开发分布上定位共性问题，用回归与独立验收检验修复。
