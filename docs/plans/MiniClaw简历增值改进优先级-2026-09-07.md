# MiniClaw 简历增值改进路线：优先做什么，为什么，做到哪里停止

审查日期：2026-09-07。目标是提升项目的实际价值、简历可信度和面试解释能力；允许新增模块及较大改造，但每项必须能用清楚的状态、边界和实验解释。本次只形成方案，不修改业务实现。

## 1. 我的判断与推荐主线

**最值得把 MiniClaw 做成“能交付可审查补丁、能解释成本、出错后知道如何恢复的 Coding Agent”。** 现有的分层架构、工具、Docker、记忆和 Trace 已足够支撑这条主线。

目前最大的机会有三处：

1. **把能力连成产品。** 已有编辑、沙箱、测试、Trace，但用户拿到的主要还是对话。新增“任务交付包”，让一次任务留下独立工作区、补丁、验证记录与结果说明，最容易让面试官看到完整价值。
2. **把优化数字变成可解释证据。** 56.41% 很醒目，但现在只能解释组合改动，不能回答每个机制的独立作用。小规模消融比继续增加检索组件更值得投入。
3. **把故障边界讲准确。** 发送前总上下文预算、进程崩溃后的未知副作用、取消后的真实清理结果，都能形成有技术深度但容易理解的工程故事。

建议先完成下表第 1–4 项；第 5–7 项选一个深入。第 8–9 项按岗位和实验结果再决定。不要把本文件当成全部必须完成的功能清单。

## 2. 扫描范围与事实边界

扫描了 `src/MiniClaw` 的分层与关键调用链，包括 llm、agent、assistant、memory、goal、tools、runtime、approval、instructions、trace、evaluation、benchmark、CLI、飞书；同时检查测试、Docker、CI、前端入口、打包配置、历史 Eval 和旧改造文档。采用源码静态审查、关键路径交叉核对及少量无 API 的离线验证，不等于逐行安全审计或全量测试通过。

本次轻量验证结果：

| 检查 | 实际观察 | 能说明什么 |
|---|---|---|
| 两项包依赖边界测试 | 通过 | llm/agent 与 coding product 的分层已有自动约束，值得保留 |
| 普通答案自动保存测试 | 默认环境因 cp932 读取 UTF-8 失败；启用 Python UTF-8 模式后通过 | 新提交行为可用，测试存在依赖机器默认编码的问题 |

证据见 [架构测试](<D:/MIniClaw/tests/test_architecture.py:26>)、[答案保存测试](<D:/MIniClaw/tests/test_simple_submission.py:60>)、[旧协议测试](<D:/MIniClaw/tests/test_request_context.py:151>)。未因此恢复旧接口、安装大依赖或重跑模型。当前进行中的强化版 Eval3 不作为本方案已完成的新成绩。

旧 [实习简历项目改造方案](<D:/MIniClaw/docs/plans/实习简历项目改造方案.md>) 包含很多有用思路，但部分完成门槛、测试数量和代码现状已经过时。以下优先级以本次源码与最新项目约定为准。

## 3. 总优先级

工期是熟悉代码的单人有效开发日粗估，包含局部测试，不包含学习、模型排队和大规模实验；实际学习时间可增加一倍。

| 顺序 | 优先级 | 改动 | 形式 | 工期 | 最直接的简历价值 |
|---:|---|---|---|---|---|
| 1 | P0 | 统一成绩、时间与费用报告，补可复查证据包 | 改造现有评测出口 | 1–2 天 | 数字有来源，运行成功与业务成功不混淆 |
| 2 | P0 | 对齐当前协议、测试与演示默认配置 | 收敛与修复 | 1–2 天 | 新机器能跑，文档与真正行为一致 |
| 3 | P1 | **任务交付包：副本→补丁→独立验证记录→导出** | **新增核心产品模块** | 4–6 天 | 从工具集合变成完整 Coding 产品 |
| 4 | P1 | **统一实验入口，做一项可归因的消融** | **新增小型实验模块** | 2–4 天＋执行 | 能讲清某项设计为什么值得保留 |
| 5 | P1 | 最终模型请求的总上下文预算检查 | 改造请求装配边界 | 1–2 天 | 解释压缩的一轮滞后与预算保护 |
| 6 | P1 | 崩溃窗口中的执行日志与恢复 | 较大但可分步改造 | 3–5 天 | 区分重试模型与重放副作用 |
| 7 | P1 | 取消结果核实、失败现场与有界输出 | 改造执行链路 | 2–3 天 | 证明发出取消指令不等于已停止 |
| 8 | P2 | **代码证据新鲜度：长期记忆关联代码版本** | **新增记忆能力** | 2–3 天 | 相关的历史事实不一定仍然正确 |
| 9 | P2 | 飞书待处理消息与投递恢复 | 可选入口改造 | 2–4 天 | 面向后端岗位的可靠消息处理故事 |

P0 是冻结简历数据和公开演示前应处理的问题。P1 不代表全部必做。默认路线是 **1 → 2 → 3 → 4**；时间不足时，第 3 项先做到单仓库文本补丁导出，第 4 项只测一个机制。

## 4. P0-1：统一报告与证据，把“成绩可信”做成能力

### 当前具体问题

- [历史展示脚本](<D:/MIniClaw/scripts/replace_dashboard_eval3.py:9>) 把没有 execution error 直接当作结果通过；同文件第 12 行把原始耗时填入有效耗时，等待时间填零，第 17 行覆盖第二批对照数据。
- 这是历史发布脚本的问题，不能直接推断当前强化版 Eval3 运行器也有相同错误。但多个发布入口并存，很容易重新引入错误口径。
- 当前 [submissions.py](<D:/MIniClaw/src/MiniClaw/evaluation/submissions.py:9>) 已经支持四维程序评分、结果待评，应该成为正式口径。
- 缓存与费用在 [efficiency_observations.py](<D:/MIniClaw/src/MiniClaw/evaluation/efficiency_observations.py:12>) 已有缺失值处理；等待区间计算则还散落在实验脚本，适合收进公共模块。

### 最小改法

建立一个统一报告出口，输入只有：冻结任务清单、逐题执行记录、四维程序结果、独立结果评审。MD、JSON 和前端全部读取同一份汇总。

每次运行独立保存 `run_id`、源码/题目/判定器版本、模型与参数、并发、预算、重试、费率来源和日期。将 judge 判定绑定运行身份及产物 hash；没有判定时就是 pending。评审数据由运行器维护，**不要求被测模型填写验收 JSON**。

统一三个公式：

- 缓存输入占比 = 有明确缓存上报的 cached input 总数 ÷ 对应 input 总数；缺失请求数量另列。
- 已知费用 = 未缓存输入 × 输入费率 + 缓存输入 × 缓存费率 + 输出 × 输出费率。未知请求/重试成本保留未知。
- 有效耗时 = 原始墙钟 − 模型等待时间区间的并集。逐题与整个批次各自算，不能把逐题耗时之和当作批次墙钟。

提供脱敏的简历证据包，至少含任务/运行身份、逐题用量、结果依据、汇总重算命令及哈希；不依赖本机 `.aster` 私有路径，也不公开未经检查的原始 Trace 和凭据。

再补一个小型判定器校准集：选五类任务，各给出正确实现、另一种等价正确实现、表面正确但边界错误、空交付。判定器必须既能拒绝取巧，也接受等价正确结果，不能只检查输出格式。

### 完成标准与面试讲法

交换两个 run 的评审文件必须被拒绝；待评分不能生成通过；重叠请求不能重复扣时间；MD/页面/JSON 的计数一致；脱离个人目录后仍能重算。

> 我发现“程序运行没报错”和“任务做对了”曾在展示层混在一起，所以把采集、程序检查、结果评审和报告发布分开，并让每个数字都能追到对应运行。

这是成果可信度改进，不应把“纠正评分误报”宣传成 Agent 能力提升。

## 5. P0-2：对齐当前契约，并让演示环境可靠

### 当前具体问题

[ARCHITECTURE.md](<D:/MIniClaw/ARCHITECTURE.md>) 仍描述 fresh verification、逐验收项登记及可新增角色工具等行为，与最新十工具及普通答案后置评审约定不一致。部分旧测试也依赖已删除的 checkpoint。

本地 Web 演示的 [默认参数](<D:/MIniClaw/frontend/local_agent_server.py:415>) 是 host＋allow；[POST 处理](<D:/MIniClaw/frontend/local_agent_server.py:331>) 没有看到 Origin/Host 校验、会话访问令牌和请求体上限。若直接把该入口作为安全演示，实际默认行为弱于简历里的隔离印象。

[静态架构资源定位](<D:/MIniClaw/src/MiniClaw/frontend.py:9>) 依赖源码仓库目录；[打包配置](<D:/MIniClaw/pyproject.toml:17>) 没有完整演示资源声明。editable 安装可用不能代表 wheel 安装到其他位置也可用。

### 最小改法

1. 建立一份简短的“当前能力契约”，README、架构图和活跃测试都据此更新。历史文档保留，但标明版本；旧测试改成验证“普通回答自动保存、待评、工具错误不被吞掉”，不恢复旧登记协议。
2. 增加开发依赖组与少量跨平台测试；文件读写显式指定 UTF-8。CI 分开运行基础离线、Docker 集成和可选检索测试，付费模型评测仍手动触发。
3. 新增无模型调用的 `doctor` 诊断入口，展示实际解释器、Docker/镜像、rg、工作区模式、检索 backend 与降级原因。只报告配置是否存在，不打印密钥。
4. 演示提供 Docker＋独立副本模式；没有 Web 审批 UI 时先对危险操作采用 deny，不以默认全放行绕过审批。host 模式需要显式选择。
5. Web 入口限定回环地址，检查 Host/Origin，使用启动时生成的访问令牌并限制请求体；先覆盖本地演示边界，不做账户系统。
6. 用干净环境验证正式安装后的命令入口。要么把静态资源按包资源发布，要么明确架构网页只在源码运行，避免承诺不一致。

### 完成标准与面试讲法

新环境能运行不调用 API 的演示；没有 BGE 模型时清楚显示降级；中文文件测试跨平台一致；旧协议不存在仍能通过当前契约测试；跨来源请求不能直接触发工具任务；用户原目录不因演示被修改。

> 我把开发环境里的隐含条件显式化，并让演示默认在隔离副本运行。这样别人看到的是可以复现的产品行为，而不是只在我电脑上成立的配置。

这项无需成为简历独立一条，但会直接减少面试现场翻车。

## 6. P1-1：新增“任务交付包”模块——最推荐的新方向

### 它解决什么

用户提出修复需求后，应该能看到“修改了什么、针对哪个初始版本、做了哪些验证、还缺什么”。当前对话、工具和报告都存在，但还缺一个统一的任务交付边界。

这不是再加一个规划器。它是在已有 Agent 外面增加三步产品流程：

```text
准备独立任务副本和起始基线
    → 运行现有 CodingAssistant
    → 固定最终产物版本
    → 在验证副本执行预先约定的检查
    → 导出补丁、差异、验证记录与最终回答
```

### 模块边界与最小接口

可新建内部 `coding_agent/task_delivery/`，只有三个核心操作：

| 内部操作 | 输入与职责 | 必须避免的行为 |
|---|---|---|
| prepare | 源工作区 → 独立副本、起始文件清单及 hash | 不能把用户原有未提交修改归到 Agent 名下 |
| verify | 已停止执行的任务副本＋预先约定的测试命令 → 原始验证记录 | 不能让模型一句“通过”替代执行；测试通过也不等于独立结果评分通过 |
| export | 同一版本的差异、验证记录与答案 → 可打开的交付目录 | 不能把旧代码测试结果挂到新补丁上 |

复用 [Runtime Snapshot](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/snapshot.py:42>)。参考 [capture_patch](<D:/MIniClaw/src/MiniClaw/benchmark/code_compression.py:231>) 的已有能力，但先拆出安全的差异生成部分：当前 benchmark 实现会操作暂存区并处理 index.lock，不能直接对用户原目录调用。

起始基线以本次任务副本为准；原 `.git` 不作为可修改任务内容复制，必要时在任务副本建立内部差异基线。最终导出 `changes.patch`、`summary.md`、原始验证日志和用量/Trace 引用。运行身份与 hash 是内部元数据，模型仍使用原十个工具和普通最终回答。

### 一个值得录屏的 Demo

准备有一处用户未提交修改的示例仓库，让 Agent 修一个边界 bug。展示：原目录未改变，任务副本中的代码得到修复，独立检查记录了被验证版本，补丁只包含 Agent 本次新增改动，补丁能在另一份起始副本中通过 `git apply --check`。

### 首版停止边界

只支持单仓库、有限大小的文本改动、一个任务一个副本、手动选定的测试命令。先导出与预览，**不做自动应用、合并、PR 发布、多 Agent 协调或依赖安装平台**。结果待评时照样能导出，但必须显示待评，不能标成验收完成。

### 完成标准与面试讲法

用户已有改动不被覆盖；新增/修改/删除都在差异中；被验证代码发生变化时旧验证记录失效；验证失败仍能查看日志和补丁；导出产物可在第二份基线副本检查。

> 我把 Agent 的交付从一段聊天改成一个可审查的变更包。Agent 负责生成修改，运行器负责隔离、固定代码版本和保存独立检查证据，用户能看到修改范围以及剩余风险。

这是独立于新增 RAG 算法的一条产品价值主线，也最适合展示你的系统设计取舍。

## 7. P1-2：新增小型实验入口，回答“哪项机制真的有效”

### 当前依据

[历史分析](<D:/MIniClaw/docs/interview/问题.md:450>) 已承认收益来自组合改动，没有拆开的因果证据。检索组件虽然实现了，但 [BGE/CE 的配置默认值](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/retrieval.py:1879>) 并不意味着每次实跑均启用；CE 的 [单测替身](<D:/MIniClaw/tests/test_memory_retrieval.py:22>) 证明链路，不证明真实模型效果。

### 最小模块与第一项实验

增加一个内部实验入口：读取固定任务清单、实验组配置和预算，调用已有 Eval，输出成对对照。无需实验管理平台或新 Web 面板。

第一次仅做三组：当前完整方案、关闭读快照复用、关闭累计工具历史预算。三组保持相同简化工具协议，不恢复旧验收负担。先选 6–10 道有代表性的已曝光回归题，每组重复 3 次用于观察稳定性；任务及重复数在运行前固定，不能看到结果后挑样本。

记录每个机制是否实际触发。没有发生压缩或读复用的任务不能用于证明该机制的收益。比较结果、四维程序状态、总 token、未缓存输入、辅助模型开销、有效耗时和费用；保留失败运行。交换/交错实验组顺序，并记录缓存状态，避免所有后跑组天然受益。

### 检索实验单独做

如要继续保留简历里的混合检索重点，再准备 30–60 条有相关证据 ID 的查询：代码符号、语义改写、同名不同项目、撤销事实和干扰证据。

依次比较关键词＋精确匹配、加 BGE、再加 CE，保持候选范围和注入预算一致，报告 Recall@k、首个正确结果排名、最终注入证据覆盖、作用域错误和冷热延迟。实际 backend、fallback、CE applied 都要记录。

注意 [retrieval.py](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/retrieval.py:1440>) 的向量调用路径：把权重设零不一定停止向量计算，实验开关必须真正改变执行路径。小样本只能说明局部取舍，不宣称广泛泛化或统计显著。

### 完成标准与面试讲法

即使实验结论是“CE 没带来净收益”，也应保留结果并考虑默认关闭。停止标准是能够回答一种机制的收益、代价和不适用情况，而不是所有开关组合全部跑一遍。

> 我先观察到总体成本下降，但没有直接归因给某个算法。随后用同任务、同预算的成对实验拆掉单项机制，测它额外解决了什么、付出了多少成本，再决定默认配置。

“测出一个复杂组件不值得默认开启并简化系统”同样是有价值的工程成果。

## 8. P1-3：完整模型请求的发送前预算检查

### 当前缺口

已有 [历史投影](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/working.py:240>)、[工具历史预算](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/history_budget.py:19>) 与 [回合结束后的压缩](<D:/MIniClaw/src/MiniClaw/coding_agent/assistant/coding.py:745>)。缺的是**最终 system＋tools＋history＋retrieval 的总窗口检查**，不是完全没有预算机制。

投影后仍会组装 system 与工具定义，[AgentLoop](<D:/MIniClaw/src/MiniClaw/agent/loop.py:124>) 随后直接发送。上一请求的 usage 不包含刚追加的新鲜工具结果或下一轮大段用户输入；fresh 保护也不能当成总窗口硬上限。

### 最小改法

在完整 ModelRequest 组装后检查一次总预算；超过安全边界时调用已有压缩流程并重新投影，仍超限则明确暂停，保留原文。不能反复压缩到预算耗尽，也不能静默删除最新授权或拆开工具调用与结果。

统一中文与英文的估算口径，结合上一请求实际 usage 和新增内容估算，保留输出及误差余量。估算不等于供应商精确 token 数，不承诺任意 tokenizer 下绝对不会超限。

将能力作为可注入的请求边界回调，保持 llm/agent 不直接依赖具体 memory 实现；不新增模型工具。

### 验收与讲法

覆盖中文大输入、小窗口配置、一批新鲜 read、超大工具参数、压缩后再追加输入。检查过大请求不会直接发送、原始记录不变、正常小请求不增加压缩和模型请求。

> 原来根据上一轮 usage 决定压缩，存在一轮滞后。我在最终请求发送前补了总预算检查，复用已有压缩机制处理可归档内容；无法安全压缩的输入则明确保留并暂停。

这是 1–2 天能做出较完整因果链的小改动，适合先练手，再做复杂恢复。

## 9. P1-4：执行日志与崩溃恢复，聚焦一个真实窗口

### 已有能力与新增价值

已有 [中断检测](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/state.py:101>)、[孤立工具调用补位](<D:/MIniClaw/src/MiniClaw/coding_agent/assistant/coding.py:254>)、暂停后恢复和同进程网络重试。

仍存在“工具已经执行，但结果/会话还没保存”的窗口：[loop.py](<D:/MIniClaw/src/MiniClaw/agent/loop.py:214>) 先执行工具，再产生完成事件；[coding.py](<D:/MIniClaw/src/MiniClaw/coding_agent/assistant/coding.py:684>) 更新完成状态与追加会话也不是一次提交。`pending_request` 仅在内存，同进程断网恢复不能直接等同进程重启恢复。

### 最小改法

内部为每次工具调用保存执行记录，状态限定为：准备、执行中、结果已保存、结果未知。记录调用 ID、参数摘要、结果路径；结果保存后才标记完成，会话落盘缺失可从执行记录补齐。

恢复按三类处理：

| 状态 | 恢复动作 |
|---|---|
| 等待模型，前序工具结果完整 | 恢复同一请求边界，保留已发生用量和剩余预算 |
| write/edit 结果未知 | 用执行前与预期执行后文件 hash 核对，不直接重复写 |
| 任意 Bash 副作用未知 | 标记未知，让 Agent 用现有工具核实，框架不自动重放 |

请求快照属于受保护的内部会话数据，不含 API 凭据，也不进入公开证据包。已脱敏或被截断的展示 Trace 不能冒充完整可恢复请求。

顺便修复 [会话读取](<D:/MIniClaw/src/MiniClaw/coding_agent/assistant/session.py:25>) 静默跳过任意损坏行的问题：尾部半行可恢复并记录，中间坏行必须显式报告，防止恢复时悄悄丢掉撤销要求或工具结果。

### 验收、边界与讲法

用独立测试子进程在“意图落盘后”“文件替换后、结果保存前”“结果保存后、会话追加前”退出，再重启。检查实际写入次数、消息配对、已确认结果复用、未知副作用不自动重做、预算不断档。

第一版仅承诺进程崩溃语义；不承诺断电事务、任意 Bash exactly-once 或跨机器调度。不引入 Redis、消息队列或工作流引擎，也不向模型增加 checkpoint 工具。

> 我把重试模型请求和重放工具动作区分开。执行可能已经发生而记录尚未保存，所以恢复时要先区分已完成、未执行和结果未知，不能简单把失败步骤再跑一遍。

这比“增加重试次数”有明显的工程深度，也更容易用现场故障演示证明。

## 10. P1-5：取消要有证据，输出要有上限

当前已经有取消令牌、Host 进程树终止、Docker 回收和原子写。改进应针对以下明确缺口：

- [Docker 清理](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/execution.py:278>) 未检查删除命令返回码，但 [取消路径](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/execution.py:181>) 会写 `container_removed=True`。
- [Bash 工具](<D:/MIniClaw/src/MiniClaw/coding_agent/tools/bash.py:76>) 的执行后快照只在正常返回路径完成，超时/取消可能缺少已发生修改的记录。
- [Host 输出](<D:/MIniClaw/src/MiniClaw/coding_agent/runtime/execution.py:97>) 使用 communicate 全量收集；Docker 已有尾部上限。两者的内存与截断语义不一致。

最小改法：清理返回 removed/still_running/unknown；只有确认删除或已不存在才记成功。进程停止后做有界现场快照；无法确认停止时明确未知。Host/Docker 共用持续排空、有限保留的流读取，分别记录接收字节、保留字节和丢失情况；被截断日志不能标为“完整输出”。

验收用本任务专用测试容器/子进程，模拟删除失败、daemon 不可达、先写文件再阻塞、stdout/stderr 同时超限。检查后续写入是否停止、现场是否保留、内存是否有界，不能只断言清理函数被调用。

> 我没有把发出 kill 当作取消成功，而是分别核对进程停止、容器回收和已经发生的文件变化；同时限制输出采集，避免工具日志先把运行器内存占满。

如果时间有限，可以只做清理真实性与失败现场，输出统一作为下一次独立改动。

## 11. P2-1：新增代码证据新鲜度模块

这是允许新增模块后，我最推荐的记忆方向。它解决的是“相关但过期”，而不仅是“能否检索到”。

已有 [read 缓存](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/read_cache.py:64>) 会核对文件 hash，但保护的是会话内工具结果复用；[长期事实蒸馏](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/distillation.py:294>) 的对话证据没有完整关联当前代码版本。

首版只覆盖能明确追溯到 read 结果的仓库事实。由运行器自动记录来源仓库、文件路径和内容 hash；召回候选进入上下文前核对。代码变化、文件删除或无法读取时，将依据标为“待复核”，保留历史并引导重读，不当作当前事实。

复用现有 scope/status/expiry。用户偏好不随代码变化失效，无法定位来源的推断不冒充已验证事实。注意 [manager.py](<D:/MIniClaw/src/MiniClaw/coding_agent/memory/manager.py:473>) 的 evidence 缺失默认状态，不能只更新一张状态表却让另一条检索路径继续注入旧事实。

先按整文件 hash 判断，候选文件少量核对即可；无关改动会触发额外复核，这是首版可接受的代价。**失效表示依据需更新，不等于事实已经证明错误。** 不急着做 AST 依赖图、知识图谱或自动事实真值推理。

Demo：第一天记住接口返回整数错误码；第二天代码改为字符串，新会话询问接口。系统发现来源变化，重读代码后回答，仍保留用户偏好。验收包括跨项目同路径、分支切换、删除、无关文件变化与用户偏好不受影响，统计旧事实误用与额外读取成本。

> 我发现长期记忆即使检索相关，也可能引用过期代码，所以把仓库事实和来源版本关联。系统先判断证据是否仍有效，再决定是否将它作为当前依据。

只有在基础记忆消融表明它有价值后，再把这项发展为简历主线。

## 12. P2-2：飞书可靠消息处理，按岗位选择

已有持久去重和 outbox，不应重复写成“从零增加幂等”。但 [inbox](<D:/MIniClaw/src/MiniClaw/platforms/feishu/dedupe.py:39>) 主要保存事件 ID/状态，[排队](<D:/MIniClaw/src/MiniClaw/platforms/feishu/router.py:167>) 在内存，重启不能仅靠这些记录重建待执行消息；长任务 processing 到期后的再次 claim 也需要明确所有权。

[DeliveryManager](<D:/MIniClaw/src/MiniClaw/platforms/delivery.py:74>) 存在发送已成功、delivered 尚未落盘的窗口，当前锁主要保护同一实例内并发。这里的本地幂等键不自动变成远端 exactly-once。

首版可以明确只支持单进程：待处理消息正文与身份落盘，消费前后更新状态；活跃任务续期或以进程存活识别中断；重启只恢复确实尚未开始的消息。投递复用稳定远端去重键（若接口支持），同本地键不同 payload 必须冲突；远端不支持去重时保留未知投递状态，不宣称绝无重复。

验收：入队后重启、任务执行中重启、处理超过 stale 时间、同键不同正文、远端成功但本地未记成功。无需 Kafka、多消费者集群或分布式调度。

如果你主要投 Agent 算法/应用工程，这项排在任务交付与实验之后；如果偏后端/平台工程，它可以替代一部分检索深挖。

## 13. 哪些方向现在不值得优先做

| 方向 | 当前不优先的理由 | 何时再考虑 |
|---|---|---|
| 多 Agent、Planner/Executor/Critic 全套 | 增加调用成本、共享状态和归因难度 | 有固定任务证明单 Agent 因可并行独立子任务而受限 |
| 再叠图数据库、更多 embedding、更多 reranker | 现有检索组件仍缺充分消融 | 当前检索错误已明确不是作用域、陈旧证据或预算问题 |
| Redis/Kafka/微服务/Kubernetes | 单用户本地 Agent 很难证明收益 | 有真实并发、跨机器或长期服务要求 |
| 重写 llm/agent 分层、迁移大型框架 | 现有分层已有测试约束，全面迁移会冲淡独立实现价值 | 已有可复现瓶颈无法在当前边界处理 |
| 再造模型验收字段协议 | 重新引入已明确移除的模型负担 | 不作为本项目当前路线；内部元数据与后置评审足够 |
| 先堆大规模题量或只挑高分展示 | 不能修复判定器、曝光、版本混用和可重复性问题 | 报告与判定可靠、小规模实验已建立后再扩充 |
| 先全面整理巨型类和所有历史脚本 | 改动面大却难对应用户收益 | 先确定唯一现行入口，围绕一次具体行为改造提取边界 |

允许大改不等于值得全改。真正能体现思考的是解释“为什么现在只做到这个范围”。

## 15. 执行顺序与学习验收

### 第一阶段：可信基线，约1–2天

校正文档/简历口径，确定现行测试契约和统一报告入口。列出历史数字的证据缺口。修复最影响复现的编码/依赖问题。记录当前状态，不删历史失败。

### 第二阶段：新增可见价值，约4–6天

只实现单仓库文本任务交付包。从准备副本、记录基线、导出差异开始，再接独立验证日志。先 CLI 和 Markdown，最后复用现有前端做预览。完成一个三分钟可录屏演示。

### 第三阶段：做一次能解释的实验，约2–4天＋运行

选择一个已有机制或发送前预算改动，准备固定任务和开关，保留全部实验。交付一页结论：什么情况下有收益、代价是什么、什么情况下不值得启用。

### 第四阶段：选一个深入方向

可靠性方向选执行日志/取消；记忆方向选真实检索消融/代码证据新鲜度；后端方向选飞书队列与投递恢复。不要同时展开三条线。

每项做完，用下面六个问题检查自己是否真的搞懂：

1. 原来哪个具体输入或故障时点会出问题？能现场复现吗？
2. 修改前后最重要的不变量是什么？
3. 为什么用这个小方案，而没有引入更大框架？
4. 哪个测试能证明修复有效，哪个反例能证明没偷偷降低要求？
5. 多花了多少时间、token、存储或代码复杂度？
6. 什么情况仍不保证？面试时能主动说出边界吗？

每项留下半页设计记录即可：问题、两个备选方案、最终选择、代价、验证。你的独立思考应体现在这些取舍和真实负结果里，而不只是模块数量。
