# MiniClaw Eval 完整说明

> 本文以当前仓库中的真实实现、`evals/*.json` 和 2026-09-05 的正式运行报告为准。它既解释“现在有什么”，也明确“哪些还没有做到”。

## 0. 先说结论

MiniClaw 当前已经形成一套真正的端到端 Agent Eval，而不是只把问题发给模型、再判断最后一句回答是否正确。

它会创建独立工作区，启动真实 `CodingAssistant`，让请求依次经过项目指令、记忆召回、AgentLoop、模型流式请求、工具执行、审批、WorkspaceGuard 或 Docker、Goal 监督、上下文压缩与 Trace，然后同时检查：

1. **Outcome**：最终结果是否正确。
2. **Process**：执行过程是否符合要求。
3. **Efficiency**：Token、成本、请求数和延迟是否超预算。
4. **Safety**：是否越界、泄密或产生不允许的副作用。
5. **Reliability**：重试、降级、取消和重启后是否仍然正确。

当前完整 Suite 包含 22 个 Case：

```text
full.json
├─ smoke.json       4 个：核心链路冒烟验收
├─ regression.json 10 个：真实 Benchmark 失败回归
└─ resilience.json  8 个：压缩、故障、审批、取消和恢复
```

正式四路并行结果：

| 指标 | 当前结果 |
|---|---:|
| Case | 22 / 22 通过 |
| Attempt | 23 / 23 通过 |
| Outcome | 100% |
| Process | 89.47% |
| Efficiency | 100% |
| Safety | 100% |
| Reliability | 100% |
| Agent 与后台请求 Token | 136,452 |
| Judge Token | 172 |
| 报告中的总成本 | $0.01811326 |
| 四路并行墙钟时间 | 133.894 秒 |

这里必须正确理解：

- **22/22 表示已声明的工程机制全部通过回归验收。**
- **它不表示 MiniClaw 面对任意 Coding 任务都有 100% 成功率。**
- Regression Case 中有一部分来自开发过程中已经见过的失败，因此它们适合防止复发，不适合作为完全独立的泛化测试集。

## 1. Test、Benchmark、Eval 和 Trace 到底有什么区别

这四个概念经常被混在一起，但它们解决的问题不同。

### 1.1 单元测试 Test

单元测试验证某个确定性代码模块是否按预期工作，例如：

- Eval JSON 能否正确解析。
- 路径检查能否阻止 `../`。
- Trace 条件匹配是否支持 `where_in`。
- Token 预算是否能正确判定超限。
- Suite include 是否会检测循环引用。

它通常不需要真实模型，也不评价 Agent 是否聪明。

### 1.2 Benchmark

Benchmark 是一批统一数据和统一评分协议，主要用于比较能力，例如：

- MemoryAgentBench：长期记忆、多跳事实和冲突处理。
- LongMemEval：长历史问答、偏好、时间和更新。
- LongMemEval-V2：包含更复杂的状态、轨迹和程序性信息。
- PointFiveLabs AI Efficiency Benchmark：长工具输出、上下文效率和证据综合。
- RepoGuardBench：Coding Agent 中的恶意上下文与危险工具行为。

Benchmark 更像“统一考试”，适合比较模型或方案；但它未必真正进入 MiniClaw 的全部执行链路。

### 1.3 Eval

Eval 是 MiniClaw 自己的工程验收系统。它关心的不只是答案，还关心：

- 是否真的修改了正确文件。
- 是否运行了真实验证命令。
- 是否触发了 Goal、Memory、Compaction。
- Bash 是否真的进入 Docker。
- 越界写入是否真的没有落到磁盘。
- 取消后子进程是否还在后台继续产生副作用。
- 429、断网、Provider 失败后是否按照设计恢复。

因此 Benchmark 的失败可以成为 Eval Case 的来源，但二者不是同一个东西。

### 1.4 Trace

Trace 是运行时留下的统一事实记录，例如：

```text
run.started
instructions.injected
memory.retrieval
model.request
model.transport
tool.call
approval.requested
approval.decision
goal.snapshot
compaction.started
compaction.completed
run.cancelled
run.completed
```

Eval 使用 Trace 判断过程；Trace 分析器也能把真实失败会话提取成候选 Eval Case。

一句话总结：

```text
Test       检查某段代码
Benchmark  比较通用能力
Eval       验收 MiniClaw 完整系统
Trace      提供 Eval 所需的过程证据
```

## 2. 当前 Eval 的整体组成

当前 Eval 可以拆成七个部分。

```text
Case / Suite 定义
       ↓
Fixture 初始工作区
       ↓
Eval Driver 与故障控制
       ↓
真实 CodingAssistant 执行
       ↓
Trace + Workspace 前后快照
       ↓
确定性检查 / LLM Judge / Budget
       ↓
聚合报告 + Baseline 回归告警
```

### 2.1 Suite：决定跑哪些题

Suite 使用 JSON 声明，包括：

- Suite 名称和版本。
- 要包含的其他 Suite。
- 全局环境变量。
- Case 列表。
- 必须覆盖的维度。
- 必须覆盖的能力标签。

相关文件：

```text
evals/smoke.json
evals/regression.json
evals/resilience.json
evals/full.json
```

`full.json` 不重复复制 22 个 Case，而是通过 `includes` 组合三个子 Suite。加载器会：

- 阻止 include 循环。
- 检查 Case ID 重复。
- 继承子 Suite 环境配置。
- 校验未知 Check、Budget 和 Phase Control。

### 2.2 Case：一项可执行验收任务

每个 Case 至少包含：

- `id`：稳定标识。
- `category`：类别。
- `prompt` 或 `phases`：发给 Agent 的请求。
- `checks`：完成后如何判断。

还可以包含：

- `fixture`：初始工作区模板。
- `goal`：要创建的持久化 Goal。
- `environment`：该 Case 独有的运行配置。
- `budgets`：Token、请求、工具、延迟等预算。
- `source`：来自哪个 Benchmark 或真实失败。
- `repetitions` 和 `min_pass_rate`：重复运行要求。
- `capabilities`：该题覆盖的能力。
- `session_mode`：多阶段是否共用 Session。

### 2.3 Fixture：给 Agent 一个真实可操作环境

Fixture 是 Case 的初始目录，例如：

```text
evals/fixtures/fix-add/
├─ calculator.py
└─ test_calculator.py
```

运行每次 Attempt 时，Runner 会复制一份 Fixture，而不是直接在原 Fixture 上执行。因此：

- 不同 Case 不共享修改。
- 同一 Case 的多次 Attempt 不共享修改。
- 并行运行不会互相覆盖文件。
- 失败现场可以保留在输出目录中复查。

### 2.4 Driver：控制环境和故障

Driver 负责把正常任务变成可重复的系统实验，当前支持：

- 指定是否恢复持久化 Goal。
- 在固定时间取消。
- 某个 Tool 开始后取消。
- 注入 HTTP 429 或 5xx。
- 注入网络断开。
- 设置 Retry-After。
- 在故障后返回可控的 Mock SSE 成功响应。
- 模拟审批通过、拒绝或超时。

这些控制来自 Eval 配置，而不是写进产品 Prompt。因此修复测试时不需要对某道题添加特殊提示词。

### 2.5 真实执行体：CodingAssistant

每个 Phase 都会创建真实 `CodingAssistant`，实际经过：

```text
用户 Prompt
  ↓
项目指令加载
  ↓
Working / Long-term Memory 检索
  ↓
AgentLoop 与 SSE 模型请求
  ↓
ToolExecutor
  ↓
参数校验与 ApprovalGate
  ↓
文件工具 → WorkspaceGuard
Bash     → Host 或 Docker Runtime
  ↓
Goal Supervisor
  ↓
Memory Consolidation / Compaction
  ↓
Trace
```

这也是当前 Eval 和“让另一个模型判断操作是否安全”最大的区别：MiniClaw 的安全组件会被真实执行。

### 2.6 Oracle：如何判断对错

当前采用“确定性规则优先，LLM Judge 兜底”的策略。

确定性判断适合：

- 文件内容。
- 文件是否被创建或删除。
- 验证命令退出码。
- 最终答案中的关键字段。
- Trace 事件和顺序。
- 工作区副作用。
- Token、成本和延迟。

LLM Judge 只适合无法稳定写成规则的开放答案，例如推荐是否真正符合用户偏好。

### 2.7 Report 与 Baseline

每次运行生成：

```text
output/
├─ summary.json
├─ report.json
├─ report.md
└─ cases/<case-id>/
   ├─ result.json
   └─ attempt-001/
      └─ workspace/
         └─ .aster/eval-sessions/.../trace.jsonl
```

- `summary.json`：适合机器读取和 Baseline 对比。
- `report.json`：包含每个 Case、Attempt、Check 和指标的完整数据。
- `report.md`：适合人阅读。
- Attempt 工作区：保留可复查的最终文件和 Trace。

## 3. 一条 Case 是怎么运行的

以 `coding_fix_add` 为例。

### 第一步：复制工作区

Runner 把 `evals/fixtures/fix-add` 复制到：

```text
.aster/evals/<run>/cases/coding_fix_add/attempt-001/workspace
```

### 第二步：记录运行前快照

遍历工作区内的普通文件并计算 SHA-256，得到修改前状态。

`.aster/**` 不计入用户文件副作用，因为那里保存的是 MiniClaw 自己的 Session、Goal、Trace、Memory 和 Artifact。

### 第三步：合并环境

优先级为：

```text
命令行/.env 基础环境
  ↓
Suite environment
  ↓
Case environment
```

Case 配置会覆盖 Suite 配置。

### 第四步：创建真实 Agent

创建模型客户端、Runtime、Approval 配置和 `CodingAssistant`。如果 Case 声明 Goal，就先写入 Goal Store。

### 第五步：运行一个或多个 Phase

单阶段 Case 直接运行 `main`。

多阶段 Case 可以模拟：

- 先保存、后召回。
- 先产生大量工具结果、后提出问题。
- 先暂停 Goal、重建 Assistant、再恢复。

`session_mode=isolated` 时，每个 Phase 有独立对话 Session，但仍使用同一个 Case 工作区和相同 Memory Scope。

`session_mode=shared` 时，多个 Phase 共用同一个 Session，适合验证上下文压缩和 Goal 持久化恢复。

### 第六步：收集 Trace

Runner 只读取属于本 Phase 实际 Run ID 的 Trace，避免同一个 Session 中旧事件污染当前结果。

### 第七步：记录运行后快照

重新计算文件 SHA-256，得到：

```text
created
modified
deleted
```

### 第八步：执行 Checks

例如：

- `calculator.py` 是否包含 `return left + right`。
- 重新运行 `python -m unittest -q` 是否退出码为 0。
- 是否只修改了 `calculator.py`。
- Goal 是否为 `complete`。
- 最终验证 Bash 是否标记 `goal_verification=true`。

### 第九步：执行预算检查

预算也会被转换为必需的 Efficiency Check。超过预算就算失败，而不是只在报告中显示数字。

### 第十步：聚合 Attempt 和 Case

如果 Case 重复 N 次：

- 计算实际通过率。
- 与 `min_pass_rate` 比较。
- 输出 `pass_at_k`、`pass_all` 和 `stable`。

当前实现中的 `pass_at_k` 表示“这 N 次中至少成功一次”，不是学术 Benchmark 中带采样组合公式的无偏 pass@k 估计量。

## 4. 五个维度为什么要拆开

### 4.1 Outcome：最后是否真的做对

如果只看模型最后一句话，会出现：

```text
模型说“已经修复”
但文件没改
或测试没跑
或测试仍失败
```

所以 Outcome 优先检查真实状态：文件、命令、Goal 和结构化结果。

当前正式 Suite 中 17 个 Case 配置了 Outcome Check，得分 100%。

### 4.2 Process：是否按正确链路完成

同样的最终结果可能由不安全或不可泛化的过程得到。例如：

- 猜出了答案但没读取证据。
- 修改成功但没执行最终验证。
- 返回正确结果但 Bash 没进 Docker。
- 回答了记忆问题但没有发生 Memory Retrieval。

Process 使用 Trace 判断发生了什么以及先后顺序。

当前 Process 为 89.47%，不是出现了必需过程失败，而是两个非必需诊断检查未命中：

- Procedural Case 没有显式调用可选 `skill`。
- 某个安全 Case 没出现可选的审批过程事件。

可选 Check 会影响维度观察分，但不会让 Case 失败。

### 4.3 Efficiency：正确之外是否可承受

Agent 可能通过疯狂重试、反复读文件和消耗几十万 Token 得到正确答案。只看正确率无法发现这种退化。

当前支持：

- 输入、输出、缓存、总 Token。
- 总成本。
- Agent 请求和后台辅助请求分账。
- Memory、Compaction Token 分账。
- 模型请求、错误、重试、Fallback。
- Tool Call、错误、取消、阻止。
- TTFT 和完整模型延迟。
- Tool 延迟。
- 墙钟时间。
- Compaction 节省 Token。
- L1/L2/Archive/L3 数量。

### 4.4 Safety：有没有产生错误副作用

安全不能只检查模型“是否同意危险请求”，因为真正重要的是危险操作有没有发生。

当前同时检查：

- Approval 决策。
- WorkspaceGuard 拒绝。
- Docker 配置。
- 敏感内容是否出现在回答中。
- 工作区前后是否出现不允许的文件变化。
- 取消后是否仍创建延迟文件。

### 4.5 Reliability：遇到故障是否还能成立

可靠性关心的不是一次成功，而是：

- 同样的 Case 重复运行是否稳定。
- 429 是否正确重试。
- 网络断开是否恢复。
- 主模型失败是否进入 Fallback。
- 用户取消是否贯穿到进程。
- Assistant 重建后 Goal 是否恢复。

## 5. 当前支持的 Check 类型

### 5.1 文件和目录

| Check | 含义 |
|---|---|
| `file_exists` | 工作区中必须存在文件 |
| `file_absent` | 工作区中不能存在文件或目录 |
| `directory_exists` | 必须存在目录 |
| `file_contains` | 文件必须包含文本 |
| `file_not_contains` | 文件不能包含文本 |
| `file_equals` | 文件必须与预期完全相等 |
| `file_regex` | 文件内容必须匹配正则 |
| `case_file_absent` | 检查 Attempt 根目录外的目标没有被越界创建 |

Eval 自己的文件检查也会做安全路径解析，不能使用 Check 路径逃出允许目录。

### 5.2 真实验证命令

`command` 使用参数数组、`shell=False` 执行，支持：

- 期望退出码。
- 输出包含指定字符串。
- 输出匹配正则。
- 独立命令超时。

这条命令是 Eval 的外部 Oracle，不是 Agent 自己声称“测试通过”。

### 5.3 最终回答

| Check | 含义 |
|---|---|
| `final_contains` | 不区分大小写包含 |
| `final_not_contains` | 不得包含敏感或错误内容 |
| `final_equals` | 去掉首尾空白后精确相等 |
| `final_normalized_equals` | 大小写折叠并归一化词元后相等 |
| `final_regex` | 正则匹配 |
| `final_json` | 提取 JSON 并检查字段 |
| `llm_rubric` | 让 Judge 按 Rubric 返回分数 |

### 5.4 Goal

`goal_status` 可以针对特定 Phase 检查：

- `active`
- `waiting_for_user`
- `verifying`
- `complete`
- `failed`
- 以及项目状态机当前实际支持的状态

### 5.5 Trace

`trace_event` 支持：

- 指定事件类型。
- 字段精确匹配 `where`。
- 数值下限 `where_min`。
- 多个等价值 `where_in`。
- 最少、最多或精确出现次数。
- 限定某个 Phase。

`where_in` 的加入是一个典型判定器修复：读取证据时 `read` 和 `grep` 可能同样有效，不应该因为模型选择了等价工具而误判失败。

`trace_sequence` 检查事件顺序，例如：

```text
tool.call
  → compaction.started
  → compaction.completed
```

它不要求事件严格相邻，只要求按顺序存在。

### 5.6 Workspace Diff

`workspace_diff` 支持：

- `required_paths`：必须修改。
- `allowed_paths`：只能修改这些。
- `forbidden_paths`：绝不能修改。
- `max_changed_files`：修改文件数量上限。

路径模式使用 glob 匹配。

### 5.7 Metric

`metric` 可以直接对聚合指标设置：

- `min`
- `max`
- `equals`

例如必须发生至少一个 L1 Artifact、至少一次 Memory 注入或模型错误必须等于 0。

### 5.8 Required 与 Optional

```text
required=true
  失败 → Attempt 失败

required=false
  失败 → 只降低维度诊断分，不影响 Case 通过
```

这避免把“推荐做法”错误升级成“唯一正确过程”。

## 6. Budget 能限制什么

当前 Budget 覆盖：

### 模型与成本

- 总、输入、输出 Token 上限。
- 成本上限。
- 总模型请求数。
- Agent 主请求数。
- 后台辅助请求数。
- Agent、Memory、Compaction Token 分账。
- 模型错误、重试、Fallback 上限。

### 工具与 Goal

- Tool Call 总数。
- Tool Error、Cancelled、Blocked 数量。
- Goal 最大尝试次数。

### 延迟

- TTFT p95。
- 模型完整延迟 p95。
- Trace 记录的累计执行时间。
- Case 真实墙钟时间。

### 压缩与记忆最低要求

- 最少 Compaction 次数。
- 最少节省 Token。
- 最少 L1 大结果 Artifact。
- 最少 L2 旧工具 Artifact。
- 最少历史 Archive。
- 最少 L3 模型摘要。
- 最少 Memory 注入数量。
- 最少项目指令来源数量。

Budget 被统一记为 Efficiency 维度的必需 Check。

## 7. Case 为什么分成 Smoke、Regression、Resilience

三组题的职责不同。

### Smoke：系统最基本的主链路还能不能工作

特点：

- 数量少。
- 覆盖最核心的正向路径和一条安全负向路径。
- 适合改代码后快速验证。
- 题目由项目根据自身架构设计。

### Regression：以前失败过的问题有没有复发

特点：

- 主要来自真实 Benchmark 失败。
- 每题保留 `benchmark`、`case_id` 和失败签名。
- 把庞大 Benchmark 缩成小型、可重复、低成本 Fixture。
- 修复应针对判定器错误或整个错误分布，不能向 Prompt 写单题答案。

### Resilience：系统在异常情况下是否仍满足不变量

特点：

- 由项目根据工程边界主动设计。
- 使用故障注入。
- 大量检查 Trace 和副作用，而非语言能力。
- 适合验证状态机、取消、重试和资源回收。

选择这三组，是为了同时覆盖：

```text
正常路径 + 历史失败 + 系统故障
```

只用 Smoke 容易“看起来都能跑”；只用 Benchmark 无法证明 Runtime；只用故障注入又无法证明 Agent 能完成真实任务。

## 8. Smoke Suite：4 个 Case 逐题说明

### 8.1 `coding_fix_add`

**来源**：MiniClaw 自建核心链路 Case。

**任务**：修复 `calculator.add`，运行真实单元测试，并通过 Goal 完成验收。

**真正执行的能力**：

- 读取和编辑代码。
- Bash 在 Docker 中运行。

### 8.2 `project_instructions`

**来源**：自建项目指令 Case。

**判定**：

**为什么选择**：Coding Agent 如果不遵守仓库指令，即使代码能运行也可能不符合项目规范。该题验证“指令确实注入”，不是只验证模型碰巧猜中内容。

**为什么选择**：安全验收必须检查磁盘状态，不能只相信模型说“被拒绝了”。

## 10. Resilience Suite：8 个 Case 逐题说明

### 10.1 `progressive_compaction_all_layers`

**来源**：根据 MiniClaw 自身三层压缩结构设计。

**环境**：把生产环境的 80k/100k 阈值按比例缩小到 3k/4k，以低成本触发同一套逻辑。

为什么没有把几百道 Benchmark 全塞进 `full.json`：

- 完整 Benchmark 运行成本和时间更高。
- 外部 Benchmark 更适合阶段性能力测量，不适合每次代码提交都跑。
- Eval 的职责是稳定回归关键机制和历史失败。
- 一个外部失败只有被缩成可复现 Fixture、加入确定性检查后，才能可靠进入日常回归。

因此合理分工是：

```text
外部 Benchmark：发现新的能力分布问题
         ↓
统一 Trace：保留失败过程
         ↓
失败聚类：确认是判定器、分布问题还是单题偶然
         ↓
代表失败 → 小型端到端 Regression Case
         ↓
完整 Eval：以后每次防止复发
```

## 12. Trace → Eval 到底是怎样的闭环

### 12.1 Trace 记录真实运行

每个 Run 写入统一 `trace.jsonl`，模型、工具、审批、Goal、Memory 和 Compaction 使用同一 Run/Trace 标识。

### 12.2 失败签名

分析器按优先级生成稳定签名：

```text
benchmark:<family>:<reason>
model:<error-code>
tool:<tool-name>:<error-code>
goal:<failure>
run:<stop-reason>
```

作用是把相同类型失败聚到一起，而不是看到一百条散乱日志。

### 12.3 从失败生成候选 Case

`create_eval_case` 会从失败 Run 提取：

- 原始 Prompt。
- Benchmark 名称和 Case ID。
- 失败签名与摘要。
- Goal。
- Provider、Model、System Prompt Hash、Tool Config Hash。
- 可重放的模型请求边界。
- 原 Benchmark Judge 信息。

### 12.4 Boundary Replay

Trace Replay 可以离线替换：

- 模型。
- Provider/Base URL。
- System Prompt。
- Tool 配置。

然后重新执行当时的模型边界，比较：

- 文本输出。
- Tool Call 名称和参数。
- Token、成本和延迟。
- Judge 结果。

但是 Boundary Replay 不真正执行工具，所以它只能判断“模型在相同上下文下会怎样决策”。

### 12.5 升级为端到端 Regression

一个自动生成的 Trace Case 不能直接等同于完整端到端 Eval。还需要人工或半自动补充：

- 可复制 Fixture。
- 最终文件或命令 Oracle。
- Workspace Diff。
- 必要 Trace 约束。
- 合理预算。

这样才能从“模型边界重放”升级成“真实 CodingAssistant 回归”。

### 12.6 修复原则

当前项目应继续遵守：

1. 先确认是否是 Judge 或判定器误杀。
2. 再确认是否是一个有代表性的分布错误。
3. 只修通用执行、检索、提示结构或 Runtime 规则。
4. 不把某题答案写进产品 Prompt。
5. 修复后重跑原失败和相邻分布。
6. 将代表性失败固化为 Regression Case。

这才是真正的 Trace→Eval，而不是“跑 Benchmark，人工看一眼错误”。

## 13. 并行、重复和隔离是怎么设计的

### 13.1 Case 级并行

`--jobs N` 使用异步信号量控制并发，当前允许 1～16 路。

```text
Case A ─┐
Case B ─┼─ 并行，独立工作区
Case C ─┼─
Case D ─┘
```

正式运行使用四路并行，从串行总耗时显著降到 133.894 秒墙钟时间。

### 13.2 Phase 保持串行

同一 Case 的多个 Phase 必须按顺序执行，否则：

- 记忆还没写完就开始召回。
- Goal 还没暂停就开始恢复。
- 工具历史还没产生就开始压缩恢复。

### 13.3 Repetition 保持串行

同一 Case 的 Attempt 当前逐次执行，易于隔离和归因。命令行 `--repeat N` 可以覆盖 Case 自身配置，最大 20 次。

### 13.4 输出目录不可复用

如果目标输出目录非空，Runner 会直接拒绝，避免新结果覆盖旧报告或混入旧 Trace。

```text
四路并发墙钟时间  133.894 s
```

Suite 墙钟时间是用户实际等待时间，不等于所有 Case duration 相加。

### 14.4 Tool Error 为什么不是系统失败

本轮 Tool Error 为 4，但其中包含预期安全拒绝，例如：

- 越界 Write 被拒绝。
- 读取 `.env` 被拒绝。
- 审批超时后的 Write 被拒绝。

因此不能直接把所有 Tool Error 都理解成坏事。当前全局 `tool_error_rate=8.70%` 会混合：

```text
预期安全拒绝 + 真正执行故障
```

这是后续报告最值得优化的指标语义之一。

### 14.5 Compaction Success Rate 为什么是 66.67%

本轮发生三次 `compaction.started`：

- 两次完成。
- 一次 `aborted`。

当前公式直接用 `completed / started`，得到 66.67%。但 Abort 可能表示确定性阶段已经把上下文压到足够小，不需要继续摘要，不一定是失败。因此后续应拆为：

- completed
- no-op/aborted-by-design
- failed

## 16. Capability Matrix 是什么

`full.json` 声明必须覆盖的能力，例如：

```text
goal_supervision
goal_restart_resume
memory_write
memory_retrieval
progressive_compaction
approval_deny
workspace_guard
docker_execution
end_to_end_cancellation
model_retry
provider_fallback
workspace_side_effects
```

完整运行时：

- 少了要求维度 → Coverage 不完整。
- 少了要求 Capability 标签 → Coverage 不完整。
- 只选择单题调试时 → 显示缺口，但不强制完整覆盖。

这样可以防止删除安全题后剩余题仍然全部通过，却继续宣称“安全覆盖完整”。

当前限制是：Capability Coverage 主要依据 Case 的声明标签，而不是自动验证某个 Capability 一定绑定了足够强的 Check。理论上错误标签也能让 Coverage 看起来完整。后续应建立：

```text
capability
  → 要求至少一种 Check
  → 要求至少一种 Trace/Runtime 证据
```

例如 `docker_execution` 应要求出现真实 Docker Runtime Trace，而不能只靠 Case 自己写了该标签。

## 17. 为什么当前设计是合理的

### 17.1 结果与过程分离

避免两种极端：

- 只看答案，忽略危险过程。
- 只允许唯一过程，误杀同样正确的实现。

### 17.2 确定性检查优先

文件 Hash、退出码和 Trace 比 LLM Judge 更稳定、更便宜，也更容易复现。

### 17.3 LLM Judge 只做语义兜底

开放推荐无法仅靠关键词完全判断，因此保留 Judge，但不让所有题都依赖 Judge。

### 17.4 真实执行而不是 Label-only

安全题真正进入 ApprovalGate、WorkspaceGuard 和 Docker，因此结果是“副作用有没有发生”，而不是“另一个模型认为这条命令危不危险”。

### 17.5 故障注入发生在边界

429、断网、审批超时和取消从 Driver 注入，不污染产品 Prompt，也不要求真实服务恰好在测试时故障。

### 17.6 Fixture 小而可复现

把大 Benchmark 的代表失败缩成最小工作区，使日常回归更快、更便宜、更容易定位。

### 17.7 Suite 组合

Smoke、Regression 和 Resilience 可以独立运行，也能组合成 Full，适合不同开发阶段。

## 19. 当前报告中几个容易误解的地方

### “Coverage Complete”不等于测试穷尽

它表示 `full.json` 声明的维度和 Capability 都至少被 Case 覆盖，不代表现实世界所有边界都测过。

### “Stable Case 22/22”不等于都重复运行

只运行一次的 Case 会自然被标记为全成功或全失败，因此 `stable=true`。真正证明随机稳定性仍需多次 Attempt。

### “Safety 100%”不等于 Docker 绝对安全

它表示当前 9 个带 Safety Check 的 Case 全部通过。没有覆盖的内核漏洞、容器逃逸和宿主 Docker 配置不在结论范围内。

### “Tool Error Rate 8.7%”不等于工具质量差

其中包含预期拒绝，应先分类再解释。

### “Fallback 通过”不等于真实第二服务一定可用

当前验证了路由和 Trace 分支，成功响应使用了可控 Mock。

### “压缩恢复通过”不等于所有 100k 历史都能恢复

当前是机制级 Fixture，需要外部长上下文 Benchmark 测量泛化恢复率。

## 20. 如何新增一个高质量 Eval Case

### 第一步：先定义不变量

不要先写 Prompt，先写“无论模型怎样做，最终必须满足什么”。

例如：

```text
目标文件测试通过
只允许修改 src/parser.py
必须执行真实验证
禁止触碰 .env
总 Tool Call 不超过 12
```

### 第二步：选择最小 Fixture

Fixture 应足以复现该分布，但不要包含无关大型依赖。

### 第三步：确定性 Oracle 优先

优先顺序建议：

```text
文件/数据库最终状态
  > 真实验证命令
  > Trace 结构
  > 最终文本规则
  > LLM Judge
```

### 第四步：Process 只约束必要过程

不要因为自己习惯 `read` 就禁止模型使用 `grep`。只有安全、验证、Goal 或协议确实要求时，才把过程设为 Required。

### 第五步：配置预算

预算应基于多次正常运行的分布设置，而不是刚好卡住某次最好结果。

### 第六步：标记来源

至少记录：

- Benchmark/真实会话来源。
- Case ID。
- 原始失败签名。
- 数据版本或 Commit。

### 第七步：验证失败敏感性

一个好的 Eval 不仅要在正确代码上通过，还应人为破坏对应机制，确认它真的会失败。

例如关闭 WorkspaceGuard 后，逃逸 Case 应失败；关闭 Archive Retrieval 后，压缩恢复 Case 应失败。

## 22. 面试时应该怎样讲

### 30 秒版本

> 我给 Coding Agent 做了一套五维端到端 Eval，不只判断最终回答，还真实运行工具、审批、Docker、Goal、Memory 和 Compaction，并结合 Trace 与工作区前后快照检查过程、副作用、Token 成本和故障恢复。历史 Benchmark 失败会被聚类并固化成独立 Fixture 回归 Case，系统还能注入 429、断网、审批超时、运行中取消和 Assistant 重启，并通过 Baseline 对正确率、成本和 p95 延迟做回归告警。

### 面试官问“为什么不是只跑 Benchmark”

> Benchmark 能比较能力，但不一定经过我项目真实的 ApprovalGate、WorkspaceGuard、Docker 和 Goal Supervisor。我的 Eval 会执行完整 MiniClaw，因此既能测答案，也能测真实副作用和运行过程。外部 Benchmark 用来发现分布问题，内部 Eval 用来稳定防止复发。

### 面试官问“22/22 是否说明能力很强”

> 22/22 说明核心工程机制和历史失败回归全部通过，不代表开放世界 Coding 成功率是 100%。当前已冻结 80 个未曝光 LongMemEval-V2 Held-out 题验证记忆泛化；安全和 Coding 仍需新的未曝光数据，并且关键 Case 还需要多次重复证明随机稳定性。

### 面试官问“为什么 Process 只有 89.47%”

> Case 的 Required Process Check 全部通过，89.47% 包含了 Optional 诊断项，例如答案正确但没有显式调用 Skill。Optional Check 用来观察 Agent 行为，不会覆盖正确的 Outcome。后续报告会把必需通过率和可选诊断覆盖分开。

### 面试官问“Trace→Eval 是否自动优化 Prompt”

> 当前自动化的是记录、失败签名、聚类、生成候选 Case、重放和回归告警；是否修代码仍由人工分析。这样可以避免系统为了提高固定题分数自动把答案写进 Prompt。修复顺序是判定器、分布问题，绝不针对单个 Case 打补丁。
