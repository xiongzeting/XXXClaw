# MiniClaw 简历导向优化方向

目标：只做能形成代码、实验和演示证据的优化。每个方向都给出大方向、小方向、落地结果、量化指标和可以写进简历的句式。

## 总体排序

| 优先级 | 大方向 | 先做的小方向 | 简历价值 |
|---|---|---|---|
| P0 | Coding 交付闭环 | TaskSpec、隔离工作区、补丁导出、独立验证 | 最高，直接证明项目能解决真实开发任务 |
| P0 | 长任务可靠性 | Goal 状态机、崩溃恢复、取消、幂等重试 | 能讲清 Agent 为什么不会过早结束或重复执行 |
| P0 | 可信完成 | 代码指纹、验证证据、独立 grader、完成门禁 | 把“调用模型”提升到“可验收系统” |
| P1 | Tool Security Runtime | Shell 能力分级、审批令牌、路径/容器隔离、审计 | 适合 AI Infra、Agent 工程、安全方向岗位 |
| P1 | Trace 驱动 Eval | 统一事件、回放、失败聚类、固定回归、质量成本报告 | 让简历数字可复现、可解释 |
| P1 | 记忆与上下文优化 | 代码版本感知、检索消融、压缩策略选择、预算控制 | 适合作为差异化专项，但必须有收益数据 |
| P2 | 工程化与性能 | 代码库地图、受控并行、缓存、模型路由、发布体验 | 有余力再做，用于补充工程深度 |

## 大方向一：把 Agent 做成真正的 Coding 交付系统（P0）

目标演示：输入真实仓库任务，Agent 在隔离副本中修改代码，运行验证，输出可应用补丁和证据包。

### 1. 结构化任务协议

**小方向**：新增 TaskSpec，把自然语言任务解析为目标、约束、验收项、预算、基线 commit 和交付格式；支持 YAML/JSON 与 CLI 参数。

**产出**：`coding_agent/task/`、任务 schema、解析失败提示、任务版本号。

**量化指标**：任务字段解析成功率、验收项覆盖率、无效任务拒绝率、同一任务重放一致性。

**简历句式**：

> 设计结构化 TaskSpec 协议，将自然语言 Coding 需求转换为目标、约束、验收标准和资源预算，支持任务可重放与结果复核。

### 2. 隔离工作区与版本基线

**小方向**：默认每个任务创建 Snapshot 或 Git worktree；记录来源 commit、文件清单和内容 hash；支持任务取消、保留、清理和再次打开。

**产出**：`runtime/workspace.py`、WorkspaceSnapshot、任务目录生命周期管理。

**量化指标**：并发任务互相污染次数为 0；快照创建耗时；补丁可应用率；取消后的残留目录率。

**简历句式**：

> 构建基于 Snapshot/Worktree 的任务级工作区隔离，绑定基线 commit 与文件指纹，支持并发任务安全修改和可回滚交付。

### 3. Patch 与 Delivery Bundle

**小方向**：生成统一 diff、修改文件清单、统计信息、验证报告、Trace 摘要和风险说明；支持导出 ZIP/JSON/Markdown。

**产出**：PatchArtifact、VerificationBundle、DeliveryManifest、单页结果报告。

**量化指标**：补丁可应用率、交付包完整率、从任务结束到导出耗时、人工复核平均耗时。

**简历句式**：

> 实现 Task→Patch→Verify→Export 完整交付链路，生成包含 diff、测试证据、Trace 和风险摘要的可审查 Delivery Bundle。

### 4. 交付前人工复核界面

**小方向**：前端展示修改文件、diff、验证命令和风险；支持批准应用、拒绝应用、重新验证和下载补丁。

**产出**：`frontend/delivery/` 页面或 CLI review 命令。

**量化指标**：复核所需步骤数、误应用率、拒绝后任务状态正确率。

**简历句式**：

> 开发可视化补丁复核流程，将 Agent 生成结果、验证证据和安全风险聚合到一次人工决策中。

## 大方向二：长任务可靠性与可恢复执行（P0）

### 1. 三层状态机：Task / Attempt / Tool Call

**小方向**：明确一次用户任务、一次模型尝试和一次工具调用的边界；定义 active、verifying、waiting_user、uncertain、complete、failed、cancelled 状态迁移表。

**产出**：`goal/state.py`、run-state.json schema、非法迁移拒绝和状态迁移 Trace。

**量化指标**：非法迁移拦截率、状态恢复成功率、终态与交付文件一致率。

**简历句式**：

> 设计 Task/Attempt/Tool Call 三级持久状态机，将模型自然停止转化为可继续的任务尝试，避免长任务过早结束。

### 2. 崩溃恢复与未知副作用

**小方向**：工具执行前后写入意图和结果；进程崩溃后先检查工作区、提交记录和幂等键，再决定重试或进入 needs_review。

**产出**：恢复扫描器、幂等操作记录、未知副作用报告。

**量化指标**：故障注入恢复成功率；重复写入/外部调用次数为 0；恢复决策延迟。

**简历句式**：

> 实现带幂等键和副作用检查的崩溃恢复机制，在进程中断和网络断开后安全续跑，避免工具副作用重复执行。

### 3. 端到端取消与资源预算

**小方向**：统一 LLM、Tool、Approval、Compaction、Host/Docker 的取消 token；增加 Token、时间、工具次数、并发数和输出大小预算。

**产出**：预算策略、取消事件、未启动工具标记、资源超限报告。

**量化指标**：取消后未启动工具比例 100%；超限拦截率 100%；取消响应 p95；单任务最大 Token/成本。

**简历句式**：

> 构建跨模型流、工具、审批和容器的统一取消传播与资源预算，控制长任务 Token、延迟和副作用上界。

### 4. 模型容错与路由

**小方向**：按“未产生可见输出”区分重试和失败；记录 429/5xx/断网；根据预算和失败类型选择备用模型。

**量化指标**：网络故障恢复率、重复输出率为 0、Fallback 成功率、平均成本变化。

**简历句式**：

> 实现带阶段超时、指数退避和有序 Fallback 的 SSE 模型客户端，保证流式输出在网络抖动下不重复、不丢状态。

## 大方向三：可信验证与完成门禁（P0）

### 1. 版本绑定的验证证据

**小方向**：每条验收证据记录工作区 hash、mutation revision、命令、退出码、日志引用、运行环境和 verifier 版本。

**产出**：VerificationResult、证据 ledger、过期证据清理机制。

**简历句式**：

> 设计版本绑定的 Verification Evidence Ledger，将验收命令、代码指纹、运行环境和判定器版本关联，阻止旧证据驱动错误完成。

### 2. 独立验证器与隐藏检查

**小方向**：Agent 可提出测试，但最终完成由独立 verifier/grader 判定；支持文件检查、命令检查、结构化 JSON、差异和回归测试。

**量化指标**：需求完成准确率、错误完成拦截率、验证命令重复执行一致率。

**简历句式**：

> 构建独立 Verification Runner，将 Agent 自建测试与外部验收分离，覆盖文件、命令、结构化输出和回归测试等多类 Oracle。

### 3. 变更感知的完成门禁

**小方向**：edit/write/bash 及外部进程修改都推进 revision；验证后代码被改动、测试被删除或证据写入失败时自动重新进入 verifying。

**量化指标**：旧证据绕过用例拦截率 100%；代码变更后的重新验证触发率 100%。

**简历句式**：

> 实现变更感知的完成 Gate，覆盖工具和外部进程修改，确保只有当前代码版本通过独立验证后才能进入 complete。

## 大方向四：Tool Security Runtime（P1）

### 1. Shell 能力分级与结构化风险分析

**小方向**：将命令拆为只读查询、工作区写入、网络访问、系统修改；解析管道、重定向、命令替换、嵌套解释器和编码执行。

**产出**：`approval/risk.py` AST/tokenizer、能力标签、解释型拒绝原因。

**量化指标**：危险命令攻击集 ≥200 条；高危漏检率 <1%；合法开发命令通过率 ≥95%。

**简历句式**：

> 设计基于命令结构和能力标签的 Shell 风险引擎，识别嵌套解释器、重定向、管道和编码执行等混淆攻击。

### 2. 不可转移的审批令牌

**小方向**：令牌绑定 session/task/tool/risk/参数 hash，加入 TTL、一次性消费、并发锁、撤销和策略版本。

**量化指标**：过期、复用、跨会话和参数替换拦截率 100%。

**简历句式**：

> 构建短时效、一次性、会话绑定的 Tool Approval Token，防止审批复用、跨任务转移和参数替换。

### 3. WorkspaceGuard 与 Docker 最小权限

**小方向**：补齐 symlink/junction/TOCTOU 防护；Docker 默认无网络、cap-drop、只读根文件系统、资源/PID 限制和敏感路径遮罩。

**量化指标**：越界访问成功率 0；敏感文件泄漏 0；容器残留率 0；网络隔离测试通过率 100%。

**简历句式**：

> 构建 WorkspaceGuard + Docker 最小权限执行环境，隔离路径、网络、资源和凭据访问边界，并通过攻击集持续回归。

### 4. 统一安全审计链

**小方向**：关联请求、工具 schema hash、策略版本、审批、实际执行、容器清理和结果；参数与内容分层脱敏。

**简历句式**：

> 设计端到端 Tool Security Audit Trail，串联策略判定、人工审批、工具执行和清理结果，实现安全事件可追溯。

## 大方向五：Trace 驱动 Eval 与工程可观测性（P1）

### 1. 统一 Trace Schema

**小方向**：统一 task_id/run_id/attempt_id/event_id/parent_event_id；记录 prompt/tool/config/index/workspace/policy hash。

**简历句式**：

> 设计统一 JSONL Trace Schema，关联模型、工具、Goal、Memory、审批、Runtime 和交付事件，支持跨层故障定位。

### 2. 安全回放与失败转回归

**小方向**：回放模型边界但不执行真实工具；从失败 Trace 生成最小 workspace fixture、Eval Case 和回归测试。

**量化指标**：失败 Trace 可重放率、回归用例生成成功率、同一失败签名聚类准确率。

**简历句式**：

> 实现不执行副作用的模型边界 Replay，并将失败 Trace 自动转换为可复现 fixture 和版本回归用例。

### 3. 五维质量成本报告

**小方向**：统一 outcome/process/efficiency/safety/reliability；分开主模型、Memory、Compaction、Judge Token/成本；报告 p50/p95、稳定率和失败簇。

**简历句式**：

> 构建五维 Eval Dashboard，同时报告任务正确率、过程合规、Token/成本、攻击拦截和重复运行稳定性，支持版本对比。

### 4. 数据划分与冻结

**小方向**：Regression、Development、Held-out、Production Trace 四轨；固定 ID、上游 commit、数据 SHA、Prompt/Tool 配置 hash。

**简历句式**：

> 建立带版本锁和曝光登记的四轨评测流程，避免开发集与保留集泄漏，并支持按任务族和攻击载体分层分析。

## 大方向六：Memory 与上下文效率（P1）

### 1. 代码版本感知记忆

**小方向**：记忆条目绑定 repo、branch/commit、文件路径、符号和时间；代码变更后标记 stale，检索时降权或过滤。

**简历句式**：

> 为长期记忆加入仓库版本、文件符号和新鲜度建模，过滤与当前代码状态冲突的历史证据。

### 2. 记忆检索成对消融

**小方向**：固定任务比较 BM25、BGE、RRF、Cross-Encoder、代码符号召回和版本过滤；记录 Recall@k、无效注入率、任务成功率、Token 和延迟。

**简历句式**：

> 在固定 Coding 任务上完成多路记忆召回与重排的成对消融，量化证据召回、任务成功率和上下文成本的权衡。

### 3. 压缩策略选择器

**小方向**：按上下文水位、未读工具证据、任务阶段选择落盘、归档、摘要或延迟压缩；记录每层节省量和质量影响。

**简历句式**：

> 实现分级 Context Compaction 策略，根据上下文水位和未读证据动态选择落盘、归档与摘要，控制长任务 Token 增长。

### 4. 预算与缓存优化

**小方向**：系统提示、工具定义、工作对话、Memory、工具结果分别计量；加入 query cache、embedding cache、索引增量更新和预算分配。

**量化指标**：输入 Token、缓存命中率、检索 p95、单任务成本、无效上下文比例。

## 大方向七：工程化与性能（P2）

### 1. Repo Map 与增量索引

生成目录、符号、调用关系和测试入口的轻量地图，只对变更文件增量更新。简历可写“降低首次定位文件数和无效 read/grep 次数”。

### 2. 冲突感知的受控并行

仅并行无副作用的 read/grep/search；写入、Bash、审批和共享 Memory 保持串行；增加文件锁和冲突检测。简历应写“冲突感知并行”，不能只写 asyncio。

### 3. 模型路由与成本预算

按任务难度、失败类型和剩余预算选择模型；用同题对照证明质量/成本变化。没有对照数据时不要写“降低成本”。

### 4. 发布与开发体验

增加一键安装、Docker smoke、示例仓库、单页 Dashboard、make eval/PowerShell 等价入口和最小演示脚本。简历可写“提供可复现安装与一键评测流程”。

## 最短执行路线

### 只做 1 个大方向

做“大方向一：Coding 交付闭环”，交付一个真实仓库任务的 Patch + Verify + Export 演示。它最容易被面试官理解，也最容易形成可验证数字。

### 做 2 个大方向

在交付闭环之后，加“大方向二：长任务可靠性”，用故障注入证明取消、恢复和幂等重试。

### 做 3 个大方向

再加“大方向五：Trace 驱动 Eval”，把前两项的成功率、稳定率、Token、成本、延迟和失败类型做成版本对比。

### 有时间做专项

- 安全岗位：优先大方向四。
- 记忆/上下文岗位：优先大方向六。
- 后端/基础设施岗位：优先大方向二、四、七。

## 最终简历句式模板

完成“大方向一 + 二 + 五”后，建议压缩成三条：

1. **可靠执行**：基于 Python 实现分层 AgentLoop 与持久 Goal Supervisor，支持流式 Tool Calling、取消、重试、Fallback 和崩溃恢复；在固定故障注入任务上达到 `X%` 恢复成功率，重复副作用为 `0`。
2. **可信交付**：构建 Snapshot/Worktree 隔离和 Task→Patch→Verify→Export 链路，使用版本绑定 Verification Gate 生成可审查补丁与独立验证证据；在 `N` 个真实仓库任务上达到 `Y%` 补丁可应用率。
3. **评测闭环**：统一记录模型、工具、Goal、Memory、审批和 Runtime Trace，支持安全回放、失败聚类和回归门禁；报告任务成功率、稳定率、Token、成本和 p95 延迟。

完成“大方向四”后，可将第 2 条替换为：

> 设计 Tool Security Runtime，结合 Shell 能力分级、审批令牌、WorkspaceGuard、Docker 网络/资源隔离和安全审计，在 `N` 条攻击样本上实现 `0` 次高危越界或敏感信息泄漏。

完成“大方向六”后，可将第 3 条替换为：

> 实现代码版本感知的四层 Memory 与 BM25/BGE/RRF/Cross-Encoder 混合召回，通过成对消融量化证据 Recall@k、任务成功率和上下文 Token 成本。

## 写简历时的硬规则

- 每条只写一个主结果，最多带两个关键机制。
- 数字必须来自固定任务、固定模型、固定配置和可提交报告。
- 写“提升/降低”必须有 baseline 和 ablation；只有绝对值就写“达到”。
- 外部 Benchmark 写清楚“适配、评判和工程闭环”是自己的工作，不把上游能力算成原创。
- 不写组件清单；优先写“问题 → 机制 → 指标 → 结果”。

### P0：工具错误协议与效率优化

586 次工具调用中有 46 次错误，下一步应按 schema、参数、路径、权限、超时、运行时和未知副作用分类，而不是只看错误总数。

建议：

- 为每类错误定义 error_code、retryable、repair_hint 和 side_effect_status。
- 参数错误本地修复并重试；权限/安全错误直接说明原因；未知副作用进入 needs_review。
- 连续相同错误只反馈一次结构化修复提示，避免模型重复发送相同调用。
- Trace 记录“首次错误 → 修复动作 → 最终结果”。

目标：工具错误率 ≤2%，同类错误重复次数下降 50%，可重试错误自动恢复率 ≥90%。

简历句式：

> 设计结构化 Tool Error Protocol，区分参数、权限、运行时和未知副作用错误，并通过修复反馈降低工具失败率。

### P0：降低重复模型轮次和上下文 Token

486 个主模型步骤、548 个全部请求，说明需要拆分统计 agent、memory、compaction、judge 请求，并定位重复轮次。

建议：

- 对 prompt、tool schema 和任务上下文做 hash，检测重复请求。
- 大工具结果落盘，只把增量和摘要放回上下文。
- 对重复 read、grep、search 做短期缓存。
- 已完成验收项停止继续探索。
- 只并行无副作用的只读工具，写入和 Bash 保持串行。

目标：每题主模型请求数下降 20%，重复上下文 Token 下降 30%，有效耗时 p95 下降 20%，结果通过率不下降。

简历句式：

### P1：对 4 个结果失败做失败簇归因

结果通过率为 80%，应逐题归因到需求理解、证据遗漏、代码逻辑、CLI 协议、边界条件、验证不足或交付格式。

- 同一失败簇构造至少 3 个变体，再决定改 Prompt、Tool、Memory 还是 Verifier。
- 每个根因生成最小回归用例。
- 先保持过程、安全、可用性 20/20，再提升结果通过率。

### P1：强化 CLI 与交付协议

### P1：把五维通过结果固化成门禁
