按用户最新要求，**先修效率**。本次改各题共用的上下文、工具说明和评测接口，没有修改模型在某道题里的答案，没有增加业务解题提示，也没有推倒检索架构。

## 重点改动

| 优先级 | 原来的问题 | 本次修改 | 要看什么效果 |
|---|---|---|---|
| 第一优先：大文件读完还要再读 | 刚返回的大文件片段也会立刻变成引用，模型可能拿不到中间内容 | 新返回的 read 片段先完整供下一次模型请求消费；读过后才按历史内容处理，仍可主动重新读取 | 重复 read、工具次数是否下降，功能是否保持正确 |
| 第一优先：压缩后丢掉刚读过的代码片段 | 摘要有文件名，却不一定有下一步需要的代码，模型又读一遍 | 会话内保存少量已读片段及文件 SHA-256；历史压缩移除它们后，核对当前文件内容一致才复用，变更或删除就失效 | 避免“压缩→重读→再压缩”；Trace 记录复用路径、版本和字节数 |
| 第一优先：历史工具内容重复输入 | 同参数、同返回内容的 read 重复保留；正常代码含 error/failed 也被当作不能压缩的错误 | 请求副本仅保留重复读取的最后一份完整结果或引用；按真实工具失败状态保留错误。大批 edit 参数按总大小处理，不只看单个字段 | 工具历史输入减少；改过的文件、不同范围、不同内容不会误当同一结果 |
| 第一优先：反复压缩已经很短的历史 | 模型输入含固定系统说明和工具定义，超过压缩触发线不等于历史本身还值得压缩 | 按实际请求里的历史表示估算可节省量；历史已在目标内时不因固定开销反复调用摘要模型，接近模型真实窗口上限时仍走压缩检查 | 摘要调用与摘要 tokens 下降；不把压缩暂缓报成故障 |
| 第一优先：工具说明每次发两遍 | 系统提示列完整说明，原生工具定义里又有相同说明 | 系统提示只留当前角色可用工具的名称与签名；完整说明和参数约束仍由工具定义提供。无活跃 Goal 时继续隐藏 goal_complete | 每次请求固定输入减少，不牺牲工具参数校验 |
| 配套：修准判定器 | 五类合法接口或表示被误判，提交故障又漏判 | 新版检查关联公开要求编号，支持已发现的合法替代表示，通过公开 CLI 与 OS 提交边界验证；未知表示或未覆盖提交方式单列为判定器待复核 | 原始成绩、纠正展示分和本次修订评分分开，不靠放宽阈值获得提升 |

片段复用有总大小上限，最多保留 16 个路径；每次实际注入不超过 `min(8192, max(1024, target_tokens × 2))` 字节，只核对不超过 1 MiB 的当前文件。它不是跨会话召回，不跳过用户或模型明确发起的 read，也不自动重放写入。注入保留原来的 assistant/tool 配对及工具数据身份，不把文件内容提升成系统指令。额外读取与哈希本身也有成本，最终是否划算仍需实跑。

## 已验证什么

- **186 项针对性离线检查通过，约 19 秒。**覆盖新鲜读取、重复内容、内容变化、删除/越界、失败保留、重启恢复、压缩收益、既有记忆与 Trace、工具执行和网络断点恢复。
- 6 类新版业务判定器在真实 Docker 中校准，每类至少两份通过的实现和两份被拒绝的错误实现；总计 **26 次控制运行，13 次通过、13 次拒绝**。参考实现只用于校准，没有复制进 Agent 工作区。
- 追加提交故障检查识别了旧原子预留的半次提交；新版 CLI 检查还发现旧交付接受空明细。原始首轮评分不覆盖这些新增检查，原分保留。
- 这不证明所有 I/O 故障或进程崩溃均已覆盖。当前注入针对 OS 替换/重命名边界的同步失败和提交后响应丢失；无法覆盖的提交方式标记判定器需要适配，不能直接判 Agent 不会做。
