# v4 修改复盘与下一步优先级

2026-09-06。对照 v2、v3、v4 冻结实现、六题完整 Trace，并用不调用模型的最小输入复现机制。本次只分析，未修改 Agent 实现、未重跑模型题。这里记录的是修改建议，不是已修复效果。

**判断：之前确实有改错和没有改完整的地方。最严重的是增加了复杂的强制验收协议，却没有同步更新模型实际收到的协议说明；随后又让模型通过反复修改检查点来解决协议错误。缓存方向值得保留，但历史裁剪与稳定前缀没有统一设计。无需整体重写项目，应集中重做验收接口、检查点状态更新及历史投影这三处。**

总 tokens 173 万 → 351 万，未缓存输入 113 万 → 167 万，结果 2/6 → 4/6。不能说全都退步，也不能用缓存占比 31.25% → 49.60% 宣称效率优化成功。五题各有两个阶段耗尽 32 步；已恢复网络波动没有作为能力失败扣分。未知原因的进程退出另行记录。

## 哪些应该保留，哪些需要重做

| 之前改动 | 判断 | 处理 |

## P0-1：先修协议不一致，停止让模型猜验收 JSON 的结构

**确切原因：**新解析器只读取每个 `task_checks` 项内部的 `comparisons`；但冻结的系统提示仍写旧格式 `{criterion_id, version, passed, evidence, artifacts}`，还要求 `evidence: string`。bash 工具说明虽改成允许 object，却也没有给出 comparisons 的嵌套结构；完成拦截器再次返回同一份旧格式。解析器升级了，发送给模型的说明没有同步升级。

103 次验收报错中，76 次是缺少 comparison ID。重新解析原始输出后：

- 27 次把 comparisons 放在整个 JSON 顶层；
- 4 次放在 evidence 内部；
- 45 次没有解析器要求的 comparisons 数组，部分仍在 evidence 中记录了实际值与预期值。

因此，至少 31 次可以直接确认是“比较数据放错层级，解析器看不见”。**这些数据不保证业务检查完整或正确，不能直接把 76 次全改成通过。** 最小复现也确认：按旧说明提交数据会被新解析器拒绝，按正确嵌套格式提交则通过。

**新的方案：**维护一份可执行的验收 schema，由它产生工具输入、错误信息和简短说明，删除互相矛盾的旧文字。增加稳定的验证执行接口：运行时提供当前 criterion ID、版本与要求的 check ID，验证程序只提交实际观测数据；退出码、文件版本、执行编号由运行时关联。协议补全只能补格式和确定的关联，不能替模型填 `passed=true` 或猜预期值。不再要求模型每次重写一大段同样的 JSON 包装代码。

**验收：**正确的验证程序能一次完成提交；结构错误立即指出具体字段路径，不触发业务代码重写；缺少真实检查、错误实际值、重复编号仍拒绝。这应先用离线协议输入检查，不急着跑六题。

定位：冻结版 `assistant/prompts.py:22`、`tools/bash.py:66`、`assistant/progress.py:177` 与 `:238`。该强制比较要求在 **v2 → v3** 加入，v3 → v4 没有改变比较解析逻辑。

## P0-2：验收结果逐项保存，检查点不能因为修格式而不断重开

**确切原因一：一个错误连带丢掉同批合法结果。** `observe()` 先从已验证集合删除本批出现的所有编号，再逐项解析；只有整个循环正常退出才保存新结果。最小复现：A、B 原来都通过；新提交中的 A 合法、B 缺字段，最终 verified 变为空。拒绝 B 是合理的，让已合法重验的 A 也消失会制造重复工作。

**确切原因二：失败信息不够具体。** 真正的比较失败只把失败编号存入 `failed_checks`；精简后的请求快照又不包含它。模型主要收到待验收描述，缺少直接可用的实际值、预期值与具体失败点。之前精简检查点时把这部分也裁掉，不合适。

**确切原因三：验收格式错误与需求变化混在一起。** 运费题调用检查点 26 次，部分要求升到版本 7；原子预留调用 17 次，最高版本 9，尽管用户分别只给了两个执行阶段。发票题又把部分 check ID 升成新的 criterion ID。轨迹显示模型在适配验收器的过程中反复改检查清单，不是每次都有新的用户需求。

**新的方案：**分开“用户需求版本、代码内容版本、验证器版本”。修改验证输出格式，不应生成新需求或令全部业务证明失效。编号由运行时分配并稳定关联；变更或撤回需要关联到相应用户消息，不能只接受模型一句“撤回了”。每项独立保存通过、业务失败、协议无效状态；被实际失败否定的旧证明不能复活，无关合法证明不跟着清空。给模型返回简短的 `检查编号 / 实际值 / 预期值 / 错误位置 / 下一步`。

同一协议错误重复且无新文件、新证据时，进入专门的协议修复路径；仍无法修复则明确暂停，不能一直消耗到第 32 步，也不能静默判通过。

**额外机制缺口：**最小复现表明，模型可在不改版本时更换整段描述而保留通过状态，也可不提供用户变更事件就撤回所有要求。这并不证明本轮利用了漏洞，但说明目前“严格验收”的约束仍主要依赖模型自觉，复杂编号管理没有换来同等可靠性。修用户需求来源关联，比继续增加编号或 prompt 更值得做。

定位：`assistant/progress.py:53`、`:145`、`:198`、`:287`。保留持久化和硬预算，不回退到“说完成就完成”。

## P1-1：把历史裁剪与缓存统一起来，避免刚稳定前缀又改旧消息

**确切原因：**v4 358 次主模型请求中，206 次诊断为历史首先发生变化。配置迁移没有摘要压缩，但 64 次请求中有 45 次历史变化；逐条对照上一次请求，26 次首先改变同一旧工具调用的参数，17 次首先改变同一工具返回，另外 2 次发生消息替换。原子预留也无摘要压缩，44 次历史变化中 42 次先改变旧调用参数或返回。

例如配置迁移 Trace 第 124 行：前次请求中的完整检查点工具结果变成归档引用；第 132、137 行：旧 write 的代码参数变成归档引用。这里能确认历史被改写，不能把每次改写等同于服务商缓存全部归零。

**之前哪里没改好：**累计历史预算每次都从原始历史重新投影，边界随着新工具调用推进；此外还有大参数替换、重复读去重、快照和状态合并。只把动态状态放到尾部，管不了其他几条改写历史的路径。因此“缓存问题已经结构性解决”的说法过早。

**新的方案：**把请求历史的投影结果也按阶段保存，同一阶段内已发送片段保持稳定，只追加新内容。到阶段结束、达到明确的高水位或出现足够收益时，一次批量归档到低水位，开启新前缀；避免越过边界后每次只再裁一小块。状态日志合并与历史压缩尽量共用边界。新鲜读取、未决工具、错误证据继续保护；接近上下文硬上限时必须允许强制压缩。

**验收：**用实际工具历史检查连续请求，不能只测试 ContextJournal；统计同一阶段前缀变化次数、重复读、未缓存输入与输出成本。不要直接删除历史预算、无限保留内容，也不要继续压低阈值碰运气。

定位：`memory/working.py:238`、`:311`，`memory/history_budget.py:10`，`agent/context.py`。这是第二个效率重点，排在验收死循环之后。

## P1-2：验收证据要来自实际行为，减少“代码和自测一起写错”

发票题有输入应返回总额 54 分，实际返回 0；原子预留的独立判定器发现非法输入未拒绝、CLI 接受无效输入、提交边界故障留下部分提交。这两题不仅是格式问题。配置迁移、脱敏、运费虽然最终结果通过，仍不能据此保证它们生成的每条自测都是正确的。

当前比较器可以校验 actual 与 expected 是否相同，但两者经常都由同一个模型写入；恢复场景的 injected/observed 也允许脚本自行声称。它提供格式化自测证据，不能自动成为独立业务正确性证明。

**新的方案：**优先复用仓库已有测试与正式输入，用可重放程序产生实际值；数据题保留分组中间表、不变量和完整异常集合；恢复题由外部故障探针记录真实注入阶段及前后状态。记录预期值的来源。运行时负责执行、采集、关联、阻止未验证完成，独立 Eval 负责外部打分，两者职责分开。

不要给通用 Agent 写“发票固定应得 54”“库存某个 case 专用补丁”。把整数/布尔边界、输入不可变、多文件提交中断、同请求重复提交等作为任务族能力验证。

## P2：缩小改动批次，补真实协议接入检查

之前大量离线检查使用测试代码手写正确的嵌套 JSON，证明解析器能处理正确格式，却没有证明模型根据系统提示和工具说明能够稳定产生该格式。这是验证范围的缺口，不代表这些单元测试没有价值。

建议顺序：先修 P0 两项并做短小确定性检查 → 选一题交付正确但验收循环的题、一题真实业务失败的题做模型接入检查 → 再改单独的历史投影机制，以固定并发做前后对比。业务通过率、完成状态和未缓存输入同时看；曝光题继续标为回归。未冻结实现时避免边改边跑，对照版本不要多路混跑造成时延难解释。

保留原始评分及原 Trace，不因发现协议缺陷就把全部旧失败改为通过。修复效果需要新运行验证，不能给出预先承诺的节省比例。
