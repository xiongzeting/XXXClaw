# 本地 Bi-Encoder 与 LongMemEval-V2 Agentic Search

## 一、这次改动解决了什么

这次完成两项真实能力，而不只是改 Benchmark Prompt：

1. MiniClaw 的向量召回从 `LocalHashVectorEncoder` 升级为真正的本地 SentenceTransformer Bi-Encoder。
2. LongMemEval-V2 不再只能“一次检索 Top-5，然后让模型一次回答”，而是接入真实 `AgentLoop`，由模型使用 `trajectory_search` 和 `trajectory_read` 迭代查找证据。

默认生产链路现在是：

```text
Query
  ├─ BM25 词法召回
  └─ 本地 Bi-Encoder 语义召回
             ↓
        加权 RRF 融合
             ↓
   最多 48 个候选进入 Cross-Encoder
             ↓
     返回可读取的父节点 ID
             ↓
 Agent 按需读取“命中状态及前后状态”
             ↓
      证据不足则换关键词再次搜索
```

核心区别：Bi-Encoder 负责从大量文档中快速找候选；Cross-Encoder 只对少量候选做更准确但更贵的精排。不能让 Cross-Encoder 直接扫描两万条文档，否则查询延迟会不可接受。

## 二、本地 Bi-Encoder

### 2.1 使用的模型

默认模型：

```text
sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
```

选择它的原因：

- 是真正的神经网络语义向量，而不是哈希近似向量。
- 同时支持中英文，既能测英文 LongMemEval，也适合 MiniClaw 自身的中文记忆。
- 输出归一化向量，可直接计算余弦相似度。
- 不需要 E5 风格的 `query:`、`passage:` 前缀改造，接入风险较小。

### 2.2 本地加载与设备选择

运行时只查找本地 Hugging Face 缓存，不会因为一次用户查询而隐式联网下载。

```ini
MINICLAW_MEMORY_VECTOR_ENABLED=true
MINICLAW_MEMORY_VECTOR_MODEL=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
MINICLAW_MEMORY_VECTOR_BATCH_SIZE=64
MINICLAW_MEMORY_VECTOR_DEVICE=auto
```

`auto` 会优先使用 CUDA；没有可用 GPU 时回退 CPU。模型对象通过进程级锁和缓存复用，避免并发请求重复加载模型。

### 2.3 批量编码和缓存

一次检索会把 Query 和尚未缓存的文档批量编码。相同文本之后直接复用内存中的向量：

```text
第一次搜索：编码 Query + 全部未缓存文档
第二次搜索：文档向量已缓存，只编码新的 Query
```

真实 LongMemEval-V2 单题烟雾测试中：

- 文档片段：21,140。
- 第一次向量阶段：约 32.70 秒，包含全部文档的冷启动编码。
- 第二次向量阶段：约 0.045 秒，只编码新查询并复用文档向量。
- 实际后端：`sentence-transformer`。
- 实际设备：`cuda`。
- 降级：`false`。

这也说明后续如果跑大量 Case，最值得继续做的效率优化是“文档向量持久化”，而不是削弱检索质量。

### 2.4 降级链

```text
本地模型与依赖可用
  → SentenceTransformer Bi-Encoder

本地模型不存在 / 依赖加载失败
  → LocalHashVectorEncoder
  → BM25 + Hash Vector + RRF 继续工作
```

降级不是静默发生。每次检索会记录：

- `vector_backend`
- `vector_model`
- `vector_device`
- `vector_load_error`
- `vector_fallback`
- `vector_seconds`

因此能够在 Trace 中区分“真正使用神经向量”和“测试其实跑了哈希兜底”。

## 三、LongMemEval-V2 如何接入 AgentLoop

### 3.1 原来的一次性模式

```text
题目到达
  → 系统用题目原文检索一次
  → 自动注入固定 Top-5 父节点，最多 15k Token
  → 模型回答一次
```

问题是检索器只能看到原始问题，无法利用第一次证据里发现的新实体、按钮名、状态或操作继续搜索。

### 3.2 现在的 Agentic Search 模式

```text
题目到达
  → 初始 Prompt 不注入轨迹证据
  → Agent 调用 trajectory_search
  → 得到父节点 ID、状态范围、短预览和分数
  → Agent 调用 trajectory_read 读取完整相邻状态
  → 证据不足时改写 Query 再搜索
  → 证据充分后输出 \boxed{答案}
```

这条路径直接使用 MiniClaw 通用 `AgentLoop` 和 `ToolExecutor`，不是 Benchmark 内部伪造循环。

### 3.3 TrajectoryMemoryIndex

每个 Case 先构建一次 `TrajectoryMemoryIndex`：

```text
TrajectoryMemoryIndex
  ├─ documents：用于 BM25 / Bi-Encoder 召回的子块
  ├─ metadata：子块属于哪个轨迹、状态和字段
  ├─ documents_by_parent：父节点到子块的映射
  ├─ state_order：状态时间顺序
  └─ retriever：共享混合检索器和模型缓存
```

Agent 多次调用搜索工具时，不会反复读取 1.2GB 的原始轨迹文件，也不会反复重新拆分文档。第一次搜索生成的文档向量还能被后续搜索复用。

### 3.4 trajectory_search

输入：

```json
{"query":"image post button title url","limit":5}
```

执行：

1. BM25 与本地 Bi-Encoder 分别召回。
2. 用加权 RRF 合并候选。
3. 用 Cross-Encoder 对有限候选精排。
4. 将命中的子块提升为父节点。
5. 返回父节点 ID、轨迹 ID、锚点状态、相邻状态范围和短预览。

搜索结果不会暴露 Benchmark 的 Gold Answer、Question ID 或隐藏评分信息。

### 3.5 trajectory_read

`trajectory_read` 只允许读取本轮 `trajectory_search` 已经返回过的 `parent_id`。模型不能猜 ID 任意遍历整个语料库。

父节点内容不是孤立 1,600 字符片段，而是：

```text
锚点前一个状态
  + 锚点命中状态
  + 锚点后一个状态
```

同时保留相关的 Goal/Outcome、Action/Thought 和 Accessibility Tree 子块，使动态问题能看到“操作前状态 → 动作 → 操作后状态”。

## 四、预算和失控保护

默认限制：

```text
最多搜索：3 次
最多读取：5 次
去重后的证据总量：15,000 Token
AgentLoop：最多 8 轮
```

保护规则：

- 未搜索发现的父节点拒绝读取。
- 同一父节点重复读取会被拒绝，避免重复消耗上下文。
- 达到搜索、读取或 Token 上限后，工具返回明确错误。
- 证据超过剩余 Token 时在工具侧截断。
- Tool Call 仍经过统一参数 Schema 校验、超时和取消机制。

这里的 15k 是“不同证据的总预算”。多轮 Agent 会在后续模型请求中携带已有历史，所以累计输入 Token 会高于 15k；这是多轮推理成本，结果中会单独统计。

## 五、Trace 记录

Agentic Search 的每次真实工具调用都会写入 Trace：

- 工具名、参数和状态。
- 搜索 Query、候选数、父节点数和耗时。
- Bi-Encoder 后端、设备、降级状态和耗时。
- Cross-Encoder 候选数、模型、是否应用和耗时。
- 读取的父节点、证据 Token、是否截断。
- 整个 AgentLoop 的模型请求数、Tool Call 数、Token、成本和错误。

真实烟雾题轨迹：

```text
2 次 trajectory_search
3 次 trajectory_read
5 次模型请求
32,462 input tokens
568 output tokens
7,407 distinct evidence tokens
约 62.10 秒总耗时
```

该题最终答案不正确，所以这次结果只证明本地 Bi-Encoder、工具调用、多轮搜索、预算和 Trace 已经端到端工作，不能作为正确率提升结论。正式效果需要在同一批题上运行 one-shot / agentic-search A/B。

## 六、如何运行 A/B

Agentic Search 默认开启：

```powershell
python -m MiniClaw.benchmark.longmemeval_v2 `
  --official-repo external/benchmarks/LongMemEval-V2 `
  --data-root external/benchmarks/LongMemEval-V2/data/longmemeval-v2 `
  --limit 40 --env-file .env
```

旧的一次性 Top-5 模式：

```powershell
python -m MiniClaw.benchmark.longmemeval_v2 `
  --official-repo external/benchmarks/LongMemEval-V2 `
  --data-root external/benchmarks/LongMemEval-V2/data/longmemeval-v2 `
  --limit 40 --env-file .env --no-agentic-search
```

两种模式分别写入：

```text
results-agentic-search.json
summary-agentic-search.json
results-one-shot.json
summary-one-shot.json
```

不会因为复用同一个输出目录而把 A/B 结果混在一起。

## 七、面试时最重要的说法

### 为什么同时需要 Bi-Encoder 和 Cross-Encoder？

Bi-Encoder 预先把 Query 和文档分别编码，适合大规模召回；Cross-Encoder 要把 Query 与每个候选拼在一起逐对计算，更准确但更慢。因此先用 BM25 + Bi-Encoder 找几十个候选，再让 Cross-Encoder 精排，而不是扫描全库。

### 为什么要把搜索做成工具？

一次性检索只能使用原始问题。Agent 读到第一批证据后，可能发现新的实体、页面标签或中间状态；工具化以后它能据此改写 Query，完成多跳和过程型检索。

### 如何避免 Agent 无限搜索？

同时限制搜索次数、读取次数、不同证据 Token 和 Agent 最大轮数；父节点必须先搜索后读取，并禁止重复读取。

### 本地模型失败怎么办？

请求期间不联网下载，失败时降级到 LocalHash，BM25 主链仍可用；同时把实际后端和失败原因写入 Trace，避免评测结果名义上使用 Embedding、实际上静默使用兜底。

## 八、验证结果

- Bi-Encoder 与 Agentic LongMemEval 专项：30 项通过。
- 全项目回归：195 项通过。
- 本地模型烟雾：CUDA 加载成功，`vector_fallback=false`。
- LongMemEval-V2 AgentLoop 烟雾：搜索、读取、预算、Token 汇总和 Trace 均端到端运行成功。
