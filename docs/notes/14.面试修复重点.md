# MiniClaw 面试修复重点

## 一句话介绍

MiniClaw 是一个参考 pi-mono 思路、使用 Python 实现的编码 Agent。重点不是简单调用大模型，而是补齐工具执行、上下文压缩、长期记忆、Goal 监督、安全审批、流式传输、取消链路和 Trace/Eval 闭环。

## 1. 工具系统

- 将工具拆成 `read / write / edit / bash / grep`，职责单一，参数使用结构化 Schema。
- `grep` 负责代码和文本搜索，`bash` 只负责命令执行，避免把所有能力塞进一个通用工具。
- 工具统一经过执行器，支持超时、取消、输出截断、错误分类、审批和 Trace 记录。
- 大型工具输出不直接长期占用上下文，而是保存为 Artifact，只给模型预览和路径。

面试重点：工具不仅是几个函数，核心是统一执行边界和副作用控制。

## 2. LLM 流式与稳定性

- OpenAI-compatible 接口改为真正的 SSE 流式解析，支持文本增量和 Tool Call 参数增量拼接。
- 支持首 Token、流空闲、总请求三类超时，以及 429、5xx、网络错误的指数退避重试和模型降级。
- 默认模型和密钥全部通过 `.env` 配置，默认使用 `gpt-5.6-luna`；DeepSeek 显式关闭思考模式。
- 修复了一个真实问题：原实现把“等待服务器响应头”错误算入 10 秒连接超时，导致慢启动请求被误判并重复调用。修复后由 HTTP 客户端负责 TCP 连接超时，响应头阶段使用首 Token 超时。
- 修复后连续 88 次模型请求全部一次成功，重试次数为 0。

面试重点：流式传输不只是输出更快，还必须正确处理半包 Tool Call、超时边界、取消和重复计费。

## 3. 四层上下文压缩

生产配置：软触发 80k、硬触发 100k、压缩目标 30k、近期原文保留 20k。

四层职责：

1. 工具结果层：大输出转 Artifact。
2. 历史归档层：完整 transcript 保存为 JSONL，原文不因摘要而丢失。
3. 任务摘要层：只保留 Goal、决策、错误、文件状态和下一步。
4. 语义记忆层：压缩前提取明确要求长期保存的稳定事实。

面试重点：摘要只能保存任务状态，不能承担完整事实恢复；完整原文必须可检索归档。

## 4. 归档检索与长期记忆

- 新问题到达时，同时检索长期语义记忆、当前会话压缩归档和历史 Episode；近期原文仍在 Working Context，不重复进入检索池。
- 检索采用 BM25 为主、向量为辅，使用 RRF 融合并 rerank。
- 在三类来源完成召回和跨来源 RRF 后，只对最多48个候选执行一次本地 Cross-Encoder 精排；模型缺失时自动退回确定性排序，避免让神经重排成为可用性单点。
- 多跳问题先自动注入最相关原文；证据不足时，模型可以继续调用 `memory.archive_search`。
- 对“当前 / 最新 / 现在”类问题增加通用时效意图检索，用 `changed / switched / replaced / no longer` 等状态变化表达补充召回，解决旧句子因字面含有 `current` 而压过新事实的问题。
- 精确多词主题短语参与 rerank，并过滤常见会话性短语，减少多词主题被单个高频词错误匹配压过。
- `remind me / what did you / we discussed` 被识别为助手历史查询；偏好与决策题命中单条消息后，自动扩展为同一 Session 的用户上下文块，并按扩展后的真实相关分重新排序。
- 推荐型 Profile Query 与决策型上下文扩展分开：无明确主题的推荐会补搜兴趣档案，已有明确主题的决策题不会被泛化兴趣词稀释。
- 覆盖与求和题在聚合前标注 `actor + actuality + time/status + value`，只统计用户明确完成的事件，排除未来计划、助手建议和假设估算。
- 版本化事实按 `subject + relation` 分组，先淘汰旧版本，再进行相关性排序，避免旧事实因为词面更相关而胜出。
- 近期未压缩事实和历史归档进入同一候选池，统一进行版本裁决。
- 长期记忆写入支持冲突检测和解决；只有用户明确要求“记住”时才自动写入，避免把临时讨论污染成稳定事实。

面试重点：检索相关性不能决定事实新旧，版本正确性必须在排序前处理。

## 5. 修复检索污染与 Top-K 重复占位

Benchmark 中发现 `memory.archive_search` 返回的 JSON 又被加入 Active Context 索引，下一次搜索会搜到上一次搜索结果，形成递归嵌套：

```text
原始事实 → 搜索结果 JSON → 再次索引 → 更大的搜索结果 JSON
```

修复方式：

- 排除 `memory` 工具产生的派生检索结果，不将其写回归档索引。
- Active Context 不再重复加入 Archive 检索池，避免回显当前问题和普通近期消息。
- 真实 `read / bash` 工具证据和 Artifact 仍然保留。

修复效果：同一高成本案例 Token 从 162,988 降到 108,494，下降约 33%；工具搜索从 5 次降到 4 次，嵌套 JSON 完全消失，答案仍正确。

后续 EventQA 又发现：渐进压缩会把重叠历史多次归档，相同正文重复占据 Top-K；长选择题还会因重复实体词和 `boredom / bored` 等词形差异漏召回。最终增加正文去重、BM25 查询词频封顶、英文停用词和轻量词形归一化，使自动注入从重复片段变为 8 段不同证据，并召回“令人厌烦的战争话题”原文。

面试重点：需要区分原始证据、派生检索结果和重复归档副本；否则准确率可能暂时不下降，但 Top-K 多样性、成本和延迟会持续恶化。

## 6. Goal 与外层监督

- Goal 保存任务目标、当前尝试、验证结果和终止状态。
- Agent 内层负责模型与工具循环，外层 Supervisor 判断是否真正完成、是否需要验证、是否应继续尝试。
- 模型输出“完成”不等于 Goal 完成，必须结合验证工具或完成条件判断。
- Goal 状态、尝试次数、失败原因和最终结果全部进入 Trace。

面试重点：Goal 解决的是长任务“模型过早停止”和“失败后不续跑”，外层监督不能只依赖模型自我判断。

## 7. 端到端取消

取消信号贯穿：

```text
CLI / 飞书 → AgentLoop → LLM SSE → Tool Executor → Bash / Docker 子进程 → Goal 尝试
```

- 取消后立即停止模型生成和后续 Tool Call。
- 本机及容器子进程会被终止并回收临时资源。
- Trace 使用 `cancelled` 状态，不把用户取消统计为普通失败。

面试重点：只实现 `/cancel` 命令没有意义，取消必须真正到达最底层进程。

## 8. 危险操作审批

- 支持 `allow / ask / deny` 三种策略。
- 对 Shell、删除、覆盖写、Git 推送和网络下载进行风险分级。
- CLI 和飞书都可审批，超时自动拒绝。
- 支持项目级白名单，审批请求、结果和最终执行状态进入 Trace。

面试重点：Docker 只是隔离手段，不等于安全策略；真实副作用必须在工具执行前被审批中间层拦截。

## 9. 项目指令自动加载

指令按层级加载：

```text
用户全局指令 → 工作区 AGENTS.md → 当前目录规则 → 文件附近规则 → 本次请求
```

- 记录每条指令的来源和覆盖关系。
- 控制注入 Token 预算，并在文件变化后使缓存失效。
- Trace 记录本次实际注入的指令。

面试重点：编码 Agent 是否可靠，很大程度取决于它能否自动发现并遵守仓库规则。

## 10. Runtime、Docker 与飞书

- Runtime 抽象负责本机和 Docker 执行方式，工具层不直接依赖具体运行环境。
- Docker Runtime 提供工作区挂载、网络策略、进程回收和资源限制，但仍需与审批系统配合。
- 飞书作为平台适配层接入 Agent，复用已有接口配置，但消息处理、审批、取消和 Trace 仍走 MiniClaw 自己的核心链路。

面试重点：平台、Agent、工具和 Runtime 分层后，CLI 与飞书只是不同入口，不需要复制核心逻辑。

## 11. Trace → Eval 数据闭环

- 统一 Trace 记录模型、Token、成本、延迟、Tool Call、审批、Goal、Compaction、重试和取消。
- 可以从真实失败会话生成 Eval Case。
- 支持离线切换模型、Prompt 和 Tool 配置进行轨迹重放。
- 为失败聚类、回归告警以及质量/成本 Dashboard 提供统一数据来源。
- 从 LongMemEval-V2 的真实失败中固化了判定器误判、静态证据漏召回、流程顺序错误和否定事实证据不足四类 Eval；重放时严格排除 Judge/Grader/Checker 请求，避免把评审模型输出误当成 Agent 最终答案。
- 统一兼容不同 Benchmark 的 `answer_gold / response_raw / usage / elapsed_seconds` 字段，使失败摘要、Token、成本和延迟能进入同一 Dashboard。

面试重点：Eval 是具体测试案例和评分，Benchmark 是标准化对比方案；Trace 是把真实线上失败转成 Eval 的数据基础。

## 12. Benchmark 结果

> 以下成功率是归档清理前的历史测量，不能直接当作当前生产链路成绩。编号事实仍可由 MemoryAgentBench 适配器独立评测，但 LongMemEval/Compaction 必须在去除特殊 Session Context 后重新跑，才能更新简历数字。

- 最终覆盖 35 个不重复“案例×模式”、25 个不重复题目，适合作为实习项目的工程验证规模。
- 官方标签为 33/35（94.3%）；两个失败是同一道 Italy 元首标签争议在 hybrid 和 compaction 两种模式中的重复计分。
- 按数据集“最大编号为最新事实”的规则为 35/35。
- 6k 多跳基线：3/3，0 次压缩，证明高 Token 主要来自长上下文压缩，而不是基础检索循环失控。
- MemoryAgentBench 32k 多跳完整 10 题：官方标签 9/10；按“最大编号为最新事实”的数据规则为 10/10。
- 唯一差异是 Italy 元首案例：较新事实与官方标签冲突，没有为了刷分破坏版本裁决。
- 32k 单跳：5/5。
- 64k 多跳：2/2，两题均只补充搜索 1 次。
- EventQA 65k 普通文本：2/2，证明归档检索能够召回普通长文本原文。
- LongMemEval 最终运行 8 组、共 56 个不重复压缩案例，七类题型各 8 题：用户事实、助手历史回答、偏好迁移、跨会话多跳、知识更新、时间推理和拒答。
- 56 题首次运行为 46/56（82.1%），保留了真实失败分布，没有只报告修复后的接近 100% 数字。
- 10 个初始失败分别归因为 Judge 等价性、时效更新、多事件时间绑定、事实实际性、无主题偏好召回、精确短语碰撞、助手角色召回和同 Session 多事实覆盖；全部经过通用分布修复后真实单题回归通过。
- Wave 8 初始为 5/7；修复“命名实体附加位置导致 Judge 误判”和“偏好题泛化建议未使用个人经历”后，两题均通过。
- 8 组首次运行共完成 56 次压缩，压缩前后上下文差值约 4,426,734 Token；该值用于衡量上下文缩减量，不等于净费用节省。
- 最新真实案例从 102,880 Token 压缩到约 21,196 Token，保留最近原文并将完整历史写入可检索 JSONL 归档。
- 此前 MemoryAgentBench 阶段的有效结果累计 115 次压缩，上下文差值约 671,626 Token；该值表示压缩前后差值，不直接等于净费用节省。
- LongMemEval-V2 Small 同一批40题初始为 7/40，17题回答 Unknown、模型错误为0；这批结果保留用于暴露轨迹召回仍不足，而不是作为简历正确率。
- 性能剖析发现主要耗时来自重复向量编码和BM25分词；加入有界缓存并在同批任务复用 Retriever 后，最终同批复跑的平均检索从23.69秒降至2.50秒，下降约89.5%。复跑为9/40、无模型错误，但相比初始7/40的差异包含模型输出波动，不归因于缓存。
- 最终40题 Trace 共记录345,109 Token、58次模型请求和约$0.035成本；其中18次为否定前提题的官方LLM Judge，回答链路没有Tool Call或Compaction，因此该批主要衡量轨迹记忆检索，而不是工具归档压缩。
- 曾尝试按题型进行字段级RRF：40题中新增3题通过、同时3题回归，没有净收益，因此完整回退，只保留判定器修复和检索缓存。该过程体现了用回归分布决定是否保留优化，而不是针对单题调参。
- 又尝试将父节点后继窗口从1个状态扩大为2个状态；虽然能补齐个别动作后页面，但13道动态状态题从基线3/13降为2/13，因此完整回退。
- 修复 LaTeX 展示包装导致的确定性 Judge 误判：`\boxed{\text{Results, Uses}}` 现在与 `Results, Uses` 等价；当前保留5类精选 Trace Eval。单次重放为2/5，但只有LaTeX项可确定归因于修复，动态状态项因模型波动偶然通过，另外三类仍是未解决回归。
- Cross-Encoder 同批40题为10/40，原确定性rerank为9/40；答案短语进入Top-5的检索代理指标由13/40升至14/40，但平均检索耗时由2.50秒升至4.39秒，因此只表述为“小幅净提升且有CPU代价”，不夸大为稳定显著增益。
- 当前全项目单元测试：187 passed。

面试重点：不仅报告成功率，还分析检索次数、压缩节省、Token、重试、标签冲突和错误类型。

## 最值得讲的三个难点

1. 摘要压缩会丢未来未知事实，因此增加完整 transcript 归档和自动检索闭环。
2. 长期语义记忆的写入冲突不能交给相关性分数，因此将冲突检测、持久化和人工解决放在写入链路；显式结构化来源的版本裁决则由来源适配器提供字段。
3. 检索结果递归写回和重叠归档重复占位会共同污染 Top-K；通过区分原始证据、派生结果并按正文去重，将单案例 Token 降低约 33%。
