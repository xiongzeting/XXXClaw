# 11. 端到端取消与中断

## 1. 这次解决的不是“停止显示”，而是停止副作用

旧实现中，`/cancel` 可以停止正在生成的模型请求，但正在运行的 Bash、Docker 容器或审批等待仍可能继续。更危险的是，一个响应里如果包含多个 Tool Call，取消当前命令后，后续写文件操作仍可能被执行。

现在每次 `AgentLoop.run()` 都创建一个共享 `CancellationToken`，同一个信号贯穿整次尝试：

```text
飞书 /cancel 或 /goal cancel        CLI Ctrl+C
                 \                 /
                  CodingAssistant.cancel(reason)
                              ↓
                    CancellationToken.cancel()
                              ↓
        ┌─────────────────────┼─────────────────────┐
        ↓                     ↓                     ↓
  LLM SSE / Retry       ToolExecutor / Approval   Goal 当前尝试
        ↓                     ↓                     ↓
  关闭 HTTP Stream       取消正在执行的 Tool       status=cancelled
                              ↓
                   Host 进程树 / Docker 容器
```

取消是幂等的。第一次取消设置原因和时间，重复取消不会重新启动清理流程。

## 2. AgentLoop 如何阻止后续 Tool Call

模型可能一次返回多个调用：

```text
1. bash: 运行测试
2. write: 覆盖配置
3. bash: git push
```

AgentLoop 仍按模型给出的顺序串行执行，但每次调用前都会检查共享 Token。若第一个 Bash 执行期间取消：

- 当前 Bash 被中断；
- 第二、第三个调用不会启动；
- 当前调用和未启动调用都生成取消型 ToolResult；
- 会话记录中补齐对应的 `role=tool` 消息，避免下一次请求出现“Assistant 声明了 Tool Call，却没有 Tool Result”的非法协议历史；
- 本轮立即以 `stop_reason=aborted` 结束。

取消型 Tool Call 的 Trace 状态是 `cancelled`，不会计入 `tool_errors`。

## 3. 本机进程如何终止

Host Runtime 启动 Bash 时创建独立进程组：

- Windows：`CREATE_NEW_PROCESS_GROUP`，取消时使用 `taskkill /PID <pid> /T /F`；
- Linux/macOS：`start_new_session=True`，取消时向整个进程组发送 `SIGKILL`；
- 最后再次回收 shell 进程并等待退出，避免僵尸进程。

因此不仅终止 shell 本身，也会终止 shell 创建的 Python、Node、编译器或测试子进程。

超时和用户取消共用同一套进程树回收逻辑，但 Trace 语义不同：超时是错误，用户取消是 `cancelled`。

## 4. Docker 如何终止和清理

每次 Docker Bash 都有唯一容器名。取消顺序为：

```text
CancellationToken
      ↓
docker rm -f <container>
      ↓
终止本机 docker run CLI 进程树
      ↓
取消并等待 stdout reader
      ↓
finally 再执行一次幂等容器删除
```

无论正常完成、超时、协程取消还是 Token 取消，`finally` 都会尝试删除容器。清理命令自身也有超时；若清理 CLI 卡住，会被强制终止。

## 5. write/edit 为什么需要单独处理

`asyncio.to_thread()` 的协程被取消，不代表后台线程会停止。如果后台线程直接覆盖目标文件，就可能出现“用户已取消，但文件随后仍被写入”。

MiniClaw 对内置 write/edit 使用两阶段原子提交：

```text
写入同目录临时文件
        ↓
再次检查 CancellationToken
        ↓
os.replace() 原子替换目标文件
        ↓
finally 删除临时文件
```

取消发生在提交前时，目标文件保持原样，临时文件会被回收。若原子替换已经完成，则该 Tool Call 会如实记录为成功，后续调用仍会停止。

## 6. Approval、Goal Judge 和 Compaction

- 等待 CLI/飞书审批时，取消会撤销等待 Future，并从 Approval Inbox 删除待审批项；
- Goal Judge 的模型请求复用同一个 Token；
- 模型式上下文压缩复用同一个 Token；
- 取消后不再开始下一次 Goal attempt；
- Goal 使用独立终态 `cancelled`，不再伪装成 `failed`。

## 7. 入口行为

### 飞书

以下消息绕过忙碌会话队列，直接取消当前会话：

```text
/cancel
cancel
取消任务
/goal cancel
```

飞书先回复“正在回收模型、工具和运行进程”，当前任务清理完成后再把原进度消息更新为取消结果。

### CLI

任务运行期间按 `Ctrl+C`：

- 若当前有任务，只取消当前任务并回到交互循环；
- 若当前没有任务，按普通中断退出 CLI。

在空闲状态输入 `/goal cancel` 会把持久化 Goal 标记为 `cancelled`。

## 8. Trace 语义

取消相关记录包括：

```text
run.cancelled
model.transport phase=cancelled
model.request status=cancelled
tool.call status=cancelled
goal.snapshot goal.status=cancelled
compaction.aborted status=cancelled
run.completed status=cancelled
```

Dashboard 单独统计：

- `cancelled_runs`；
- `tool_cancelled`；
- Tool Error Rate 只计算真正的 `status=error`；
- 被用户取消的轨迹不进入失败聚类，也不触发普通质量回归告警。

## 9. 行为边界

取消无法回滚在信号到达前已经完成的真实副作用。例如一个命令已经完成 Git push，之后再取消不能撤销远端提交。因此危险操作审批仍然必须保留。

MiniClaw 保证的是：

1. 收到取消后不启动新的 Tool Call；
2. 尽快终止仍在运行的本机进程或容器；
3. 未提交的内置 write/edit 不覆盖目标文件；
4. 清理临时文件、输出读取任务和容器；
5. Trace 如实区分 cancelled、error 和 success。
