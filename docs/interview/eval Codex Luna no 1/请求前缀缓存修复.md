# 请求前缀缓存修复（2026-09-06）

已修改主代码，依据同目录的《缓存命中分析》。本记录只报告实现和离线验证，**还没有这版代码的模型 A/B 收益**。

## 原来与现在

原来每次请求为 `system → 最新检查点 → 最新召回 → 历史`。前面的状态一变，后面的长历史就可能无法复用前缀缓存。

现在为 `system → 历史（含先前已发送的状态增量）→ 新工具结果之后的必要增量`。变化写在尾部；没变化不追加。原用户要求和完整工具调用/返回对不被重排。

| 改动 | 原来 | 修改后 | 为什么 |
|---|---|---|---|
| 任务检查点 | 每次重发最新整块状态，并放在历史前 | 状态按键追加带 revision 的 set/remove；最新值替代同键旧值 | 小状态变化不改写前面的长历史；撤回和失效仍有明确记录 |
| 召回记忆 | 排序、分数、来源变化可能重写整块 | 以作用域、来源类型、record_id 标识记录，以内容和有效来源信息生成版本；只追加更新或移出当前引用的记录 | 仅重排或评分变化不重发；内容大小写改变也能识别 |
| 状态积累 | 直接追加所有快照会越来越长 | 默认累计 8 条更新，或基线之后增量累计达到 12 KiB，在下一次变化时生成 reset 基线；请求不再携带旧增量，原日志保留 | 在明确边界接受一次前缀变化，避免无上限累积 |
| 频繁压缩 | 主要依靠触发长度和最小收益 | 保留原有净缩短检查，新增至少 8 条普通对话/工具消息的间隔；接近上下文安全边界时绕过间隔 | 避免小幅变化就重建摘要；不为缓存牺牲上下文安全 |
| 可观测性 | 难以分清动态块还是历史先发生变化 | Trace 记录稳定前缀消息数、序列化字节数、首次变化组件、组件哈希和增量 revision；更新块成本另列 context_updates | 可进一步比较未缓存输入和耗时；字节数不冒充服务端缓存 token |

## 保住了什么

- 状态增量是 **assistant 层的不可信参考数据**，不是用户授权。真实用户要求仍来自对话，完成拦截仍读取 TaskProgress 与实际文件哈希。
- 文件改变后，验收证据失效、待验收项重新出现、工具重新开放；最终 JSON 不一致仍被拦截。原来合法的撤回与验收版本机制保留。
- 只在整组工具返回后追加增量；尚有未完成调用时不插入。状态消息不会让刚返回的大 read 内容立即被裁掉。
- 增量进入 append-only 会话和模型请求 Trace；重启恢复后可识别已经发送的状态。压缩丢掉旧基线时，由当前状态源补全，不能从旧摘要猜测。
- 内部状态不显示为聊天回复，也不作为新知识再次建立归档索引或进入长期整理的增量，避免自产自召回。
- 网络恢复复用原中断请求与现场，不因为增加状态日志重放已执行工具。
