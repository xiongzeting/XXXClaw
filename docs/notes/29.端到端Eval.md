# MiniClaw 端到端 Eval

## 先说结论

MiniClaw 的 Eval 已经不是“给模型一道题，再看最后一句像不像正确答案”，而是把真实任务拆成五个相互独立的判断维度：

```text
真实 CodingAssistant
  ├─ 结果 Outcome：事情到底做对没有
  ├─ 过程 Process：是否按正确链路执行
  ├─ 效率 Efficiency：用了多少 Token、钱和时间
  ├─ 安全 Safety：有没有越界或留下危险副作用
  └─ 可靠性 Reliability：重跑、故障和重启后是否仍然成立
          ↓
统一 Trace + 工作区前后快照
          ↓
确定性检查 / 可选独立 Judge
          ↓
Case 报告、失败聚类、基线对比、回归告警
```

完整入口是：

```powershell
python -m MiniClaw.evaluation.cli evals\full.json --env-file .env --jobs 4
```

`full.json` 组合 Smoke、历史失败回归和系统韧性三套 Suite，共 22 个端到端 Case。它还声明了必须覆盖的能力矩阵；缺少某个要求的维度或能力时，即使已有 Case 全部通过，完整运行仍会失败。

`--jobs 4` 会并行运行四个独立 Case；每个 Case/Attempt 使用独立工作区，因此不会共享文件副作用。单个 Case 内的多 Phase 仍保持顺序，以保留跨会话记忆、压缩和 Goal 恢复语义。

## Eval 真正执行了什么

每次 Attempt 都复制一份独立 Fixture，然后创建真实的 `CodingAssistant`。执行路径包括：

```text
Prompt
  → 项目指令加载
  → 长期记忆召回
  → AgentLoop
  → SSE 模型请求
  → Tool Executor
  → ApprovalGate
  → WorkspaceGuard / Docker
  → Goal Supervisor
  → Memory consolidation / Compaction
  → Trace
```

因此它不是模型自评，也不是只重放旧 JSON。文件修改、Docker 命令、审批拒绝、上下文归档、Goal 状态和取消都真实发生在隔离工作区中。

## 五个维度分别判断什么

### 1. Outcome：结果正确性

支持判断：

- 文件是否存在、不存在、内容相等、包含或匹配正则。
- 真实验证命令是否按期望退出码结束，并检查输出。
- 最终回答是否包含、不包含、精确等于、归一化相等或符合正则。
- 最终回答是否为满足字段约束的 JSON。
- Goal 是否到达预期状态。
- 无法用规则稳定判断的开放回答，可交给独立模型按 Rubric 评分。

Outcome 只回答“结果对不对”，不会强迫模型必须使用某个具体工具。某种工具使用方式如果只是偏好，会作为非必需 Process 检查，不会把正确结果误判成失败。

### 2. Process：执行过程

支持从 Trace 判断：

- 某类事件是否发生、发生次数是否达到最小值、最大值或精确值。
- 事件字段是否匹配，例如 Bash 是否真的来自 Docker、验证调用是否带 `goal_verification=true`。
- 多个事件是否按顺序出现，例如 `tool.call → compaction.started → compaction.completed`。
- Goal 是否创建、等待用户、恢复、验证和完成。
- 项目指令实际注入了多少来源。
- Memory 是否检索、注入、整理、写入事实或遇到冲突。
- L1 大工具输出、L2 旧工具结果、闭合历史归档和 L3 模型摘要是否真实发生。
- 审批请求、决定和执行状态是否一致。

### 3. Efficiency：效率与成本

支持统计和设置上下限：

- 输入、输出、缓存和总 Token。
- 总成本与独立 Judge 成本。
- Agent 主请求数和后台辅助请求数分账。
- Memory、Compaction 使用的 Token 分账。
- 模型错误、重试、降级次数。
- TTFT mean / p50 / p95。
- 完整模型延迟 mean / p50 / p95。
- Tool Call 总数、错误率、平均和 p95 延迟。
- 总运行时间和端到端墙钟时间。
- Cache Ratio。
- Compaction 次数、成功率及节省 Token。
- L1/L2 Artifact 和历史 Archive 的数量与体积。

主 Agent 请求与后台 Memory/Compaction/Judge 已分开统计。这样“答案只需四轮，但结束后又做了一次记忆整理”不会再被误判为 Agent 超预算；总 Token 和总成本仍然会覆盖所有请求。

### 4. Safety：安全与副作用

运行前后会对工作区文件做 SHA-256 快照，得到：

```text
created / modified / deleted
```

支持判断：

- 必须修改哪些路径。
- 只允许修改哪些路径。
- 禁止触碰哪些路径。
- 最多允许变化多少文件。
- 父目录逃逸是否被 WorkspaceGuard 阻止。
- `.env` 等敏感文件是否未泄露。
- Approval 的 allow / ask / deny、用户批准、拒绝和超时。
- Docker Runtime 是否启用、网络是否隔离。
- 取消后是否没有产生延迟副作用。

Eval 内部产生的 `.aster/**` Trace、Session 和 Artifact 不计入用户工作区副作用。

### 5. Reliability：稳定性与故障恢复

每个 Case 可以配置重复次数和最低通过率，并输出：

- `pass_rate`：实际重复运行的通过比例。
- `pass_at_k`：这批运行中是否至少成功一次。
- `pass_all`：是否每次都成功。
- `stable`：结果是否稳定地全成功或全失败。

此外，Eval 支持可控故障注入：

- 首次返回 429 或 5xx，检查自动重试。
- 首次网络断开，检查无可见输出时恢复。
- 主路由失败，检查 Provider/Model fallback。
- 在模型生成中按时间取消。
- 在指定 Tool 开始后取消，检查子进程或容器停止。
- 模拟审批批准、拒绝或超时。
- 多 Phase 共用持久化 Session，重建 Assistant 后恢复 Goal。

故障是从 Eval Driver 注入到真实执行边界，不需要在产品 Prompt 中增加某一道题的特殊规则。

## 22 个完整 Case 的组成

```text
Smoke（4）
  ├─ 编码修改 + Goal + Docker 真实验证
  ├─ AGENTS.md 项目指令
  ├─ 跨会话记忆写入和召回
  └─ Workspace 父目录逃逸

Regression（10）
  ├─ MemoryAgentBench 多跳记忆失败
  ├─ LongMemEval 偏好记忆失败
  ├─ 长工具证据综合
  ├─ Procedural Memory
  ├─ 动态状态 / 静态证据 / 拒答
  └─ Approval / 敏感文件 / Docker 网络隔离

Resilience（8）
  ├─ L1 + L2 + Archive + L3 完整压缩
  ├─ 429 重试
  ├─ 网络断开重试
  ├─ Provider/Model fallback
  ├─ Ask 审批通过
  ├─ 审批超时 Fail Closed
  ├─ Docker Bash 运行中取消
  └─ Assistant 重建后 Goal 恢复与恰好一次副作用
```

## 报告与回归告警

每次运行产生：

```text
output/
  ├─ summary.json
  ├─ report.json
  ├─ report.md
  └─ cases/<case>/attempt-xxx/
       ├─ workspace/
       └─ 真实 Session、Trace、Goal、Artifact
```

与 Baseline 对比时会告警：

- 总通过率下降至少 5 个百分点。
- 任一维度下降至少 5 个百分点。
- Token 增长超过 15%。
- 成本增长超过 20%。
- TTFT 或模型 p95 延迟增长超过 25%。
- Tool/Model 错误率恶化。
- 原来通过的 Case 变成失败。
- Baseline Case 消失。
- 完整 Suite 缺少要求的维度或能力。

## 面试时怎么讲

可以概括为：

> 我没有只用最终答案正确率评测 Agent，而是让 Eval 真实执行 CodingAssistant、工具、审批、Docker、Goal、Memory 和 Compaction，再从 Outcome、Process、Efficiency、Safety、Reliability 五个维度评分。历史 Benchmark 失败会沉淀为隔离 Fixture 回归 Case；系统级 Case还能注入 429、断网、审批超时、运行中取消和 Assistant 重启。报告会分账 Agent 与后台请求、比较工作区副作用，并对通过率、Token、成本和 p95 延迟做 Baseline 回归告警。

## 仍需诚实说明的边界

“覆盖完整”指核心工程维度和已声明能力都有可执行 Case，不代表穷举所有现实故障。当前没有模拟机器断电、文件系统损坏、Docker daemon 自身崩溃或外部服务发生不可逆副作用后的分布式事务恢复。这些属于更高成本的混沌工程，不是实习项目必须完成的门槛。
