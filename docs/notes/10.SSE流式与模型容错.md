# 10. SSE 流式传输与模型容错

## 1. 为什么旧实现不是真流式

旧版请求发送：

```json
{"stream": false}
```

服务端完成整个回答后，MiniClaw 才拿到 JSON，再把完整文本包装成一次 `text_delta`。AgentLoop 的事件接口虽然叫 `stream()`，网络层实际仍是阻塞整包响应。

现在请求使用：

```json
{
  "stream": true,
  "stream_options": {"include_usage": true}
}
```

底层使用异步 HTTP 连接逐行读取 `text/event-stream`，每个 `data:`事件到达后立即解析。

## 2. SSE 数据流

```text
HTTP POST /chat/completions
        ↓
响应 Content-Type: text/event-stream
        ↓
逐行读取 data: {...}
        ↓
SSEDecoder 合并多行 data
        ↓
StreamAccumulator
  ├─ content → 立即 text_delta
  ├─ tool_calls[index] → 分片缓存
  ├─ usage → TokenUsage
  └─ finish_reason / [DONE]
        ↓
AssistantReply + completed
```

如果响应不是 `text/event-stream`，客户端返回 `MODEL_STREAM_UNSUPPORTED`，不会重新退回伪流式模式。

## 3. 文本增量

假设服务端依次发送：

```text
data: {"choices":[{"delta":{"content":"Hel"}}]}

data: {"choices":[{"delta":{"content":"lo"}}]}
```

MiniClaw 会立即产生：

```text
ModelEvent(text_delta, "Hel")
ModelEvent(text_delta, "lo")
```

最终 `AssistantReply.content`仍为 `Hello`，因此实时 UI 和持久化上下文使用的是同一份结果。

## 4. Tool Call 参数拼接

OpenAI 流式协议会把函数名和 JSON 参数拆成多个片段：

```text
index=0 name="wr"  arguments="{\"path\":\"a"
index=0 name="ite" arguments=".txt\",\"content\":\"OK\"}"
```

客户端按 `tool_calls[index]`维护独立缓冲区：

```text
id        call_ + 1      → call_1
name      wr + ite       → write
arguments 两段字符串拼接 → JSON 解码
```

只有参数完整且解码结果是 JSON Object 时，才产生最终 `ToolInvocation`。不完整参数返回 `MODEL_TOOL_ARGUMENTS_INVALID`，不会执行工具。

## 5. 四种超时

| 超时 | 默认值 | 作用 |
|---|---:|---|
| Connect | 10 秒 | 建立连接并获得响应头 |
| First Token | 60 秒 | 从请求开始到第一个文本/推理/Tool 参数片段 |
| Idle | 30 秒 | 已开始生成后，相邻 SSE 数据之间的最长等待 |
| Total | 120 秒 | 单次模型传输尝试的完整墙钟时间 |

对应错误：

```text
MODEL_CONNECT_TIMEOUT
MODEL_FIRST_TOKEN_TIMEOUT
MODEL_IDLE_TIMEOUT
MODEL_TOTAL_TIMEOUT
```

当多个期限同时接近时，报告真正最先到达的期限。例如 Total 只剩 2 秒、Idle 还有 30 秒时，会报告 Total Timeout。

配置：

```text
MINICLAW_LLM_TOTAL_TIMEOUT=120
MINICLAW_LLM_CONNECT_TIMEOUT=10
MINICLAW_LLM_FIRST_TOKEN_TIMEOUT=60
MINICLAW_LLM_IDLE_TIMEOUT=30
```

旧变量 `MINICLAW_LLM_TIMEOUT`仍作为 Total Timeout 兼容别名。

## 6. Cancellation Token

每次 `AgentLoop.run()`创建一个 `CancellationToken`，并放入 `ModelRequest`：

```text
AgentLoop.cancel(reason)
        ↓
CancellationToken.cancel()
        ↓
正在等待响应头 / SSE 行 / Retry Backoff 的任务立即结束
        ↓
HTTP 流关闭
        ↓
AssistantReply(stop_reason="aborted")
        ↓
run.completed(status="cancelled", stop_reason="aborted")
```

飞书 `/cancel`会直接向当前会话的 Assistant 发送取消信号，不进入普通会话队列，因此能够中断正在生成的模型回答。Token 现在也贯穿 ToolExecutor、Host/Docker Runtime、Goal Judge 和 Compaction；完整设计见 `11.端到端取消与中断.md`。

## 7. 重试规则

自动重试的情况：

- HTTP `408 / 409 / 425 / 429`；
- HTTP `5xx`；
- DNS、连接失败、远端断开和协议断流；
- 首 Token、Idle 或 Total Timeout；
- 服务端通过 SSE 返回的临时错误。

指数退避：

```text
delay = min(max_delay, base_delay × 2^retry_index)
delay *= 1 ± jitter
```

默认：

```text
MINICLAW_LLM_MAX_RETRIES=2
MINICLAW_LLM_RETRY_BASE_SECONDS=0.5
MINICLAW_LLM_RETRY_MAX_SECONDS=8
MINICLAW_LLM_RETRY_JITTER_RATIO=0.2
```

服务端 `Retry-After`会参与延迟计算，但不会突破本地最大等待。

## 8. 为什么输出后不自动重试

如果已经向用户发送：

```text
正在修改登录模块……
```

此时连接断开，再从头重试可能导致：

- UI 出现重复文本；
- 模型生成不同 Tool Call；
- 同一个外部操作被计划两次；
- Trace 无法确定哪条输出属于哪次尝试。

因此规则是：

```text
尚未产生用户可见输出 → 可以重试或降级
已经产生 text_delta/tool_call → 失败，不自动重放
```

Tool Call 参数在完成前只存在客户端缓冲区，没有交给 AgentLoop，因此仅收到部分参数时仍可以安全重试。

## 9. Provider 与模型降级

降级路由必须显式配置：

```text
MINICLAW_LLM_FALLBACKS=primary:backup-model,deepseek:deepseek-chat
```

执行顺序：

```text
当前 provider/model
  → 当前路由内部重试耗尽
  → primary/backup-model
  → 该路由重试耗尽
  → deepseek/deepseek-chat
```

跨 Provider 路由必须配置对应的 Provider 专用密钥。例如 DeepSeek fallback 必须有：

```text
MINICLAW_DEEPSEEK_API_KEY=...
```

MiniClaw 不会因为发现一个通用 Key 就静默把请求发给另一个 Provider。这避免把项目上下文意外发送到未经用户授权的服务。

## 10. Trace 与成本统计

一次逻辑模型调用只产生一条：

```text
model.request
```

每次真实网络尝试另外产生：

```text
model.transport phase=attempt_started
model.transport phase=attempt_failed
model.transport phase=retry_scheduled
model.transport phase=fallback_selected
model.transport phase=attempt_succeeded
model.transport phase=cancelled
```

最终 `model.request`包含：

- 实际成功的 Provider 和模型；
- `attempts / retries / fallbacks`；
- 首 Token 延迟；
- 最终 Stop Reason；
- 最终成功响应的 Token 和成本。

失败的 429、5xx 或断线尝试不会再次生成 `model.request`，因此 Dashboard 不会把一个逻辑调用统计成多次调用，也不会重复累加最终响应成本。

## 11. 失败关闭原则

- Tool 参数无法拼成合法 JSON：不执行工具；
- 已有可见输出后断线：不自动重放；
- 所有路由失败：返回结构化模型错误；
- 用户取消：返回 `aborted`，不作为普通模型错误；
- Fallback 没有专用 API Key：启动配置阶段直接报错；
- Trace 写入失败不会反过来破坏模型请求。
