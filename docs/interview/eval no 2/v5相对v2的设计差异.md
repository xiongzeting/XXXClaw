# v5 相对 v2 的设计差异：只列源码中确实改变的部分

对照对象：两次六题实跑的 `efficiency-revision-v2/snapshot/src` 与 `efficiency-revision-v5/snapshot/src`。不是对照事后继续变化的工作区代码。共 21 个源文件不同、106 个相同；完整文件清单和逐文件差异已保存到 `.aster/evals/efficiency-revision-v5/design-diff/`。本次只分析，没有修改 Agent 实现、没有跑模型题。

**v5 最主要的变化是：记忆与检查点由前置整块注入变为尾部状态更新；工具历史增加累计预算和持久化请求视图；验收从模型自报通过升级为程序逐项比较，并增加需求版本、交付检查和暂停约束。召回算法本身没有更换。**

## 1. 记忆召回：算法不变，改变身份、去重和更新方式

### 1.1 同一个 Eval 对话不再每阶段换身份（v2→v3）

| v2 | v5 |
|---|---|
| `session_id = case.id + phase_id`。同一题共用一个对话文件，但 turn1、turn2 等得到不同身份 | `session_id = case.id + session_key`。shared 模式下，同题各阶段使用同一个身份 |
| 自动检索已有“排除当前会话的 episode/archive”过滤，但前阶段 ID 不等于当前 ID，会被当成其他会话 | 原有过滤能识别同一共享会话的前阶段历史，减少自己的历史又从长期记忆注入回来 |

改变的是 Eval 创建 CodingAssistant 时的身份参数，不是把所有独立会话合并。semantic 事实也没有被一刀切排除；显式记忆查找和原文回读仍有入口。

源码：[runner.py:380](D:/MIniClaw/.aster/evals/efficiency-revision-v5/snapshot/src/MiniClaw/evaluation/runner.py:380)。

### 1.2 当前对话已经包含的长文本，不再自动重复注入（v2→v3）

v2 会合并检索候选内部的重复内容，但没有这道“与当前对话对照”的过滤。

v5 在自动检索的候选融合前增加检查：统一空白后，候选长度至少 80 个字符，并且完整出现在某条当前消息内，则跳过。它是严格文本包含检查，不是另一个语义模型，也不是相似度达到某阈值就删除。

这一步位于各来源搜索之后，主要减少后续候选和注入，不能说它省去了所有底层检索计算。短文本、改写后的近义文本不一定去得掉；显式检索不套用这道自动过滤。

### 1.3 “记忆是否变化”的判断更接近内容版本（v3→v4）

| v2 | v5 |
|---|---|
| 指纹把内容转小写、压缩空白，同时包含全部 metadata | 指纹保留原内容，忽略显式列出的 score、BM25/vector 排名等统计字段 |
| 排名统计变化可能触发刷新；大小写变化反而可能被忽略 | 尽量避免把排序波动当成事实更新，同时保留代码、ID 的精确内容变化 |
| 动态合并新结果主要依赖来源和记录 ID | 新结果声明 `superseded_record_ids` 时，从合并候选中移除被替代记录 |

它不是“所有分数字段都永远不会影响刷新”的保证：过滤器明确排除了若干字段，而不是统一识别任意统计元数据。实际注入的状态记录还使用更小的 metadata 白名单，不携带检索排名。

### 1.4 新增内部状态消息不再反向写成长期记忆（v3→v4）

v5 新增了 `MiniClaw Context Update`，里面本来就是召回结果与任务状态。为防止“召回结果→生成新记忆→再次召回”，新增以下排除：

- 不作为 episode 的最后一条助手结论。
- 不作为蒸馏时的助手结论。
- 不进入归档搜索索引和稳定事实抽取。
- 不作为模型摘要的语义输入。
- 保留在原始会话和请求 Trace 中，但不显示成用户看到的聊天回复。

## 2. 请求组装：从每次改开头，变成在末尾追加变化（v3→v4）

v2 的主要顺序：

```text
system
当前任务检查点（user 角色）
当前召回记忆块（user 角色）
历史对话与工具结果
```

v5 的主要顺序：

```text
system
已经存在的历史对话、工具结果、历史状态更新
本次新增的状态更新（有变化才追加，assistant 角色）
```

**目的：**即使当前检查点多出一条错误，也尽量不改已经发过的长历史前缀。不是把历史发送给模型的成本变成零，而是争取服务商对相同前缀复用缓存。

### 2.1 新增 ContextJournal

当前状态按键组织：任务状态是 `task.*`；记忆键包含作用域、来源、记录 ID，避免不同会话的同名记录互相覆盖。每条记忆还包含内容版本哈希与有限来源信息。

| 情况 | v2 | v5 |
|---|---|---|
| 检查点/记忆没有变化 | 下一次仍组装完整的前置块 | 不追加新状态消息 |
| 某一项改变 | 重建整个前置块 | 追加该项的 `set` |
| 某一项不再有效 | 下一次前置块不再列它 | 追加明确的 `remove` |
| 更新记录越来越多 | 没有状态日志这一层 | 达到整合条件后追加 `reset` 全量状态，后续请求投影忽略旧状态更新 |

默认整合条件是已有 8 条状态更新，或此前增量消息累计约 12 KiB。**这是触发整合的条件，不是整个上下文或单条记忆的硬上限。**一次新的大更新也可能越过阈值；当前全量状态自身可以更大。

状态只在工具调用和对应返回完整之后追加，避免拆开工具协议。原始日志不删除旧更新，删除的是下一次请求中的旧投影。

### 2.2 角色与授权语义改变

v2 的任务检查点、召回块用 user 角色；v5 用带专门名称和标记的 assistant 内部消息，并标明它是参考数据，不是用户授权，最新用户要求优先。

这只是隔离数据与指令来源，不代表模型已经能自动理解所有授权语义。项目指令真正变更、完成状态导致工具定义改变、压缩发生时，前缀仍可能变化，不能宣称 system 和 tools 从此永远不变。

### 2.3 接近步数上限的提醒也移到末尾

v2 会把“只剩几步”的 system 提醒放到整个请求最前面；v5 追加到请求末尾。32 步上限没有提高。

## 3. 压缩记忆：改变触发间隔、历史地位和重复包装

### 3.1 成功压缩后，新增至少 8 条消息再考虑下一次（v3→v4）

v2 没有这道最小消息间隔。v5 成功压缩后计数清零；不足 8 条新消息且离模型硬上下文边界还有余量时，暂缓再次压缩。

这里是 **8 条消息，不是 8 轮用户对话或 8 次模型调用**：助手消息、工具返回都可能计入，内部状态更新不计入。接近模型窗口减预留量时允许越过间隔继续压缩；旧 legacy 策略不使用这道新间隔。

重启加载会话时也会恢复压缩后的消息计数，不仅靠当前进程内存。

### 3.2 压缩摘要从 system 角色降为 assistant 历史笔记（v3→v4）

| v2 | v5 |
|---|---|
| 摘要以 system 消息重新放回工作上下文 | 摘要以 assistant 消息放回 |
| 摘要模板有“Current User Request 是当前指令”一类措辞 | 明确说明摘要是历史证据，最新用户要求和有版本的验收状态优先 |

这针对的是旧摘要里“还需要检查”与当前验收已通过相冲突的问题。它没有自动逐句清除所有过期待办；改变了摘要的角色和解释方式，不能视作已经保证过期状态不会影响模型。

### 3.3 摘要不再不断套自己的旧模板（v2→v3，v3→v4继续调整）

v2 把完整 Previous Checkpoint 再套进新检查点。v5 加入 `_flatten_checkpoint`，去掉自己重复生成的若干标题和固定套话；业务文字、版本冲突、撤回内容和归档引用保留。

这不是对业务事实做新的语义去重，也没有新增一套“只修改几句话”的模型摘要算法。模型摘要仍会看到既有摘要与待归档内容，只是清理了模板并排除内部状态消息。

### 3.4 压缩切分与事实提取适配内部状态

v5 不把内部状态消息当成安全切分点、语义增量或事实提取来源；旧摘要也不会因为改成 assistant 角色而再次作为普通对话全文归档。

## 4. 工具历史：新增累计预算，再让裁剪结果保持稳定

这一部分改变的是“把哪些历史发给模型”，不是删除实际文件或原始会话，也不是替模型多调用一个工具。

### 4.1 从单条大文本裁剪，增加已完成工具的累计裁剪（v2→v3）

v2 已会把大工具结果、大参数落成可回读的引用。但每条只有几 KB 时，很多条历史可以一起变得很大。

v5 新增 `bound_tool_history`：统计已完成且未失败的工具调用参数与返回的累计 UTF-8 字节数。超过整合条件后，把较旧的完整调用/返回对存为 JSON artifact，把其中能缩短的字符串换成引用。

保护未完成调用、已标记失败的调用、刚返回的结果和最近两组已完成调用。受保护内容或很短的字段不会被强行删掉，因此预算可能仍有 excess，不是无条件裁到一个死值。

### 4.2 新增上下两道阈值（v4→v5）

低水位的实现公式是：

```text
min(16,384, max(4,096, target_tokens × 2)) 字节
```

取值为 4–16 KiB。这是内部启发式字节预算，不能理解成用 tokenizer 精确换算。

已有可复用视图时，高水位为低水位的两倍，即 8–32 KiB；超过高水位后批量尝试归档到低水位。新的阶段/不能复用旧视图时直接按低水位整合。这样避免每新增一条记录就裁掉另一小块旧内容。

### 4.3 新增 StableRequestView（v4→v5）

| v2 | v5 |
|---|---|
| 每次从原始历史重新生成待发送副本 | 保存已经发送过的裁剪视图 |
| 旧工具结果可能在后续请求中不断换成不同的引用 | 同一用户阶段且原始历史前缀未变时，复用旧片段，只处理新后缀 |
| 没有持久化的请求视图文件 | 保存 `.request-view.json`，用原始消息哈希和配置确认能否重用，重启可加载 |

新用户消息、历史压缩、状态 reset 导致投影变化、配置变化等会使旧视图不再匹配；到高水位也允许批量重建。它追求阶段内稳定，不是绝对 append-only。已有读快照投影仍在后续运行，因此不能保证所有来源都永远不改前缀。

## 5. 工具调用与验收：由“提交通过结论”改为“登记要求并比较证据”

### 5.1 v2 主要相信模型提交的 passed 和文字证据

v2 的 `bash(task_verification=true)` 要求程序输出：

```json
{"task_checks":[{"criterion_id":"total","version":1,"passed":true,"evidence":"实际值与预期一致","artifacts":["result.json"]}]}
```

Runtime 会检查命令状态、编号、版本、字段类型及文件哈希，但不会解析文字里的算式并重新比较金额。`passed=true` 主要来自模型编写的程序声明。

### 5.2 v5 增加逐项比较引擎（v2→v3）

新增 behavior/data/recovery 三类验收项目，以及要求覆盖的 `check_ids`。比较支持：

- actual/expected 的严格 JSON 类型与值相等；布尔 true 不等同整数 1。
- 数组成员比较保留重复次数，不能用集合去重掩盖多余记录。
- 从已授权 JSON 文件的指定路径读取实际值；文件最大 1 MiB，并关联内容哈希。
- required check ID 覆盖检查；缺项、重复项、非法指针不能通过。
- recovery 类型要求提交提交前、提交中、响应丢失、重试四类场景证据。

**边界：这些是已登记要求的机械核对，不会自动发现所有业务要求。behavior 若未登记 check_ids，也不等于程序会补齐所有比较。自写 expected 和 injected/observed 声明仍不是独立的正确性证明。**

### 5.3 v5 新增推荐接口 bash.verification（v4→v5）

现在将“实际观测输出”和“怎样比较”分开：

```text
验证程序输出：{"observations":{"net":2300}}
工具参数绑定：criterion_id=total，check_id=net，pointer=/net，expected=2300
另填：expected_source 和被测 artifacts
```

这只是协议形状示例，实际 net 必须由程序计算。

流程变成：

```text
校验工具参数及权限
→ 命令执行前校验验收计划，绑定当前需求版本
→ 执行命令
→ 收集一个 observations JSON 记录
→ 根据绑定取实际值，与 expected 做严格比较
→ 关联调用编号、命令哈希、被测文件哈希
→ 按项目保存结果，返回待办与失败细节
```

模型可以省去手填需求版本与 passed，但仍要填写已有 criterion/check ID、路径、expected、来源、文件列表，也仍要产生正确的 JSON 外壳。**“修正字段绑定后只重解析旧输出、不重新执行命令”是下一步建议，v5 尚未实现。**

当前实跑暴露的 `/observations/net` 与 `/net` 混淆正发生在这里：Runtime 先取出 observations 对象，因此指针应相对这个对象。v5 没有自动容错这两种写法。

### 5.4 输出解析和旧协议兼容改变

| v2 | v5 |
|---|---|
| 直接对整个 stdout 做 json.loads | stdout/stderr 中寻找唯一完整的目标 JSON 记录，可有单独日志行 |
| evidence 只接受非空字符串 | 也接受非空 JSON 对象 |
| 没有 comparisons 的兼容迁移 | 旧比较数据在根部或 evidence 内部时，只有能唯一映射到要求才规范化，并保留迁移记录 |

## 6. 任务检查点：编号、版本、证据失效与交付状态更严格

### 6.1 编号和版本不再完全交给模型手管（主要 v4→v5）

v2 要求新 criterion 显式带 ID、description、version；只要版本不下降，模型可以更新描述或撤回要求。规则主要写在提示里。

v5 新项目可以省略 ID/version，Runtime 分配；完全相同的描述和类别可复用已有 ID，歧义则要求指定。它不是语义同义词匹配。已有项目省略 kind/check_ids 时保留原值；不能把已有比较 ID 无意升级成新的父项目。

修改实质要求、检查列表或撤回项目，必须提交当前 `requirement_revision`，且它来自比原项目更新的真实用户消息。版本由 Runtime 在有效变更时加一；只改显示文字用 label。

真实用户输入入口会增加 user_revision 并保存用户文本哈希；Goal 自动继续、网络重试、恢复按钮不增加用户需求版本。这个检查能阻止同一阶段随意换需求，**不能证明最新那句自然语言确实授权撤回某个具体要求**。

此外，任务已经 completed 后，v5 在新的用户输入入口就重开任务状态；不是自动永久保留上个已完成任务的全部验收证明。跨用户阶段的证据复用仍有限。

### 6.2 同批验收按项目保存（v4→v5）

v2 某一条解析错误可能把整个 verified 集合清空。v5 在顶层记录可解析、项目可识别的前提下逐项保存：A 合法、B 错误时，保留 A；B 进入自己的错误状态。真正重验 B 时旧 B 证明被清掉，不能借旧成功覆盖新失败。

整份 JSON 都不可解析时仍无法凭空提取 A；“逐项独立”不是忽略所有结构错误。

### 6.3 未执行的工具不再让旧证明失效（v4→v5）

执行器新增 `not_started`：参数/前置检查拒绝，或结构化验收计划在执行前拒绝时标记。TaskProgress 遇到它直接跳过文件修改失效逻辑。

v2 也有文件变动使证明失效，但不知道有些命令其实完全没开始，可能作保守失效。v5 区分“命令根本没执行”与“执行后失败”。验收路径也从手写 `/workspace/` 转换改为复用 Runtime 的 WorkspaceGuard。

### 6.4 精简注入状态，保留错误细节（v2→v3，v4→v5补齐）

v2 将除恢复消息、变更历史外的大部分状态序列化给模型，可能带很长的 evidence、文件哈希和旧总结。

v5 通过 snapshot 仅注入当前要求、版本、待办、已验证文件名、失败检查和有限 actual/expected、next_action、delivery_state 等。完整证据仍在磁盘与 Trace。失败观察每个要求最多呈现 8 项，单项超长值会缩写。

下一步优先提示协议错误，再提示实际比较失败，再看剩余工作；不会只显示泛泛的“尚未验收”。

## 7. 完成和恢复：验收通过后收敛，验收卡住时暂停

### 7.1 全部已登记要求通过后，临时不给模型任何工具（v2→v3）

条件包括：本轮确实更新了任务状态、没有正在运行的显式 Goal、有要求清单、待办为空、无验收错误、所有要求证据仍有效。

v2 在这种情况下仍提供完整工具表；v5 返回空工具列表，促使模型给出最终交付。如果模型仍发起本次请求未提供的工具，循环层会拒绝执行。

这是新增的收尾限制。**“没有显式 Goal 时隐藏 goal_complete”在 v2 已存在，不是 v5 新改动。**

### 7.2 最后回答也可以按已验证字段检查（v2→v3）

v2 拦截器主要看待办和验收状态，不把最终答案字段再与已验证数据比对。

v5 的 comparisons 可登记 `final_pointer`，最终 JSON 对应字段必须匹配；不匹配则拦回重做，恢复工具可用性。v2 已有完成守卫的回复缓冲，此次是在输出前增加字段一致性守卫，不是首次加入缓冲。

**没有登记 final_pointer 的字段不会被自动检查。**因此不能把这个能力写成“v5 所有最终答案都已逐字段验证”；依赖锁的 V1 编号错误仍可能漏过。

### 7.3 结束时再核对一次待验收状态（v2→v3）

v2 的 finish 对非 error/aborted/预算耗尽的结束基本会把有状态的任务记成 completed。v5 在结束时再次调用完成拦截：仍有待验收项就保存恢复消息并标为暂停，而不是成功。

### 7.4 新增三次同错提前暂停（v4→v5）

v2 主要靠硬步数上限结束重复尝试；v5 根据错误集合与 workspace_epoch 生成签名，同一签名连续出现 3 次就 `verification_stalled` 暂停。resume 清掉这次重试计数，但保留要求和进度，也不凭空产生新用户授权。

它不是“每题只允许 3 次工具错误”。错误内容变化或工作区修改可能重置签名，因此两种错误来回切换仍可能耗到 32 步。本轮脱敏触发了提前暂停，发票和运费仍有步数耗尽。

### 7.5 网络恢复更强调复用同一请求快照（v3→v4）

v2 已有局部请求重试与副作用不重放；v5 在恢复未完成请求时，提前识别 pending_request，跳过再次刷新动态记忆/状态和组装新消息，直接复用保存的请求。

这次没有增加无限重试，也没有整体重跑整题或提高网络重试次数；核心恢复策略文件未改变。改的是恢复入口的请求组装顺序，避免“重试的是旧请求，却先把新状态写入了对话”。

## 8. Eval 和观测：新增证据，不等于新增通用事务能力

### 8.1 新增通用提交故障探针（v2→v3）

新增 `evaluation/faults.py`。给它一个能创建隔离状态的 factory，它先测出正常操作经过哪些 os.replace/os.rename 提交点，再逐点在提交前/后注入故障并重试同一个业务请求，检查状态是否部分提交、重试是否重复生效。

它是可被测试调用的工具，不是任意 bash 自动获得事务能力，也不是断电、并发写入或所有数据库提交方式的模拟器。六题原有 oracle 脚本没有因为这个模块出现就自动换成新判定器。

### 8.2 新增请求前缀诊断（v3→v4）

记录前后请求最先变化的是 model、tools、system、history 或状态更新，记录完全相同的前缀消息数和序列化字节数。它测的是客户端消息相等，不是服务商缓存 token 数。

### 8.3 新增缺失用量的识别及非打分观察项（v3→v4）

模型适配层新增 `usage_reported` 与 `cache_usage_reported`，区分“明确报告缓存为 0”和“根本没给缓存统计”。Eval 只有用量、缓存数据和费率完整时才给出估算费用，否则标为 unavailable，避免把缺失数据当免费。

新增 report_only 指标通路：可展示缓存命中率和估算费用，但不计入五维分数。Trace 增加 context_updates 估算桶，避免把新状态消息完全混入普通对话。

### 8.4 验收协议错误现在也标记为工具 error（v4→v5）

v2 常把协议错误附在反馈文本中，工具状态仍成功；v5 将它同时标成工具 error。所以原始工具错误计数 13→61 有标记口径变化。两版统一按“工具 error 或携带验收错误”取并集是 21→61，才更适合比较错误事件数量。

## 9. 与 v2 相比，不能误算为新设计的内容

只作边界校正：BM25/BGE/RRF/重排核心、记忆配置与四层模块、原有 query 精简及渲染预算、Docker/WorkspaceGuard 的隔离引擎、allow/ask/deny 审批体系、grep/read/write/edit 实现、显式 Goal 的基本监督、网络局部重试都不是本次重新实现。安全相关增量主要是历史角色、需求修订来源、验收计划预检与复用路径防护。

新记忆状态用 JSON 重包装后还有键名、内容版本、来源和增量日志的开销；原来记忆渲染预算并不是对这些新增字节的精确统一 token 上限。这也是“状态追加后缓存更好”不能直接等同“请求总体更小”的原因之一。

## 10. 设计变化与实测结果分开看

这轮结果支持“配置迁移的请求与成本减少、整体未缓存输入减少”；不支持“所有这些设计都已达到预期”。相对 v2：结果 2/6→4/6，未缓存输入下降 22.2%，总 tokens 却增加 27.3%，验收错误反馈 8→52。

尚未在 v5 实现的后续方案包括：错误绑定无副作用重解析、按 check_id 减少手填路径、识别交替协议错误、跨新用户阶段自动按要求差异复用证明。不得把这些建议当成现有功能。
