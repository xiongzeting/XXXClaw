# MiniClaw Benchmark：结果、过程、效率三轴设计与外部数据集选型

## 1. 目标

MiniClaw Benchmark 不再只回答“成功还是失败”，而是同时回答三个问题：

```text
结果 Result：最终完成了多少，完成得多正确？
过程 Process：模型是否按正确方式理解、定位、修改、验证和恢复？
效率 Efficiency：为得到这些结果消耗了多少时间、Token、费用和无效操作？
```

每个任务输出连续的 `R / P / E` 三个 0–100 分，完整通过率只作为一个附加指标。排行榜必须展示三轴分数、总体分、分位数和置信区间，不能只显示一个成功率。

## 2. 为什么以前容易得到接近 0% 或 100%

常见原因包括：

- 任务数量太少；
- 所有任务难度相近；
- 每个任务只有“全部测试通过”和“没有全部通过”两个结果；
- 基础设施错误也被算成模型失败；
- 一个任务只运行一次，没有估计随机性；
- 对当前模型而言，任务已经过易或过难；
- 只计算最终状态，不计算部分测试、回归保护和中间产物；
- 便宜地立即失败可能在“效率榜”上看起来很好。

新设计通过连续结果分、难度校准、重复试验和条件效率分解决这些问题。

## 3. 单任务评分

### 3.1 Result：结果分，0–100

仓库修改类任务建议按下面的比例评分：

| 指标 | 权重 | 说明 |
|---|---:|---|
| Patch 可应用、项目可构建 | 10 | 修改能落盘、语法有效、依赖和构建入口未损坏 |
| Fail-to-Pass 测试修复率 | 35 | 原本失败、应由本任务修复的测试中实际通过的比例 |
| Pass-to-Pass 回归保持率 | 20 | 原本正常的测试仍然通过的比例 |
| 隐藏验收条件覆盖率 | 15 | 安全、边界、异常和规格测试的通过比例 |
| 修改范围正确性 | 10 | 是否改到了正确文件，是否出现无关重写和大范围 churn |
| 任务特定产物完整度 | 10 | 文档、配置、迁移、输出文件或结构化结果是否齐全 |

建议公式：

```text
R = 10·Build
  + 35·F2P_ratio
  + 20·P2P_ratio
  + 15·Acceptance_ratio
  + 10·Scope_quality
  + 10·Artifact_completeness
```

其中每个子项先归一化到 0–1。官方 benchmark 的 `resolved` 仍保留，但只表示 `R ≥ 95` 且关键测试全部通过。

对于 Terminal-Bench，应解析 pytest CTRF 或其他 verifier 明细，使用“通过断言数 / 总断言数”形成连续分数；官方 `reward.txt` 的 0/1 只用于保持对外兼容。

### 3.2 Process：过程分，0–100

过程分主要从统一 Trace 自动计算：

| 指标 | 权重 | 可观察证据 |
|---|---:|---|
| 项目指令遵守 | 15 | `instructions.injected`、作用域、最终修改是否违反规则 |
| 问题定位质量 | 15 | 是否先搜索/读取相关代码，命中文件比例，是否遗漏关键文件 |
| Tool Call 有效率 | 10 | 参数是否合法，未知工具、重复失败调用和空操作比例 |
| 修改策略质量 | 10 | 精确 edit 与无必要整文件覆盖、重复撤销、Patch churn |
| 验证闭环 | 15 | 是否运行相关测试，修改后是否重新验证，验证是否新鲜 |
| 失败恢复能力 | 10 | 命令失败、模型重试、局部规则刷新后是否调整策略 |
| 安全与审批 | 10 | 是否绕过 deny、是否等待 ask、取消后是否停止副作用 |
| Goal 与上下文管理 | 10 | Goal 状态、证据、Compaction 时机和恢复是否正确 |
| Trace 完整性 | 5 | 模型、工具、审批、指令、Goal、Compaction 事件是否闭合 |

```text
P = Σ weight_i · process_metric_i
```

过程分不能依赖模型自述“我已经检查过”，只使用工具执行、文件差异、测试日志和 Trace 事件作为证据。

### 3.3 Efficiency：效率分，0–100

效率必须在结果条件下解释。立即失败虽然便宜，但不能成为高效任务。

| 指标 | 权重 | 说明 |
|---|---:|---|
| 端到端耗时 | 20 | 从 run.started 到 run.completed，排除已确认的基础设施等待 |
| 非缓存输入 Token | 15 | 真正新增的模型上下文消耗 |
| 缓存输入利用 | 5 | 缓存命中和重复上下文复用 |
| 输出 Token | 10 | 推理和回答长度成本 |
| 实际费用 | 15 | Trace 中不重复统计重试的真实 USD |
| 模型请求与轮数 | 10 | 完成同样结果所需的模型边界次数 |
| Tool Call 数量 | 10 | 搜索、读取、编辑、验证调用数量 |
| 浪费与重试 | 10 | 重复读取、相同失败命令、无变化 edit、无效 transport 重试 |
| Patch churn | 5 | 总写入量相对最终有效 diff 的比例 |

每个“越小越好”的指标使用对数归一化，防止一个极端长任务支配全部分数：

```text
score(x; target, cap)
  = 100 · clip(log(cap / x) / log(cap / target), 0, 1)
```

- `target`：参考实现或中位模型的合理消耗；
- `cap`：超过后该项记 0 分的预算上限；
- 小于 target 的值记满分，不因极小差异无限加分。

效率榜同时报告：

```text
cost_per_result_point
seconds_per_result_point
tokens_per_result_point
```

当 `R < 10` 时，这三个比率标记为 `not-useful`，不参加效率排名。

## 4. 总体分不能用简单平均

建议使用加权几何平均：

```text
Overall = 100
        · (R / 100)^0.55
        · (P / 100)^0.25
        · (E / 100)^0.20
```

结果占主要权重，而且任何一轴严重失衡都会拉低总分。这样可以避免：

- 便宜但完全失败的 Agent 得到高分；
- 暴力消耗大量 Token 的 Agent 只靠结果进入第一名；
- 最终碰巧通过但过程危险、不可复现的轨迹被当成优秀实现。

报告必须始终同时展示 `R / P / E / Overall`，不能只展示 Overall。

## 5. 避免成功率饱和的任务选择机制

### 5.1 先做 Pilot，不直接冻结全量题目

每个候选任务使用至少三个参考配置试跑：

```text
低成本配置：luna + 低/中 reasoning
默认配置：luna + 当前 MiniClaw 默认参数
高能力配置：terra/sol 或更高 reasoning
```

每个配置至少运行 2 次。根据连续 Result 分和完整解决率估计任务难度。

### 5.2 Core 集只保留有区分度的题目

以默认参考配置的完整解决概率 `p` 为例：

| 分组 | p 区间 | Core 占比 |
|---|---:|---:|
| Easy | 0.65–0.85 | 20% |
| Medium | 0.35–0.65 | 50% |
| Hard | 0.15–0.35 | 30% |

`p > 0.95` 或 `p < 0.05` 的任务不进入主要排名，只保留少量作为 ceiling/floor probe。最终目标是默认 MiniClaw 的完整解决率约 40%–70%，平均 Result 分约 50–75，而不是追求一个看起来更漂亮的数字。

### 5.3 固定锚点与滚动新题并存

```text
30% Anchor：长期固定，用于版本回归
50% Calibrated Core：按难度稳定分层
20% Fresh/Adversarial：新题、真实失败和安全边界题
```

Fresh 部分每月或每个大版本轮换，减少过拟合和训练数据污染。

### 5.4 每题重复运行

- 日常 PR 回归：每题 1 次，使用固定种子和低成本子集；
- 周期 Benchmark：每题 3 次；
- 正式对外结果：每题 5 次，Terminal-Bench 2.1 官方也是 5 trials/task。

报告 `pass@1`、`pass@3`、均值、标准差、Bootstrap 95% CI，不能只报告最好一次。

## 6. 推荐的 MiniClaw Benchmark 组成

### Tier A：MiniClaw 本地诊断集

建议先建立 40–60 个小型、完全离线的仓库任务，专门覆盖 MiniClaw 自己的能力边界：

- read/grep 定位；
- 精确 edit 与多文件 write；
- AGENTS.md 层级覆盖和首次写入保护；
- Tool Call 参数错误恢复；
- Bash 失败后诊断；
- 审批 allow/ask/deny；
- 取消正在运行的进程；
- Goal 验证门；
- 80k/100k Compaction；
- 长期记忆冲突；
- Direct/Snapshot 隔离；
- SSE 重试和 Provider fallback；
- Trace 完整性。

本地集提供最细的过程诊断，但不能替代外部 benchmark。

### Tier B：外部 Coding Core

从仓库级 benchmark 中按语言、类别和难度抽取 30–60 个任务，作为主要结果集。

### Tier C：Terminal/Runtime Challenge

抽取 15–30 个 Terminal-Bench 2.1 任务，测 Bash、容器、长链操作、异常恢复、安全和效率。

### Tier D：Fresh Holdout

使用 SWE-bench-Live 新月份任务或真实失败 Trace 生成的 Eval Case，防止只优化固定老题。

## 7. 外部 Benchmark 调研结果

### 7.1 Terminal-Bench 2.1——当前最建议先下载

官方地址：https://github.com/harbor-framework/terminal-bench-2-1

关键事实：

- 89 个真实、复杂的容器终端任务；
- Apache-2.0；
- 使用 Harbor 执行，支持 Agent Adapter；
- 每个任务有 `task.toml`、难度、类别、专家/初级开发者耗时、资源和超时配置；
- 任务包括软件工程、异步调试、安全修复、构建、科学计算等；
- 官方 verifier 多数最终仍输出 0/1，但测试内部有多个 pytest 断言，可以由 MiniClaw Benchmark 解析为部分得分；
- Harbor 原生记录输入 Token、缓存 Token、输出 Token、成本、执行时长和轨迹；
- 官方正式榜要求每题 5 次。

最有参考价值的是：官方 2026-07-11 结果中，`gpt-5.6-luna + Codex + max` 为：

```text
Accuracy: 75.73% ± 1.32%
Trials: 445，也就是 89 × 5
pass@2: 83.48%
pass@3: 86.40%
pass@5: 88.76%
平均单次耗时: 457.3 秒
总费用: 241.45 USD
```

这证明任务对当前默认模型仍有区分度，没有接近 0% 或 100%。MiniClaw 的脚手架不同，不能直接把上述分数当成预期成绩，但非常适合用来比较 MiniClaw 与成熟 Agent 的过程和效率差距。

缺点：

- 不全是传统仓库 Issue 修复；
- 单任务最长 15 分钟，镜像和依赖可能较大；
- MiniClaw 需要实现 Harbor Agent Adapter；
- 官方奖励多数是二元，需要额外解析测试明细才能形成连续 Result。

### 7.2 SWE-PolyBench Verified——最适合做仓库编码主结果集

官方地址：https://github.com/amazon-science/SWE-PolyBench

关键事实：

- 完整集 2,110 个真实 Issue；
- PB500 为 500 个分层样本；
- Verified 为 382 个任务；
- Java 72、JavaScript 100、Python 113、TypeScript 100；
- Bug / Feature / Refactoring 类型可分层；
- Verified 附带人工/模型注释，包括 Issue 描述质量、代码修改质量、测试质量、任务难度和类别；
- 提供预构建 GHCR Docker 镜像；
- 实例结果包含通过测试和失败测试列表；
- 支持文件检索指标和 node retrieval 指标；
- MIT。

它特别适合 MiniClaw，因为可以直接按 `task_difficulty_choice` 选中等题，按语言和任务类别平衡，天然比随机抽 SWE-bench 更容易把成功率控制在有区分度的范围。

缺点：

- GitHub 仓库约 175 MB，真正占空间的是按实例拉取的镜像；
- README 建议 16 核、64 GB 内存时开 10–12 线程；当前机器只能低并发顺序跑；
- 数据集托管在 Hugging Face；本次从当前网络访问 Hugging Face API 超时，因此现在不应直接依赖全量自动下载；
- 仍需为 MiniClaw 做“任务容器 → Agent → Patch → 官方 evaluator”的适配。

### 7.3 SWE-bench Verified——对外可比锚点，不适合当前立刻下载全量

官方地址：https://github.com/SWE-bench/SWE-bench

关键事实：

- 500 个由工程师确认可解的 Python Issue；
- MIT；
- Docker 评测成熟，行业可比性最好；
- 报告可区分 patch apply、基础设施失败、unresolved 和 resolved；
- 测试日志可以进一步计算 F2P/P2P 部分分数。

官方明确建议：

```text
至少 120 GB 空闲磁盘
16 GB RAM
8 CPU cores
x86_64
```

当前机器磁盘条件不满足，因此只适合作为未来扩容后的 Anchor，不建议现在全量下载镜像。

### 7.4 SWE-bench-Live / MultiLang——最适合 Fresh Holdout

官方地址：https://github.com/microsoft/SWE-bench-Live

关键事实：

- 自动持续更新；
- Python、C/C++、C#、Java、TS/JS、Go、Rust；
- 2026-08 的 MultiLang 已达到 1,077 个任务；
- 另有 Windows 专项任务，能直接测 PowerShell 和 Windows 行为；
- 支持按月份选择任务，适合污染控制；
- MIT。

缺点：

- 官方建议每个 gold patch 运行 3 次过滤环境波动；
- 普通实例约需 4 CPU、16 GB RAM，部分大型 C++ 仓库可能需要约 50 GB RAM；
- 当前机器不适合全量或高并发执行；
- 应作为每月少量 Fresh 题，而不是第一套下载的主 Benchmark。

### 7.5 SWE-smith——最适合生成可调难度题，不是第一套正式 Benchmark

官方地址：https://github.com/SWE-bench/SWE-smith

关键事实：

- 52k 任务；
- 250+ 仓库环境；
- 可以把任意 GitHub 仓库变成 SWE-gym，并持续合成新题；
- MIT；
- 特别适合从大量候选中筛选默认 MiniClaw 通过率位于 15%–85% 的任务。

缺点：

- 官方明确只支持/测试 Ubuntu 22.04，不计划支持 Windows 或 macOS；
- 更偏数据生成与训练基础设施；
- 需要大量 Docker 环境和筛选成本。

适合以后在独立 Linux 机器上构建动态题库。

### 7.6 RE-Bench——连续评分很好，但方向过重

官方地址：https://github.com/METR/RE-Bench

它包含 7 个长时 AI R&D 任务，很多任务原生就是连续分数，例如性能、loss、胜率和运行时间，非常符合“不只看 0/1”的理念。

但任务涉及模型训练、Triton/GPU Kernel、缩放律和 AI 研究工程，成本高、耗时长、部分需要 GPU，不适合作为 MiniClaw 的日常编码基准。可以未来选 1–2 个作为 Long-Horizon Challenge。

### 7.7 BigCodeBench-Hard——便宜，但不适合作为 Agent 主榜

官方地址：https://github.com/bigcode-project/bigcodebench

- Hard 子集 148 题；
- 执行快；
- Apache-2.0；
- 但主要是 HumanEval 风格的函数级代码生成；
- 不需要真实仓库探索，也很少使用 read/grep/edit/bash、Goal、审批、记忆或 Compaction；
- 仓库已经 archived。

它只能测 LLM 层基础编码能力，不能代表 MiniClaw Agent 能力。

## 8. 当前机器适配结论

本机实测：

```text
RAM: 15.7 GB
逻辑 CPU: 20
C: 剩余 8.3 GB
D: 剩余 22.8 GB
Docker Desktop Linux Engine: 可用
Docker Images: 36.51 GB，其中 20.63 GB 可回收
Docker Build Cache: 29.4 GB，其中 14.89 GB 可回收
```

本次没有执行任何清理操作。

结论：

- 可以下载 Benchmark 的 GitHub 代码和元数据；
- 不适合预拉 SWE-bench 全量镜像；
- Terminal-Bench 和 SWE-PolyBench 应按单任务按需拉镜像、低并发运行并及时清理单个任务镜像；
- 在正式运行前，最好把 Docker 数据盘迁移到空间更大的磁盘，或者先安全释放至少 60–120 GB；
- 15.7 GB RAM 适合单并发，部分大任务仍会 OOM，应在 Pilot 中标记为 infrastructure-invalid，而不是模型失败。

## 9. 下载建议

### 如果现在只选一个

选择：**Terminal-Bench 2.1**。

理由：

1. GitHub 可直接访问，不依赖本次连接失败的 Hugging Face；
2. 任务数量 89，规模适中；
3. 与默认模型 `gpt-5.6-luna` 有官方 75.7% 参考点；
4. 原生记录 Token、缓存、成本、时间、轨迹；
5. 最适合验证 MiniClaw 的 Runtime、Bash、工具循环、取消、安全和恢复；
6. 通过解析 verifier 子测试，可以把官方二元奖励升级成连续 Result。

第一阶段只下载代码和任务定义，不预拉全部镜像。随后先适配 8–12 个 software-engineering 任务，跑通 MiniClaw → Harbor → Trace → 三轴评分闭环。

### 第二个下载

选择：**SWE-PolyBench Verified**。

它作为仓库 Issue 修复主结果集更合适。等 Hugging Face 网络恢复后，先选择 24 个任务：

```text
Python / JavaScript / TypeScript / Java 各 6 个
Quick / Complex / Hard 分层
Bug / Feature / Refactoring 平衡
```

Pilot 后只保留默认 MiniClaw 完整解决概率在 15%–85% 的任务。

### 暂时不要下载

- SWE-bench Verified 全量镜像：磁盘不足；
- SWE-bench-Live 全量：内存、磁盘和环境波动成本过高；
- SWE-smith 全量环境：Windows 不受支持，规模过大；
- RE-Bench：需要长时算力和部分 GPU；
- BigCodeBench：不能充分测 Agent。

## 10. 推荐实施顺序

```text
1. MiniClaw Benchmark 通用数据模型与 R/P/E 评分器
2. 从现有 Trace 计算 Process 和 Efficiency
3. Harbor Agent Adapter
4. Terminal-Bench 2.1 的 8–12 题 Pilot
5. 难度校准，扩到 24–30 题 Core
6. SWE-PolyBench Verified Adapter
7. 四语言 24 题 Pilot
8. 固定 Anchor + Calibrated Core + Fresh Trace Case
9. Dashboard 展示分布、置信区间和 Pareto 前沿
```

Dashboard 至少展示：

- R/P/E 雷达图；
- 每题连续 Result 热力图；
- 难度分桶通过率；
- Token–Result、Cost–Result、Latency–Result 散点图；
- Pareto frontier；
- 失败阶段漏斗；
- Tool Call 重复率；
- Prompt/模型/工具配置对比；
- 版本回归及 Bootstrap 95% CI。
