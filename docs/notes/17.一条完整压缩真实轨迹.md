## 2. 阶段零：对象初始化时发生了什么

Benchmark 创建：

```python
MemoryManager(
    workspace=case_dir,
    session_path=case_dir / "transcript.jsonl",
    session_id="d6233ab6",
    ...
)
```

此时主要对象关系是：

```text
MemoryManager
├─ WorkingContext
│  └─ transcript.jsonl
├─ ContextArtifactStore
│  └─ .aster/context-artifacts/d6233ab6/
├─ ArchiveMemoryIndex
│  └─ .aster/memory/archive-index.jsonl
├─ SemanticMemoryStore
│  └─ .aster/memory/MEMORY.md
├─ EpisodicMemoryStore
│  └─ .aster/memory/episodes/
└─ ProceduralMemoryStore
   └─ .aster/skills/
```

### 2.1 初始化后立即存在什么

Semantic Store 会确保下面的文件存在：

```text
cases/d6233ab6/.aster/memory/MEMORY.md
```

这条真实 Case 中最终大小为：

```text
319 Bytes
```

内容只是空的托管 Semantic Memory 结构。因为这条历史中没有符合明确“记住：...”格式的候选，后续：

```text
candidates = 0
remembered = 0
duplicates = 0
conflicts = 0
rejected = 0
```

### 2.2 此时还不存在什么

Artifact Store 和 Archive Index 都是惰性写入：

```text
.aster/context-artifacts/d6233ab6/
    第一次真正保存 Artifact 时才创建文件

.aster/memory/archive-index.jsonl
    第一次追加 Archive Record 时才产生内容
```

### 2.3 transcript.jsonl 如何产生

每来一条历史消息，Benchmark 执行：

```python
messages.append(message)
manager.append(message)
```

`manager.append()` 会调用：

```python
WorkingContext.append_message(message)
```

然后在 `transcript.jsonl` 追加一行：

```json
{
  "type": "message",
  "id": "一个随机 message id",
  "message": {
    "role": "user 或 assistant",
    "content": "原始内容",
    "tool_calls": [],
    "tool_call_id": null,
    "name": null
  },
  "timestamp": "..."
}
```

这里的“轨迹”是 append-only 的：

```text
第一条消息 → 文件第一行
第二条消息 → 文件第二行
第三条消息 → 文件第三行
```

不会为了节省空间改写前面的行。

## 3. 从 0k 到 80k：只追加，不做上下文压缩

这条 Case 由 44 个历史 Session 组成。Benchmark 只在每个历史 Session 结束时调用一次：

```python
manager.maybe_compact(
    messages,
    estimate_context_tokens(messages),
)
```

所以水位不是每条消息都检查，而是在 LongMemEval 的 Session Boundary 检查。

几个接近阈值的真实水位：

| 历史消息位置 | 刚结束的历史 Session | 累计估算 Token | 行为 |
|---:|---|---:|---|
| 238 | `32f28c7b_1` | 70,915 | 不压缩 |
| 252 | `ultrachat_237324` | 74,143 | 不压缩 |
| 264 | `e419b7c3_4` | 77,389 | 不压缩 |
| 274 | `ultrachat_125013` | 79,373 | 不压缩 |

代码判断是：

```python
if tokens_before <= soft_trigger_tokens:
    return None
```

因此：

```text
79,373 <= 80,000
```

什么也不做。

### 3.1 这一阶段目录是什么样

概念上主要是：

```text
cases/d6233ab6/
├─ transcript.jsonl          # 持续增长
└─ .aster/
   └─ memory/
      └─ MEMORY.md           # 319 Bytes，仍为空
```

因为主轨迹没有 Tool Result，所以此时还没有单独的 `.txt` Tool Artifact。

### 3.2 80k 以下是否可能出现 Artifact

可能。

真实主轨迹没有工具，但普通 CodingAssistant 中，任何水位下只要一个实时 Tool Result 达到：

```text
UTF-8 Bytes >= 16,384
```

就会立即写入：

```text
.aster/context-artifacts/<session>/
  <tool>-<tool-call-id>-<random>.txt
```

这叫 Tool Result Artifact 化，不叫整段历史压缩。

此时：

- 完整结果在 `.txt`；
- Working Context 中的 Tool Result 被替换成路径、大小、SHA-256 和约 4,000 字符预览；
- 不会生成 Compaction Event；
- 不会生成 History Archive JSONL；
- 不会生成 Checkpoint。

因此：

```text
16 KiB
控制的是单条 Tool Result

80k/100k
控制的是整个 Working Context
```

## 4. 第一次超过 80k：83,782 Token

第 286 条历史消息结束后：

```text
Session：ecfd2047_1
Token：83,782
transcript.jsonl 当时大小：399,060 Bytes
```

代码判断：

```text
83,782 > 80,000
83,782 <= 100,000
```

因此：

```text
reason = soft
```

### 4.1 Soft 并不是先判断能否提交，再生成文件

当前 `_compact()` 的真实顺序是：

```text
1. 找切点
2. 复制旧消息
3. 旧 Tool Result Artifact 化
4. 生成完整 History Archive JSONL
5. 写 Archive Index
6. 提取明确 Stable Facts
7. 生成 Deterministic Checkpoint
8. 判断是否需要模型摘要
9. 如果是 Soft 且需要模型摘要，return None
```

注意第 9 步发生在文件和索引已经写完以后。

所以这次虽然 Soft 最终没有提交，却实际新增了：

```text
.aster/context-artifacts/d6233ab6/
  context-transcript-compaction-b12195c72ea0-5097dc1c588d.jsonl

.aster/memory/archive-index.jsonl
```

### 4.2 Archive #1 的真实数据

```text
文件大小：278,229 Bytes
归档消息：214 条
  User：105
  Assistant：109

历史运行写入 Index Records：378 条
  原始 message：302
  已移除的派生 Session Context：76

当前实现只会写入普通 message/tool_artifact，不再合成 Session Context。
清理后的精确 Record 数需要重新运行该 Case 后统计。

Archive Index 此时约：536,451 Bytes
```

### 4.3 为什么没有提交压缩

这条 LongMemEval 历史几乎全是 User/Assistant 对话，不是 Tool 日志。

因此归档的非 Tool 语义内容明显超过：

```text
4,500 Token
```

代码判断需要 Model Checkpoint。

但 Soft 阶段禁止调用模型摘要，所以：

```python
if use_model and reason == "soft":
    return None
```

### 4.4 这时内存和磁盘发生了不同变化

磁盘：

```text
新增 Archive #1
新增 Archive Index Records
```

内存中的 `messages`：

```text
没有切换成 Checkpoint
仍然保留全部 286 条历史消息
仍然约 83,782 Token
```

Session `transcript.jsonl`：

```text
没有追加 type=compaction 事件
```

这意味着单看 transcript，会看不出这次 Soft Prepare；但磁盘上的 Artifact 和 Archive Index 能证明它发生过。

在普通 `CodingAssistant` 路径中，Soft 暂缓会被记录为：

```text
compaction.aborted
reason = soft trigger deferred because deterministic compaction could not meet the target
```

但 LongMemEval Benchmark 直接调用 `MemoryManager`，只主动记录成功的 `compaction.completed`，因此这条 Benchmark Trace 没有记录 Soft Aborted。

## 5. 继续增长：五次 Soft Prepare

因为第一次 Soft 没有提交，内存仍然保存全部消息。后续每个 Session 结束后只要还在 80k 到 100k，就会再次执行准备阶段。

真实轨迹如下：

| 次数 | Token 水位 | Archive 文件 | Archive Bytes | 归档消息 | 新增 Index Records | Index 累计 Bytes | 是否提交 |
|---:|---:|---|---:|---:|---:|---:|---|
| 1 | 83,782 | `...b12195c...jsonl` | 278,229 | 214 | 378 | 536,451 | 否 |
| 2 | 89,253 | `...0cc528c...jsonl` | 301,995 | 232 | 410 | 1,117,774 | 否 |
| 3 | 91,980 | `...87df0a8...jsonl` | 314,751 | 244 | 428 | 1,724,604 | 否 |
| 4 | 96,218 | `...ae92be9...jsonl` | 333,163 | 260 | 456 | 2,369,298 | 否 |
| 5 | 98,191 | `...132d2c7...jsonl` | 342,003 | 268 | 469 | 3,031,617 | 否 |

对应 `transcript.jsonl` 自身变化：

| Token 水位 | transcript Bytes | transcript 中 Compaction Event |
|---:|---:|---|
| 83,782 | 399,060 | 没有 |
| 89,253 | 423,704 | 没有 |
| 91,980 | 437,596 | 没有 |
| 96,218 | 457,270 | 没有 |
| 98,191 | 466,701 | 没有 |

### 5.1 为什么这些 Archive 高度重叠

因为内存没有真正提交压缩。

第一次可能归档消息：

```text
1 ... 214
```

第二次可能归档：

```text
1 ... 232
```

第三次可能归档：

```text
1 ... 244
```

所以后面的 Archive 包含前面大部分正文。

### 5.2 为什么 Index Record ID 仍然不同

Archive Record ID 的身份包含：

```text
session_id
source_kind
source_path
message_index
chunk_index
content
```

即使 Content 相同，只要 `source_path` 是不同的 Compaction Archive 文件，Record ID 就不同。

因此 `_append()` 的 Record ID 去重不能阻止这些记录进入 Index。

搜索时会再按归一化正文去重，所以 Top-K 不会被这些副本全部占满，但磁盘空间已经产生。

### 5.3 五次 Soft 的实际空间代价

前五个 Archive 本身已经约：

```text
1.50 MiB 左右
```

Archive Index 在 Hard 之前已经达到：

```text
3,031,617 Bytes
```

这条真实轨迹证明：

> 当前 Soft Compaction 的准备顺序适合验证可恢复性，但对长期磁盘控制并不理想。更合理的实现应当先判断 Soft 是否能提交，或将 Prepare 写入临时区，只有 Commit 时再发布 Artifact 和 Index。

本文只记录现状，不在这里修改实现。

## 7. Hard 阶段如何选择切点

`_find_cut_point()` 从最后一条消息向前累计 Token，直到至少达到：

```text
keep_recent_tokens = 20,000
```

然后寻找一个完整 User Turn 开头。

这条真实轨迹最终得到：

```text
归档消息：284 条
保留近期消息：59 条
```

第一条保留消息的 ID：

```text
d85f8b19ac79412ca539b28e1a413c22
```

它对应原始 transcript 第 285 行：

```text
role = user
session = ecfd2047_1
turn = 11
```

也就是说：

```text
transcript 第 1～284 条消息
    → 归档

transcript 第 285～343 条消息
    → 近期原文保留
```

近期 59 条消息的估算大小为：

```text
19,667 Token
```

这非常接近配置中的 20k。

### 7.1 为什么切点不是精确等于 20k

因为不能为了精确 Token 数把一个 User Turn 或 Tool Call/Result 对从中间切开。

算法优先级是：

```text
完整回合和可恢复性
    高于
精确卡在 20,000
```

semantic_tokens = sum(

## 11. Model Checkpoint 最终长什么样

完整 Checkpoint 有 6,117 个字符，本文不全部复制。

它的结构为：

```text
## Current User Request

## Model Checkpoint
  ## Continuation checkpoint
  - 归档中有哪些历史主题
  - 用户偏好和事实
  - 仍需注意的信息

## Archived Source
  Archive Path
  SHA-256

## File State
  Read Files
  Modified Files

## Recovery Rules
```

### 11.1 Current User Request 由程序精确保存

当时最新 User Request 是：

```text
希望继续探索历史小说和谍战类书籍，
询问类似作品或作者推荐。
```

它不是让摘要模型从 76k 输入中猜出来的，而是程序从最新 User 消息直接提取，然后放在最前面。

### 11.2 Model Checkpoint 摘要了什么

归档中包含许多不同历史话题，模型提炼了例如：

- 预算和情绪性消费；
- 2,000 美元 Gucci 手袋；
- Mint、YNAB 和信封预算；
- 音乐和演唱会偏好；
- 阅读目标；
- 社交媒体休息；
- 语言学习；
- 家庭、健康、关系和职业话题。

它并不保存所有原句。需要具体事实时仍然依赖 Archive 检索。

### 11.3 File State 为什么为空

这条 LongMemEval Case 没有 Coding Tool Call：

```text
Read files：none
Modified files：none
```

如果是编码任务，Checkpoint 会从 Assistant Tool Calls 中提取：

```text
read / grep → Read Files
write / edit → Modified Files
```

+ 59 条原始近期消息
= 60 条内存消息

### 12.1 压缩后 Token 如何算出 21,196

真实数据：

```text
近期 59 条消息：19,667 Token
Checkpoint：6,117 字符 ÷ 4 ≈ 1,529 Token
```

相加：

```text
19,667 + 1,529 = 21,196
```

这正是 Compaction Record 中的：

```text
estimated_tokens_after = 21,196
```

### 12.2 节省差值

```text
102,880 - 21,196 = 81,684
```

这里的 81,684 是上下文前后差值，不是净费用节省。

因为压缩模型本身消耗了：

```text
76,138 Input
1,158 Output
```

长期收益来自后续多轮不必重复携带被移出的 81k 上下文。

## 19. 如果程序在压缩后重启

这条真实 Case 没有执行重启，但当前代码的恢复路径是确定的。

`WorkingContext.load()` 会：

```text
1. 读取 transcript.jsonl 全部行
2. 收集所有 type=message
3. 找到最后一个 type=compaction
4. 读取 summary
5. 找到 first_kept_message_id
6. 合成一条 System Checkpoint
7. 从 first_kept_message_id 开始恢复所有后续原始消息
8. 追加 type=recovery 事件
```

针对本 Case，重启后的 Active Context 会是：

```text
System Checkpoint
+ transcript 第 285 条消息开始的所有原始消息
+ Compaction 后继续追加的消息
```

不会重新把第 1～284 条全部塞回模型。

但第 1～284 条仍存在于：

```text
原始 transcript.jsonl
最终 History Archive
Archive Index
```

## 20. 如果后续再次超过 80k/100k

这条 Case 压缩后只增长到约 48k，没有第二次压缩。

如果继续增长：

```text
Checkpoint
+ 近期原文
+ 新消息
```

再次超过阈值，新的 Compaction 会：

1. 把旧 Synthetic Checkpoint 排除在 Archive Message 副本之外；
2. 读取 `_previous_summary`；
3. 生成新的 Archive；
4. 新 Checkpoint 合并 Previous Checkpoint；
5. 选择新的 `first_kept_message_id`；
6. 再次替换内存 Active Messages。

这样任务状态可以跨多轮压缩延续。

完整事实仍然不依赖 Previous Summary，而是通过多个 Archive 召回。

## 24. 补充分支：模型摘要失败

Hard 阶段调用模型时，可能发生：

- Provider Error；
- 返回空内容；
- Output 全部是无效内容；
- RuntimeError；
- 流式请求失败且最终没有 Reply。

因为完整 Archive 已经先写入，系统可以回退：

```text
strategy = deterministic-fallback
```

Details 记录：

```text
model_summary_error
layers_applied += deterministic-summary-fallback
```

然后仍然提交：

```text
Deterministic Checkpoint + Recent Messages
```

所以模型摘要失败不会导致完整历史丢失，也不会让 Hard Compaction 完全失效。

## 25. 补充分支：压缩取消

Cancellation Token 检查阶段：

```text
compaction_start
compaction_prepare
compaction_model
compaction_commit
```

### start 取消

还没开始准备，直接退出。

### prepare 取消

停止后续压缩。取决于取消发生时机，可能尚未生成文件，也可能某些准备文件已经写入。

### model 取消

正在生成 Model Checkpoint 时停止 LLM 请求，不继续 Commit。

### commit 前取消

不追加 Compaction Event，也不切换 Active Messages。

普通 CodingAssistant Trace 记录：

```text
compaction.aborted
status = cancelled
```

## 26. 补充分支：Archive Index 写入失败

History Archive 文件保存后，Archive Index 写入包裹在异常处理里。

如果 Index 失败：

```text
Archive 原文仍存在
Checkpoint 仍可生成
Compaction 仍可能提交
```

Details 增加：

```text
archive_index_error = "异常类型: 错误信息"
```

结果是：

- 任务仍可继续；
- 完整原文没有丢；
- 自动检索可能无法召回这批新 Archive；
- 模型仍可根据 Checkpoint 中的路径主动读取原文件。

这是“压缩可用性”和“检索可用性”分离的降级设计。

## 28. 补充分支：找不到可安全切点

Compaction 需要：

- 至少有旧消息可以归档；
- 至少有近期消息可以保留；

## 29. 这条轨迹最值得注意的四个事实

### 29.1 压缩前先保存完整原文

Model Summary 不是唯一副本。摘要错了也可以从 Archive 恢复。

### 29.2 Checkpoint 不等于 Archive

```text
Archive：363,118 Bytes，284 条完整消息
Checkpoint：6,117 字符，任务交接信息
```

二者数量级和职责不同。

### 29.3 transcript 没有变短

压缩减少的是：

```text
下一轮发给模型的 Active Context
```

不是磁盘上的审计轨迹。

真实 transcript 最终仍达到：

```text
630,379 Bytes
```

### 29.4 当前 Soft Prepare 会造成磁盘重复

同一条 Case 在真正 Hard Commit 之前已经产生 5 个 Archive Snapshot。

检索去重保护了 Top-K，但没有保护磁盘容量和 Index 扫描成本。

这是当前实现最明确的后续优化点之一。
